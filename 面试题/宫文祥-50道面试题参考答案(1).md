## 一、Python 基础与工程化

**1. Python 的 GIL 是什么？FastAPI 异步服务里 CPU 密集任务如何避免阻塞事件循环？**
答：GIL 是 CPython 的全局解释器锁，保证同一时刻只有一个线程执行字节码，主要是为了简化内存管理（引用计数）。在 FastAPI 这类基于 asyncio 的异步框架里，事件循环是单线程的，一旦在其中执行 CPU 密集任务（如大文件解析、向量计算、数据清洗），就会长时间占用循环，导致所有请求被阻塞。解决方式：一是用 asyncio.to_thread 或 loop.run_in_executor 把 CPU 任务丢到线程池/进程池执行，释放事件循环；二是用进程池 ProcessPoolExecutor 绕过 GIL 做并行计算；三是把重计算拆到独立 worker 服务。而 LLM 调用、数据库查询这类 IO 密集任务本身就适合 async，直接 await 即可。结合我的项目，PDF 清洗分片、Embedding 批量向量化就是 CPU 密集环节，应异步化处理，避免拖垮问答接口。

**2. 装饰器、生成器、上下文管理器的原理，以及应用。**
答：三者都是 Python 语言层面的重要特性。装饰器本质是接收函数并返回新函数的闭包，常用于日志、鉴权、缓存、重试，比如 FastAPI 的 @app.get 和依赖注入。生成器通过 yield 惰性产出值，逐条生成而非一次性加载，天然适合流式输出——FastAPI 的 StreamingResponse 就是用生成器逐 chunk 产出 SSE 数据，还能配合背压控制内存。上下文管理器实现 __enter__/__exit__，保证资源（数据库连接、文件句柄、锁）用完自动释放，FastAPI 里用 async with 管理 LLM 客户端连接池也很常见。三者在 AI 服务里高频出现：重试装饰器包裹模型调用、生成器实现流式 token 输出、上下文管理器管理会话与日志上下文。

**3. async/await 与多线程、多进程的区别？AI 服务里如何选型？**
答：async/await 是单线程内的协作式并发，通过事件循环在 IO 等待时切换任务，几乎没有线程切换开销，适合大量并发 IO 场景，如调用 LLM 接口、查向量库、SSE 推送。多线程是真正并行但受 GIL 限制，CPU 密集任务收益有限，适合调用 C 扩展释放 GIL 的 IO 操作或需要共享内存的场景。多进程能绕过 GIL 实现真正的并行计算，但进程间通信和数据拷贝有成本，适合重 CPU 任务。AI 服务选型：请求入口和高并发 IO 用 async，文档解析、Embedding、数据清洗等 CPU 密集部分放到线程池/进程池或独立 worker。实践中常组合使用——FastAPI 异步路由 + 后台进程池跑批处理。

**4. FastAPI + Pydantic 如何做入参与输出校验？「多层校验」具体怎么做？**
答：FastAPI 基于 Pydantic 做自动校验，请求体用 BaseModel 定义字段类型、必填、默认值与约束（Field 的 min_length、pattern、ge 等），非法请求会在进入业务逻辑前被 422 拒绝；响应侧用 response_model 保证返回结构一致并自动过滤多余字段。所谓多层校验是指：第一层 Pydantic 做格式与类型校验；第二层业务规则校验（如问题长度、敏感词、权限）；第三层对模型输出的校验，用 JSON Schema 或正则约束输出格式，不合格就重试或降级。我在项目里对 Agent 工具入参做了正常、空参、非法参数、超时等多组用例，输出层增加格式与合规约束，正是多层校验的落地。

## 二、RAG 与向量检索

**5. 什么是 RAG？完整链路？为什么企业多选 RAG 而不是微调？**
答：RAG（检索增强生成）是一种把外部知识检索与大模型生成结合的范式。完整链路：文档清洗过滤→分块→Embedding 向量化→写入向量库→用户提问向量化→相似度检索召回 Top-K 片段→（可选）rerank 重排→把片段拼进 prompt 作为上下文→大模型基于事实生成回答。相比微调，企业更倾向 RAG 的原因：成本低、见效快，无需 GPU 训练；知识可随时增删改、实时更新；回答可溯源到原文，便于合规审计；幻觉相对可控。我在恒鑫、华瑞两个项目都走这条链路，并针对 PDF 图文表格做了多模态向量化，补齐了非文本资料检索短板。

**6. Embedding 是什么？余弦/点积/欧氏相似度怎么选？**
答：Embedding 是把文本、图片等非结构化数据映射成高维稠密向量，使语义相近的内容在向量空间里距离更近，从而支持语义检索。常用相似度：余弦相似度衡量方向一致性，对向量模长不敏感，最常用；点积计算快，但受模长影响，需先归一化；欧氏距离衡量绝对距离，对模长和维度尺度敏感。实践中多数模型（如 OpenAI、BGE 系列）输出已归一化，此时余弦与点积等价。选型还要考虑维度、语种、领域适配，并用 rerank 模型做二次精排。我的项目里接入多模态 Embedding 处理图文，检索后再校验相关性，以提升召回精度。

**7. 向量数据库（Milvus、Chroma、FAISS、pgvector、ES）如何选型？**
答：选型主要看规模、过滤能力、部署与生态。小规模或原型用 Chroma、FAISS 即可，本地轻量；FAISS 是库不是服务，需自管持久化。生产大规模、高并发用 Milvus，分布式、支持多种索引（IVF、HNSW）与标量过滤，适合带权限元数据过滤的场景。pgvector 嵌入 PostgreSQL，适合已有 PG、需要事务和关系数据强一致的场景，还能用 SQL 结合过滤。ES/OpenSearch 向量检索适合已有全文检索体系、需要混合检索（关键词+向量）的场景。我项目里知识库要按岗位做细粒度权限隔离，所以重点看「向量检索 + 元数据标量过滤」能力。

**8. 文档分块（chunking）有哪些策略？分块大小与重叠怎么权衡？**
答：分块是把长文档切成适合检索与模型上下文的小片段。常见策略：固定长度切分（按 token/字符，简单但可能切断语义）；按段落/标题/章节切分（保留结构）；递归字符切分（按分隔符优先级逐步切）；语义分块（用模型判断边界，成本高）。分块大小影响召回粒度——太小上下文不足、易碎片化，太大会引入噪声、超 token 上限；重叠（overlap）用来避免关键词或语义被切在两块之间，通常取 10%-20%。实际要结合 embedding 的 token 上限与模型上下文窗口调优，还可采用父子文档（小块检索、大块喂给模型）或多级索引提升效果。

**9. PDF 中图片和表格如何做多模态向量化与检索？**
答：针对 PDF 图片、表格无法检索的问题，核心是「解析 + 分别向量化 + 融合检索」。先用 PDF 解析工具（如 pdfplumber、Unstructured、OCR）把文档拆成文本、图片、表格三类：表格转成结构化文本（Markdown/JSON）或单独索引，保留行列关系；图片走 OCR 提取文字或直接用多模态 Embedding（CLIP 类、图文对齐模型）生成向量；文本正常向量化。检索时同时召回文本、表格、图片三类结果并融合排序，回答时附上原文页码/位置便于溯源。我在恒鑫机械项目里就是补齐了工艺、安全类 PDF 的图文表格向量化，解决了非文本资料检索不到的问题。

**10. 如何评估检索效果？召回率、精确率、MRR、NDCG 分别是什么？**
答：检索评估衡量「该找的有没有找到、排得对不对」。召回率 Recall=召回的真正相关文档/所有相关文档，衡量是否有遗漏；精确率 Precision=召回结果里相关的比例，衡量是否引入噪声；MRR（平均倒数排名）看第一个相关文档排第几，取倒数平均，值越接近 1 越好；NDCG 考虑排序位置与相关度分级（相关程度打分），对排序质量更敏感。实际做法：构造带标注的固定测试集（如我项目的 126 条业务 Query），对每条 Query 人工标注相关文档，计算这些指标来对比不同 chunking、Embedding、检索参数的效果，做 A/B 迭代。

**11. 什么是大模型幻觉？RAG 链路里有哪些缓解手段？**
答：大模型幻觉指生成内容看似合理但缺乏事实依据、甚至编造。RAG 链路中的缓解手段：1）提高检索质量，召回准确、相关片段并做 rerank，从源头给足事实依据；2）强制引用，要求模型回答必须基于给定上下文并标注来源；3）Prompt 约束，明确「不知道就说不知道」、禁止编造；4）输出约束与格式校验，限制回答范围；5）设置拒答规则，超出知识库或置信度低时直接拒答；6）结果校验与人工兜底，高风险场景转人工。我在项目里通过 Promptfoo+AutoPE 迭代提示词、增加输出约束与拒答规则，把合规准确率从 72% 提到 91%。

## 三、LangChain / LangGraph / LlamaIndex

**12. LangChain 的核心抽象有哪些？各自职责？**
答：LangChain 把 LLM 应用拆成可组合的抽象：LLM/聊天模型封装调用与 token 处理；PromptTemplate 管理提示词模板与变量；Chain 把多个步骤串联；Retriever 抽象检索接口，对接各种向量库；Tool 封装可被模型调用的函数；Agent 用 LLM 做推理决策、选择并调用工具；Memory 管理对话历史；Callback 提供日志、追踪、流式回调钩子。理解这些抽象后，能快速组合出 RAG、Agent 等应用。不过生产上复杂编排我更倾向用 LangGraph，因为它能显式控制状态流转与循环，可观测性和可控性更好。

**13. LangGraph 相比 AgentExecutor 的优势？State/Node/Edge 怎么设计？**
答：LangChain 原生 AgentExecutor 是「思考→行动→观察」的固定循环，黑盒且难控制，容易出现死循环、难做条件分支和持久化。LangGraph 把流程建模成图：State 是共享状态结构体（定义跨节点传递的字段），Node 是处理单元（意图识别、工具调用、结果校验、答案输出等），Edge 是有向边，条件边根据状态字段动态路由到不同节点，还支持循环、并行与 checkpointer 持久化。优势在于：流程显式可控、便于调试与测试、支持断点续跑与时间旅行回放、可观测性强。我的 Agent 项目正是用 LangGraph 划分 Node + 条件路由，配合最大循环限制治理死循环。

**14. LlamaIndex 的常见索引类型与适用场景？**
答：LlamaIndex 提供多种索引：VectorStoreIndex 把文档向量化，做语义检索，最常用；SummaryIndex（列表索引）逐条存节点，适合全部遍历或摘要聚合；KeywordTableIndex 基于关键词建表，适合精确词匹配；TreeIndex 层级树结构，适合结构化问答；DocumentSummaryIndex 为每篇文档生成摘要、先查摘要再定位正文，适合大文档库；还有 KnowledgeGraphIndex 支持图谱问答。选型看场景：纯语义问答用 VectorStoreIndex，需要关键词精确匹配用 Keyword，长文档先摘要后精读用 DocumentSummary。我项目里知识库问答以 VectorStoreIndex 为主，结合元数据过滤做权限隔离。

**15. 为什么把 Agent 拆成「意图识别、工具调用、结果校验、答案输出」？条件路由怎么实现？**
答：把 Agent 拆成意图识别、工具调用、结果校验、答案输出四个 Node，是「单一职责」思想：每个节点只做一件事，便于单独测试、调优和定位问题，也方便在不同节点插桩日志与校验。State 结构体保存 question、intent、tool_result、validation、answer 等字段。条件路由根据状态判断下一步：意图识别后判断是否需检索/调工具；工具调用后判断结果是否合法，非法则重试或走降级；结果校验通过才到答案输出，否则拒答或人工兜底。这样异常分支显式可控，避免传统 Agent 黑盒循环。我在 LangGraph 里用条件边实现这套流转，并配置最大循环次数与超时拦截。

**16. Function calling 机制？如何做参数与结果校验？**
答：Function calling 是模型按约定输出结构化调用指令的机制：我们把工具能力用 JSON Schema 描述（名称、用途、参数类型），随请求发给模型；模型判断需要调用时返回函数名和参数 JSON；应用执行该工具，把结果作为新消息回填给模型，模型再生成最终回答。参数校验在模型返回后立即做：用 Pydantic 校验类型、必填、范围，拦截空参数与非法参数；结果校验判断返回值是否可用（非空、格式正确、无异常），失败则重试、换工具或降级。我在 MCP 插件工具上写了正常、空参、非法参数、超时多组用例，就是为了在进入主流程前拦掉工具异常。

## 四、Agent 与 MCP

**17. MCP 是什么？解决什么问题？与传统 function calling 区别？**
答：MCP（Model Context Protocol）是 Anthropic 提出的开放协议，标准化模型应用与外部工具、数据源的连接方式。它解决的问题是：过去每接一个新工具/数据源都要为每款模型写一遍适配，形成 N×M 的重复开发；MCP 定义了统一的客户端-服务端协议，让工具、资源、提示词以标准接口暴露，模型应用只需实现一次 MCP 客户端即可复用任何 MCP Server。与传统 function calling 的区别：function calling 是模型层的调用约定，工具定义和调用散落在各应用里、不可复用；MCP 把它下沉为独立、可插拔、可共享的服务协议，工具即插即用。我的项目基于 MCP 做插件化工具开发。

**18. MCP 的 Host/Client/Server 与 Tools/Resources/Prompts 是什么？**
答：MCP 采用客户端-服务端架构：Host 是宿主应用（如 Claude Desktop、你的 Agent 应用），负责创建多个 Client 并管理连接；Client 是协议客户端，与服务端一对一建立连接、维护会话；Server 是提供具体能力的服务进程。Server 通过三种原语暴露能力：Tools 是可被模型调用的函数（如查库、调接口）；Resources 是可被读取的数据/文件（如知识库文档）；Prompts 是可复用的提示词模板。通信基于 JSON-RPC，能力发现通过 initialize/list 等握手完成。一次工具调用流程：Host 经 Client 请求 Server 的 tool 列表→模型选择并调用→Server 执行返回结果→回填模型。我项目用这套实现了插件化工具。

**19. 多 Agent 协作有哪些模式？如何选择？**
答：常见模式有三种。编排式（Orchestrator）：中心 Agent 把任务拆解、分发给子 Agent 并汇总，流程可控、结果稳定，适合确定性强的业务流程。自主式/对话式：多个 Agent 平等对话协商，灵活但难控、成本高。层级式（Hierarchical）：Supervisor 监督多个 worker，按需调度并仲裁，兼顾灵活与可控，LangGraph 的 supervisor 模式很典型。选型看任务复杂度、可控性要求、成本预算：任务清晰用编排式，开放探索用自主式，需要统筹多专业角色用层级式。我的「多 Agent 工作流」偏编排式，意图识别、检索、校验、生成各司其职，由状态机统一调度。

**20. Agent 工具调用死循环怎么产生？如何防护？**
答：死循环通常因为模型反复调用同一工具、工具结果异常导致模型重试，或缺少明确终止条件。防护手段：1）设置最大工具调用/循环次数，超限强制终止并降级；2）单次与总超时拦截，避免长时间空转；3）结果去重检测，连续相同调用则打断；4）设置终止信号，让模型明确输出 FINISH；5）Token/成本预算，超出即停；6）对工具入参出参做校验，异常直接短路；7）最后人工兜底。我在恒鑫项目里配置了 Agent 最大循环次数限制，并对 MCP 工具做多组异常用例测试，从机制上遏制了死循环与接口雪崩。

## 五、Prompt 工程与评测

**21. Prompt 工程核心技巧有哪些？**
答：常用技巧：1）角色设定，明确「你是某领域的专家」以引导风格；2）Few-shot，给少量示例让模型照葫芦画瓢；3）思维链 CoT，让模型分步骤推理，提升复杂问题准确率；4）结构化输出约束，要求 JSON/Markdown 格式并用 Schema 校验；5）上下文管理，把检索到的资料、对话历史有序组织；6）负面示例与边界说明，明确什么不能做、何时拒答；7）变量化模板，把提示词做成可复用模板。我在项目里维护提示词模板，用 Promptfoo+AutoPE 批量生成多套方案做 A/B 迭代，叠加输出约束与拒答规则，稳定提升了合规准确率。

**22. 如何搭建提示词评测体系？Promptfoo 和 AutoPE 分别做什么？**
答：提示词评测体系 = 固定测试集 + 自动/人工评估 + 版本对比。先把真实业务问题整理成带标准答案或评估维度的测试集（我的项目是 126 条业务 Query），避免每次靠拍脑袋。然后跑不同提示词方案，用 Promptfoo 做批量评测：它支持跑多套 prompt、多模型，输出结构化结果、断言与回归报告，适合做 CI 回归。AutoPE 用于自动化 Prompt 工程，批量生成、变异多套提示词方案并评估打分，帮我们快速找到更优写法。评估维度包括准确率、合规性、拒答率、格式正确性等。最后做 A/B 对比，选最优方案上线并持续迭代。

**23. 「合规准确率 72%→91%」具体是怎么做到的？**
答：具体方法分四步：第一，构建固定测试集——收集工厂 126 条真实业务 Query，覆盖工艺、安全等场景，人工评审每条的合规标准，形成可复用的评测基准。第二，批量生成方案——用 AutoPE 基于种子提示词批量生成多套提示词变体，用 Promptfoo 跑完所有方案拿到量化评分。第三，A/B 迭代——针对不合规回答，分析是缺约束还是知识没检索到，逐步增加「输出约束」（如必须引用规程、禁止编造）和「拒答规则」（超范围问题明确拒答）。第四，收敛回归——反复对比，最终方案把合规准确率从 72% 提升到 91%。关键是用数据驱动替代主观调 prompt。

**24. 如何设计「无关问题拒答」规则？如何避免误拒？**
答：设计拒答规则的核心是「先判领域、再定置信度、给友好话术」。判断方式：用关键词/分类模型/LLM 判断问题是否属于本知识库业务范围，超出范围直接拒答；对范围内但检索不到充分证据的问题，设定相关性阈值，低于阈值就拒答并引导用户换问法。避免误拒：1）用固定测试集回归，同时看拒答率和漏答率，找到平衡点；2）给模型「能答就答、不能答就说不知道」的明确指令，而非一刀切；3）保留人工兜底转工单通道。我在华瑞项目里配置无关问题拒答规则，把准确率从 70% 提到 88%，同时配合工单流程兜底知识库未覆盖的问题。

## 六、大模型服务稳定性

**25. 自适应重试、熔断、降级、限流分别是什么？怎么落地？**
答：重试：对瞬时失败（网络抖动、429 限流）做有限次重试，配合指数退避与抖动，避免雪上加霜，注意幂等。熔断：连续失败达阈值后熔断器打开，直接快速失败一段时间，防止不断打挂下游，半开状态试探恢复。降级：主链路不可用时返回兜底结果（缓存答案、友好提示、简化模型），保证可用性。限流：限制单位时间请求量，保护上游 LLM 配额与自身服务。我在 AI 服务里落地：模型调用做自适应重试+熔断，连续超时自动切断；问答超时或失败降级为预设兜底话术；入口做限流；配合 Agent 最大循环限制控制 Token 消耗，形成多层防护。

**26. Token 消耗不可控如何治理？**
答：Token 消耗不可控主要来自：输入上下文过大、输出过长、Agent 反复调用、无超时。治理手段：1）限制输入长度，检索片段只取最相关的 Top-K 并裁剪；2）限制输出 max_tokens，约束回答篇幅；3）上下文压缩，多轮对话用摘要/滑窗只保留必要历史；4）设置 Agent 最大循环次数与总超时，防止无限调用；5）成本预算，超预算即停止或降级；6）缓存命中，相似问题复用已有结果；7）监控每请求 token 与成本，异常告警。我的项目配置了 Agent 最大工具循环次数限制与超时拦截，从机制上控制了 Token 与成本。

**27. 模型接口超时怎么设置？SSE 流式中断怎么处理？**
答：超时要分层设置：连接超时（建立连接）、首字节超时（LLM 首 token）、总时长超时，分别控制不同阶段，避免无限等待。SSE 流式输出中断要区分「模型侧中断」和「客户端断连」：模型侧中断做重试或降级，返回已生成内容 + 兜底提示；客户端断连用 asyncio.CancelledError 捕获并清理资源、停止上游请求，避免后台空转。重试要注意幂等与去重，防止重复计费或重复输出。前端捕获请求超时与接口异常，给友好兜底回复。我在项目里对问答做了超时拦截与断连处理，保证异常时用户也能得到可理解的结果。

**28. 分层会话记忆怎么设计？Checkpoint 持久化作用？**
答：分层记忆把「当前对话」和「长期信息」分开：短期记忆保留最近若干轮消息，保证多轮连贯；长期记忆用摘要（把历史对话压缩成摘要）、用户画像或向量记忆（重要事实存入向量库按需召回），控制上下文长度。Checkpoint 是 LangGraph 的状态持久化机制，把每次状态快照（含消息、中间结果、节点进度）写入存储，作用是：1）断点续聊，服务重启不丢会话；2）多轮上下文恢复；3）可回溯、可重放，便于排查线上问题；4）支持时间旅行调试。我在项目里依托 Checkpoint 完成 Agent 会话持久化，并持久保存会话与工具调用日志用于复现排查。

**29. 会话、工具调用日志如何记录？线上问题如何复现排查？**
答：做法是结构化 + 全链路 + 可检索。每条日志带会话 ID、请求 ID（trace id）、时间戳、模型、工具、入参/出参（脱敏）、耗时、token 数、错误信息等字段，输出为 JSON，方便聚合检索。全链路用 trace id 串联「入口→意图→检索→工具→生成」各环节，定位慢在哪一步。持久保存会话与工具调用日志，线上问题可通过 session id 完整重放当时的上下文与调用序列，快速复现。再配合监控面板看延迟、错误率、token 消耗等指标，异常时按链路下钻。我项目里「持久保存会话、工具调用日志」正是为了线上问题可复现、可排查。

## 七、后端 FastAPI / SSE

**30. SSE 与 WebSocket 区别？问答为什么常用 SSE？**
答：SSE（Server-Sent Events）是 HTTP 上的单向服务器推送：客户端发普通 HTTP 请求，服务端保持长连接持续向客户端推数据，客户端不能反向发消息（除非再开请求），协议简单、自动重连、易穿透代理、有浏览器原生 EventSource 支持。WebSocket 是全双工持久连接，双向实时通信，适合聊天室、协同编辑等需要频繁双向交互的场景。问答场景用 SSE 的原因：大模型回答是服务端单向流式吐 token，客户端只需接收，不需要双向；SSE 复用 HTTP 基建、部署简单、兼容代理，比 WebSocket 更轻量可靠。我在项目里用 FastAPI 的 SSE 实现流式问答。

**31. FastAPI 如何实现 SSE 流式响应？注意哪些问题？**
答：用 StreamingResponse 返回 text/event-stream，响应体是一个异步生成器，逐块 yield「data: xxx」格式的数据，模型每产出 token 就推送。要点：1）设置正确的响应头（Content-Type: text/event-stream、Cache-Control: no-cache）；2）生成器里捕获客户端断连（asyncio.CancelledError）并清理上游请求；3）处理背压，避免服务端产出远快于客户端消费；4）设置分层超时，必要时发心跳/注释行保持连接；5）注意中间件缓冲，避免开启会缓冲整个响应的压缩或代理。我在华瑞项目里就用这套实现流式对话，并与前端做状态联动。

**32. FastAPI 的依赖注入、中间件、异常处理机制？**
答：依赖注入用 Depends 声明，FastAPI 自动解析并缓存同请求内相同依赖，可做鉴权、数据库会话、配置注入，支持层级嵌套，让代码解耦可测。中间件（@app.middleware）在请求/响应间执行，适合跨切面逻辑：CORS、日志、耗时统计、统一鉴权、异常兜底，用 BaseHTTPMiddleware 或纯 ASGI 中间件。异常处理用 @app.exception_handler 注册，把业务异常统一转成规范 JSON 响应，避免把堆栈泄露给前端。我在 AI 服务里：Depends 做用户鉴权与权限，中间件记录请求日志与链路 id，异常处理器统一返回友好错误格式，保证接口规范一致。

**33. 如何设计一个对外 AI 问答接口？请求/响应怎么定义？**
答：接口分请求与响应两段设计。请求：query（问题）、session_id（会话，支持多轮）、可选参数（知识库 id、模型、是否流式）、鉴权头、限流标识；用 Pydantic 定义并校验。响应：流式用 SSE 逐段推 content，非流式返回完整 JSON；统一结构含 code、message、data，data 里带 answer、引用来源（source 文档+页码）、是否拒答、耗时等；错误码区分参数错误、无权限、超时、上游失败。还要考虑：幂等、限流、超时、对存量业务系统的兼容对接（统一网关/签名）。我项目里用 FastAPI 接口 + SSE 流式对接存量业务系统，并做多层入参输出校验。

## 八、Docker / DevOps

**34. Dockerfile 编写要点？多阶段构建与镜像瘦身？**
答：要点：1）选精简基础镜像（python:3.x-slim / alpine），减小体积与攻击面；2）多阶段构建：构建阶段装依赖、编译，运行阶段只拷贝产物，分离构建与运行；3）利用分层缓存，先 COPY 依赖清单再 pip install，源码变更不触发重装；4）.dockerignore 排除缓存、虚拟环境等；5）固定依赖版本（requirements 锁版本）保证可复现；6）非 root 用户运行，降低安全风险；7）合理设置 WORKDIR、CMD/ENTRYPOINT。我在华瑞项目里编写 Dockerfile 完成 AI 服务容器化部署，并随业务反馈持续迭代版本。

**35. 模型服务 CPU/GPU/内存配置与扩缩容怎么考虑？**
答：先明确部署形态：走 API 调用（如通义、OpenAI）无需自管 GPU，重点在请求并发与超时；自部署开源模型才考虑 GPU。资源确定靠压测：测单请求延迟、吞吐、显存占用，算单卡能扛多少 QPS，据此定实例规格。内存要覆盖模型权重 + KV cache。扩缩容：AI 服务无状态化（会话存外部），水平扩容用负载均衡 + 健康检查 + 自动扩缩容（HPA 按 CPU/QPS/队列长度）；模型服务常驻显存、冷启动慢，需预留缓冲或预热。我在项目里用 Docker 容器化，服务无状态，便于水平扩展与滚动更新。

**36. AI 服务版本迭代与回滚怎么做？**
答：核心是「代码与配置分离 + 版本化 + 灰度」。代码用镜像 tag 版本化，git 打 tag 对应镜像，可快速回滚到上一版本。配置外置：提示词、模型名、阈值、拒答规则等放配置中心/环境变量，改提示词不用重新发版，实现快速迭代。发布用灰度/金丝雀：先切小流量观察错误率、延迟、合规指标，稳定后全量；回滚一键切回旧镜像或旧配置。数据库/索引变更要向前兼容，避免回滚时数据不匹配。我在项目里把 Prompt 约束与代码解耦，便于根据业务反馈持续迭代，同时保证可回滚。

**37. 生产环境日志、监控、告警怎么搭建？**
答：分指标、日志、链路、告警四层。指标：请求量、延迟（P50/P99）、成功率、错误率、token 消耗、工具调用次数、缓存命中率等，用 Prometheus 采集 + Grafana 看板。日志：结构化日志聚合到 ELK/Loki，按会话、trace 检索。链路：OpenTelemetry 等做分布式追踪，串联调用链。告警：设阈值（错误率突增、P99 超标、LLM 上游不可用、成本超预算），分级通知，配合熔断降级自动止血。AI 服务还要监控合规/拒答率、幻觉相关指标。我在生产里保障 AI 服务稳定性，重点看超时、错误率与 token 成本。

## 九、安全与权限

**38. 企业私有知识库如何做细粒度权限管控？**
答：核心是「身份 + 数据标记 + 全链路过滤」。先定义权限模型：用户→角色/岗位/部门→可访问的知识库/文档范围，形成 ACL。数据侧：每个向量分块在入库时打上元数据标签（所属文档、密级、部门），检索时把用户权限翻译成过滤条件，向量检索 + 标量过滤（如 Milvus/pgvector 的 filter）只召回有权访问的片段。生成侧：拼接上下文前再次校验，避免越权内容进入 prompt。我在恒鑫项目里按岗位隔离知识库访问权限，解决了涉密工艺、安全资料无访问隔离的风险，规避敏感资料泄露。

**39. API 密钥管理、敏感数据脱敏与合规怎么做？**
答：密钥管理：API Key 不进代码库，放环境变量或密钥管理服务（Vault、云 KMS），定期轮换，按最小权限分配，不同环境隔离，日志中脱敏。敏感数据脱敏：输入输出做脱敏——用正则匹配手机号、身份证、密钥等，或用模型识别 PII 后替换/打码；涉密资料按权限控制访问。合规：符合数据安全法、个保法等要求，收集最小化、明确用途、留痕可审计；结合我的「华为云操作安全与隐私保护合规认证」，在云上配置安全组、加密存储、操作审计。整体是「最小权限 + 全程脱敏 + 可审计」。

**40. 如何防 Prompt 注入与越狱？有哪些防御？**
答：Prompt Injection 是攻击者在用户输入里植入指令，诱导模型忽略系统设定或泄露提示词。防御：1）输入过滤与清洗，识别并剥离可疑指令；2）系统提示词与用户输入强隔离，明确「用户输入是数据不是指令」；3）输出约束，限制回答范围、禁止输出内部提示词与密钥；4）工具权限最小化，即使被诱导也不越权执行危险操作；5）内容审核，输出前过滤敏感/违规内容；6）上下文隔离，检索片段也需防投毒；7）高风险操作人工确认。我项目里多层入参输出校验 + 输出约束 + 权限最小化，就是防御注入与越狱的实践。

## 十、前端 / 跨端 / 鸿蒙

**41. Vue3 组合式 API 与 Proxy 响应式原理？**
答：Vue3 用 Proxy 实现响应式：reactive 把对象包成 Proxy，读取属性时依赖收集（track），写入时派发更新（trigger）；ref 对基本类型包装成 .value，内部也是靠 Proxy/reactive。相比 Vue2 的 Object.defineProperty，Proxy 能拦截新增/删除属性、数组索引变化，性能更好、无需 $set。组合式 API（setup）把同一功能的响应式状态和逻辑组织在一起，便于复用（composables）和 Tree-shaking。我在茶园电厂项目里用 Vue3 + TypeScript 开发风险管控、台账等模块，大量使用组合式 API 复用表单校验与看板逻辑。

**42. UniApp 如何做 Web/小程序多端适配？条件编译是什么？**
答：UniApp 用一套代码编译到 Web、小程序、App 多端，核心是「统一 + 条件编译 + 降级」。统一：用内置组件和 uni.xxx API 抹平平台差异，rpx 响应式单位自适应不同屏幕。条件编译：#ifdef MP-WEIXIN / #ifdef H5 等指令按平台编译不同代码，处理平台专属逻辑。样式与生命周期差异（如小程序无 DOM、页面 onShow/onLoad）要分别处理；不支持的 API 做能力检测与降级。我在茶园智安宝做了 Web+小程序双端，处理样式兼容与交互 BUG，保证两端功能体验一致。

**43. JSBridge 原理？H5/小程序与鸿蒙原生怎么通信？scope 分级授权怎么做？**
答：JSBridge 是 H5/小程序与原生之间的通信桥。原理：原生把桥接对象注入 WebView（如 window.xxx），JS 调用桥方法并传参（序列化成 JSON），原生收到后分发到对应模块处理，结果通过回调/Promise 回传给 JS；鸿蒙端用 ArkTS 实现这些原生接口。小程序侧通过自身的 JSBridge 协议调用 Native。scope 分级授权：接口按敏感度分级，调用时校验授权状态，未授权弹出引导，用户拒绝则拦截调用并回调失败，形成「校验→引导→拦截」闭环。我在淘宝 JSBridge 项目里实现设备信息、文件系统、路由等模块，并独立完成文件系统 20+ 接口。

**44. 鸿蒙 MegaAbility、PersistentStorage 作用？软键盘遮挡 TabBar 怎么解？**
答：MegaAbility（鸿蒙 Mega 架构的 Ability）是应用能力的载体，负责生命周期（onCreate/onShow/onHide/onDestroy）与页面承载，小程序 API 运行时正是挂载在 Ability 上对接系统能力。PersistentStorage 是持久化存储，基于键值对落盘，用于保存需要跨启动保留的数据（如登录态、配置），区别于内存态 AppStorage。软键盘遮挡 TabBar 的解决：监听键盘高度变化（onKeyboardHeightChange/视觉避让），键盘弹出时给页面加 padding-bottom 或滚动定位到输入框，收起时还原，配合 flex 布局让内容区自适应。我在鸿蒙项目里解决了软键盘遮挡 TabBar 等兼容问题并搭建真机调试链路。

## 十一、系统设计 / 场景

**45. 从零设计一个企业级 RAG 问答系统，考虑哪些模块？**
答：模块划分：1）数据接入层：对接 PDF/Word/数据库等多源数据，做清洗过滤、OCR、表格解析；2）索引层：分块策略、Embedding、向量库 + 元数据，多模态图文表格向量化；3）检索层：向量检索 + 关键词混合 + rerank 重排；4）生成层：提示词模板、上下文拼接、流式输出、引用溯源；5）权限层：细粒度 ACL 过滤；6）评测层：固定测试集 + Promptfoo/AutoPE 迭代；7）稳定性层：重试熔断降级、超时、多层校验、会话记忆与 Checkpoint；8）运维层：Docker 部署、监控告警、日志链路。这套正是我两个 RAG 项目的完整架构。

**46. 知识库未覆盖且模型答不好时，如何设计兜底闭环？**
答：设计思路是「分层兜底 + 反馈回流」。判断层：用相关性阈值/意图分类判断问题是否可答、知识库是否覆盖。兜底层：1）拒答 + 澄清引导，请用户补充信息或换问法；2）推荐相关问题或已有 FAQ；3）置信度不足或高风险场景自动转人工——生成工单，带上对话上下文推给坐席，前端做状态联动展示「已转人工」。回流层：人工解决后的答案沉淀回知识库，形成闭环，下次同类问题可自动回答。我在华瑞项目里设计了「知识库未覆盖 → 自动流转工单 → 人工坐席」的闭环，解决了 AI 无法回答问题的兜底路径。

**47. 多租户场景下如何隔离向量数据与权限？**
答：分数据、索引、访问三层隔离。数据层：每条向量/文档记录带 tenant_id 字段，存储按租户分区或分库（大规模）。索引层：物理隔离（每租户独立索引/集合）最安全，成本高；逻辑隔离（共享索引 + tenant_id 过滤）成本低，检索时必须强制带上租户过滤条件，防漏。访问层：鉴权后从 token 取租户身份，检索与生成全链路携带租户过滤，任何查询不能跨租户；配置和密钥也按租户隔离。审计：记录每租户访问日志。逻辑隔离 + 严格过滤是主流做法，我在项目里用元数据标量过滤实现岗位/租户级隔离。

**48. AI 服务突发大量超时与雪崩，如何定位与止血？**
答：分「止血→定位→恢复→复盘」四步。止血：立即开启限流、降级、熔断，优先保住核心服务，返回兜底话术；必要时扩容或切备用。定位：看监控（QPS、错误率、P99）、日志、链路追踪，快速判断瓶颈在哪一层——上游 LLM 限流/故障、下游向量库慢查询、网络抖动、还是自身资源耗尽（CPU/内存/连接池）。恢复：针对性处理——上游故障则切备用模型/降级，检索慢则加缓存/调索引，资源耗尽则扩容或优化。复盘：记录根因、加防护（熔断阈值、超时、限流）、补充告警。我的服务有重试熔断超时机制，能自动切断雪崩源头。

## 十二、项目深挖 / 软技能

**49. 讲一个你遇到的最难的技术问题，以及如何定位解决？**
答：S（情境）：在恒鑫机械项目里，Agent 出现工具调用死循环、接口雪崩，且直接问大模型会输出不符合工厂安全规范的答案。T（任务）：既要保证回答合规，又要让 Agent 稳定运行。A（行动）：先用 126 条真实业务 Query 建评测集，用 Promptfoo+AutoPE 批量迭代提示词、增加输出约束与拒答规则；再用 LangGraph 拆节点、加条件路由，配置最大循环次数、超时拦截、熔断降级，并对 MCP 工具写多组异常用例。R（结果）：合规准确率 72%→91%，死循环与雪崩得到控制，服务稳定上线。关键体会是「用数据驱动 + 机制兜底」而非靠调参碰运气。

**50. 如何做技术选型、制定接口规范、跨团队协作推进 AI 项目落地？**
答：技术选型：基于「需求 + 成本 + 团队栈 + 生态成熟度」评估——如选 LangGraph 是因为状态编排可控、可持久化，选向量库看权限过滤与规模，选 FastAPI 因异步与 Pydantic 生态。接口规范：定义统一的请求/响应结构、错误码、鉴权方式、SSE 数据格式，写文档并和前后端对齐，评审后冻结。跨团队协作：和产品对齐需求与验收标准，和后端约定接口契约，和测试共建评测集与用例，用任务排期同步进度，闭环线上反馈。同时沉淀可复用 AI 组件与提示词模板，降低后续成本——这也是我简历里强调的工程化能力。
