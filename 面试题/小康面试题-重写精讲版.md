# 一、Python 与算法基础

> 高频必答：Q3 三数之和、Q8 合并有序数组、Q10 恢复 BST、Q5 哈希表、Q11 协程。手写代码题要先说思路和复杂度，再写；写完主动报边界用例，这是加分项。

### Q1. list 和 tuple 的区别？〔原一·1〕

**考点**：可变性、可哈希、内存布局、语义。

**答**：核心区别是可变性，由此派生四点。

1. **可变性**：list 支持增删改；tuple 创建后不能改引用（元素本身是可变对象时，元素内容仍可变）。
2. **可哈希**：元素都可哈希时 tuple 可哈希，能作 dict 的 key、set 的元素；list 永远不行。
3. **性能**：tuple 定长，CPython 一次分配、开销更小、创建更快，小 tuple 还有缓存；list 有预留容量（over-allocate），扩容有拷贝成本。
4. **语义**：tuple 表达"一条记录 / 固定结构"（如 `(doc_id, chunk_id, score)`），list 表达"同类元素集合"。

工程上：配置常量、函数多返回值、缓存 key 用 tuple；需要频繁增删用 list。RAG 里我会用 tuple 做不可变的元数据键。

**追问**：`(1, [2])` 能哈希吗？不能，hash 时会抛 `TypeError`，因为内部 list 不可哈希。

### Q2. append 和 extend 的区别？〔原一·2〕

**答**：`append(x)` 把 x 当成**一个整体**追加，列表嵌套；`extend(iterable)` 迭代取出**每个元素**逐个追加，相当于 `a += iterable`。

```python
a = [1, 2]
a.append([3, 4])   # [1, 2, [3, 4]]
a.extend([3, 4])   # [1, 2, [3, 4], 3, 4]
a.extend("ab")     # 字符串也会被拆成 'a','b'，这是常见坑
```

性能上 extend 会一次性预估容量、批量搬移，比循环 append 少多次扩容，批量合并检索结果应优先 extend。项目里合并多路召回结果用 `extend`，避免出现 `[[...], [...]]` 的嵌套结构还要再 flatten。

**追问**：`a += b` 对 list 等价于 extend（原地修改），而 `a = a + b` 会新建列表。

### Q3. 数组有正有负，找出所有和为 0 的三元组（三数之和）⭐〔原一·3〕

**思路**：排序 + 双指针 + 跳过重复。固定第一个数 `nums[i]`，问题退化成有序数组的两数之和，左右指针向中间收。时间 O(n²)，额外空间 O(1)（不计结果）。

```python
def three_sum(nums):
    nums.sort()
    res, n = [], len(nums)
    for i in range(n - 2):
        if nums[i] > 0:                 # 最小的都 > 0，后面不可能凑 0
            break
        if i > 0 and nums[i] == nums[i - 1]:
            continue                    # 第一个数去重
        l, r = i + 1, n - 1
        while l < r:
            s = nums[i] + nums[l] + nums[r]
            if s == 0:
                res.append([nums[i], nums[l], nums[r]])
                while l < r and nums[l] == nums[l + 1]: l += 1   # 第二数去重
                while l < r and nums[r] == nums[r - 1]: r -= 1   # 第三数去重
                l += 1; r -= 1
            elif s < 0:
                l += 1
            else:
                r -= 1
    return res
```

**边界**：长度 < 3、全 0（只输出一个 `[0,0,0]`）、重复元素多、溢出（Python 无此问题）。**两数之和等于 0** 则用哈希：遍历时查 `-num` 是否出现过，O(n)。

**加分**：如果只要"是否存在"而非全部组合，可以直接用 set，O(n²) 降到 O(n)；如果数据是流式的，维护"已见数字集合"即可。

### Q4. yield 是什么？yield from 有什么用？〔原一·4〕

**答**：`yield` 让普通函数变成**生成器**：执行到 yield 时返回值并**挂起现场**（局部变量、指令位置都保留），下次 `next()` 从挂起处继续。它实现的是惰性求值，不一次性占用内存，适合大文件逐行读、流式输出。

`yield from sub` 是**委托**：把迭代过程交给子生成器，省掉一层 `for x in sub: yield x`，并且能透传 `send()` / `throw()` / 返回值（`StopIteration.value`）。

```python
def stream_answer(chunks):
    for c in chunks:
        yield f"data: {c}\n\n"
```

项目里 LLM 的 SSE 流式输出就是生成器：上游每来一个 token 就 yield 一帧，FastAPI 用 `StreamingResponse` 直接消费，首字延迟从"等全文"降到几百毫秒。注意生成器只能遍历一次，且异常要在生成器内部处理好，否则连接会断。

**追问**：生成器 vs 迭代器 vs 可迭代对象——生成器一定是迭代器；迭代器实现 `__next__`；可迭代对象实现 `__iter__`。

### Q5. 哈希表的底层原理？哈希冲突怎么处理？〔原一·5〕

**答**：底层是**数组 + 哈希函数**。key 经 hash 得到整数，再对容量取模（或用位运算）映射到槽位，理想情况 O(1)。

冲突指不同 key 落到同一槽位，主流四类解法：

1. **链地址法**：每个槽挂链表，过长转红黑树（Java HashMap，阈值 8）。实现简单、删除方便，但指针跳转缓存不友好。
2. **开放寻址法**：冲突后按探测序列找下一个空槽，线性探测、二次探测、双重哈希。**Python dict 用的是开放寻址 + 扰动探测**（不是简单线性探测），把高位也参与寻址，减少聚集。
3. **再哈希**：换一个哈希函数重算。
4. **公共溢出区**：冲突元素统一放另一张表。

还要提**负载因子**：超过阈值（Java 0.75，CPython 约 2/3）就扩容并 rehash，均摊 O(1)。最坏情况全冲突退化为 O(n)。

工程点：key 必须可哈希且 hash 稳定（可变对象做 key 是事故源头）；Python 3.7+ dict 有序，是 compact dict 的实现副作用，不是语言承诺的排序语义，别依赖它做业务排序。

### Q6. 说一下 Trie（字典树）的原理和用途〔原一·6〕

**答**：Trie 是把字符串按字符逐层拆开的前缀树：根为空，边代表字符，从根到某节点的路径就是一个前缀，节点可存 `is_end` 和 payload。插入/查询复杂度 O(L)，L 为串长，与词表大小无关。

用途：

- **前缀匹配 / 自动补全**：输入 "retr" 联想 retrieval；
- **词典匹配**：敏感词过滤、实体词典、领域术语识别（AC 自动机是 Trie + 失配指针，多模式匹配 O(n)）；
- **RAG 里的 query 纠错 / 同义词归一 / 实体链接**，比遍历词表快得多。

缺点是**空间换时间**：纯指针实现每个节点一个 dict，中文词表很吃内存，生产上用**双数组 Trie（Double-Array Trie）** 或压缩 Trie（Radix Tree）压缩。

**加分**：向量检索解决"语义相近"，Trie 解决"字面前缀精确"，两者互补，不是替代关系。

### Q7. 什么是低秩？PEFT、Adapter、LoRA 分别是什么？〔原一·6〕

**答**（原文 `A=BA` 是笔误，正确是 `ΔW = BA`）：

**低秩**：一个 m×n 矩阵若能用两个瘦矩阵相乘近似，`ΔW = B·A`，其中 `B∈R^{m×r}`、`A∈R^{r×n}`、`r ≪ min(m,n)`，就说它秩为 r。参数量从 m×n 降到 r(m+n)。依据是微调时的权重更新本身具有低内在秩（LoRA 论文的实证结论）。

**PEFT**：参数高效微调的总称——冻结主干，只训练极少量参数，显存和存储成本降一两个数量级，效果接近全参微调。

- **LoRA**：在 Q/K/V/O 等线性层旁挂 `B·A` 分支，`h = Wx + (α/r)·B(Ax)`。A 高斯初始化、B 零初始化，保证训练开始时增量为 0。推理可把 `W + (α/r)BA` 合并回主干，**零额外延迟**。
- **Adapter**：在 Transformer 子层后串行插入"降维-激活-升维"瓶颈层。不改变主干，但**增加了网络深度**，推理有额外开销，且不能合并。
- 另有 **Prefix-Tuning / P-Tuning**：在输入或每层前拼可训练的软提示向量，不改编权重，但占用上下文长度。

选型：显存紧、要多任务热插拔、要求无损推理 → LoRA；需要极强任务特化且不在意延迟 → Adapter；生成任务、少样本 → Prefix/P-Tuning。

### Q8. 合并两个有序数组到 nums1（原地）⭐〔原一·7〕

**思路**：nums1 尾部是空的，**从后往前**双指针，每次把较大的放到 `k`，避免覆盖 nums1 尚未处理的元素。时间 O(m+n)，空间 O(1)。

```python
def merge(nums1, m, nums2, n):
    i, j, k = m - 1, n - 1, m + n - 1
    while j >= 0:                       # nums2 处理完即可结束
        if i >= 0 and nums1[i] > nums2[j]:
            nums1[k] = nums1[i]; i -= 1
        else:
            nums1[k] = nums2[j]; j -= 1
        k -= 1
    return nums1
```

**边界**：n=0（直接返回）、m=0（把 nums2 拷过去）、有相等元素（取 `>` 保证稳定）。**为什么从后往前**：从前往前需要额外数组或大量搬移；从后往前利用尾部空位，天然原地。

**追问**：如果是链表合并，就用哨兵节点 + 双指针，不用倒序。

### Q9. Python 常见魔术方法？`&` 和 `and`、`|` 和 `or` 的区别？〔原二·7〕

**答**：魔术方法（dunder）让对象接入 Python 协议：

- 构造/表示：`__init__`、`__new__`、`__str__`（给人看）、`__repr__`（给调试看）；
- 容器：`__len__`、`__getitem__`、`__setitem__`、`__iter__`、`__contains__`；
- 调用/上下文：`__call__`（对象当函数用）、`__enter__`/`__exit__`；
- 比较/哈希：`__eq__`、`__hash__`、`__lt__`。

`&`/`|` 是**按位运算符**：整数按二进制位运算；集合并交；numpy 逐元素布尔运算。`and`/`or` 是**逻辑运算符**，且**短路**：

- `a and b`：a 为假直接返回 a（不返回 bool），否则返回 b；
- `a or b`：a 为真直接返回 a，否则返回 b。所以 `x = x or default` 在 x 为 `0`/`""`/`[]` 时会误用默认值，这是常见 bug。

优先级 `not > and > or`。项目里判断"检索结果非空且分数过阈值"会写 `if docs and docs[0].score > 0.5:`，利用短路避免索引越界。

### Q10. 恢复二叉搜索树（两个节点被交换）⭐〔原二·27〕

**思路**：BST 的**中序遍历严格递增**。交换两个节点后，序列里会出现 1 处或 2 处逆序（相邻交换只 1 处）。遍历时记录第一次逆序的前驱 `first`、最后一次逆序的当前节点 `second`，最后交换二者的值即可。时间 O(n)，递归栈 O(h)。

```python
def recover_tree(root):
    first = second = prev = None
    def inorder(node):
        nonlocal first, second, prev
        if not node: return
        inorder(node.left)
        if prev and prev.val > node.val:
            if first is None:
                first = prev          # 第一次逆序：取前驱
            second = node             # 后面每次逆序都更新，取最后一个
        prev = node
        inorder(node.right)
    inorder(root)
    first.val, second.val = second.val, first.val
```

**加分**：要求 O(1) 空间就用 **Morris 中序遍历**（利用叶子节点的空右指针做线索，遍历完再还原），空间 O(1)。**注意**：题目通常要求交换节点值而非节点本身，若要真正交换节点，需要记录父节点处理指针。

**边界**：只有两个节点、被交换的是相邻节点、根节点被换。

### Q11. Python 协程的原理？〔原二·54〕

**答**：协程是**单线程内的协作式并发**。核心三件套：协程对象（`async def` 调用产生）、事件循环（event loop）、`await` 挂起点。

执行到 `await` 时，若 IO 未就绪，协程把控制权交还事件循环并保存现场；事件循环用 **IO 多路复用（Linux 下 epoll）** 同时监听大量 fd，哪个就绪就恢复对应协程。所以它**不是并行**，而是"等待时不占线程"，一个线程可扛上万并发连接，切换在用户态、成本远低于线程。

适用：网络 IO 密集（LLM API、向量库、数据库、SSE）。不适用：CPU 密集（会堵死事件循环）。

项目里 FastAPI 路由全异步，调 LLM 用 `httpx.AsyncClient`，多路检索用 `asyncio.gather` 并发。**坑**：在协程里直接调同步阻塞库（requests、同步 DB 驱动、大文件解析）会卡住整个 loop，必须 `await asyncio.to_thread(...)` 或丢进线程/进程池。

**追问**：协程 vs 线程——协程由程序调度、无线程切换和锁开销；线程由 OS 抢占调度、需要锁保护共享状态。

### Q12. 多进程和多线程的通信方式？怎么选型？〔原二·55〕

**答**：

- **多进程**：`multiprocessing.Queue`（最常用）、`Pipe`（点对点）、`Manager`（共享 dict/list，走代理较慢）、`shared_memory`（大数组零拷贝）、信号量/锁。数据要 pickle 序列化，跨进程有拷贝成本。
- **多线程**：`queue.Queue`（线程安全）、`Lock`/`RLock`、`Event`、`Condition`、`Semaphore`。共享内存，但要防竞态。

**GIL**：CPython 同一时刻只有一个线程执行字节码，所以多线程**不能加速纯 CPU 计算**，但 IO 等待时会释放 GIL，所以 IO 密集仍有效。

选型口诀：**IO 密集 → 协程 / 线程；CPU 密集 → 多进程；GPU 推理 → 异步 + 批处理**（瓶颈在卡，不在 Python）。

项目里：PDF 解析、清洗、embedding 前的文本处理用 `ProcessPoolExecutor`；LLM 请求和向量库查询用 `asyncio`；不要用多线程去并发调本地 GPU 模型，会互相抢显存。

### Q13. 介绍一下 PyTorch 的 Tensor〔原二·56〕

**答**：Tensor 是 PyTorch 的基础数据结构，本质是**带设备信息和自动微分能力的多维数组**。关键属性：

- `shape` / `dtype` / `device`：形状、类型（fp16/bf16/int8）、所在设备（cpu/cuda）；
- `stride`：内存步长，`view` 依赖它，`reshape` 不满足时才拷贝；
- `requires_grad` + `grad_fn`：构成计算图，`backward()` 自动求导。

常用操作：广播、索引、`view/reshape`、`permute`、`matmul`、`softmax`、`norm`。CPU 与 GPU 之间 `.to(device)` 有拷贝开销，要批量搬、避免在循环里搬。

项目里：embedding 输出做 L2 归一化后算余弦相似度矩阵（`F.normalize` + `@`），或者把一批 chunk 打成 `[B, L]` 的 token 张量送模型。**注意**推理时用 `torch.inference_mode()`，省显存且更快。

### Q14. PyTorch 和 TensorFlow 的区别？〔原二·53〕

**答**：

- **图模式**：PyTorch 动态图（define-by-run），写 Python 一样调试，`pdb` 能打断点；TF1 是静态图（先建图再跑），调试痛苦，TF2 默认 eager 已靠拢动态图。
- **生态**：LLM / Agent 生态几乎全在 PyTorch（transformers、vLLM、PEFT、TRL、DeepSpeed）；TF 在传统 CV、TFLite 端侧、TFX 生产流水线仍有存量。
- **部署**：PyTorch 走 TorchScript / ONNX / TensorRT / Triton；TF 走 SavedModel / TF Serving / TFLite。
- **分布式**：PyTorch 的 DDP/FSDP 是当前大模型训练主流；TF 的 TPU 支持是它的独特优势。

结论：做 LLM 应用选 PyTorch，没有悬念；选型更多看团队存量和部署目标，而不是框架优劣。

### Q1. 介绍一个你最熟悉的 RAG 项目 ⭐〔原二·1、二·28〕

**答（STAR 口述版，约 90 秒）**：

**S 背景**：公司内部有 2 万多份产品文档、制度、工单和 PDF 手册，员工找答案靠人问 + 全文搜索，平均要 20 分钟，且答案散落在多个系统。

**T 任务**：我做的是一个面向内部文档的**知识库问答 Agent**，目标是"问一句，给出带出处的答案"，把平均查找时间压到 1 分钟内，同时把幻觉控制在可审计的范围。

**A 动作**：我负责检索链路、Agent 编排、评估和微调数据。链路是：多格式解析 → 清洗 → 结构化分块（带标题层级和 overlap）→ BGE embedding 入 Milvus → 查询侧做意图识别和 query 改写 → BM25 + 向量**混合召回** → BGE-rerank 精排 top5 → 组装带引用的 prompt → LLM 生成 → 校验 Agent 做忠实度和引用检查 → 返回答案 + 原文片段。

**R 结果**：上线后 top10 召回从 71% 提到 92%，答案忠实度人工抽检从 68% 提到 88%，P95 延迟 2.8s，日均 3000+ 次提问，badcase 率从 18% 降到 7%。

**收尾（主动留钩子）**：最难的不是模型，是 PDF 表格解析和"该拒答时要拒答"，这两块我可以展开讲。

**追问准备**：为什么不用纯向量？为什么不用微调替代 RAG？知识库多大？QPS 多少？成本多少？——每个数字都要能解释来源（离线评估集 / 监控大盘 / 账单）。

### Q2. 你在项目里具体负责哪部分？模型是多模态的吗？〔原二·9〕

**答**：我主要负责四块：

1. **检索链路**：分块策略、混合召回、rerank、参数调优；
2. **Agent 编排**：意图识别、工具定义、多轮记忆、拒答兜底；
3. **评估体系**：构建 300 条带标注的评估集，做离线回归 + 线上监控；
4. **微调数据**：构造 SFT / 偏好数据，做 LoRA 微调，稳定工具调用格式。

**多模态**：第一版是纯文本，图片走 OCR 转文字；第二版对图表类 PDF 引入了版面分析（标题/表格/图片分块）+ 多模态 embedding，图片单独建索引，检索时文本和图片一起召回，回答里能直接嵌原图。**没有一上来就上多模态**，是因为 80% 的问题答案在正文，先把文本链路做稳，ROI 更高。

**追问"你个人写了多少代码"**：说清楚自己从 0 写的模块（如检索服务和评估脚本），以及复用的开源组件（LangChain、Milvus），别把框架能力说成自己的。

### Q3. 讲一下 RAG 的完整链路（离线 + 在线）⭐〔原二·16、二·35〕

**答**：分两条链路。

**离线入库**：

1. **采集**：PDF / Word / Excel / 网页 / 飞书文档，记录来源、版本、权限；
2. **解析**：文本、表格、图片分别抽；扫描件走 OCR；保留标题层级和页码；
3. **清洗**：去页眉页脚、水印、乱码、断行合并、去重（SimHash / MinHash）；
4. **分块**：标题感知 + 递归切分，512 token，overlap 15%，子块带父块摘要和元数据；
5. **向量化**：BGE-M3 / bge-large-zh，批量编码，归一化；
6. **入库**：Milvus 存向量 + 标量字段（来源、权限、版本、页码），同时建 BM25 倒排索引；
7. **质检**：空块率、乱码率、重复率、解析抽样人工验收。

**在线问答**：

1. **接入**：鉴权、限流、会话 ID；
2. **理解**：意图分类（知识问答 / 闲聊 / 越界 / 工具任务）、query 改写（指代消解、同义词扩展）、复杂问题拆子问题；
3. **召回**：BM25 与向量并行召回各 top50，RRF 或加权融合；
4. **精排**：cross-encoder rerank 取 top5，过滤低分；
5. **组装**：按 token 预算裁剪，拼系统提示 + 上下文（带编号）+ 历史对话；
6. **生成**：流式输出，强制引用编号，温度 0.1~0.3；
7. **校验**：忠实度检查、引用是否存在、敏感词、格式；
8. **落盘**：query、召回列表、分数、prompt、答案、耗时，全链路 trace。

**一句话总结**：离线决定"能不能找到"，在线决定"找得准不准、说得对不对"。

### Q4. chunk 的 overlap 你是怎么调优的？〔原二·2〕

**答**：overlap 的作用是防止一句话或一个语义单元被切在边界上，两边都读不全。

我的做法：

1. **先定 chunk size**：按 embedding 模型的最佳输入长度和答案粒度定，中文业务文档用 512 token；表格、条款这类必须整块保留的，按结构切，不强求长度。
2. **overlap 取 10%~20%**：512 对应 64~100 token，大约一到两句话。overlap 太小会跨块断义；太大则重复内容多，召回同质化、浪费 token、还可能把无关内容带进 prompt。
3. **看文本特征**：长句、法律条款、操作步骤多的文档加大到 20%；FAQ、短句多的降到 5%~10%。语义分块本身边界准，overlap 可以更小。
4. **用数据定，不拍脑袋**：固定评估集上对比 recall@10、context precision、答案忠实度，同时看平均上下文 token 数和 P95 延迟，取性价比拐点。我们最后是 512/64 最优，再大召回只涨 1 个点，token 成本涨 20%。

**加分**：更好的方案是**父子块**——子块（256）负责精准召回，命中后把父块（1024）喂给模型，既保证召回粒度又保证上下文完整，可以显著降低对 overlap 的依赖。

### Q5. 做知识库时具体遇到过什么问题？〔原二·3〕

**答**：按链路说五类，每类给一个解法，别只报问题。

1. **解析层**：扫描件 OCR 错字、双栏 PDF 串行、表格错位、页眉页脚混入正文。解法是多引擎兜底（pdfplumber / PyMuPDF / MinerU）+ 版面分析 + 规则清洗 + 抽样人工验收。
2. **结构层**：Word/PDF 的标题层级丢失，chunk 变成"无源之水"。解法是解析时保留 heading path，写进 chunk 元数据，检索时一起返回，prompt 里带上"出自《XX》第 3.2 节"。
3. **切分层**：一刀切把表格、代码、条款切断。解法是按内容类型路由不同 splitter，表格转 Markdown 整块保留。
4. **检索层**：同义词/缩写召回不到（"报销" vs "费用核销"），纯向量对型号、编号不敏感。解法是混合检索 + 同义词词典 + query 改写。
5. **生成层**：模型不看上下文、自己编；多轮对话指代漂移。解法是强约束 prompt + 引用校验 + 多轮 query 改写（把"它"补全成实体）。

还有两个工程问题：**增量更新**（文档改了要能定位到旧 chunk 删除重建，用 doc_id + version 做幂等）和**权限隔离**（检索时按用户部门做标量过滤，绝不能先召回再过滤）。

### Q6. 上线之后怎么监控生成答案的质量？⭐〔原二·4〕

**答**：分四层，自动 + 人工 + 用户信号 + 兜底。

1. **检索层**：recall@k（离线评估集）、hit rate、上下文相关性、空召回率、平均召回条数。线上没有标注，就用"用户是否追问/点踩"做弱标签。
2. **生成层**：忠实度（答案的每个事实能否在上下文中找到依据，用 LLM-as-judge + 人工校准）、答案相关性、引用准确率、拒答率、平均输出长度。
3. **用户信号**：点赞/点踩、复制、追问次数、会话放弃率、转人工率。点踩必须能回捞完整 trace。
4. **系统层**：P95/P99 延迟、首 token 延迟、超时率、5xx、token 成本、GPU 利用率。

**机制**：全链路日志（query → 改写后 query → 召回 chunk 及分数 → rerank 分数 → prompt → 原始输出 → 校验结果），每天自动跑评估集回归，指标跌超阈值告警；每周人工抽检 100 条，badcase 归因到"解析/切分/召回/排序/生成/拒答"六类，进 backlog。

**关键点**：LLM-as-judge 要和人工标注做一致性校验（Cohen's kappa），否则指标不可信。

### Q7. 这个项目是医院相关的吗？〔原二·5〕

**答**（按真实情况二选一，别编）：

- **不是医疗**：我做的是企业内部文档知识库。医疗场景的要求会更高一档：幻觉零容忍、答案必须逐条溯源到指南/文献、知识库要有版本和生效日期、涉及诊疗建议要有免责声明和医生复核，合规上还要脱敏和审计日志。我的项目里"引用 + 校验 + 拒答"这套机制是通用的，但医疗要把阈值调得更保守。
- **是医疗**：是的，医疗 RAG 的核心不是"答得像"，而是"答得可审计"。我们的做法是：答案必须带原文引用（指南名称 + 章节 + 页码），检索只信任有资质的知识源，模型不确定就拒答并转人工；知识库按版本和生效日期管理，过期指南直接下架；评估上把"无依据陈述率"作为一级指标。

**提醒**：这题是背景核验题，简历写什么就答什么，不要为了显得高级硬蹭医疗。

### Q8. 生成器（底座模型）的区别和迭代思路？〔原二·6〕

**答**：这里的"生成器"指最终负责写答案的 LLM。按训练阶段分：

- **Base**：只会续写，不理解指令，直接拿来问答会答非所问，适合做领域继续预训练；
- **Chat / Instruct（SFT）**：指令对齐，会遵循格式，是 RAG 的默认选择；
- **偏好对齐（DPO/RLHF）**：更符合人类偏好，更简洁、更少有害输出，但可能"过度自信"，事实性要靠 RAG 兜；
- **领域微调模型**：术语、话术更贴业务，但通用推理可能退化，需要混通用数据防遗忘。

**迭代路径**：先用通用 Chat 模型把链路跑通（这时瓶颈通常在检索，不在模型）→ 用评估集定位是"没召回"还是"召回了不会用"→ 后者才考虑微调或换更大的模型 → 最后用 DPO 调风格和拒答行为。**不要一上来微调**，先证明 RAG 链路已经到位。

选型维度：中文能力、上下文长度、function call 稳定性、推理成本、私有化许可。

### Q9. 微调数据集怎么来的？为什么要微调？什么情况才需要微调？⭐〔原二·9〕

**答**：**数据来源**四路：

1. 真实用户 query + 人工标注的标准答案（质量最高，但少）；
2. 业务专家按场景编写的问答对；
3. 强模型生成 + 人工/规则校验（低成本扩量，注意去重和多样性）；
4. 从知识库文档反向构造（给定段落生成问题，再要求答案必须引用该段）。

比例上真实数据优先，合成数据做补充；要留出**与训练集同分布但不重叠**的评测集，否则指标虚高。

**为什么微调**（RAG 解决"不知道"，微调解决"不会用/不按格式"）：

- 领域术语和黑话理解差，query 改写和答案表述不专业；
- **工具调用格式不稳定**，JSON 经常缺字段、乱加解释，Agent 链路经常断；
- 输出格式、话术、拒答策略需要统一；
- 检索已经很好，但模型"看到了不会用"，忠实度和完备性上不去。

**不需要微调**：知识更新频繁（微调记不住还会过期）、只是查文档、通用能力够用、没有高质量数据。这些情况 RAG + prompt 更划算。

### Q10. 基于什么版本微调？需要多少 GPU？训练多久？〔原二·10〕

**答**（给一个自洽的例子，按实际改）：

- **底座**：Qwen2.5-7B-Instruct；
- **方法**：LoRA，r=16，alpha=32，target 为 q/k/v/o + gate/up/down，bf16；
- **数据**：8k 条 SFT（真实 3k + 合成 5k），2 轮，max_len 4096，batch 32（梯度累积）；
- **硬件**：单卡 A100 40G 或 2×3090 24G（开 gradient checkpointing + flash-attn）；
- **耗时**：单卡约 3~4 小时，成本几十块钱；
- **效果**：工具调用 JSON 合法率从 82% → 99%，领域术语准确率 +6 个点，通用能力用 MMLU 子集验证无显著下降。

**32B**：LoRA 全量 target 大约 20~24G 显存，单卡 A100 80G 可跑；**70B** 要 ZeRO-3 / FSDP 多卡，或者 QLoRA 4bit 单机多卡。**全参微调** 7B 大约需要 8×A100 80G（ZeRO-3），不是一张卡能干的。

**面试提醒**：说清楚是"几张卡、什么卡、多少数据、多少 step"，这三个数字对不上很容易被追问穿。

### Q11. 推理引擎怎么部署？并发多少？接口是什么？〔原二·11、二·48〕

**答**：用 **vLLM** 起 OpenAI 兼容服务，接口就是 `/v1/chat/completions`，支持流式（SSE）和非流式；Embedding 和 rerank 也各自起独立服务，通过内网 HTTP 调用。

**并发**：不是"固定支持多少并发"，取决于 `max_model_len`、`gpu_memory_utilization`、输入输出长度。7B + 4k 上下文 + A10 24G，单卡稳定在 20~40 路并发（P95 < 3s），再往上要靠多副本 + 网关负载均衡。压测用 Locust/wrk 按真实输入长度分布打，别看空载 QPS。

**为什么独立部署**：模型是重资源、长启动的服务，独立部署才能单独扩缩容、灰度升级、做资源隔离；应用层保持无状态，方便水平扩展。

**追问"流式怎么做的"**：vLLM 流式返回增量 token → 后端用 SSE 透传 → 前端逐字渲染；中间加超时、断连检测和 token 计数。

### Q12. RAG 的难点、痛点与适用场景？〔原二·12、二·49〕

**答**：难点分五层，每层一句话 + 一个对策：

1. **解析难**：PDF 表格、扫描件、多栏排版，垃圾进垃圾出。→ 多引擎 + 版面分析 + 质检。
2. **切分难**：语义边界和长度限制矛盾，切碎丢上下文，切大引入噪声。→ 父子块 + 标题感知。
3. **检索难**：语义与关键词各有盲区，长文档里有"相似但不相关"的干扰项。→ 混合召回 + rerank + 元数据过滤。
4. **生成难**：模型不忠于上下文、长上下文中间信息丢失（lost in the middle）、多跳问题不会推理。→ 引用约束 + 递归检索 + 上下文重排。
5. **运营难**：知识更新、权限、版本、成本、评估，都是长期工程。→ 增量索引 + 权限过滤 + 回归评估。

**适用场景**：企业知识库/客服、制度合规问答、售后与工单辅助、研发文档助手、法律/医疗等强溯源场景、个人第二大脑。
**不适用**：需要实时计算、强事务操作、创意写作、纯结构化统计分析——这些该走工具/SQL/代码，不该硬塞给 RAG。

### Q13. query 的边界怎么设计？超纲问题怎么办？⭐〔原二·13、六·10〕

**答**：先分类，再路由，最后兜底。

**入口分类**（用小模型或 LLM 做，成本低）：

1. **知识问答**：走 RAG；
2. **工具任务**：查订单、算数值、发邮件，走 function call；
3. **闲聊**：轻量回应，不检索；
4. **越界/敏感**：直接拒答；
5. **模糊/歧义**：反问澄清，而不是硬猜。

**边界判定**：检索后看 top1 分数和分数间隔，低于阈值判为"知识库没有"；再用一个轻量 NLI/LLM 判断"召回内容是否真的支持回答"。两道闸门比单看相似度可靠。

**拒答话术**要具体："我在现有资料里没有找到相关规定，建议你联系 HR 或查看《XX 制度》第 X 章"，而不是干巴巴的"我不知道"。拒答也是产品体验的一部分。

**兜底**：连续两次没查到 → 转人工/提工单；同时把这类 query 记下来，作为知识库补充的输入。

### Q14. 你怎么评价这个系统？〔原二·14〕

**答**：四个维度，每个维度给指标和动作。

1. **效果**：检索 recall@10 / context precision，生成忠实度、答案相关性、引用准确率、拒答准确率；离线评估集 + 线上抽检。
2. **性能**：首 token 延迟、P95 端到端、吞吐 QPS、单次成本（token + GPU 折旧）。我们的目标是 P95 < 3s，单次 < 0.05 元。
3. **稳定性**：超时率、5xx、JSON 解析失败率、空召回率、模型服务可用性；有降级策略（rerank 挂了就跳过，LLM 超时就返回召回片段）。
4. **可维护性**：知识增量生效时延、版本回滚能力、badcase 归因效率、监控覆盖率。

**加分**：把"业务指标"也说出来——人均查找时长、转人工率、工单量下降，这些才是老板关心的。

### Q15. 整合后的数据落成什么文件格式？〔原二·17、二·18〕

**答**：分层存储，各司其职：

- **原始层**：PDF/Word/HTML 原文件存对象存储（MinIO/S3），路径含 doc_id 和版本，保证可回溯；
- **解析层**：每篇文档的解析结果存 JSON（含 blocks、页码、heading path、表格结构），便于重切分而不必重新解析；
- **切片层**：`chunks.jsonl`，一行一个 chunk，字段 `chunk_id / doc_id / text / heading / page / tokens / hash / acl`；jsonl 的好处是流式读写、追加方便、坏一行不影响全局；
- **索引层**：向量入 Milvus（或 FAISS 文件），BM25 用倒排索引（Elasticsearch / bm25s），元数据入 PostgreSQL 做过滤和权限；
- **评估层**：`eval.jsonl`，字段 `query / gold_chunks / gold_answer / type`；
- **日志层**：按天分区的 JSON 或 Parquet，进数仓做分析。

**追问"为什么不用一个数据库全存"**：向量、倒排、标量过滤的索引结构不同，混存会互相拖累；用 id 关联，各取所长。

### Q16. 召回多个切片后有优先级吗？还是一股脑塞进 prompt？⭐〔原二·19、二·20〕

**答**：绝不一股脑塞。有完整的排序和裁剪流程：

1. **粗召回**：BM25 top50 + 向量 top50，按 chunk_id 去重；
2. **融合**：RRF 或加权归一化，得到统一分数；
3. **精排**：cross-encoder 对 (query, chunk) 逐对打分，取 top5~8；
4. **业务加权**：时效性（新文档优先）、来源权威度、用户权限、是否命中标题，做小幅加权；
5. **多样性**：同一文档最多取 2~3 块，避免一个文档霸榜；用 MMR 去冗余；
6. **预算裁剪**：按 token 预算从高到低装，超了就截断或摘要，保证总上下文不超过窗口的 60%。

低分直接丢弃，宁缺毋滥——塞 20 条不相关的内容，比只给 3 条相关的更容易诱发幻觉。**上下文污染比信息不足更可怕**。

### Q17. 混合检索具体指什么？两个通道有权重吗？⭐〔原二·21、二·22、二·36、二·37、二·42、二·44、四·15〕

**答**：混合检索 = **稀疏检索（BM25）+ 稠密检索（向量）**，两路并行召回后融合。

- **BM25**：基于词频和逆文档频率，公式核心是 TF 饱和（k1）+ 文档长度归一（b），擅长精确匹配型号、编号、专有名词、缩写。不需要训练，可解释，但对同义词和语义改写无能。
- **向量**：embedding 后算余弦/内积，擅长语义相似、跨表述匹配，但对数字、罕见实体不敏感，且可能"相似但不相关"。

**融合方式**：

1. **加权求和**：分数归一化后 `score = α·bm25 + (1-α)·cos`，我们线上 α=0.3，向量 0.7；α 用评估集网格搜索，不是拍脑袋。
2. **RRF（倒数排名融合）**：`score = Σ 1/(k + rank_i)`，只看排名不看原始分数，天然规避两路分数量纲不一致的问题，k 常取 60。**推荐默认用 RRF**，稳定、免调参。
3. **动态权重**：query 里有引号、型号、数字 → 提高 BM25；口语化长问句 → 提高向量。

项目里我先用 RRF 上线，再用评估集验证加权版本，收益 < 1 个点就保持 RRF，少一个调参维度。**追问"两路各召回多少"**：各 50，融合后 100，rerank 取 5，比例由 token 预算和延迟倒推。

### Q18. 项目里的"语义解析"是什么类型？〔原二·43〕

**答**：不是单纯的意图分类，而是一条轻量 NLU 流水线：

1. **意图识别**：知识问答 / 工具调用 / 闲聊 / 越界，决定路由；
2. **query 改写**：多轮指代消解（"它的保修期"→"XX 型号的保修期"）、错别字纠正、同义词/缩写扩展；
3. **查询拆解**：多跳问题拆成子问题（"A 和 B 的报销比例分别是多少" → 两个子查询），分别检索再合并；
4. **结构化抽取**：时间、部门、产品型号等槽位，转成元数据过滤条件；
5. **校验 query**：生成"给定片段能否支持该结论"的判断型 query，供忠实度校验和引用检查使用；
6. **边界判定**：是否需要澄清、是否超纲。

实现上用一个小模型（Qwen 7B / 规则）做分类和改写，复杂拆解才调大模型，控制成本和延迟。**关键点**：改写后的 query 要和原 query 一起检索（多路召回），避免改写引入语义漂移。

# 三、文档解析、清洗与分块

> 这一章是 RAG 的"地基"。面试官爱问细节，因为它最能区分"调过 LangChain demo"和"真做过落地"。
> 一条主线记住：**解析保结构 → 清洗保质量 → 分块保语义 → 质检保下限**。

### Q1. 数据来源格式有哪些？〔原三·1〕

**答**：按解析难度分四类：

1. **结构化**：Excel、CSV、数据库表、JSON——字段明确，直接映射成文本或走 SQL Agent；
2. **半结构化**：Word、Markdown、HTML、PPT——有标题层级，重点是把 heading 转成元数据；
3. **非结构化**：PDF（文本型 / 扫描型 / 混合型）、图片、扫描件——最费劲；
4. **流式/协作类**：飞书/钉钉/Confluence 文档、工单、聊天记录、邮件——要通过 API 增量同步，还要处理权限和版本。

不同来源走不同的 loader，但**统一输出成同一种内部结构**（blocks：文本/表格/图片 + 页码 + 标题路径 + 来源），后面的清洗和分块才能复用。

### Q2. 复杂的 PDF 怎么解析？⭐〔原三·2、三·13〕

**答**：先判类型，再选引擎，不能一把梭。

1. **文本型 PDF**：`pdfplumber` 抽文本和表格，`PyMuPDF` 抽取速度快、能拿 block 坐标；按坐标做**阅读顺序重排**，解决双栏串行。
2. **扫描型/图片型**：先渲染成图（200~300 DPI），走 OCR（PaddleOCR / PP-StructureV3）或版面分析模型（MinerU / Marker），输出带层级的 Markdown。
3. **表格**：`pdfplumber` / `camelot`（lattice 有线表、stream 无线表）抽成二维结构，转 Markdown 保留行列；跨页表要按表头合并。
4. **公式**：转 LaTeX（MinerU / Mathpix），否则公式会变成乱码。
5. **图片**：单独抽出来存对象存储，OCR 文字入索引，原图在答案里回显。
6. **兜底**：多引擎跑同一页，用文本长度、乱码率、词典命中率投票选最优；低质量页打标进人工队列。

**准确率保障**：抽样 200 页人工标注，算字符准确率（CER）和表格还原率；线上监控空块率、乱码率、平均块长突变。目标不是 100%，而是"错了能被发现"。

### Q3. 切块（chunking）策略有哪些？怎么选？⭐〔原三·3〕

**答**：四类，按优先级组合使用。

1. **固定长度**：按 token 数硬切，简单快，但必然切断语义，只适合日志、流水账。
2. **递归字符切分**：按 `\n\n → \n → 。 → ，` 的优先级递归切，尽量在自然边界断开，`RecursiveCharacterTextSplitter` 就是这套。**默认首选**。
3. **结构感知**：按标题、章节、条款、表格切，chunk 带上 heading path 和页码。业务文档、法规、手册必须用这个。
4. **语义切分**：相邻句子算 embedding 相似度，在相似度骤降处断开。边界最准，但慢、贵，适合长文重点章节。

**工程做法**：结构感知优先 → 超长的块再递归切 → 表格/代码整块保留 → 加 10%~20% overlap → 子块带父块摘要（parent-child retrieval）。

**选型看三点**：文档结构强不强、答案粒度多细、预算多少。FAQ 用问答对切；手册按小节切；合同按条款切。

### Q4. 文档数据怎么预处理？〔原三·4〕

**答**：目标是"去掉噪声、补回结构、保证可追溯"。清单：

- **噪声**：页眉页脚、页码、水印、广告、目录页、重复的法律声明；
- **文本**：合并被 PDF 硬换行切断的句子、统一全半角、去零宽字符和控制符、修复乱码（编码探测 + 字符集白名单）；
- **结构**：把字号/加粗/编号识别成标题层级，生成 heading path；
- **表格**：合并跨页表、补表头、转 Markdown；
- **去重**：文档级 SimHash，段落级哈希，避免同一份制度有 5 个版本全入库；
- **质量分**：空块、超短块（<20 字）、乱码率高、重复率高的块直接过滤或打标；
- **元数据**：来源、部门、生效日期、密级、版本，缺一不可，后面权限和时效都靠它。

**原则**：清洗规则要可配置、可回溯，别写死；保留"原始文本 → 清洗后文本"的映射，出问题能定位是规则误杀。

### Q5. 长文本怎么切？缺失标题标签怎么补？〔原三·5〕

**答**：

**切分**：先按文档结构切大节，再对超长节做递归切分，最后按 token 上限兜底。**不要从头到尾一把递归**，会丢掉章节归属。每个 chunk 存 `heading_path`（如"第三章 > 3.2 报销标准"）。

**缺标题/缺层级**的补法（按成本从低到高）：

1. **规则**：用编号模式（`第X章`、`1.2.3`、`一、（一）`）和字号/加粗特征推断；
2. **版面模型**：用 layout 模型识别 title/section header；
3. **LLM 补全**：对没有标题的块，让模型根据内容生成 5~10 字的小标题和一句话摘要，写进元数据（不是改写正文）；
4. **聚类补全**：对整篇无结构的长文，先做段落聚类，再给每簇生成标题。

**注意**：LLM 生成的标题只用于检索辅助，原文事实不能改；要在元数据里标记 `title_source=llm`，便于追责。

### Q6. 长文档的层级和段落关系怎么构建？〔原三·6〕

**答**：三种粒度，按需组合。

1. **树形结构（最常用）**：文档 → 章 → 节 → 段，每个节点存 id、标题、摘要、子节点列表。检索命中叶子，返回时沿路径带出父级标题；或者直接把父节点内容一起喂给模型（parent-child）。
2. **摘要链**：给每个章节生成摘要，自底向上聚合；检索先匹配摘要定位章节，再进章节内精搜。适合几百页的手册。
3. **图谱结构**：把"条款引用条款""步骤依赖步骤"抽成边，用于多跳问题（"违反第 5 条按第 12 条处罚"）。成本高，只对强关联文档做。

**段落关系**还可以用**相邻扩展**：命中一个 chunk 后，自动把前后各一个 chunk 带上，解决"定义在前一段、结论在后一段"的断裂问题。实现简单，收益明显。

### Q7. Jina 的数据预处理是怎样的？〔原三·7〕

**答**（原文表述有误，更正）：Jina 是 **embedding 模型**（jina-embeddings-v3），不是数据处理框架。它的输入处理要点：

1. **不需要手工加 `[CLS]/[SEP]`**——模型内部有 tokenizer 和特殊 token，和 BERT 时代的手工拼接不一样；
2. **区分 query / passage**：v3 用 **task LoRA**（`retrieval.query` / `retrieval.passage`）区分两侧编码，用错任务类型会掉点；
3. **长度**：支持 8192 上下文，但超过训练分布的长文本效果会衰减，仍建议按 512~1024 切；
4. **维度**：支持 Matryoshka 截断（1024 → 512/256/128），用少量精度换存储和速度；
5. **预处理**：去 HTML 标签、去多余空白、保留原文标点；不要做过度清洗（去停用词会伤语义）。

**一句话**：embedding 模型的"预处理"主要是**任务前缀、长度截断、归一化**，不是 NLP 传统意义上的分词清洗。

### Q8. 为什么不用 tiktoken 而用 BM25？两者底层逻辑是什么？〔原三·8〕

**答**（前提不成立，先纠正再答）：**tiktoken 和 BM25 不是一类东西，不存在二选一**。

- **tiktoken** 是 OpenAI 的 **BPE 分词器**，作用是把文本切成 token、数长度、做截断。它不负责检索。
- **BM25** 是**稀疏检索排序函数**，靠词频 TF、逆文档频率 IDF、文档长度归一化算相关性。它前面需要分词（中文用 jieba，英文用空格/词干），跟 tiktoken 没关系。

实际项目中两者**配合使用**：tiktoken 统计 token 控制 chunk 大小和 prompt 预算，BM25 负责关键词召回。原文提到的"null client 和 server"应是听误，BM25 没有 client/server 之分；如果说的是部署形态，Elasticsearch 把它做成查询能力（有 server），`bm25s`/`rank_bm25` 是本地库（无 server）。

**追问"中文 BM25 怎么分词"**：jieba + 领域词典，或 char-level bigram（免分词，对错别字鲁棒）；要和向量检索用同一套归一化（全半角、大小写）。

### Q9. 为什么没有用语义分块？〔原三·9〕

**答**：不是不用，是**不全用**，因为性价比不划算。

语义分块的问题：

1. **贵且慢**：每个句子都要编码，一本 300 页的 PDF 要几分钟，全量重建索引成本高；
2. **阈值难定**：相似度跌多少算边界，因文档而异，调参成本高；
3. **不稳定**：同一文档换个 embedding 模型，切出来的块就变了，不利于版本管理；
4. **收益有限**：结构化文档本来就有一二三级标题，按结构切已经接近最优。

我的策略是**分层**：90% 文档用"结构感知 + 递归切分"，只对无标题的长文、会议纪要、访谈记录用语义分块；而且用轻量句向量 + 抽样，不全量跑。评估上如果语义分块带来的 recall 提升 < 2 个点，就不值得上。

### Q10. Word / PDF / Excel / 图片怎么统一转成向量库？〔原三·10〕

**答**：统一成"标准块"再入库，流程：

1. **分发 loader**：docx 用 python-docx（读样式判断标题）、xlsx 用 openpyxl/pandas（按 sheet + 表头转 Markdown）、pdf 按 Q2、图片走 OCR；
2. **归一化**：全部转成 `blocks = [{type, text, page, heading_path, meta}]`；
3. **清洗 + 去重**：同 Q4；
4. **分块**：按类型路由（正文递归切、表格整块、问答对按对切）；
5. **向量化**：批量 encode，L2 归一化，记录模型版本；
6. **写库**：向量 + 标量元数据（doc_id、部门、密级、生效日期）一起写 Milvus；同时写 BM25 索引；
7. **回写映射**：chunk_id ↔ 原文位置，用于引用和高亮。

**Excel 特别注意**：别把整张表拍平成一行字符串，行列关系会丢。按"表名 + 表头 + 每行一条记录"转成自然语言或 Markdown，检索命中后再还原成表格展示；数值统计类问题直接路由到 SQL Agent，不要让 RAG 硬算。

### Q11. 多模态文档怎么处理？〔原三·11〕

**答**：三条路线，按需求选：

1. **OCR 转文本**（成本最低）：图片/扫描件抽文字入普通索引。适合文字为主的截图、扫描合同；缺点是丢版式和图表语义。
2. **多模态 embedding**（图文同空间）：图片用 CLIP/SigLIP 类模型编码，文本用文本塔编码，同一向量空间检索；或者用 jina-clip、BGE-VL。适合"以图搜图""用文字找图"。
3. **多模态 LLM 生成描述**（效果最好、最贵）：让 VLM 给每张图生成"图片描述 + 关键信息"（如"图 3：2023 年销售额同比增长 12%"），把描述当文本入库，原图 id 存元数据。检索命中描述，回答时回显原图。**这是目前工程上最实用的方案**。

项目里我用的第 3 种 + 第 1 种兜底：图表先 VLM 描述，再 OCR 补充坐标轴和数据标签；PDF 里的流程图额外抽成 Mermaid 或步骤文本。

### Q12. 文档里的表格怎么处理？⭐〔原三·12〕

**答**：表格是 RAG 的老大难，核心是"别把它拍平"。

1. **抽取**：pdfplumber/camelot 抽二维结构；无边框表用 stream 模式或视觉模型；跨页表按表头 merge。
2. **表示**：转 **Markdown 表格**（保留行列）或 JSON（`{"列名": 值}`），比空格拼接的纯文本可读性高一个量级。
3. **切分**：小表整块入一个 chunk，不要切；大表按行分组，但**每块都重复表头**，否则检索到的行没有列名，模型看不懂。
4. **增强**：给表加一句自然语言摘要（"本表为 2024 年各区域报销上限，共 5 行 4 列"），提升召回率；表名和表头写进元数据。
5. **检索**：表格块单独打 `type=table` 标签，问题里出现"多少/对比/排名"时提高表格块权重。
6. **计算**：涉及求和、同比、筛选的，走 **SQL Agent / pandas 工具**，不要让 LLM 读表算数，它会算错。

**追问"表格检索不准怎么办"**：两路——一路文本化检索，一路把表格转成"行级描述"（每行一句自然语言）建索引，两路结果合并。

### Q13. PDF 解析质量怎么判定？怎么保证准确率？〔原三·13〕

**答**：三层质检。

1. **自动指标（每篇必跑）**：空文本率、乱码字符占比、平均块长、重复块比例、页数与文本长度比（扫描页可能整页无字）、表格行列数是否异常、OCR 置信度均值。
2. **抽样人工（按批次）**：每批抽 5%~10%，标注字符准确率 CER、表格还原率、阅读顺序正确率；低于阈值整批退回换引擎。
3. **线上反馈（持续）**：用户点踩里归因"答非所问/内容残缺"，反查对应 chunk，定位是解析还是检索问题。

**保证手段**：多引擎投票、扫描件提高 DPI、版面分析后再 OCR、对低质量页单独走 VLM 重解析、建立"解析黑名单"（某些来源的 PDF 一律人工处理）。

**关键认知**：解析错误不可能为零，要做的是**让错误可见、可定位、可回滚**，而不是追求完美。

### Q14. 解析出错怎么处理？〔原三·14〕

**答**：分级处理，不要一律重试。

1. **可自动修复**：换引擎重解析（pdfplumber → MinerU → VLM）、调 OCR 参数、重新合并断行、补表头。
2. **可隔离**：低质量块打 `quality=low` 标签，检索时降权或不参与，避免污染答案；同时在管理后台提示"该文档解析异常"。
3. **必须人工**：核心制度、合同、财报类文档，进人工校对队列；校对结果回写，形成样本。
4. **兜底话术**：如果用户问的正好是低质量块，明确告知"该文档解析可能不完整，建议查看原文第 X 页"，并给出原文链接。

**监控**：解析失败率、低质块占比、人工返工率进大盘；某类来源突然升高就查模板是不是变了。

### Q15. 基于 token 分块，有指标判断好坏吗？〔原三·15〕

**答**：有，分" intrinsic（块本身）"和 "extrinsic（下游效果）"两类。

**块本身**：

- 平均/分位块长、超长块占比；
- **边界截断率**：以句号/问号结尾的块占比，越低说明切得越碎；
- 重复率（overlap 带来的冗余）；
- 标题覆盖率：有多少块带 heading path；
- 表格/代码被切断的比例。

**下游效果**（最终标准）：

- recall@k、context precision；
- 答案忠实度、完备性；
- 平均上下文 token 数、P95 延迟（成本）；
- badcase 中"上下文缺失/上下文噪声"的归因占比。

**方法**：固定其他变量做 A/B，比如只改 chunk size（256/512/1024），看 recall 和 token 成本的曲线，取拐点。**没有绝对值标准，只有相对最优**。

### Q16. 试过不同分块方法吗？语义分块是不是最优？〔原三·16〕

**答**：试过四类，结论是**没有普适最优，只有场景最优**。

- 固定长度：基线，recall 最低，但速度最快；
- 递归切分：性价比最高，比固定长度 recall +8~12 个点；
- 结构感知：在有标题的文档上最好，比递归再 +3~5 个点，且引用可读性最好；
- 语义分块：在无结构长文上最好，但比结构感知只高 1~2 个点，成本高 5~10 倍。

最终组合是"结构感知 + 递归兜底 + 父子块"，语义分块只用于特定文档类型。**面试时一定要给出这个"组合 + 取舍"的结论**，而不是站队某一个方法。

### Q17. 上下文窗口怎么管理？生成 token 怎么控制？〔原三·17、三·18〕

**答**：上下文是预算，要像管钱一样管。

**输入侧**：

1. **检索裁剪**：rerank 后只取 top5，按分数和多样性筛选，低分直接丢；
2. **预算分配**：系统提示 10%、历史对话 20%、检索上下文 60%、留给输出 10%；
3. **压缩**：长 chunk 抽摘要句、相邻块合并、去重（同一文档多块只留最相关段）；
4. **重排**：把最相关的放在**开头和结尾**，中间容易丢（lost in the middle）；
5. **硬截断**：按 token 精确计算，宁可少给一条，也不要截断半句话。

**输出侧**：`max_tokens` 限制、要求结构化简短回答、流式输出 + 超时中断、长答案分段生成。

**多轮对话**：滑动窗口 + 摘要记忆（旧对话压缩成要点），指代消解后再检索，避免把整段历史塞进去。

**度量**：监控平均输入 token、超窗率、因截断导致的 badcase 占比。

### Q18. 图表/表格处理，多进程还是多线程？两条数据让模型回答呢？〔原二·40、二·41〕

**答**：先判断瓶颈，再选并发模型，别背口诀。

**文档解析（CPU 密集 + 部分 IO）**：

- PDF 解析、OCR 前处理、文本清洗是 CPU 密集，用**多进程**（`ProcessPoolExecutor`），绕过 GIL；
- 文件下载、读写对象存储是 IO 密集，用**线程池 / asyncio**；
- OCR/版面模型如果用 GPU，就**批处理 + 单进程多 batch**，多进程会抢显存。

**两条数据让模型回答**：

- 调**远程 LLM API**：瓶颈是网络等待，用 `asyncio.gather` 或线程池并发，两条几乎同时返回；
- 调**本地 GPU 模型**：瓶颈是卡，开两个线程不会更快，反而抢显存；应该**合批**（batch=2）一次前向，或用 vLLM 的连续批处理；
- 纯 CPU 小模型：多进程才可能真并行。

**一句话**：IO 等待 → 协程/线程；CPU 计算 → 进程；GPU 推理 → 批处理 + 异步调度。

# 四、Embedding、向量库、检索与评估

> 这章是 RAG 的"命中率"。回答套路：**先讲原理一句话，再讲工程取舍，最后给项目数字**。
> 面试官最想听的不是公式，而是"你怎么知道它有效"。

### Q1. 一段文本怎么变成 embedding？底层发生了什么？⭐〔原四·1〕

**答**：不是"查表"，是**模型前向编码**。

1. **分词**：文本切成 subword token（BPE/WordPiece），加特殊 token；
2. **编码**：过 Transformer（多层 self-attention + FFN），每个 token 得到一个上下文相关的向量；
3. **池化**：把所有 token 向量聚合成一个句向量。常见三种：取 `[CLS]`（BERT 系）、**均值池化**、**last-token**（LLM-based embedding，如 Qwen3-Embedding）。BGE 中文模型用的是 **CLS 池化**；
4. **归一化**：L2 归一化，让内积等价于余弦相似度；
5. **降维/量化**（可选）：Matryoshka 截断或 PQ 压缩。

**关键点**：embedding 模型的训练目标是**对比学习**——正样本对（query, 相关段落）拉近，负样本（in-batch negatives + 难负例）推远，损失用 InfoNCE。所以它学到的"相似"是**检索相关性**，不是"字面相似"。

**项目落点**：离线批量 encode 要关梯度、用 fp16、按长度排序分桶减少 padding；线上 query 编码要控制延迟，通常 <20ms。

### Q2. 词向量用的是什么模型？怎么选？〔原四·3、四·7〕

**答**：我们主用 **BGE 系列**：中文 `bge-large-zh-v1.5`（1024 维），多语言/长文用 `bge-m3`（支持 dense + sparse + 多向量，8192 上下文），英文场景用 `bge-base-en` 或 `jina-embeddings-v3`。

**选型看五个维度**：

1. **语言/领域**：中文优先 BGE、Qwen3-Embedding、Conan；医疗/法律选领域微调版；
2. **长度**：512 够用就用小模型，长文档才上 8k；
3. **维度与成本**：1024 维比 768 维存储和检索都贵，Matryoshka 可截断；
4. **MTEB/C-MTEB 分数**：只作参考，必须在自己评估集上验；
5. **部署**：能否私有化、GPU 显存、批量吞吐。

**注意 query 侧指令**：BGE v1.5 的 query 要加"为这个句子生成表示以用于检索相关文章："前缀，passage 不加；用错会掉几个点。bge-m3 则用 `retrieval.query` / `retrieval.passage` 区分。

**换模型必须重建全量索引**，不同模型的向量空间不兼容，不能混用。

### Q3. 用了医疗领域专用向量模型，为什么还要 RAG？〔原四·4、四·6〕

**答**：两者解决的不是同一个问题。

- **领域 embedding** 解决"**找得准**"：让"心梗"和"急性心肌梗死"在向量空间里靠近，提升召回质量。
- **RAG** 解决"**知道最新的、私有的知识**"：embedding 只改变表示方式，**不携带任何文档内容**；模型的参数里也没有你医院昨天的指南、今天的排班、患者的病历。

打个比方：领域 embedding 是"更好的图书馆索引卡"，RAG 是"真的去书架上把书取来给模型看"。索引再好，书不在馆里也没用。

**协作方式**：领域 embedding 负责检索 → 召回权威片段 → 通用/领域 LLM（Qwen2.5 医疗版）基于片段生成 → 引用溯源。如果领域模型本身经过继续预训练，术语理解更好，但**知识时效性仍然靠 RAG 保证**。

### Q4. Qwen2.5 和医疗领域模型怎么协作？〔原四·5〕

**答**：按"能力分工"，不要让两个模型都做同一件事。

- **Embedding 侧**：用医疗领域 embedding（或 BGE-M3 医疗微调版）做召回，保证术语匹配；
- **生成侧**：Qwen2.5-7B/14B-Instruct 作为主生成器，负责理解问题、组织答案、遵循引用格式；如果医疗领域模型在术语和指南表述上更强，就把它作为**领域专家**，用路由或投票融合；
- **校验侧**：再用一个模型（或同一模型换 prompt）做忠实度检查，判断答案是否都能在召回片段中找到依据；
- **兜底**：涉及剂量、诊断、禁忌的，强制引用 + 免责声明 + 转人工，不追求"全自动"。

**关键**：多模型协作要有**路由规则**和**降级策略**，不能串行堆叠导致延迟爆炸。我们的做法是"小模型路由 + 大模型兜底"，P95 控制在 3s 内。

### Q5. 幻觉是什么？多少？RAG 前后降了多少？怎么算的？⭐〔原四·5〕

**答**：**幻觉**指答案里出现了无法被给定上下文或权威知识支持的内容——包括编造事实、张冠李戴、过度推断。

**量化口径**（必须说清楚，否则数字没意义）：

1. 把答案拆成**原子事实陈述**（claim）；
2. 逐条判断能否在召回上下文中找到支持（entailed / contradicted / neutral）；
3. `幻觉率 = 不被支持的 claim 数 / 总 claim 数`。

用 LLM-as-judge 打标 + 人工抽 100 条校准一致性（kappa > 0.7 才采信）。

**项目数字**（示例，按实际改）：纯基座模型直接答，幻觉率约 45%；加 RAG（混合召回 + rerank + 引用约束）后降到 12%；再加校验 Agent 和拒答策略，降到 7%。**注意区分"幻觉率"和"错误率"**，后者还包括检索没召回到导致的"漏答"。

**追问"怎么保证 judge 不瞎判"**：固定 judge 模型和 prompt 版本、双人标注校准集、对边界样本人工复核；judge 只看"是否有依据"，不让它评价"答案好不好"。

### Q6. 召回率怎么算？为什么这样算？⭐〔原四·9〕

**答**：

`Recall@k = 前 k 个结果中命中的相关文档数 / 全部相关文档数`

- **分母**是标注的全部相关 chunk（gold set），衡量"该找的有没有漏"；
- **分子**是 top-k 里命中的数量；
- 有时用**命中率 HitRate@k**：top-k 里只要有一个相关就算 1，更宽松，适合只有唯一答案的场景。

**为什么 RAG 更看重召回**：召回漏了，后面的 rerank 和 LLM 再强也变不出来（garbage in, garbage out）；精确率不够可以靠 rerank 过滤，召回不够无法补救。所以粗召回阶段宁可多召回（top50），精排阶段再收紧（top5）。

**注意**：chunk 级召回和文档级召回要分开算；一个 query 有多个相关 chunk 时，分母是 chunk 数，不同标注粒度会导致数字不可比。评估集必须固定切分版本。

### Q7. 召回率为什么会变高？〔原四·10〕

**答**：按贡献排序，给项目里的实际动作：

1. **切分优化**（贡献最大）：结构感知 + 父子块，块内语义完整，跨块断裂减少 → +8 个点；
2. **混合检索**：BM25 补上型号、编号、专有名词的精确匹配 → +6 个点；
3. **query 改写**：指代消解、同义词扩展、多路改写 → +4 个点；
4. **embedding 升级**：换更强的中文/领域模型 → +3~5 个点；
5. **元数据过滤**：按部门、文档类型、时效过滤，减少无关候选 → 提升精度，间接提升有效召回；
6. **rerank**：严格说它提升的是 precision@k，不是 recall，但 top5 的"有效召回"会上升。

**方法论**：每次只改一个变量，在固定评估集上跑，记录 recall@5/10 和延迟成本；避免"一起改，涨了也不知道为什么"。

### Q8. 评估的是 top 多少的召回率？〔原四·11〕

**答**：看**下游用多少**。我们 rerank 后只把 top5 送进 prompt，所以主指标是 **recall@5**；但粗召回阶段会看 **recall@50**，因为那是 rerank 的输入上限。

- `recall@50` 衡量"粗召回有没有把答案捞进来"，目标 > 95%；
- `recall@5` 衡量"最终上下文够不够"，目标 > 90%；
- 同时看 `MRR@10`（第一个相关结果排多前）和 `NDCG@10`（排序质量）。

只报一个 recall@10 没有意义，要说清楚"在哪个阶段、给谁用"。

### Q9. 召回率、上下文精度这些指标大概多少？〔原四·12〕

**答**（示例数字，按项目改，且要能解释）：

- recall@50：96%（粗召回，rerank 输入）
- recall@5：91%（最终上下文）
- context precision：84%（送进 prompt 的块里，真正相关的比例）
- context recall：89%（回答所需信息被上下文覆盖的比例）
- 答案忠实度：88%（人工抽检）
- 答案相关性：90%
- 拒答准确率：93%
- P95 延迟：2.8s

**关键**：这些数字要来自同一套评估集、同一版本切分、同一 judge 口径；面试官追问"怎么算的"时，能说出样本量（如 300 条 query、1200 个相关 chunk）和标注方式。

### Q10. Rerank 模块怎么实现？⭐〔原四·13、二·30、二·31、二·38〕

**答**：rerank 是**精排**，用 cross-encoder 对 (query, passage) 逐对打分。

**流程**：

1. 粗召回 100 条（BM25 50 + 向量 50），去重；
2. 取 top50 送 rerank（太多会慢）；
3. 模型输入 `[query, passage]` 拼在一起，cross-attention 让 query 和文档每个 token 互相看，输出一个相关性 logit；
4. 按分数降序，卡阈值（如 0.3），取 top5；
5. 分数做 min-max 或 sigmoid 归一，便于和业务权重融合。

**模型**：`bge-reranker-v2-m3`（中英多语，效果好）、`bce-reranker-base`（轻量）、Cohere Rerank（API）。

**性能**：50 对 × 512 token，单卡 T4 约 100~200ms；优化手段是**截断 passage 到 256 token**、动态 batch、fp16、只对 top30 精排。**延迟敏感场景**可以两级：小模型粗排 top20，大模型精排 top5。

**追问"rerank 和向量检索的本质区别"**：向量是双塔，query 和 doc 分别编码，速度快但交互少；cross-encoder 是单塔，两者拼一起编码，精度高但不能预计算，只能对小候选集用。

### Q11. "交叉编码器精排 + LLM 辅助重排 + 递归检索"这段怎么写、怎么讲？〔原四·14〕

**答**：这是一段典型的"技术堆叠描述"，讲的时候要拆成三层，并说明**触发条件**，否则听起来像堆名词。

1. **第一层：cross-encoder 精排**——粗召回 top50，用 bge-reranker 逐对打分，过滤低相关，取 top5。解决"相似但不相关"。
2. **第二层：LLM 辅助重排**——当候选分数接近（如 top5 分差 < 0.05）或问题需要多条件匹配时，把 top10 的标题+摘要给 LLM，让它按"能否回答该问题"重新排序（listwise）。**不是每次都调**，只在高不确定场景触发，控制成本。
3. **第三层：递归检索（Recursive Retrieval）**——LLM 判断当前上下文是否足够：不够就拆子问题、生成新 query、再检索，最多 2~3 轮；每轮把新片段合并去重，直到信息足够或达到轮数上限。解决多跳问题（"A 的上级单位去年发的制度里关于 B 的规定"）。

**效果**：上下文相关性 +6 个点，多跳问题准确率 +15 个点，代价是 P95 延迟 +0.8s。所以要设**开关和预算**，简单问题走单轮。

**风险**：递归容易死循环和 query 漂移，必须设最大轮数、分数阈值和"无新增信息就停"的判据。

### Q12. 向量量化是什么？〔原二·29〕

**答**：量化是把高精度向量/权重压成低精度，**用少量精度换存储和速度**。

常见方式：

1. **标量量化 SQ**：FP32 → INT8，每维 1 字节，体积降 4 倍，召回损失通常 <1%；
2. **乘积量化 PQ**：把 D 维切成 M 段，每段用 256 个聚类中心编码（1 字节），体积降为 M 字节；用**非对称距离**（ADC）查表算距离。适合亿级向量；
3. **IVF-PQ**：先倒排聚类分桶（nlist），查询只扫 nprobe 个桶，再 PQ 算距离，是 FAISS 的经典组合；
4. **二值量化**：1 bit/维，用汉明距离，极致压缩，适合粗筛。

**取舍**：PQ 会损失精度，通常做法是"PQ 粗筛 top100 → 原始向量精算重排 top10"。Milvus/FAISS 都支持。

**项目**：百万级以内用 HNSW + FP16 就够，没必要上 PQ；上亿才考虑 IVF-PQ + 磁盘索引。**别为了炫技上量化，先看数据规模**。

### Q13. 怎么用知识图谱提升检索？〔原二·32、二·33、二·34〕

**答**：图谱补的是**实体关系和多跳推理**，不是替代向量检索。

**做法**：

1. **建图**：从文档抽实体和关系（LLM + 规则），存 `(头实体, 关系, 尾实体)`，节点挂 chunk_id 溯源；
2. **实体链接**：query 里识别实体（"Qwen2.5"、"华东区"），消歧后定位到图节点；
3. **子图召回**：取该实体 1~2 跳邻居，转成自然语言三元组（"Qwen2.5 — 发布于 — 2024 年 9 月"），作为额外上下文；
4. **融合**：图谱片段和向量片段一起送 rerank，或作为独立通道做 RRF；
5. **多跳**：沿关系路径扩展，解决"张三是李四的上级，李四的部门归谁管"这类链式问题。

**影响**：抽得准 → 补全关联信息，多跳准确率明显提升；抽错 → 引入噪声，反而降低忠实度。所以要**限制图谱只在高置信实体上生效**，并保留原文片段做交叉验证。

**边界**：开放域闲聊、纯语义相似问题，图谱没用；强结构化、实体关系密集的领域（医疗、金融、法务、组织架构）收益最大。

### Q14. 向量库为什么用 FAISS？怎么部署？怎么选型？〔原二·45、二·47〕

**答**：FAISS 是**向量检索库**，不是数据库：单机、极快、索引类型全（Flat/IVF/HNSW/PQ），适合百万级、离线或单机服务。缺点是**没有服务化、没有分布式、没有标量过滤和权限、持久化要自己做**。

**选型**：

- **FAISS**：原型、单机、数据量 <1000 万、追求极致性能；
- **Milvus**：生产级分布式，支持 HNSW/IVF/PQ、标量过滤、多副本、权限，适合亿级和多租户；
- **Chroma**：轻量，Python 友好，适合 demo 和小知识库；
- **pgvector**：已有 PostgreSQL、要事务和 SQL 联合过滤，中小规模；
- **Elasticsearch/OpenSearch**：已有全文检索体系，要 BM25 + 向量混合；
- **Qdrant/Weaviate**：过滤和混合检索体验好，中小团队友好。

**部署**：Milvus 用 Docker Compose（etcd + MinIO + Milvus）或 K8s Operator；FAISS 就是进程内索引 + 定时落盘/对象存储快照。生产必须考虑：副本、快照备份、索引重建时的双写切换、按租户隔离 collection/partition。

**项目**：开发期 FAISS，上线换 Milvus，原因是需要按部门做标量过滤和水平扩容。

### Q15. 关键词检索的重排序怎么做？两路怎么融合？〔原二·36、二·37〕

**答**：分两层。

**层一：BM25 自身排序**。BM25 分数 = IDF × TF 饱和项 × 长度归一，参数 k1=1.2、b=0.75。它自带排序，但分数和向量分数**量纲不同**，不能直接相加。

**层二：融合后统一精排**：

1. **分数归一化**：各自 min-max 或 z-score 到 [0,1]，再加权求和；
2. **RRF**：只用排名，`score = Σ 1/(60 + rank)`，无需归一化，最稳；
3. **统一送 rerank**：把两路候选合并去重，用 cross-encoder 对 (query, passage) 重新打分，**BM25 的原始分数只作为特征之一**，不单独决定顺序。

**项目做法**：RRF 融合 top100 → rerank top20 → 取 top5。关键词通道负责"不漏精确匹配"，向量通道负责"不漏语义改写"，rerank 负责"最终谁排前面"。

**追问"BM25 权重 0.3 怎么来的"**：评估集网格搜索 + 业务观察（型号类 query 多）；不要声称有理论最优。

### Q16. 除了召回率，检索评估还看什么？〔补充〕

**答**：四个层次，避免只用单一指标自欺。

1. **命中类**：Recall@k、HitRate@k、MRR（第一个相关的倒数排名）、NDCG@k（考虑相关度分级和位置折扣）；
2. **上下文质量**：context precision（上下文里相关块占比）、context recall（回答所需信息被覆盖的比例）、冗余度（同一文档重复块比例）；
3. **端到端**：答案忠实度、答案相关性、答案正确率、拒答准确率；
4. **工程**：检索延迟、索引大小、QPS、单次查询成本。

**方法**：固定评估集 + 分层分析（按 query 类型：单跳/多跳/精确匹配/口语化），看哪一类拖后腿；只看总体均值会掩盖短板。

# 五、LLM 基础、注意力、采样与上下文

> 这章的问题是"广度题"，不要求推导公式，但要求**说人话 + 知道边界**。
> 遇到原文里明显听误的题（`pseudo`、`conformer 多头 batch`、`Grop`），先确认题意再答，比硬编造更加分。

### Q1. 大模型不稳定，prompt 设计有哪些方法？⭐〔原五·1〕

**答**：prompt 的目标是**降低输出方差**，手段分五类：

1. **角色与任务**：明确"你是内部制度问答助手，只依据给定资料回答"，界定边界；
2. **结构化**：用固定段落（背景 / 资料 / 问题 / 输出格式），XML 或 Markdown 标签分隔，避免指令和资料混淆；
3. **示例（Few-shot）**：给 2~3 个"输入→输出"样例，尤其是拒答、引用格式的样例；
4. **推理引导**：复杂问题用 CoT（"先列要点再结论"），但**不要把思维链暴露给用户**；
5. **约束与校验**：要求"每个结论后标注 [1][2]""资料中没有就说不知道""输出 JSON，不要多余文字"；配合程序侧 JSON Schema 校验和重试。

**工程化**：prompt 版本化管理（git + 版本号），用评估集回归，改动必须跑 diff；线上记录 prompt 版本，badcase 才能归因。**temperature 调低**（0~0.3）比堆 prompt 更直接。

### Q2. Zero-shot、One-shot、Few-shot 的区别？〔原五·2〕

**答**：按给模型示例的数量分。

- **Zero-shot**：只给指令，不给例子。依赖模型的指令遵循能力，适合通用任务，成本最低，但格式和边界容易飘。
- **One-shot**：给 1 个完整示例。能锚定输出格式和粒度，适合"格式明确但任务简单"的场景。
- **Few-shot**：给多个示例（通常 3~5 个）。能教会模型分类边界、话术风格、复杂输出结构；示例要**覆盖易错类别**，不是随便凑数。

**取舍**：示例不是越多越好——占 token、可能引入偏差（模型照抄示例里的实体）、示例顺序也有影响。做法是先用 zero-shot 打底，badcase 聚类后针对性补示例，再看评估集是否真的涨。

**项目**：工具调用的 prompt 用 3 个 few-shot（正常调用、缺参数、该拒答），JSON 合法率从 82% 提到 97%。

### Q3. Prompt 设计和 few-shot 设计有什么区别？〔原五·3〕

**答**：两者是"规则"和"样例"的关系，互补而非替代。

- **Prompt 设计**：写清楚**任务、角色、约束、输出格式、边界**，是"告诉模型怎么做"；考的是表达清晰度和指令优先级。
- **Few-shot 设计**：给**输入输出的具体示范**，是"做给模型看"；考的是样例的代表性、多样性和正确性。

**什么时候用哪个**：任务规则简单但格式严格 → prompt + 1 个样例足够；分类边界模糊、风格难描述 → 多给 few-shot；两者都做，通常是"系统 prompt 定规则 + few-shot 定格式 + 输出校验兜底"。

**坑**：few-shot 示例和系统指令冲突时，模型往往跟示例走；示例里有错误，模型会学错。所以示例必须进版本管理，和评估集一起回归。

### Q4. 普通 prompt 和 CoT prompt 的主要区别？〔原五·5〕

**答**：

- **普通 prompt**：直接给指令，模型一步给答案。快、省 token，适合事实查询、格式转换、简单分类。
- **CoT（思维链）**：要求模型**先输出推理步骤，再给结论**（"让我们一步步思考"或给推理示例）。适合数学、多跳推理、复杂决策，能显著降低错误率。

**原理**：把一次"隐式映射"拆成多步"显式计算"，给模型更多中间 token 做"草稿纸"，相当于增加了计算深度。

**代价**：输出变长、延迟和成本上升；推理过程可能"编得通但结论错"（unfaithful CoT），不能盲目信任。

**工程做法**：内部用 CoT 提升准确率，对外只返回结论；或者用"先列要点，再给答案"的轻量版。RAG 里更常用的是**结构化推理**（先判断问题类型 → 再列需要的资料 → 再回答），比自由发挥的 CoT 更可控。

### Q5. Top-k、Top-p、temperature 分别是什么？〔原五·7〕

**答**：三者都作用在**采样**阶段，控制生成的随机性。

- **Temperature**：对 logits 除以 T 再 softmax。T→0 趋近贪心（最确定），T=1 保持原分布，T>1 更随机。事实问答用 0~0.3，创意写作用 0.7~1.0。
- **Top-k**：只保留概率最高的 k 个 token，其余置零。k 小更保守，k 大更多样；缺点是固定 k 不适应分布形状（有时前 3 个就占 95%，有时前 50 个才够）。
- **Top-p（nucleus）**：按概率降序累加，保留累计概率达到 p 的最小集合。分布尖锐时集合小，平坦时集合大，**自适应**，通常比 top-k 更好用。常用 p=0.9~0.95。

**组合**：一般 temperature + top-p，top-k 作辅助；再配 repetition penalty 防复读。**注意**：top-p 和 top-k 同时开时取交集，可能过度限制。

**追问"为什么 temperature=0 还不完全确定"**：GPU 浮点非确定性、batch 内其他请求影响、MoE 路由、并行归约顺序，都会带来微小差异。

### Q6. 大模型训练的三个阶段？〔原五·8〕

**答**：

1. **预训练（Pre-training）**：海量无标注语料，做 next-token prediction，学语言和世界知识。成本最高（千卡月级），产出 Base 模型。
2. **监督微调（SFT）**：用"指令-回答"数据训练，教会模型遵循指令、对话、格式化输出。几万到几十万条，成本低几个数量级。
3. **偏好对齐（RLHF / DPO）**：用人类偏好数据让回答更有用、更安全、更符合风格。RLHF = 奖励模型 + PPO；DPO 直接用偏好对优化，省掉奖励模型。

**领域迁移**的常见路径：领域继续预训练（注入术语和语料）→ SFT（教任务格式）→ DPO（调风格和拒答）。资源有限就只做 LoRA SFT，效果通常已经够用。

**追问"RAG 和这三个阶段什么关系"**：RAG 不改参数，属于推理期的知识注入，和训练阶段正交，可以叠加。

### Q7. 为什么执着于 int4？精度损失不大吗？〔原五·9〕

**答**：因为**显存是硬约束**，int4 能把权重体积压到 FP16 的 1/4：7B 模型从 14GB 降到约 4GB，单张 24G 卡就能跑，成本直接降一个档。

**精度**：不能一概而论。

- 用 **GPTQ / AWQ** 这类训练后量化，配合 group-wise（128 一组）和激活感知，7B 以上模型在通用任务上通常只掉 1~2 个点，困惑度上升但下游感知不明显；
- **QLoRA 的 NF4** 是"量化基座 + LoRA"，训练时反量化计算，效果接近 16bit LoRA；
- **极端推理、数学、长链任务**对量化更敏感，可能掉 5 个点以上；
- 2bit 以下损失明显，一般不用于生产。

**判断标准**：不要看困惑度，要**在自己的评估集上跑**；同时看长输出是否复读、JSON 是否更容易坏、多语言是否退化。

**结论**：int4 是"用可接受的精度换 4 倍显存"，要先评测再上线，并保留 FP16 兜底。

### Q8. 什么是 CoT？为什么有效？〔原五·11〕

**答**：CoT（Chain-of-Thought）是让模型**显式输出中间推理步骤**再给答案的提示技术。代表作是 "Let's think step by step" 和 few-shot CoT。

**为什么有效**：Transformer 的每层计算量固定，直接出答案相当于"一步算完"；CoT 把问题拆成多步，每步都有 token 作为中间状态，相当于**增加了串行计算深度**，把难题分解成简单子问题。

**变体**：

- Zero-shot CoT：加一句"一步步思考"；
- Self-Consistency：采样多条推理路径，对答案投票；
- Tree-of-Thought：搜索多条推理分支；
- ReAct：推理与工具调用交替（Agent 常用）。

**局限**：小模型（<10B）CoT 收益不稳定；推理链可能不忠实（结论对但过程编的）；成本和延迟上升。

**项目**：Agent 里用 ReAct 式的"思考→行动→观察"，但对外隐藏思考过程，只输出结论和引用。

### Q9. 多头注意力和"多轮"是一回事吗？〔原五·12〕

**答**：不是，这是两个层面的概念，原文这题大概率是口误或混淆。

- **多头注意力（Multi-Head Attention）**：Transformer **层内**的机制。把 Q/K/V 投影到 h 个子空间，各自算 scaled dot-product attention，再拼接、线性变换。不同头关注不同模式（语法、指代、位置），总计算量与单头大维度相当。变体有 MQA（多查询）、GQA（分组查询），用于**减少 KV cache**，Llama 2/3 都用 GQA。
- **多轮对话**：**应用层**的交互，用户和模型来回多次，需要把历史拼进上下文或做记忆管理。

如果面试官问的是"多头注意力和多轮注意力"，可能是想问 **multi-head vs multi-query**：MHA 每个头独立 K/V，KV cache 大；MQA 所有头共享一组 K/V，cache 小但效果略降；GQA 折中，每组的头共享 K/V。

**回答策略**：先澄清"您问的是层内多头，还是推理时的 KV cache 优化"，再分别答，别顺着错误前提硬讲。

### Q10. pseudo 和 MoE 的区别？各自适合什么训练任务？〔原五·13、五·14〕

**答**（先澄清术语）：**MoE 是模型结构，pseudo 不是与之对等的结构**，这题大概率是听误或多题混在一起。按最可能的三种理解答：

1. **pseudo-labeling（伪标签）**：用模型给无标注数据打标，再当训练数据，属于**半监督/数据增强**。适合标注贵、无标注数据多的场景（分类、检索、蒸馏）。风险是确认偏差，要置信度过滤 + 人工抽检。
2. **pseudo-relevance feedback（伪相关反馈）**：检索里把首轮 top 结果当"伪相关"做 query 扩展，提升召回。适合短 query、召回不足的场景。
3. 如果问的是 **PEFT vs MoE**：PEFT 是"冻结主干、只训少量参数"的微调方法（LoRA/Adapter）；MoE 是"多个专家 + 门控路由，每次只激活部分参数"的模型结构，用来在**不显著增加推理算力**的前提下扩大参数量。

**MoE 的优劣**：优势是容量大、训练/推理只激活 Top-k 专家（如 2/8），适合超大模型；劣势是显存占用高（所有专家都要加载）、负载不均衡、路由不稳定、微调容易过拟合少数专家。

**一句话**：pseudo 是"造数据/扩查询"的手段，MoE 是"扩容量省算力"的架构，不在一个维度。

### Q11. Transformer 的底层原理？⭐〔原五·15〕

**答**：一句话：**用自注意力建模序列内任意两个位置的依赖，堆叠多层做表示学习**。

一个 Decoder Block：

1. **输入嵌入 + 位置编码**：LLM 多用 RoPE（旋转位置编码），通过旋转 Q/K 注入相对位置；
2. **Masked Self-Attention**：`Attention(Q,K,V) = softmax(QKᵀ/√d_k + mask)·V`，因果 mask 保证只能看左边；多头并行；
3. **残差 + LayerNorm**：LLM 普遍用 **Pre-Norm + RMSNorm**，训练更稳；
4. **FFN**：两层线性 + 激活（SwiGLU），中间维度通常是 hidden 的 2.7~4 倍，承担大部分参数；
5. **堆叠 N 层**，最后接 LM Head 输出词表 logits。

**复杂度**：注意力 O(n²d)，长上下文时是瓶颈，所以有 FlashAttention、稀疏注意力、线性注意力、GQA 等优化。

**为什么强**：并行（不像 RNN 必须串行）、长依赖、可扩展（scaling law：参数/数据/算力同时放大，loss 平滑下降）。

### Q12. FlashAttention 了解吗？⭐〔原五·16〕

**答**：FlashAttention 是**IO 感知的精确注意力算法**，核心不是减少计算量，而是减少 GPU 显存读写。

**问题**：标准注意力要把 n×n 的注意力矩阵写回 HBM 再读出来，显存占用 O(n²)，带宽成为瓶颈。

**做法**：

1. **分块（tiling）**：把 Q/K/V 切成小块，放进 SRAM（片上高速缓存）里算；
2. **在线 softmax**：分块累加时动态维护最大值和归一化因子，不需要先看完整行；
3. **重计算（recomputation）**：反向传播时不存注意力矩阵，用前向的统计量重算，省显存。

**效果**：显存从 O(n²) 降到 O(n)，速度 2~4 倍，且**结果与标准注意力完全一致**（不是近似）。FlashAttention-2/3 进一步优化并行度和 FP8。

**工程**：transformers、vLLM、SGLang 默认开启；长上下文训练/推理基本必配。

### Q13. Conformer 是什么？"多头 batch"指什么？〔原五·17〕

**答**：**Conformer = Convolution + Transformer**，是语音识别里的经典架构（Google, 2020）。它把 Transformer 的全局建模能力和 CNN 的局部建模能力结合：每个 block 里有多头自注意力 + 深度可分离卷积 + 前馈层，用残差连接。

**为什么语音需要它**：语音的局部纹理（音素、共振峰）用卷积抓更高效，长程依赖用注意力抓，两者互补。NLP 里很少用，因为文本的局部性没语音那么强。

**"多头 batch"**：不是标准术语，可能是问 "multi-head + batch" 的实现细节（多头计算如何 batch 成矩阵乘），或者 "multi-head attention 的 batch 维度怎么组织"。答法：把 `[B, H, L, d]` 四个维度一次 matmul，H 和 B 都并到 batch 维，GPU 利用率最高；mask 要广播到 `[B, 1, L, L]`。

**回答策略**：先确认术语，再答；不确定就诚实说"这个词我不确定指什么，您是指 X 吗"。

### Q14. 一个 batch 里序列长度递减，怎么处理？〔原五·18〕

**答**：这题问的是**变长序列的批处理效率**。长度差异大时，短序列会被 padding 到最长，浪费算力。

常见做法：

1. **长度分桶（bucketing）**：按长度排序后分桶，同桶内 padding 少；
2. **动态 batch**：按 token 总数而非样本数组 batch（如每批 4096 token），长短混排；
3. ** packing**：把多条短序列拼成一条长序列，用 attention mask 或 varlen 机制隔离，训练时几乎无浪费（FlashAttention 的 varlen 接口）；
4. **推理侧连续批处理（continuous batching）**：vLLM 的核心，不等整批结束，谁生成完谁退出，新请求立刻补位，序列长度自然参差也没关系。

**项目**：离线 embedding 用长度分桶 + 动态 batch，吞吐提升约 40%；在线 LLM 用 vLLM 连续批处理，不用自己管。

### Q15. 介绍一下 LLaMA 和训练框架〔原五·19〕

**答**：LLaMA 是 Meta 的开源 decoder-only 模型系列，特点：

- **架构**：Pre-Norm + RMSNorm、SwiGLU、RoPE、因果注意力；Llama 2/3 用 **GQA** 降低 KV cache；
- **分词**：Llama 3 换 128k BPE 词表，多语言和压缩率更好；
- **规模**：7B/13B/70B（Llama 2），8B/70B/405B（Llama 3）；
- **生态**：HF transformers 原生支持，社区微调/量化版本最全。

**训练/微调框架**：

- **transformers + accelerate**：最基础，单机多卡够用；
- **DeepSpeed / FSDP**：ZeRO 分片，70B 以上必需；
- **TRL**：SFT/DPO/PPO 的高层封装；
- **PEFT**：LoRA/QLoRA；
- **LLaMA-Factory / Unsloth**：低代码微调，适合快速验证；
- **Megatron-LM**：大规模预训练，张量/流水并行。

**推理**：vLLM、SGLang、TensorRT-LLM、llama.cpp（端侧）。

### Q16. 项目的输入是什么？〔原五·20〕

**答**：不是单一 query，而是一个结构化输入包：

1. **用户 query**：原始问题；
2. **会话历史**：最近 N 轮 + 历史摘要，用于指代消解；
3. **用户画像/权限**：部门、角色、可访问的知识库范围（用于过滤）；
4. **检索上下文**：top-k chunk + 来源 + 页码 + 分数；
5. **工具结果**：如果走了 function call，带上返回值；
6. **系统配置**：当前时间、语言、输出格式、prompt 版本。

**关键**：这些字段在日志里要全量落盘，否则出了问题无法复现。输入侧还要做长度预算和敏感信息脱敏。

### Q17. "多 gen" 是什么？怎么用？〔原五·27〕

**答**：指**多次生成（multiple generations）**：同一个 prompt 采样多条候选，再选最优或投票。常见三种用法：

1. **Self-Consistency**：多条 CoT 推理路径，对最终答案多数投票，提升数学/推理准确率；
2. **Best-of-N**：生成 N 条，用奖励模型/打分器/LLM judge 选最高分，用于对齐和高质量数据合成；
3. **候选重排**：生成多个答案，用 rerank 或规则选最符合格式的。

**代价**：成本 ×N，延迟 ×N（可并行）。所以只在高价值、低容错场景用（医疗、法律、代码生成），普通问答不划算。

**项目**：离线构造 DPO 数据时，对同一 prompt 生成 4 条，用规则 + judge 选出 chosen/rejected 对。

### Q18. "Grop 是怎么生成的？"——应该是 GRPO ⭐〔原五·28〕

**答**（原文猜"Group 分组采样"，更准确是 **GRPO, Group Relative Policy Optimization**，DeepSeek-R1 带火的强化学习算法）：

**GRPO 的做法**：

1. 对同一个问题，用当前策略采样 **G 条**输出（一个 group）；
2. 每条用奖励模型/规则打分，得到 `r_1...r_G`；
3. **组内归一化**算优势：`A_i = (r_i - mean(r)) / std(r)`，即"比同组平均好多少"；
4. 用 PPO 的 clipped 目标优化，加 KL 约束防止偏离参考模型。

**和 PPO 的区别**：PPO 需要一个和策略同规模的 **Critic（价值网络）** 估计 baseline，显存和训练成本高；GRPO **用组内均值代替 Critic**，省掉一个模型，训练更省、更稳。

**适合什么**：有可验证奖励的任务（数学、代码，答案对错可判）、推理能力提升。**不适合**：奖励难以自动判定、需要细粒度打分的开放任务。

**"分组"怎么生成**：同一 prompt 复制 G 份，调高 temperature 采样，保证多样性；组内要有对有错，否则优势全为 0，没有梯度。

# 六、微调：SFT / DPO / LoRA / 分布式

> 微调题的核心不是背公式，而是回答三个问题：**为什么调、拿什么调、怎么证明调有效**。
> 所有参数量、显存、时长都要能自己推一遍，面试官最喜欢在这抓细节。

### Q1. RAG 项目怎么优化？（按收益排序）〔原六·1〕

**答**：先定位瓶颈，再动手，顺序很重要。

1. **评估先行**：建 200~500 条带标注的评估集，把链路拆成"召回 / 排序 / 生成 / 拒答"四段，分别算指标，找到最短的那块板。
2. **解析与切分**（通常收益最大）：修 PDF 表格、保留标题层级、父子块、按类型路由 splitter。
3. **召回**：混合检索（BM25 + 向量）、query 改写、同义词词典、多路召回。
4. **排序**：cross-encoder rerank、RRF 融合、业务权重（时效/权威度）、MMR 去冗余。
5. **上下文**：预算裁剪、最相关放首尾、相邻块扩展、去重。
6. **生成**：强约束 prompt、引用编号、few-shot、temperature 调低、换更强的底座。
7. **后处理**：忠实度校验、引用存在性检查、敏感词、拒答兜底。
8. **微调**：只在前面的都到位、且瓶颈确实是"模型不会用/格式不稳"时才做。
9. **工程**：缓存（query→答案、embedding 缓存）、并发、流式、降级。

**一句话**：RAG 的效果 = 检索质量 × 上下文组织 × 模型遵循能力，先用评估定位乘数最小的那一项。

### Q2. 微调的目的是什么？〔原六·2〕

**答**：四类目的，按常见程度排：

1. **格式与行为对齐**：稳定输出 JSON、固定话术、稳定 function call 参数——这是 Agent 场景最实际的收益；
2. **领域语言适配**：术语、缩写、行业表达，让模型"听得懂、说得出"；
3. **任务特化**：分类、抽取、改写、审核等固定任务，小模型微调后可以替代大模型，降本；
4. **风格与偏好**：语气、详略、拒答策略，用 DPO 调。

**微调不解决**：知识更新（会过期）、长尾事实（记不住）、检索问题（该给资料还是得给）。**"知识"归 RAG，"行为和格式"归微调**，这是最清晰的分工。

### Q3. 微调后模型表现怎么样？怎么证明？〔原六·3〕

**答**：要给"前后对比 + 分项指标 + 副作用"。

**示例**：

- 工具调用 JSON 合法率：82% → 99.2%；
- 参数抽取字段准确率：76% → 91%；
- 领域术语问答准确率：+6 个点；
- 拒答准确率：85% → 93%（该拒的拒，不该拒的不拒）；
- 通用能力：MMLU 子集 -0.8 个点（可接受），长文本总结能力基本不变；
- 延迟：合并 LoRA 后无变化。

**怎么证明**：

1. 固定评估集（同分布、不泄漏），微调前后各跑一次；
2. 分类型看（单跳/多跳/格式/拒答），别只看总分；
3. 人工盲评 100 条（不知道哪个是微调版），看偏好率；
4. 回归通用能力，防止灾难性遗忘；
5. 线上灰度 A/B，看真实点击、点踩、转人工率。

**注意**：如果评估集是用同一个大模型生成的，指标会虚高，要有真人标注的子集。

### Q4. 什么场景需要微调？什么场景不需要？⭐〔原六·4〕

**答**：

**需要**：

- 输出格式极严格（JSON Schema、固定模板），prompt 怎么调都偶尔坏；
- Agent 工具多、参数复杂，function call 稳定性是瓶颈；
- 强领域术语，通用模型理解成本高；
- 有大量高质量标注数据，且任务边界稳定；
- 想用小模型替代大模型降本（蒸馏 + 微调）。

**不需要**：

- 知识频繁更新（微调记不住，还会过期）；
- 只是"查文档回答问题"，RAG 就够；
- 数据量少（<500 条高质量），先做 prompt / few-shot；
- 问题主要是检索不准，微调生成模型没用；
- 需要严格溯源，微调后的模型更"自信"，反而更难审计。

**判断方法**：做一次" oracle 实验"——把正确答案直接放进 prompt，如果模型还是答错/格式错，说明是模型能力问题，可以考虑微调；如果放进去就对了，说明是检索问题。

### Q5. 你怎么管理模型、数据和实验？〔原六·5〕

**答**：三件套 + 一条铁律。

1. **代码**：git 管理训练脚本、配置（YAML）、prompt；每次实验一个 commit。
2. **数据**：数据集版本化（DVC / 对象存储 + manifest），记录来源、清洗规则、去重哈希、标注人；训练集/验证集/测试集按 doc_id 切分，防止同文档泄漏。
3. **模型**：LoRA 权重按 `base_model + dataset_version + config_hash` 命名，存模型仓库（MLflow / ModelScope / OSS）；每次产出附评估报告。
4. **铁律**：**任何上线模型都能追溯到"哪份数据 + 哪个配置 + 哪次评估"**，否则回滚就是灾难。

**发布流程**：离线评估 → 影子流量（不返回给用户，只记录）→ 灰度 5% → 全量；出问题一键切回上一个版本。推理服务支持多 LoRA 热插拔（vLLM 的 multi-LoRA），不用重启。

### Q6. 挑一个传统项目说一下〔原六·6〕

**答**（这题考"你不是只会调包"，必须准备一个非 AI 项目，下面给模板，替换成你的）：

> 我之前做过一个**订单对账服务**：每天把三方支付流水和内部订单表做核对，找出金额不一致、状态滞留的单子。
>
> 我的工作：设计对账任务调度（Celery + Redis），把 T+1 全量改成增量 + 定时补偿；用分片把千万级流水拆成 64 片并行；对差异单做规则引擎分类（少付/多付/重复支付/状态不同步），自动生成工单。
>
> 难点是**幂等和一致性**：任务重试不能重复记账，我用唯一键 + 状态机 + 乐观锁解决；还有大表关联慢，加了复合索引和冷热分离。
>
> 结果：对账时长从 3 小时降到 20 分钟，差异单人工处理量下降 70%。

**讲法**：背景 → 你负责的模块 → 一个技术难点 → 量化结果。不要讲成产品介绍。

### Q7. 团队里文本/数据格式怎么定规范？〔原六·7〕

**答**：定 schema、定版本、定校验，三层。

1. **Schema 先行**：所有中间数据用 JSON/JSONL，字段名、类型、必填、枚举值写进 JSON Schema 或 Pydantic 模型；新增字段必须可选且有默认值，保证向后兼容。
2. **版本化**：数据文件带 `schema_version`，prompt 带 `prompt_version`，模型带 `model_version`；升级走迁移脚本，不原地改历史数据。
3. **校验入流水线**：写入前跑 schema 校验 + 业务校验（长度、编码、去重），失败进死信队列，不污染主表。
4. **文档与约定**：一份 README 写清楚字段含义、样例、常见错误；code review 检查格式。
5. **工具统一**：统一用 pandas/pydantic 读写，禁止手写字符串拼 JSON。

**好处**：下游不用猜字段；出问题能定位是数据还是代码；多人协作不会各写各的。

### Q8. 你会 Go 吗？〔原六·8〕

**答**（如实，不要硬吹）：`主要用 Python，Go 能写基础服务，读过一些开源项目。` 如果会一点，补一句具体的："用 Gin 写过内部 API 网关，做过 JWT 鉴权和限流；但高并发和 GC 调优还在学。"

### Q9. RAG 助手的准确率多少？〔原六·9〕

**答**：先定义"准确率"，再给数。

- **检索侧**：recall@5 = 91%，context precision = 84%；
- **生成侧**：答案正确率（人工判"能回答问题且无事实错误"）= 86%，忠实度 88%；
- **端到端**：用户不追问、不点踩、不转人工的比例 = 82%；
- **拒答**：该拒的拒掉 93%，误拒 4%。

**口径**：300 条评估集，双人标注，分歧由第三人裁决；"正确"要求同时满足"答对 + 有引用 + 无编造"。

**如果被追问"为什么不是 95%"**：剩下 14% 里，约一半是知识库本身没有（该补文档），三成是解析/切分问题，两成是复杂多跳。**把错误归因讲清楚，比数字漂亮更重要**。

### Q10. 用户问的和知识库无关怎么办？（微调视角）〔原六·10〕

**答**：流程同"边界设计"，这里补微调能做什么。

1. **入口分类**：意图识别判为"越界/闲聊/工具任务"，直接路由，不进检索；
2. **检索后判定**：top1 分数低、或 NLI 判"上下文不支持"，走拒答；
3. **拒答话术**：说明"资料里没有"，给替代路径（找谁/看哪份文档），不编造；
4. **微调的作用**：用"越界问题 → 拒答"的样本做 SFT/DPO，让模型学会**稳定拒答**，而不是被 prompt 偶尔带偏；同时用"边界内但表述不同"的样本防止过度拒答。
5. **兜底**：连续拒答或用户明确不满意 → 转人工/提工单；把拒答 query 回流，作为知识库建设清单。

**衡量**：拒答准确率 + 误拒率两个指标一起看，只追求"不乱答"会把可用性做没。

**答**：这题只考**诚实和一致性**，简历怎么写就怎么答，不要修饰。

可以补一句正向信息："是在职读的，所以项目是在真实业务里做的，不是实验室 demo；时间管理上确实是挑战，但这两年也逼着我把工程能力补起来了。"

如果是全日制就直说。**不要编**，背调一查就穿，而且这类问题回答时的犹豫比答案本身更减分。

### Q12. LoRA 适合什么样的训练任务？〔原六·12〕

**答**：LoRA 适合"**任务明确、数据量中等、算力有限、要多版本并存**"的微调。

具体：

- **SFT 指令微调**：最常用，几千到几万条，效果接近全参；
- **领域适配**：术语、话术、格式；
- **DPO/RLHF**：LoRA 也能挂在偏好优化上，省显存；
- **多任务/多租户**：一个基座 + 多个 LoRA，热插拔，按租户切换。

**不太适合**：

- **继续预训练**（注入大量新知识）：LoRA 容量不够，通常要全参或高秩；
- **分布差异极大的新语言/新模态**：低秩撑不住；
- **需要改变模型结构**的任务。

**秩怎么选**：简单格式对齐 r=8~16；领域适配 r=32~64；数据量大、任务难就往上加，同时调 alpha（常取 2r）。先小后大，用验证集定。

### Q13. Qwen 32B 这种架构，LoRA 参数个数怎么算？⭐〔原六·13〕

**答**：公式：**每个线性层 `r × (d_in + d_out)`**，总参数量 = 各层求和 × 层数（只算挂 LoRA 的层）。

以 **Qwen2.5-32B** 为例（hidden=5120，64 层，40 个 attention 头、8 个 KV 头，head_dim=128）：

- q_proj：`16 × (5120 + 5120) = 163,840`
- k_proj：`16 × (5120 + 1024) = 98,304`（KV 头只有 8 个，输出 1024 维）
- v_proj：同 k，`98,304`
- o_proj：`16 × (5120 + 5120) = 163,840`

单层合计 `524,288`，64 层约 **33.6M**，只占 32B 的 **0.1%** 左右（约 67MB fp16）。

如果只挂 q、v：`(163,840 + 98,304) × 64 ≈ 16.8M`。
如果加 MLP（gate/up/down，intermediate=27648）：每层再加约 `16×(5120+27648)×2 + 16×(27648+5120) ≈ 1.57M`，总量翻几倍。

**面试技巧**：先写公式，再代数字，最后说"具体以配置文件为准"；不要背一个孤立数字。

### Q14. 通义千问 3 是什么架构？〔原六·14〕

**答**：Qwen3 是阿里 2025 年发布的开源系列，**Decoder-only 自回归**，覆盖 dense 和 MoE 两条线（如 0.6B~32B dense，30B-A3B / 235B-A22B MoE）。

架构要点：

- **GQA + RoPE + SwiGLU + RMSNorm**，Pre-Norm，和主流 LLaMA 系一致；
- **MoE 版本**用细粒度专家 + 共享专家，激活参数远小于总参数（235B 总参、22B 激活），推理成本接近 22B；
- **思考模式 / 非思考模式**融合在一个模型里，可通过 prompt 或参数切换（`enable_thinking`）；
- **多语言**覆盖 100+ 语言，词表扩大；
- 训练上强调**推理数据合成 + 强到弱蒸馏 + 四阶段后训练**。

**回答边界**：如果记不清具体层数/头数，就说"具体超参以 config 为准"，别编。面试官更想听"MoE + 思考模式"这两个特征。

### Q15. 微调用什么框架？TRL 基于什么？〔原六·15、六·16〕

**答**：常用栈：

- **transformers**：模型加载、训练循环底座；
- **PEFT**：LoRA/QLoRA/Adapter 实现；
- **TRL**：SFTTrainer、DPOTrainer、PPOTrainer、GRPOTrainer 的高层封装；
- **accelerate / DeepSpeed / FSDP**：多卡与显存优化；
- **LLaMA-Factory / Unsloth**：低代码、快验；
- **vLLM**：推理和 rollout（GRPO/PPO 采样）。

**TRL 基于 HuggingFace transformers + accelerate + PEFT**，不是独立框架；它把"数据打包、loss mask、参考模型、KL 约束"这些容易写错的细节封装好，所以社区微调基本都用它。

**选型**：快速验证用 LLaMA-Factory；要改 loss/采样逻辑用 TRL；大规模预训练用 Megatron/DeepSpeed。

### Q16. PPO 和 DPO 的底层原理区别？⭐〔原六·17〕

**答**：

**PPO（RLHF 的经典做法）**：

1. 先用偏好数据训一个**奖励模型** `r(x,y)`；
2. 策略模型生成回答，奖励模型打分；
3. 用 PPO 最大化 `E[r] - β·KL(π || π_ref)`，同时用 **Critic** 估计基线降方差；
4. 需要同时加载策略、参考、奖励、Critic 四个模型，显存和调参成本高，容易不稳定。

**DPO（Direct Preference Optimization）**：

- 不训奖励模型，直接把"偏好"写成分类 loss：让 chosen 的**隐式奖励**高于 rejected，`L = -log σ(β·[(log π(y_w|x) - log π_ref(y_w|x)) - (log π(y_l|x) - log π_ref(y_l|x))])`；
- 数学上可证明 DPO 的最优解与 RLHF 同族，只是把奖励用策略的似然比表示，省掉显式奖励模型和在线采样；
- 只需要策略 + 参考两个模型，离线数据即可训练，稳定、便宜。

**取舍**：DPO 简单稳定，适合"有偏好对、想快速对齐"；PPO/GRPO 能利用在线探索和可验证奖励，上限更高，适合推理任务，但工程复杂。**工业界多数先 DPO，推理模型用 GRPO。**

### Q17. 分布式训练了解吗？〔原六·18〕

**答**：按"切什么"分四类：

1. **数据并行（DP/DDP）**：每卡一份完整模型，喂不同数据，梯度 all-reduce。简单，但显存不省。
2. **ZeRO / FSDP**：把优化器状态（ZeRO-1）、梯度（ZeRO-2）、参数（ZeRO-3）分片到各卡，用通信换显存；FSDP 是 PyTorch 原生版。70B 全参微调基本靠它。
3. **张量并行（TP）**：把单层矩阵切到多卡（Megatron），适合单机 NVLink 内高带宽互联。
4. **流水并行（PP）**：把不同层放不同卡，按 micro-batch 流水，减少空泡；常和 TP 组合成 3D 并行。
5. **专家并行（EP）**：MoE 专用，不同专家放不同卡，需要 all-to-all 通信。

**配套**：混合精度（bf16）、gradient checkpointing、梯度累积、sequence parallel、通信重叠。

**经验**：单机 8 卡优先 DDP/FSDP；跨机带宽差，尽量少 TP；先 profile 通信占比，再决定切法。

### Q18. 一张 H100 能跑什么？〔原六·19〕

**答**：H100 80G，按任务分：

- **推理**：7B FP16 轻松，32B FP16 勉强（权重 64G，余量小），70B 要 int4/AWQ 或 2 卡；MoE 大模型看激活参数和专家放置。
- **LoRA 微调**：7B~32B 单卡可跑（32B 需 gradient checkpointing + 小 batch）；70B 一般 2~4 卡或 QLoRA。
- **全参微调**：7B 约需 4~8 卡（ZeRO-3），32B 要 16 卡以上，70B 要数十卡。
- **预训练**：单卡只能做小模型实验，没有实际意义。

**注意**：显存估算 = 权重 + 梯度 + 优化器状态 + 激活。全参 Adam fp32 优化器状态约是权重的 4 倍，加梯度 2 倍，所以 7B 全参大约 80G+，必须分片。LoRA 只算 LoRA 参数的优化器状态，所以省。

### Q19. LoRA 的原理、优势、调哪些层、推理怎么用？⭐〔原五·21、五·23、五·24、五·26〕

**答**：

**原理**：冻结原权重 `W`，旁路加低秩分解 `ΔW = B·A`，`B∈R^{d×r}`、`A∈R^{r×k}`、`r≪min(d,k)`。前向 `h = Wx + (α/r)·B(Ax)`。A 随机初始化、B 零初始化，训练起点等价于原模型。梯度只更新 A/B，参数量降 2~3 个数量级。

**优势**：

- 显存小（不用存主干梯度和优化器状态），单卡可调 7B~32B；
- 权重文件小（几十 MB），多任务多版本易管理；
- 训练快，效果好，接近全参；
- **推理可合并**：`W' = W + (α/r)BA`，零额外延迟；也可不合并，动态切换。

**调哪些层**：注意力 `q/k/v/o` 是标配；追求效果加 MLP 的 `gate/up/down`。经验：**q/v 性价比最高**，全挂效果最好但参数翻几倍。Embedding/LM head 一般不调（词表大、易过拟合）。

**推理**：两种方式——合并导出成普通模型（推荐，简单快）；或基座 + LoRA 动态加载（vLLM multi-LoRA，适合多租户）。

### Q20. LoRA 和 QLoRA 的区别？〔原五·22〕

**答**：

- **LoRA**：主干保持 FP16/BF16，只训练低秩旁路。显存 ≈ 基座 + 少量 LoRA 状态。
- **QLoRA**：先把主干**量化到 4bit（NF4）并冻结**，前向时反量化计算，LoRA 旁路仍是 BF16。显存进一步降，7B 可在 24G 甚至 16G 卡上微调 13B。
- **QLoRA 的三个关键技术**：NF4（按权重分布设计的 4bit 数据类型）、**双重量化**（对量化常数再量化，省显存）、**paged optimizer**（显存峰值时把优化器状态换到 CPU，防 OOM）。

**取舍**：QLoRA 更省显存，但训练慢 20%~40%（反量化开销），且 4bit 基座会带来轻微精度损失；显存够就 LoRA，不够才 QLoRA。**推理时可以把 LoRA 合并到 4bit 权重上，也可以反量化合并到 FP16**，前者省显存、后者精度高。

# 七、推理部署与性能优化（vLLM / 容器 / K8s）

> 这章的题看起来杂，其实就三件事：**怎么让模型跑得快、怎么让它不挂、怎么在挂了之后能降级**。
> 回答时先给结论，再给参数，最后给数字。

### Q1. vLLM 是训练框架还是推理框架？FlashAttention 呢？〔原六·20〕

**答**：**vLLM 是推理/服务框架**，不负责训练。它解决的是"模型怎么高吞吐、低延迟地对外提供 API"：PagedAttention 管理 KV cache、连续批处理、OpenAI 兼容接口、多卡张量并行、量化、多 LoRA。

**FlashAttention 是注意力算子优化**，训练和推理都能用，属于底层 kernel，不是框架。它通过分块和在线 softmax 减少 HBM 读写，降低显存、加速长序列。

**关系**：vLLM 内部会调用 FlashAttention（或 FlashInfer/FlashMLA）作为 attention backend；训练框架（transformers/TRL）也会用它。三者层次：框架（vLLM）→ 算子（FlashAttention）→ 硬件（GPU）。

**易错点**：别说"vLLM 用来微调"；也别把 FlashAttention 说成"近似注意力"，它是精确计算。

### Q2. vLLM 为什么快？讲一下 PagedAttention 和连续批处理 ⭐〔原六·21〕

**答**：两个核心机制。

**1. PagedAttention（分页 KV cache）**

- 传统做法给每个请求预分配一段连续显存，按最大长度预留，浪费严重（内部碎片 + 外部碎片），利用率常常只有 20%~40%；
- PagedAttention 把 KV cache 切成固定大小的 **block**（如 16 token），用**块表（block table）**把逻辑连续的 KV 映射到物理不连续的块，像操作系统的虚拟内存分页；
- 好处：按需分配、几乎零碎片、支持**前缀共享**（同一 system prompt 的请求共享 KV，prefix caching）、支持 beam search 的 copy-on-write；
- 效果：吞吐提升 2~4 倍，同样显存能跑更多并发。

**2. Continuous Batching（连续批处理）**

- 静态 batch 要等整批里最长的序列生成完才能换下一批，短请求被拖死；
- 连续批处理以 **iteration** 为粒度调度：每个 decode step 后，完成的请求立刻退出，排队的请求立刻补位；
- 配合 **chunked prefill**，把长 prompt 的 prefill 切成小块，和 decode 混跑，避免长请求阻塞短请求（降 TTFT 抖动）。

**一句话**：PagedAttention 解决"显存装得下更多请求"，连续批处理解决"GPU 不空转"，两者相乘就是吞吐。

### Q3. vLLM、TensorRT-LLM、SGLang 怎么选？〔原六·22〕

**答**：

| | vLLM | TensorRT-LLM | SGLang |
|---|---|---|---|
| 定位 | 通用推理服务 | NVIDIA 极致优化 | 高吞吐 + 结构化输出 |
| 上手 | 最简单，pip 即用 | 需编译 engine，绑定 GPU 型号 | 较简单 |
| 性能 | 很好 | 通常最高（FP8/FP4、kernel 融合） | 很好，prefix 复用强 |
| 灵活 | 高，新模型支持快 | 低，换模型要重建 engine | 中高 |
| 特色 | PagedAttention、多 LoRA | in-flight batching、量化 | RadixAttention、xgrammar 约束解码 |

**选型**：快速上线、模型迭代快、要多 LoRA → vLLM；追求极致延迟/吞吐、GPU 型号固定、有专人维护 → TensorRT-LLM；大量共享前缀（few-shot、Agent 系统提示）、要严格 JSON 输出 → SGLang。

**现实**：多数团队 vLLM 起步，压测后发现瓶颈再针对性换；别一上来就上 TRT-LLM，engine 构建和版本适配很费人。

### Q4. vLLM 做过哪些优化？调哪些参数？⭐〔原六·23〕

**答**：按"显存、吞吐、延迟"三组调。

**显存**：

- `--gpu-memory-utilization 0.85~0.92`：留一点给 CUDA context 和碎片，别设 1.0；
- `--max-model-len`：按业务实际最大长度设，不要直接开到模型上限，KV cache 按这个预留；
- `--quantization awq/gptq/fp8`：显存不够时上量化；
- `--swap-space`：CPU 交换区，缓解峰值，但会慢。

**吞吐**：

- `--max-num-seqs`：并发序列上限，太小 GPU 空转，太大显存爆；
- `--max-num-batched-tokens`：单步最多处理多少 token，控制 prefill 块大小；
- `--enable-prefix-caching`：系统提示相同就开，命中率高的场景提升明显；
- `--tensor-parallel-size`：多卡切分，单机内优先。

**延迟**：

- `--enable-chunked-prefill`：长 prompt 不阻塞短请求；
- 关掉不必要的 logprobs、采样参数；
- 短输出场景可以 `--enforce-eager` 减少 CUDA graph 捕获开销（但通常 graph 更快，要实测）。

**方法**：用真实输入长度分布压测（Locust），看 TTFT、TPOT、P95、吞吐四条曲线，找拐点；不要只报空载 QPS。

### Q5. 静态部署和动态部署的区别？〔原二·52〕

**答**：

- **静态部署**：服务启动时把模型权重全部加载进显存，常驻进程，请求来了直接推理。**首 token 快、延迟稳定**，但占卡、扩缩容慢。
- **动态部署**：按需加载/卸载模型（多模型路由、Serverless），请求来了才加载。**省资源、支持多模型**，但冷启动要几十秒到几分钟，不适合在线低延迟场景。

**变体**：常驻基座 + 动态挂 LoRA（vLLM multi-LoRA），兼顾两者——基座不重复加载，LoRA 几十 MB 秒级切换，多租户场景很实用。

**选型**：在线问答用静态常驻 + 多副本；离线批处理用动态/队列；多模型低频场景用 Serverless（KServe、RunPod）。

### Q6. 容器化部署有哪些坑？⭐〔原二·51〕

**答**：按踩坑频率排：

1. **CUDA 版本不匹配**：宿主机 driver 版本要 ≥ 镜像 CUDA runtime 要求；用 `nvidia-container-toolkit`，别在容器里装 driver。基础镜像选 `nvidia/cuda:12.x-runtime` 或官方 vLLM 镜像。
2. **镜像太大**：不要把模型权重打进镜像，用 PVC/对象存储挂载；多阶段构建，清 apt 缓存。
3. **共享内存不足**：PyTorch DataLoader / NCCL 默认用 `/dev/shm`，容器默认 64MB，必须 `--shm-size=8g` 或挂 tmpfs，否则报 "Bus error"。
4. **显存被占满**：多个容器共享一张卡没做隔离，或者上一个进程没退干净；用 `nvidia-smi` + MIG 或整卡独占。
5. **模型加载超时**：K8s 的 liveness probe 在模型还没加载完就把 Pod 杀掉；要分开 **startupProbe**（长）和 **livenessProbe**（短）。
6. **端口/网络**：容器内监听 `0.0.0.0` 而不是 `127.0.0.1`；NCCL 多机要开 IB/RoCE 和对应端口。
7. **权限**：别用 root 跑服务；模型目录只读挂载。
8. **时区/编码**：日志时间错乱、中文乱码，基础镜像里设 `TZ` 和 `LANG`。

### Q7. 服务部署在哪？发布流程？版本怎么更新？〔原七·17〕

**答**：K8s 为主。

**部署**：模型服务（vLLM）和业务服务（FastAPI）分开部署，各自 HPA；模型用 StatefulSet 或 Deployment + PVC 缓存权重；前面挂 Ingress/网关做鉴权、限流、路由。

**发布流程**：

1. 构建镜像 → 推送仓库 → 更新 tag（禁止 latest）；
2. 新版本先起 1 个 Pod，跑**离线评估集 + 健康检查**；
3. **影子流量**：把真实请求复制一份给新版本，只记录不返回，对比输出差异；
4. **灰度**：按 5% → 20% → 50% → 100% 放量，监控错误率、延迟、点踩率；
5. **回滚**：保留上一个 ReplicaSet，指标异常一键 `kubectl rollout undo`；
6. **模型更新**：LoRA 走热加载，基座模型走双版本并行 + 切流，避免全量重启。

**注意**：模型加载慢，滚动更新要设 `maxUnavailable: 0` + `maxSurge: 1`，否则会短暂全部不可用。

### Q8. 并发上来怎么扛？限流、超时、降级怎么做？〔补充〕

**答**：四层防护。

1. **接入层**：网关限流（按用户/IP/QPS）、鉴权、请求体大小限制；排队用令牌桶，超了返回 429 而不是拖死。
2. **服务层**：异步 + 连接池；LLM 调用设**连接超时 + 读超时**（如 3s/60s）；单请求最大 token 限制；重试只对幂等错误、最多 2 次、带退避。
3. **模型层**：vLLM 设 `max-num-seqs` 上限，超出排队；多副本 + 负载均衡；长请求走独立队列，避免阻塞短问答。
4. **降级**：rerank 超时 → 跳过精排，直接用融合分数；LLM 超时 → 返回召回片段 + "请查看原文"；向量库挂 → 降级到 BM25；全部挂 → 友好错误页 + 转人工。

**压测**：按真实长度分布打，观察 P95/P99 和错误率拐点，容量按峰值 1.5 倍留余量。

### Q9. 显存怎么估算？GPU 怎么选？〔补充〕

**答**：显存 = **权重 + KV cache + 激活 + 框架开销**。

1. **权重**：`参数量 × 每参数字节`。FP16=2B，INT8=1B，INT4=0.5B。7B FP16 ≈ 14GB，INT4 ≈ 4GB。
2. **KV cache**：`2 × 层数 × KV头数 × head_dim × 序列长度 × batch × 字节数`。
   例：Qwen2.5-7B（28 层、4 个 KV 头、128 维、FP16），每 token 约 `2×28×4×128×2 ≈ 57KB`；32k 上下文单请求约 1.8GB。
3. **激活**：推理很小，训练时与 batch×seq 成正比，训练要额外算。
4. **开销**：CUDA context、碎片、通信 buffer，留 10%~20%。

**选型**：7B 推理 24G（4090/A10/L4）够；32B FP16 要 80G（A100/H100）；70B 要 2×80G 或 int4 单卡；高并发看**显存带宽**和 KV cache 容量，不只看算力。**性价比**：L4/L20 适合中小流量，A100/H100 适合高吞吐和长上下文。

### Q10. 线上要监控哪些指标？〔补充〕

**答**：分四层，缺一层就会"用户说慢，你却不知道慢在哪"。

1. **业务层**：QPS、日活、点踩率、转人工率、拒答率、答案长度分布、badcase 类型。
2. **应用层**：端到端 P50/P95/P99、**TTFT（首 token 延迟）**、TPOT（每 token 时间）、超时率、5xx、重试率、各阶段耗时（改写/召回/rerank/生成/校验）。
3. **模型层**：GPU 利用率、显存占用、KV cache 使用率、排队长度、batch size、prefill/decode 耗时、token 吞吐（tokens/s）。
4. **数据层**：向量库 QPS/延迟、召回条数分布、空召回率、索引大小、BM25 命中率。

**告警**：P95 延迟突增 50%、错误率 >1%、空召回率翻倍、GPU 显存 >95%、模型服务不可用。**日志**要带 trace_id，能串起一次请求的全链路。

# 八、Agent、LangChain / LangGraph、工具调用

> Agent 岗的重中之重。回答要体现"**能落地**"：不是会调 `AgentExecutor`，而是知道它什么时候会死循环、怎么让它停下来、怎么证明它比单次 RAG 好。

### Q1. 什么是 AI Agent？它由哪几部分组成？⭐〔原二·25〕

**答**：Agent = **LLM + 规划 + 工具 + 记忆 + 反思**，本质是"让模型在多步执行中自己决定下一步做什么"，而不是一问一答。

- **LLM（大脑）**：理解目标、决策、生成；
- **Planning（规划）**：任务拆解、步骤排序、何时停止；
- **Tools（手脚）**：检索、计算器、SQL、API、代码执行，扩展模型能力边界；
- **Memory（记忆）**：短期对话、长期偏好/事实；
- **Reflection（反思）**：检查结果、纠错、重试。

**和 RAG 的区别**：RAG 是"一次检索 + 一次生成"的固定流水线；Agent 是"**循环**：想 → 做 → 看 → 再想"，能处理需要多工具、多跳、动态决策的任务。

**边界**：简单问答不要上 Agent，延迟和成本都会翻倍；Agent 适合"步骤不确定、需要外部动作"的任务。

### Q2. ReAct 范式是什么？⭐〔原二·26〕

**答**：ReAct = **Reasoning + Acting**，让模型交替输出"思考"和"行动"，用工具返回的观察修正下一步。

循环：

1. **Thought**：我需要先查什么 / 现在信息够不够；
2. **Action**：调用哪个工具、参数是什么；
3. **Observation**：工具返回结果；
4. 回到 1，直到 **Final Answer**。

**例子**：问"去年华东区销售额是多少，同比增长多少" → 思考要查 2024 和 2023 两个数 → 调 SQL → 观察结果 → 发现缺 2023 → 再调一次 → 计算同比 → 回答。

**工程要点**：

- 必须设**最大轮数**（如 8）和**总超时**，否则会死循环烧钱；
- 工具描述要清晰，否则模型选错工具；
- 观察结果要截断，避免上下文爆炸；
- 记录完整 trace（每轮 thought/action/observation），否则无法调试；
- 生产上更推荐**结构化 function call**，而不是让模型自由输出文本再解析。

### Q3. Agent 的完整流程？〔原七·8、八·3〕

**答**：以"内部知识库 + 工单系统"为例：

1. **接入**：鉴权、会话 ID、加载历史；
2. **理解**：意图分类（问答/工具/闲聊/越界），query 改写；
3. **规划**：判断是否需要拆子任务，选工具；
4. **执行**：调检索 / SQL / API，拿 observation；
5. **判断**：信息够不够？不够回到 3（有最大轮数）；
6. **生成**：组织答案，附引用；
7. **校验**：事实、格式、权限、敏感词；
8. **落盘**：trace、耗时、token、工具调用记录；
9. **记忆**：写入会话历史/摘要。

**关键设计**：把"规划"和"执行"分开，执行层做成幂等工具；每一步都可观测、可中断、可重放。

### Q4. 为什么用 Tool 模式？什么时候不该用？〔原七·7〕

**答**：因为 LLM 有三个硬限制：**知识过期、不会算、不能操作外部系统**。Tool 把这三件事外包出去。

适合：

- 需要实时/私有数据（订单、库存、天气）；
- 精确计算（金额、税率、统计）；
- 有副作用的操作（建单、发邮件、改状态）；
- 需要检索（RAG 本身就是一个 tool）。

**不该用**：

- 模型自己就能答的常识/写作；
- 一次检索就能解决的简单问答（用固定 RAG 链更稳更快）；
- 高风险不可逆操作（转账、删库）——必须加人工确认。

**判断标准**：任务步骤是否确定。确定 → 工作流（workflow）；不确定、需要模型临场决策 → Agent。

### Q5. 工具怎么选？工具描述（prompt）怎么写？〔原七·9、七·11〕

**答**：工具选择靠**描述 + schema**，不是靠模型猜。

**工具描述写法**（每个工具）：

1. **一句话说明能力**："查询指定区域、指定月份的销售总额"；
2. **什么时候用/不用**："仅当用户明确询问金额时使用；不要用于预测"；
3. **参数说明**：类型、格式、枚举、示例、必填/可选；
4. **返回说明**：字段含义、单位、空结果怎么表示；
5. **错误约定**：参数非法时返回什么，模型该如何重试。

**选择策略**：工具多时（>10）先做**工具检索**（按 query 召回 top5 工具描述），再让模型选，避免 prompt 过长和误选；也可以用路由模型先分大类。

**减少误调用**：参数用 JSON Schema 严格约束 + 枚举；加"不确定就反问"的指令；对高风险工具加二次确认。

### Q6. 一次任务会调用几次 LLM？怎么控成本？〔原七·11〕

**答**：不是固定值，取决于任务复杂度。一次简单问答 1 次；一次带工具的任务通常 **3~6 次**：意图识别 1 次 + 每轮"思考/选工具"各 1 次 + 最终生成 1 次 + 校验 1 次。

**控制手段**：

1. **能不用 LLM 就不用**：意图分类用规则/小模型，参数抽取用正则/小模型；
2. **合并调用**：把"意图 + 改写 + 工具选择"合成一次结构化输出；
3. **缓存**：相同 query 的答案、embedding、工具结果缓存；
4. **限制轮数**：`max_iterations=6`，超了返回当前最优结果并说明；
5. **模型分级**：路由/校验用小模型，最终生成用大模型；
6. **上下文裁剪**：工具结果截断、历史摘要，别每轮都带全量。

**度量**：平均 LLM 调用次数、平均 token、单次任务成本，作为一级指标监控。

### Q7. Tool 和 Function Call 的区别？⭐〔原七·12〕

**答**：

- **Function Calling 是模型的一种能力/协议**：你把函数的 JSON Schema 传给模型，模型判断要不要调、返回结构化的 `tool_calls`（函数名 + 参数 JSON）。它**只负责"说"，不负责"做"**。
- **Tool 是应用层的封装**：包含 schema、描述、实际执行函数、参数校验、超时重试、权限控制、结果格式化。它是"能被 Agent 调用的完整能力单元"。

关系：Function Call 是 Tool 的**调用协议**；Tool 是 Function Call 的**落地实现**。没有 function call 能力的模型，也能用 ReAct 文本解析实现工具调用，但不稳定。

**工程细节**：模型返回的参数必须校验（JSON Schema + 业务规则），失败要回灌错误让模型重试；执行要设超时和幂等；结果要截断，避免超长。

### Q8. Agent 的 Memory 怎么实现？〔原七·10〕

**答**：分四层，按"用不用得上"选。

1. **Buffer Memory**：全量保留最近 N 轮，简单但会爆上下文；
2. **Window Memory**：只留最近 k 轮，适合短对话；
3. **Summary Memory**：旧对话用 LLM 压缩成摘要，省 token，但会丢细节；
4. **Vector Memory**：历史写入向量库，按当前 query 检索相关记忆，适合长期偏好和跨会话；
5. **Entity Memory**：抽取用户/项目等实体及属性，结构化存储，适合客服/助手。

**生产做法**：短期用 window + summary，长期用向量库；用 `session_id` 隔离；记忆写入前做去重和敏感信息过滤；给用户"清空记忆"的入口（合规）。

**LangGraph** 用 **checkpointer** 把整个 State 按 `thread_id` 持久化，天然支持多轮、断点续跑、时间旅行，比手写 memory 稳。

### Q9. Agent 怎么处理并发和多会话？〔原七·13〕

**答**：核心是**无状态服务 + 外部化状态**。

1. **会话隔离**：每个会话一个 `session_id/thread_id`，State 存在 Redis/Postgres，不放在进程内存里；
2. **并发模型**：FastAPI 异步 + `asyncio`，每个请求独立协程；工具调用用连接池；长任务丢队列（Celery）异步执行，前端轮询/SSE；
3. **幂等**：同一 session 的写操作加锁（Redis 分布式锁），防止用户连点导致重复建单；
4. **限流**：按用户/会话限制并发和 token 预算，防止一个用户打满 GPU；
5. **多类型数据**：文本、文件、图片统一走"上传 → 对象存储 → 解析任务 → 结果引用"的异步链路，会话里只存引用，不存大对象。

**坑**：不要在全局变量里存对话历史；不要让一个长任务阻塞事件循环；跨 Pod 要保证 session 粘性或状态共享。

### Q10. 多轮输入和分页文档怎么落地？〔原七·14〕

**答**：

**多轮**：

1. 每轮把 query 和最近历史一起做**指代消解/改写**（"它的价格" → "X 型号的价格"）；
2. 改写后的 query 去检索，原始 query 保留用于日志；
3. 历史用 window + summary，超长就压缩；
4. 用户切换话题时清空/降权旧上下文，避免污染。

**分页文档**：

1. 前端分页/滚动加载，后端按 `doc_id + page` 取块，不要一次返回全文；
2. 检索命中某页时，返回该页上下文 + 前后各一页，兼顾完整性和 token；
3. 大文件走异步解析任务，前端显示进度；
4. 引用定位到"文档 + 页码 + 块 id"，支持点击跳转原文。

### Q11. Agent 的稳定性怎么保证？哪些能力该沉淀成 service？〔原七·15〕

**答**：稳定性靠"**约束 + 兜底 + 可观测**"。

1. **约束**：JSON Schema 校验、参数枚举、最大轮数、超时、token 预算、工具白名单；
2. **兜底**：工具失败重试（幂等 + 退避）、降级（跳过 rerank/返回检索片段）、拒答、转人工；
3. **隔离**：每个工具独立超时和熔断，一个工具挂不拖垮整个 Agent；
4. **可观测**：全链路 trace、每步输入输出、错误分类、告警；
5. **评测**：固定任务集回归，覆盖正常/边界/恶意输入。

**该沉淀成 service 的**：检索服务、LLM 推理服务、rerank 服务、文档解析服务、工具网关（统一鉴权/限流/审计）、会话状态服务。**不该沉淀的**：具体业务的 prompt 编排，留在应用层快速迭代。

### Q12. Agent 生成的内容怎么限制、评测和验证？〔原七·16〕

**答**：三道闸。

1. **生成前**：system prompt 约束范围、禁止事项、输出格式；工具权限最小化；敏感操作人工确认。
2. **生成中**：结构化输出（JSON Schema / 函数调用）、流式内容过滤、超长截断。
3. **生成后**：
   - **格式校验**：JSON 解析、字段必填、枚举合法；
   - **事实校验**：每个 claim 是否有检索片段支持（NLI/LLM judge）；
   - **安全校验**：敏感词、PII 脱敏、合规规则；
   - **业务校验**：金额范围、权限、状态机合法性。

**评测**：任务成功率、工具调用准确率、参数正确率、平均轮数、越权率、有害输出率；离线跑固定集，线上灰度 + 人工抽检。**不能只看"回答像不像"，要看"任务有没有完成"**。

### Q13. 多 Agent 协作的流程？〔原八·7〕

**答**：常见三种拓扑：

1. **Supervisor（主管制）**：一个路由 Agent 拆任务、分发给检索/计算/校验子 Agent，汇总结果。最常用，可控。
2. **Pipeline（流水线）**：A 的输出是 B 的输入，如"抽取 → 校验 → 格式化"，适合固定流程。
3. **Debate/Swarm（辩论/ swarm）**：多个 Agent 给方案，互相批判或投票，适合开放性决策，成本高。

**一次请求的流程**（supervisor）：

用户输入 → 路由 Agent 判意图 → 分发给子 Agent（并行/串行）→ 子 Agent 返回结构化结果 → 汇总 Agent 合并、去冲突 → 校验 Agent → 输出。

**关键**：子 Agent 之间**只传结构化结果，不传自由文本**；设全局超时和预算；路由要有 fallback；用 LangGraph 的 subgraph 管理，别用一堆 if-else 硬编。

### Q14. 为什么要多 Agent？什么时候不该用？〔原八·8〕

**答**：

**好处**：

- **职责单一**：每个 Agent 的 prompt、工具、评测都独立，好维护、好迭代；
- **上下文隔离**：子 Agent 只带自己需要的信息，避免长上下文互相干扰；
- **并行**：检索、计算可以同时跑，降低延迟；
- **权限隔离**：不同 Agent 给不同工具权限，降低越权风险。

**代价**：

- 调用次数和 token 成本成倍增加；
- 延迟叠加，链路难排查；
- 错误会在 Agent 之间传播，汇总层很难发现；
- 状态一致性和超时控制复杂。

**不该用**：任务步骤固定（用 workflow）、单工具能解决、对延迟敏感、团队没有可观测能力。**先从单 Agent + 多工具开始，真的拆不开再上多 Agent。**

### Q15. LangChain 的原理？常用类有哪些？⭐〔原二·15、七·2、七·3、七·9〕

**答**：LangChain 是**LLM 应用的编排框架**，核心是把组件抽象成统一接口，用 `Runnable` 协议串起来。

- **模型层**：`ChatOpenAI`、`ChatAnthropic`，统一 `invoke/stream/batch`；
- **Prompt**：`ChatPromptTemplate`、`MessagesPlaceholder`；
- **检索**：`VectorStoreRetriever`、`BM25Retriever`、`MultiQueryRetriever`、`EnsembleRetriever`；
- **切分**：`RecursiveCharacterTextSplitter`；
- **链**：LCEL（`prompt | llm | parser`）、`ConversationalRetrievalChain`；
- **工具/Agent**：`Tool`、`AgentExecutor`、`create_react_agent`；
- **记忆**：`ConversationBufferMemory`、`SummaryMemory`；
- **回调**：`BaseCallbackHandler`，做日志、追踪、流式。

**原理**：每个组件实现 `Runnable`（`invoke`/`ainvoke`/`stream`/`batch`），用 `|` 组合成 DAG，运行时逐级传值；回调系统在关键节点发事件，LangSmith 就是消费这些事件做追踪。

**评价**：原型快，但 `AgentExecutor` 是黑盒循环，复杂流程难控；生产复杂 Agent 我更倾向 **LangGraph**。

### Q16. LangGraph 的 State / Node / Edge 是什么？⭐〔原七·3〕

**答**：LangGraph 把 Agent 建模成**状态图**。

- **State**：一个共享的、可持久化的数据结构（TypedDict/Pydantic），字段如 `messages / intent / docs / tool_result / answer`。用 `Annotated[list, add_messages]` 这类 **reducer** 定义"新值怎么合并进旧值"（追加还是覆盖）。
- **Node**：一个函数，输入 State、输出**增量更新**。常见节点：意图识别、检索、工具调用、校验、生成。
- **Edge**：节点间的流转。普通边是固定顺序；**条件边**（`add_conditional_edges`）根据 State 里的字段路由，比如"检索为空 → 追问 / 否则 → 生成"。
- **Checkpointer**：按 `thread_id` 持久化每步 State，支持多轮、断点续跑、人工介入（`interrupt`）、时间旅行回放。
- **Subgraph**：把子流程封装成图，支持多 Agent 嵌套。

**相比 AgentExecutor 的优势**：流程显式、可测试、可中断、可回放、能加循环上限和人工审核节点。**代价**：要自己设计状态和路由，前期成本高。

**项目**：我用 `intent → retrieve → grade → (generate | rewrite → retrieve) → verify → answer`，`grade` 判断召回是否足够，最多重试 2 次，`verify` 不过就拒答。

### Q17. LangChain 报错怎么定位？LLM 的错误处理和规则校验怎么做？〔原七·4、七·5〕

**答**：分三层定位，从外到内。

1. **框架层**：看完整 traceback，重点是最后一个"业务代码"栈帧；LangChain 的异常常被 `OutputParserException`、`ValidationError` 包装，要看 `__cause__`。
2. **链路层**：挂 callback / LangSmith，打印每个 Runnable 的输入输出，定位是 prompt 变量缺失、retriever 返回空、还是 parser 失败。
3. **模型层**：dump 原始请求和响应（注意脱敏），看是否超长、被限流、返回了非 JSON、触发内容过滤。

**常见错误与处理**：

- **输出不是合法 JSON** → 用 `PydanticOutputParser` + 重试 + 降级；prompt 里给 schema 和示例；
- **工具参数错** → JSON Schema 校验，把错误信息回灌给模型重试；
- **上下文超长** → 裁剪、摘要、换长上下文模型；
- **限流/超时** → 指数退避重试、熔断、降级；
- **空召回** → 走拒答，不要硬编。

**规则校验**：输出侧统一用 Pydantic/JSON Schema + 业务规则（金额范围、枚举、权限），校验失败不让它进下一步。**校验要放在代码里，不要只写在 prompt 里。**

### Q18. 让你从 0 设计一个 Agent 系统，怎么做？⭐〔原五·4、七·6、八·6、八·7〕

**答**：按"目标 → 架构 → 约束 → 评测 → 上线"五步。

1. **定义任务边界**：解决什么问题、成功标准是什么、哪些不能做（高风险操作）、用户是谁。
2. **选形态**：步骤固定 → workflow；步骤不定 → 单 Agent + 多工具；职责复杂且可拆 → supervisor 多 Agent。
3. **分层架构**：
   - 接入层：鉴权、限流、会话；
   - 编排层：LangGraph，State + 节点 + 条件边 + checkpointer；
   - 能力层：检索、SQL、API、计算器，统一工具网关（schema、超时、重试、审计）；
   - 模型层：vLLM 推理服务，按任务分级选模型；
   - 数据层：向量库、业务库、日志。
4. **约束与兜底**：最大轮数、超时、token 预算、工具白名单、人工确认、拒答、降级。
5. **评测与上线**：任务成功率、工具准确率、平均轮数、P95 延迟、成本；离线集回归 → 影子 → 灰度 → 全量；全链路 trace + 告警。

**一句话**：Agent 的难点不在"让它能做什么"，而在"**让它在该停的时候停、该拒的时候拒、出错时能查**"。

### Q19. 了解 MCP 吗？（加分项）〔补充〕

**答**：MCP（Model Context Protocol）是 Anthropic 提出的**模型与外部工具/数据源之间的标准化协议**，基于 JSON-RPC。

- **角色**：Host（宿主应用，如 IDE/客户端）→ Client（连接器）→ Server（能力提供方）；
- **三类能力**：Tools（可执行函数）、Resources（可读取的数据）、Prompts（预置提示模板）；
- **传输**：stdio（本地进程）、SSE / Streamable HTTP（远程）；
- **价值**：把"每个应用自己接一遍工具"变成"写一次 Server，所有支持 MCP 的客户端都能用"，类似工具界的 USB-C。

**和 function calling 的关系**：function calling 是模型层协议，MCP 是**工具接入层协议**；Agent 通过 MCP 发现工具，再把 schema 转成 function call 给模型。

**注意**：MCP Server 有执行权限，要做鉴权、沙箱、审计，别随便连不可信 Server。

# 九、工程化、排查与系统设计

> 这章区分"能跑 demo"和"能上线"。回答要有**清单感**：分层、分步骤、给工具名、给判据。
> 排查题的黄金结构：**先定位在哪一层 → 再看什么指标 → 最后怎么修 + 怎么防复发**。

### Q1. 从 0 到 1 设计一个可扩展的 Python 项目，从哪几方面做？⭐〔原二·50〕

**答**：六个方面，按"先骨架后血肉"。

1. **分层目录**：
   ```
   app/
     api/          # 路由、鉴权、参数校验
     core/         # 配置、日志、异常、常量
     services/     # 业务编排（rag、agent、eval）
     clients/      # LLM、向量库、DB 客户端
     models/       # Pydantic schema / ORM
     utils/
   tests/          # 单测、集成测试、评估
   configs/        # yaml / .env.example
   Dockerfile
   pyproject.toml
   ```
2. **配置与解耦**：`pydantic-settings` 读环境变量，配置分级（dev/staging/prod），密钥走 Secret，不硬编码。
3. **接口抽象**：LLM、Embedding、Rerank、VectorStore 都定义 Protocol/ABC，实现可替换（换模型不改业务）。
4. **可观测**：结构化日志（JSON + trace_id）、指标（Prometheus）、链路追踪（LangSmith/OpenTelemetry）、统一异常处理（业务异常 → 明确错误码）。
5. **质量**：pytest 单测 + 集成测试 + 评估集回归；ruff/mypy/pre-commit；CI 跑 lint + test + build。
6. **交付**：Docker 多阶段构建、docker-compose 本地一键起、K8s 部署、健康检查、灰度回滚。

**扩展性**：插件化注册（工具、loader、splitter 用注册表）、异步优先、无状态服务 + 外部状态、幂等设计。

### Q2. 从用户进入系统到返回答案，完整链路是什么？〔原八·3、八·2〕

**答**：以在线问答为例，标出每步的耗时预算（总 P95 < 3s）：

1. **接入**（<20ms）：DNS/网关 → 鉴权（JWT）→ 限流 → 生成 trace_id；
2. **会话**（<20ms）：取 session 历史/摘要，判断是否新会话；
3. **理解**（100~300ms）：意图分类 → query 改写/指代消解 → 槽位抽取；
4. **路由**（<10ms）：知识问答 / 工具任务 / 闲聊 / 越界；
5. **检索**（100~300ms）：BM25 与向量并行 → RRF 融合 → 去重；
6. **精排**（100~200ms）：rerank top20 → top5，卡阈值；
7. **组装**（<20ms）：按 token 预算拼 system + 历史 + 上下文 + 问题，标引用编号；
8. **生成**（首 token <800ms，总 1~3s）：vLLM 流式输出；
9. **校验**（100~300ms，可与流式并行）：引用存在性、忠实度、敏感词；
10. **返回**：SSE 推流 → 结束帧带引用和耗时；
11. **落盘**：trace、token、工具调用、用户反馈，异步写，不阻塞响应。

**关键**：能并行的都并行（双路召回、校验与生成）；能异步的都异步（日志、记忆写入）；每步都有超时和降级。

### Q3. 检索之前做了哪些处理？〔原八·5〕

**答**：五步，目的分别是"干净、明确、可检索、可过滤、可兜底"。

1. **清洗**：去首尾空白、全半角统一、去控制字符、纠正常见错别字；
2. **意图识别**：判断是不是知识问答，不是就走别的分支，避免无效检索；
3. **改写**：多轮指代消解（"它/这个"补全）、同义词/缩写扩展、口语转书面；
4. **拆解**：多跳/对比类问题拆子查询，分别检索；
5. **结构化**：抽时间、部门、产品等槽位，转成元数据过滤条件（如 `dept=华东 AND year=2024`）；
6. **边界**：空 query、超长 query、敏感 query 直接拦截或澄清。

**注意**：改写后的 query 要和原 query **一起检索**（多路召回），防止改写漂移；改写结果要落日志，方便归因。

### Q4. 召回率是怎么算出来的？线上怎么算？〔原八·6〕

**答**：

**离线**：固定评估集，每条 query 人工标注相关 chunk（gold），跑检索，算 `recall@k = 命中 gold 数 / gold 总数`，再对所有 query 取平均。文档级和 chunk 级要分开。

**线上没有标注**，用三种替代：

1. **弱标签**：用户点击了引用、复制了答案、没有追问 → 视为正样本；
2. **LLM 判定**：用 judge 判断"召回片段是否包含回答所需信息"，抽样计算；
3. **人工抽检**：每周抽 100 条真实 query 标注，作为线上质量的校准集。

**监控**：空召回率、平均 top1 分数、分数分布漂移、用户追问率。**分数分布整体下移**往往意味着新文档解析质量差或 embedding 服务异常。

### Q5. RAG 出错了怎么检查？⭐〔原八·9〕

**答**：按链路二分，先定位"是没找到，还是找到了没用对"。

| 层 | 检查 | 典型现象 |
|---|---|---|
| 解析 | 原文 chunk 是否完整、表格是否错位 | 答案缺关键数字 |
| 切分 | 命中块是否被截断、是否缺标题 | 答非所问、上下文断裂 |
| 改写 | 改写后 query 是否偏离原意 | 召回完全不相关 |
| 召回 | gold 是否在 top50；分数多少 | 空召回/低分 |
| 融合 | 两路结果是否被错误加权 | 精确匹配被淹没 |
| 精排 | rerank 分数是否合理、是否误杀 | 好块排到后面 |
| 组装 | 上下文是否超长被截断、顺序是否合理 | 模型"没看到"关键信息 |
| 生成 | 模型是否忽略上下文、是否编造 | 忠实度低 |
| 校验 | 是否漏放/误杀 | 该拒没拒、不该拒拒了 |

**方法**：拿一条 badcase，把 trace 里每一层的输入输出都打出来，**从后往前**看第一处不对的地方。不要一上来就改 prompt。

### Q6. 答案有问题怎么 debug、怎么 fix？〔原八·10〕

**答**：先归因，再修，最后加回归。

**归因四问**：

1. **知识库里有没有？** 没有 → 补文档，不是模型问题；
2. **召回有没有？** 没有 → 修解析/切分/embedding/query 改写；
3. **召回了但排得靠后？** → 修融合/rerank/权重；
4. **上下文里有但答错？** → 修 prompt/模型/上下文长度/顺序，必要时微调。

**修复优先级**：数据 > 检索 > prompt > 微调。**80% 的 badcase 在前两层**。

**防复发**：

- 把这条 case 加进评估集（带 gold），每次改动回归；
- 同类 case 聚类，一次性修一类，而不是打补丁；
- 记录修复前后的指标，写进变更日志。

**话术**："我不会直接改 prompt 让它'看起来对了'，而是先确认是检索问题还是生成问题，否则会把一个 bug 变成两个。"

### Q7. 平时用什么排查工具？〔原八·4〕

**答**：

- **链路追踪**：LangSmith（LangChain 生态）、Langfuse（开源，可自部署）、OpenTelemetry + Jaeger；
- **日志**：结构化 JSON + trace_id，ELK/Loki 检索；关键节点打输入输出（脱敏）；
- **指标**：Prometheus + Grafana，看延迟、错误率、token、GPU；
- **检索调试**：自己写的 debug 脚本，输入 query 直接打印 top50 的 chunk、分数、来源；向量库自带的可视化/查询控制台；
- **模型侧**：vLLM 的 metrics、`nvidia-smi`、Nsight（性能）；
- **复现**：把 trace 里的 prompt 原样重放，固定 seed/temperature 对比输出。

**习惯**：出问题先保存现场（trace_id、prompt、召回列表），再改代码；否则复现不了。

### Q8. 用 Copilot 吗？分析一下优缺点。〔原八·1〕

**答**：用，但定位是"加速打字，不是替你思考"。

**优点**：

- 样板代码（CRUD、Pydantic 模型、测试骨架、正则）几乎不用手写；
- 不熟悉的库能快速给出用法示例，省查文档时间；
- 重构/改名/补类型提示很顺手；
- 写 commit message、注释、文档也快。

**缺点**：

- **幻觉 API**：编造不存在的方法/参数，尤其是新版本库；
- 训练数据里的代码可能有 bug 或过时写法；
- 安全风险：可能生成硬编码密钥、SQL 拼接、不安全的反序列化；
- 上下文理解有限，复杂业务逻辑经常"看起来对，边界错"；
- 过度依赖会弱化调试能力。

**我的用法**：样板和测试让它写，核心链路（检索、Agent 状态机、并发、权限）自己写 + 逐行 review；所有生成代码必须过 lint、类型检查、单测；敏感代码不进外部模型。

### Q9. 用 AI 写代码，效率提升多少？〔原八·2〕

**答**：分场景，别给一个笼统的倍数。

- **样板/胶水代码**：提升 50%~70%，基本是"审一遍就能用"；
- **测试用例**：提升明显，尤其是边界用例的枚举；
- **不熟悉的库**：从"查半小时文档"到"5 分钟跑通 demo"；
- **核心算法/架构**：提升有限，甚至为负——要花时间验证它是否真的对。

**整体体感**：日常开发 20%~30% 的效率提升，但 **review 和调试时间会增加**，净收益取决于任务类型。

**关键**：AI 负责"广度"，人负责"深度"；把时间从敲键盘转移到设计、验证和边界思考上，这才是真正的提效。

### Q10. 线上出事故怎么处理？〔补充〕

**答**：按"止血 → 定位 → 修复 → 复盘"四步，顺序不能反。

1. **止血**：先回滚/切流/降级，恢复可用性，不要在线上边查边改；保留现场（Pod、日志、trace）。
2. **定位**：看时间线（什么时候开始、哪个版本/配置变更）、影响面（多少用户、哪些功能）、错误分布（某类 query？某个模型？某个节点？）。
3. **修复**：根因修复 + 临时补丁；修完先在影子/灰度验证。
4. **复盘**：时间线、根因、为什么没提前发现、改进项（监控/测试/流程），每项有 owner 和 deadline。

**预防**：变更必须可回滚；关键指标有告警；灰度发布；演练降级预案；把事故 case 加进评估集。

# 附录 E：高频避坑清单

1. **数字要自洽**：文档 2 万份 → chunk 30 万 → top50 召回 → top5 入 prompt；别出现"100 万文档、单卡 7B、P95 200ms"这种组合。
2. **别把 RAG 说成微调**：知识更新归 RAG，格式/行为归微调。
3. **别把向量检索说成"理解语义"**：它只是相似度，仍会召回"相似但不相关"。
4. **别说"召回率 99%"**：没有标注口径的高召回不可信。
5. **别说"用了 Agent 就一定更好"**：简单任务用 workflow，成本和稳定性都更优。
6. **别说"temperature=0 就完全确定"**：GPU 非确定性仍在。
7. **别说"LoRA 没有精度损失"**：是"损失可控"，要评测。
8. **别硬编不会的**：术语听不清就问"您是指 X 吗"，比瞎答加分。
