## 01 RAG 检索增强（Q1–Q3）

RAG 是简历必写项，面试官重点问你「混合检索怎么真的拼起来」以及「面对脏数据（PDF 扫描件、表格）怎么处理」。

### Q1 多阶段 RAG，BM25 加向量混合检索——两种结果怎么合并？实际提升在哪？

**考察意图**：不是问「有没有用混合检索」，而是问「两路分数怎么融合」，看是否真的实现过 RRF / 加权。

**答题要点**：

- 融合策略：**RRF（Reciprocal Rank Fusion）** 或归一化加权求和，不能直接把两路 Top-K 拼一起。
- 为什么不能直接拼：BM25 是词频分、向量是余弦相似度，量纲不同，直接比大小没意义，要先排名融合或归一化。
- RRF 做法：对每个文档在每一路里的排名取倒数再求和，公式为 RRF(d) = Σ 1/(k + rank_i(d))，常数 k 常用 60。
- 各司其职：向量路抓语义/同义词，BM25 抓精确匹配（人名、ID、术语、型号、代码标识符）。
- 实际提升：**召回率** 提升（单路向量对精确词会漏），精确匹配召回提升；再外挂 Rerank 精排效果更好，最好能报出自己的 Recall@K。

### Q2 PDF 扫描件、OCR、表格结构化这些，踩过坑没？

**考察意图**：真实工程经验，看有没有处理过脏数据，能不能讲出「怎么清洗」。

**答题要点**：

- 扫描件：本质是图片，要先 OCR 才有文本；坑在清晰度、扫描倾斜、双栏布局、印章/水印污染。
- 表格：不能靠纯文本抽取，要用版面分析；坑在行列表格、跨页表格、合并单元格、复杂表头。
- 结构化：OCR 错字会污染 embedding 和 chunk，直接拖垮检索质量；还要处理公式、代码块、页眉页脚噪声。
- 工具链：PaddleOCR / PP-Structure、Unstructured、LlamaParse、Tesseract。
- 关键说清「清洗管线」：版面分割 → 表格结构识别 → 后处理校验 → 按块重建 chunk。

### Q3 识别准确率能做到多少？

**考察意图**：量化意识 + 诚实，别吹 99.9%，也别答不上来。

**答题要点**：

- 先定义口径：字符级 CER（字错率）vs 字段级 vs 端到端抽取准确率，口径不同数字差很多，先说清你报的是哪个。
- 分场景报数：清晰电子版 PDF ≈100%；打印扫描件 OCR 95%+（受清晰度影响）；复杂表格结构化 85–90%。
- 说明怎么评：抽样 + 人工标注 gold set；怎么优化：预处理、换模型、加后处理规则。

## 02 状态管理（Q4–Q5）

只要简历写了 LangGraph 多 Agent，State 与 Checkpoint 是必考题，考你有没有真懂 channel / reducer / 命名空间。

### Q4 State 和 Checkpoint 怎么搞的？多个 agent 一块跑，状态不会互相覆盖吗？

**考察意图**：LangGraph 状态管理与并发隔离，是「真用过」和「只看过教程」的分水岭。

**答题要点**：

- State：用 TypedDict（或 Pydantic）定义 Schema，每个 key 可以配 reducer（如 add_messages、add、覆盖式默认）。
- Checkpoint：图的持久化快照，支持断点续跑、回溯、human-in-the-loop。
- 多 Agent 隔离：每个子图用独立 namespace / thread_id 存 checkpoint，主图用另一个 namespace 汇总，两边互不覆盖。
- 关键点：reducer 决定「并发更新怎么合并」——两个节点同时向 messages 写，用 add_messages 会累积而不会覆盖。

### Q5 State 全局管理怎么做的？

**考察意图**：全局状态 vs 局部状态的取舍与设计。

**答题要点**：

- 区分两类：全局共享状态（放进 State Schema，各节点读写）+ 节点局部变量（不上升全局）。
- reducer 选型：对话历史用 add_messages 累积、计数用 add 累加、单值用默认覆盖。
- 大对象慎入全局 State（节点间传递有成本），用引用或外部存储；State 可被 checkpoint 完整 dump，便于调试。

## 03 MCP 协议（Q6–Q10）

MCP 是 2026 年 Agent 面试的高频重灾区，从接口设计一路问到短板和流式，考的是批判性认知。

### Q6 Choice 接口包成 MCP 工具，标准接口怎么设计？兼容性有问题吗？

**考察意图**：工具命名规范、入参 schema 设计、向后兼容意识。

**答题要点**：

- 命名：唯一、语义化、避免重名（可加 domain 前缀）；description 要写清楚，模型靠 description 选工具。
- 入参：JSON Schema 定义 name / type / description / required；参数尽量枚举化、给默认值。
- 出参：结构化返回 + 统一错误码约定。
- 兼容性：加字段向后兼容（新字段设可选）、不删改旧字段语义、版本化、灰度放量。

### Q7 现场举一个你项目里的 MCP 工具例子，入参出参怎么定义的？

**考察意图**：具体落地能力，能不能当场写出 inputSchema。

**答题要点**：

- 给一个真实工具（如「查订单状态」）口述结构：入参 order_id（string，必填），出参 status + tracking_list 列表。
- 强调 inputSchema 三要素：参数名、类型、描述；描述质量直接决定模型调用准确率。

### Q8 没有 MCP 之前，大模型调工具是怎么个流程？

**考察意图**：对技术演进的理解，不是只背「MCP 统一了工具接入」这句话。

**答题要点**：

- 原生 Function Calling：模型输出 function_call + 参数 JSON → 你解析 → 手动 dispatch → 把结果回填上下文。
- 手写工具注册表：每个工具单独写一份 schema 描述，自己写路由分发逻辑。
- 痛点：N 个工具 × M 个模型要各自适配，无统一发现与权限管理。
- MCP 的价值：统一「发现 + 描述 + 调用 + 权限」协议，Client / Server 解耦，一次接入多处复用。

### Q9 MCP 有什么坑或者短板？

**考察意图**：批判性认知，别只会夸 MCP。

**答题要点**：

- 标准仍在快速演进，版本兼容有坑（早期 SDK 与新版 transport 不兼容）。
- 认证授权模型早期不成熟（OAuth 支持是逐步补齐的）。
- 流式 / 长连接支持弱（SSE 是后补的，且工具结果本身非流式，见 Q10）。
- 生态碎片化、server 质量参差不齐、debug 与可观测工具少、权限粒度偏粗。

### Q10 MCP 返回结果能不能流式？

**考察意图**：MCP 细节，考你有没有分清「模型流式」和「工具结果流式」。

**答题要点**：

- MCP 核心是 request / response；传输层新版支持 Streamable HTTP（替代旧 HTTP+SSE），但流式主要用于 LLM 输出。
- 要流式给用户看的是「模型生成」，不是「工具结果」；工具执行结果通常一次性返回。
- 实际工程：LLM 输出走 SSE 流式，工具调用结果在侧边/日志里一次性补全。

## 04 多 Agent 架构（Q11）

### Q11 你项目是多 Agent 主子架构吗？

**考察意图**：架构模式认知，看你能不能讲清拓扑和为什么这么选。

**答题要点**：

- 先答清拓扑：Supervisor（主 Agent 规划 + 分发）+ Worker（子 Agent 各管一摊），父子关系清晰。
- 对比其他模式：串行流水线、并行分工、对等协商、评审竞争，各适合什么场景。
- 为什么主子：任务可天然按领域拆分、统一入口、好管控。
- 主子架构的坑：主 Agent 易成瓶颈、子 Agent 间信息不共享——靠共享 State / 消息总线缓解。

## 06 工程落地（Q14–Q16）

### Q14 子任务挂了，比如数据抓回来空的，工作流怎么重试或降级？

**考察意图**：健壮性工程，别只会说「改 prompt」。

**答题要点**：

- 先判断错误可重试性：网络超时可重试，业务校验失败不可重试。
- 重试：指数退避 + 最大次数上限。
- 降级：数据抓空 → 返回兜底文案 / 跳过非关键步骤 / 标记降级。
- 幂等：写操作接口幂等，避免重复写数据。
- 可观测：全链路日志 + Trace，失败可定位复现。

### Q15 FastAPI 加 SSE 做流式，LangGraph 图状态机里怎么抓到每个节点的结果实时推前端？

**考察意图**：流式 + 图执行结合，是真实现过才答得好的考点。

**答题要点**：

- LangGraph 用 astream / astream_events，每个节点执行时对外发事件。
- 监听几类事件拿到中间态：节点开始/结束（on_chain_start/on_chain_end）、token 级增量（on_llm_stream）、工具开始/结束（on_tool_start/on_tool_end）。
- FastAPI 用 StreamingResponse + SSE（event-stream），把节点事件序列化后实时推给前端。

### Q16 为什么选 LangGraph 不直接用 LangChain？

**考察意图**：框架选型判断力，分清「组件库」和「图运行时」。

**答题要点**：

- 定位不同：LangChain 是组件库（Prompt 模板、检索器、工具、链），LangGraph 是图 / 状态机运行时。
- LangChain 的 Chain 是线性 DAG，多步循环、条件分支、回溯做不了。
- LangGraph 支持：显式状态、循环、条件边、checkpoint 持久化、human-in-the-loop、流式、并发子图。
- 结论：复杂有状态的多步 Agent 必须用图；LangGraph 可以和 LangChain 组件混用，不是二选一。

## 07 Agent 本质与循环（Q17–Q19）【补充】

### Q17 Agent 和 Chatbot 的本质区别在哪？

**考察意图**：Agent 岗第一道分水岭，看能否讲清「自主决策 + 行动」背后的系统含义，而不是背定义。

**答题要点**：

- Chatbot 的工作模型：用户输入 → LLM 推理 → 输出文本，一轮结束。
- Agent 的模型：用户输入 → 推理 → 决定调哪个工具 → 执行 → 观察结果 → 决定下一步 → 循环直到目标达成。
- Agent 相比 Chatbot 多出四大能力：感知（理解意图）、规划（任务拆解排序）、行动（调工具）、记忆（跨步骤/会话保留状态）。
- 加分点：主动指出「自主性是双刃剑」——权限给多会有危险操作，给少退化成 Chatbot；生产环境核心是设计安全的自主边界（权限、审批、审计）。

### Q18 Agentic Loop 是什么？ReAct 的消息格式怎么设计？

**考察意图**：概念好答，面试官会追问到底层消息协议（工具调用结构、结果回填角色），答不上来就暴露「只看过教程」。

**答题要点**：

- Agentic Loop 是 Agent 的流水线：Think（思考）→ Act（行动）→ Observe（观察）→ 循环。
- ReAct 是最经典实现，让模型在「推理」和「行动」之间交替。
- 关键在消息格式：模型只输出结构化的「工具调用请求」（工具名 + 参数 + 唯一 id），不自己执行；真正执行由外部 Executor 完成，再把结果回填给模型。
- 易踩坑点：工具调用 id 必须与结果一一对应，否则会报错；思考过程单独留存，便于审计。

### Q19 CoT → ReAct → ToT 的递进关系是什么？

**考察意图**：不是背定义，而是讲清「为什么需要从 CoT 升级到 ReAct」——真实任务需要和外部世界交互。

**答题要点**：

- CoT（思维链）：让模型一步步写出推理过程，但只能「想」，不能「做」。
- ReAct：把推理和行动交错，让 Agent 边想边做，真实任务里用来跟外部世界交互。
- ToT（思维树）：同时探索多条推理路径，选择最优方案。
- 递进逻辑：CoT 解决「推理」，ReAct 解决「推理 + 行动」，ToT 解决「多路径探索」；要能讲出项目里踩过「模型只想想得挺好、但什么都没做」的坑。

## 08 记忆系统设计（Q20）【补充】

### Q20 短期/长期记忆怎么设计？超出上下文窗口怎么办？有没有遇到过记忆污染？

**考察意图**：记忆是 Agent 落地最全的坑，考是否真处理过信息压缩、遗忘、冲突仲裁，而不是只看过论文。

**答题要点**：

- 分层设计：工作记忆（当前任务状态）、短期记忆（会话内上下文）、长期记忆（跨会话持久化）。
- 超出上下文窗口：滑动窗口保留最近 N 轮 + 摘要缓冲 + 长期记忆外置向量库按需检索。
- 长期记忆更新策略：写入时机、去重、过期淘汰要说清。
- 记忆污染：脏信息混入长期记忆会持续误导——靠来源标记、多轮信息冲突仲裁、定期清理来缓解。

## 09 工具调用健壮性（Q21–Q23）【补充】

### Q21 Agent 调了三个工具就死循环了，异常处理写在哪？

**考察意图**：高频「异常处理在哪写的」，看有没有工程兜底思维，而不是只会说「改 prompt」。

**答题要点**：

- 设最大执行步数上限，超限强制终止并兜底返回。
- 检测重复：连续多步无进展（结果无变化）触发停止或重规划。
- 超时与熔断：单步工具设超时，连续失败则熔断降级。
- 兜底：异常分支返回可理解的失败文案，同时留全链路日志便于回溯。

### Q22 工具返回超长结果把 token 撑满了怎么办？连续三次返回相同数据怎么办？

**考察意图**：工程混沌假设，看有没有从 Demo 走向生产的意识。

**答题要点**：

- 超长结果：在工具侧做结果预剪裁（截断、摘要、只取关键字段），避免撑爆 token 预算。
- 连续相同数据：做低差异检测，结果变化量低于阈值就判定异常，触发重规划或停掉，防止空转死循环。

### Q23 给 Agent 配了十几个工具，怎么避免模型选错工具？

**考察意图**：工具治理，企业端高度关注的痛点。

**答题要点**：

- 工具描述模板化规范：名称唯一、描述清楚，并加入失败案例、适用边界，减少歧义。
- Prompt 显式约束：每步只允许推荐一个最可能的工具，减少多工具并行引发的幻觉。
- 参数枚举化 + 默认值 + 必填校验，降低填参出错概率。

## 10 MCP 与安全进阶（Q24–Q25）【补充】

### Q24 MCP 和 A2A 到底什么关系？

**考察意图**：分清垂直连接和水平连接，别把两条协议当成竞争关系。

**答题要点**：

- MCP（Model Context Protocol）：垂直连接，解决 Agent 怎么调用外部工具和数据——「我能用什么」。
- A2A（Agent-to-Agent Protocol）：水平连接，解决 Agent 之间怎么互相发现、委托任务、交换结果——「我能和谁合作」。
- 两者是严格的分层协作关系，不是二选一；工具治理复杂度从 O(N×M) 降到 O(N+M)。

### Q25 MCP 实际使用中有什么安全风险？

**考察意图**：批判性认知 + 安全视野，答到攻击面与防御方案的远超「会背概念」。

**答题要点**：

- 核心风险：Context Poisoning（上下文污染）——工具描述会被全量注入上下文，恶意指令可借工具元数据污染推理，已被 OWASP 列为 LLM 应用头号漏洞。
- 三大攻击面：上下文操纵、服务端注入（Server-Side Injection）、跨 server 危害。
- 防御方案：工具描述审计、权限最小化、传输加密、第三方 server 安全审查、输出侧过滤。

## 11 RAG 与模型进阶（Q26–Q28）【补充】

### Q26 RAG 知识库文档更新了怎么办？总不能每次全量重建吧？

**考察意图**：经典工程题，考增量更新与 chunk 边界意识。

**答题要点**：

- 只答「找到变的 chunk 更新向量」不够——面试官会追问「内容变了，chunk 边界还和原来一样吗」。
- 用 hash / 版本号检测变更，先删后增，按文档或段落粒度做增量。
- 变更大的文档重新切分重嵌入，局部微调才做局部更新，兼顾一致性与成本。

### Q27 检索质量差怎么办？分块策略、向量维度、rerank 怎么定？

**考察意图**：不问「什么是 RAG」，问「质量差怎么办」，看是否真调过检索管道。

**答题要点**：

- 分块策略：大小、重叠量、语义边界，避免把语义切断。
- embedding 向量维度按模型能力选，匹配存储与算力。
- rerank 必要性：召回靠向量宽召回，精排靠 rerank（如 Cross-Encoder）提准确率。
- 多路召回 + 混合检索，平衡精度和召回。

### Q28 微调和 RAG 怎么选？怎么缓解大模型幻觉？

**考察意图**：基础但高频，看技术选型判断力。

**答题要点**：

- 微调：教模型领域知识/风格/格式，训练成本高、更新慢；RAG：注入外部知识，实时更新、可溯源、成本低、可控性强。
- 幻觉缓解：RAG 挂知识、prompt 约束「不知道就直说」、联网查证、让模型自检并标注不确定、结果引用溯源。
- 结论：知识时效性和可追溯用 RAG，稳定能力/风格用微调，实际常组合使用。
