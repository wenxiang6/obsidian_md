## 模块一：生命周期专题（你重点要求，面试高频必问）

### 第 1 题：请详细讲 HarmonyOS UIAbility 的完整生命周期，每个回调做什么？

**核心知识点** UIAbility 是 Stage 模型下应用的入口组件，生命周期共 4 个状态、6 个回调：

表格

|状态|回调|触发时机|典型操作|
|---|---|---|---|
|创建|`onCreate()`|Ability 首次创建，只调一次|初始化全局变量、注册监听、加载资源|
|前台|`onForeground()`|从后台切到前台，每次可见都调|恢复播放、刷新数据、重新注册传感器|
|获取焦点|`onWindowStageCreate()`|窗口创建，可获取 WindowStage|设置 UI 页面、设置窗口属性、注册键盘监听|
|失去焦点|`onWindowStageDestroy()`|窗口销毁前|注销键盘监听、释放窗口资源|
|后台|`onBackground()`|切到后台，每次不可见都调|暂停播放、保存数据、注销传感器、停止动画|
|销毁|`onDestroy()`|Ability 彻底销毁，只调一次|释放全局资源、反注册监听、断开连接|

**记忆口诀**：Create 一次 → Foreground/Background 反复切 → Destroy 一次；WindowStageCreate/Destroy 跟窗口走。

**你的项目结合**：灵锡项目在`onWindowStageCreate`里设置主页面并注册软键盘高度监听，解决键盘遮挡问题；`onBackground`里暂停扫码和定位，降低功耗。

### 第 2 题：鸿蒙页面（Page）和自定义组件的生命周期有哪些？和 UIAbility 什么关系？

**核心知识点**

- **页面级（被`router`或`Navigation`管理的页面）**：没有独立生命周期回调，靠`aboutToAppear`/`aboutToDisappear`感知。
- **自定义组件生命周期**：
    - `aboutToAppear()`：组件即将出现，**只调一次**，适合初始化数据、注册事件。
    - `aboutToDisappear()`：组件即将销毁，**只调一次**，适合清理定时器、反注册监听、销毁 WebView。
    - `aboutToUpdate()`：组件即将重新渲染，可做更新前拦截（NEXT 中较少用）。
- **关系**：UIAbility 管整个应用实例，页面 / 组件管 UI 层。Ability 销毁 → 所有页面组件销毁；页面销毁 ≠ Ability 销毁（Ability 可能还在后台）。

**你的项目结合**：灵锡项目每个用 WebView 的页面，在`aboutToDisappear`里主动`controller.destroy()`释放 WebView，防止内存泄漏。

### 第 3 题：鸿蒙 UIAbility 生命周期 vs Android Activity 生命周期，一一对应讲清楚？

**核心知识点（对比表，直接背）**

表格

|鸿蒙 UIAbility|Android Activity|区别|
|---|---|---|
|`onCreate()`|`onCreate()`|都是首次创建，鸿蒙只初始化，不加载 UI|
|`onWindowStageCreate()`|`onCreate()`里 setContentView|鸿蒙把 "加载 UI" 单独拆到窗口创建回调|
|`onForeground()`|`onStart()` + `onResume()`|鸿蒙把 "可见 + 获焦点" 合并成一个回调|
|`onBackground()`|`onPause()` + `onStop()`|鸿蒙把 "失焦 + 不可见" 合并成一个回调|
|`onWindowStageDestroy()`|无独立回调|鸿蒙窗口资源单独管理|
|`onDestroy()`|`onDestroy()`|都是最终销毁|

**关键差异总结**：

1. Android 是 6 个回调（create/start/resume/pause/stop/destroy），鸿蒙精简成 4 个核心回调（create/foreground/background/destroy）+ 2 个窗口回调。
2. Android 把 "可见" 和 "获焦点" 分开（onStart/onResume），鸿蒙合并了，更简洁。
3. 鸿蒙多了`WindowStage`概念，UI 加载和窗口管理解耦。
4. Android 一个 App 可以有多个 Activity 栈，鸿蒙一个 UIAbility 对应一个页面栈，多 Ability 场景用`UIAbility`+`Want`跳转。

**你的项目结合**：你有 Android（快电项目）和鸿蒙（灵锡、淘宝）双端经验，面试时直接说 "我做过 Android 转鸿蒙迁移，最深的感受是生命周期回调少了一半，窗口管理更清晰，但要注意鸿蒙没有 onResume，恢复逻辑全放 onForeground"。

### 第 4 题：Android Service 的生命周期，鸿蒙用什么替代？

**核心知识点**

- Android Service：`onCreate → onStartCommand → onDestroy`，或绑定服务`onBind → onUnbind`。
- 鸿蒙 Stage 模型下没有传统 Service，用以下替代：
    - **后台任务（BackgroundTask）**：短时后台操作，如下载、音乐播放。
    - **连续任务（ContinuousTask）**：需要长时间后台运行，如导航、计步，需申请权限并显示通知。
    - **Agent**：ExtensionAbility 的一种，用于后台数据同步、推送等。
    - **WorkScheduler**：延迟 / 定时任务，类似 Android WorkManager。
- 鸿蒙后台限制比 Android 更严，不允许随意后台保活，必须走系统规范的后台任务 API。

### 第 5 题：页面跳转（router/Navigation）时，生命周期怎么触发？返回栈怎么管理？

**核心知识点**

- **router 模式**：
    - `router.pushUrl()`：新页面`aboutToAppear`，旧页面不销毁（压栈），旧页面`aboutToDisappear`**不触发**（还在栈里）。
    - `router.back()`：当前页`aboutToDisappear`，上一页`aboutToAppear`**不触发**（一直在）。
    - `router.replaceUrl()`：当前页销毁，新页创建。
- **Navigation 模式（NEXT 推荐）**：
    - 用`navPathStack`管理路由栈，`pushPath`/`pop`/`replace`。
    - 生命周期触发逻辑和 router 类似，但 Navigation 支持更灵活的栈管理和转场动画。
- **注意坑**：用 router.pushUrl 跳转后，旧页面的定时器如果没停，会继续跑，导致内存泄漏和性能问题。

**你的项目结合**：灵锡项目用 Navigation 做页面路由，乘车码页面跳转到账单页时，在`aboutToDisappear`里暂停二维码刷新定时器，返回时在`aboutToAppear`恢复。

## 模块二：ArkTS / ArkUI 基础

### 第 6 题：ArkTS 和 TypeScript 是什么关系？ArkTS 在 TS 基础上加了什么？

**核心知识点**

- ArkTS 是 TypeScript 的**超集**，兼容 TS 语法，在其基础上扩展：
    1. **声明式 UI 语法**：`build()`函数里写组件，链式调用配置属性。
    2. **装饰器体系**：`@Component`、`@Entry`、`@State`、`@Prop`、`@Link`等。
    3. **强类型约束**：比 TS 更严格，禁止 any 类型（严格模式下），编译期做类型检查。
    4. **状态驱动渲染**：状态变量变更自动触发 UI 刷新。
    5. **ArkUI 组件库**：内置 Text、Button、List、Column 等组件。
- NEXT 中 ArkTS 是唯一开发语言，JS 范式（hml+css+js）已被移除。

### 第 7 题：@State、@Prop、@Link、@ObjectLink、@Provide/@Consume、@Observed，数据流向和适用场景全梳理

**核心知识点（对比表）**

表格

|装饰器|数据流向|适用场景|注意点|
|---|---|---|---|
|`@State`|组件内部，私有|组件自身状态，如开关、计数|必须初始化，变更触发当前组件刷新|
|`@Prop`|父→子，单向|父传子，子只展示不修改|简单类型，子修改不影响父|
|`@Link`|父↔子，双向|父子共享状态，子修改父同步|父组件用`$$变量名`传入|
|`@ObjectLink`|父↔子，双向（复杂对象）|嵌套对象 / 数组的双向同步|配合`@Observed`装饰的类使用|
|`@Observed`|标记类|被`@ObjectLink`引用的类必须加|不加则嵌套属性变更不触发刷新|
|`@Provide`|祖先→后代，跨层|跨多层组件传值，不用逐层传|按变量名匹配，类似 React Context|
|`@Consume`|消费 @Provide|后代组件获取祖先的值|双向同步|

**记忆口诀**：State 自己用，Prop 父传子只读，Link 父子双向，ObjectLink 复杂对象双向，Provide/Consume 跨层透传。

**你的项目结合**：灵锡项目钱包模块用 @ObjectLink+@Observed 管理订单对象，修改订单里的嵌套字段（如订单状态）能正确触发 UI 刷新；用 @Provide/@Consume 在 Tab 页和深层子页面间传用户信息，避免逐层传参。

### 第 8 题：声明式 UI 的渲染原理是什么？状态变更后怎么更新？

**核心知识点**

1. 声明式 UI = 描述 "UI 长什么样"，不直接操作 DOM / 控件。
2. 状态变量（@State 等）变更 → 框架标记脏组件 → 重新执行`build()` → 生成新的 UI 描述树 → Diff 算法对比新旧树 → 只更新变化的节点。
3. 性能关键点：
    - 避免在`build()`里做耗时计算。
    - 用`@Memo`缓存计算结果。
    - 大列表用`LazyForEach`懒加载。
    - 减少不必要的状态变量，状态变更范围越小越好。

---

### 第 9 题：ForEach 和 LazyForEach 什么区别？大列表怎么优化？

**核心知识点**

- `ForEach`：一次性渲染所有子组件，数据量大时卡顿、内存高。
- `LazyForEach`：懒加载，只渲染可视区域内的 item，滚动时回收复用，类似 Android RecyclerView。
- `LazyForEach`必须实现`IDataSource`接口：`totalCount()`、`getData(index)`、`registerDataChangeListener()`等。
- 列表优化手段：
    1. 用`LazyForEach`替代`ForEach`。
    2. item 高度固定，用`cachedCount`预加载。
    3. 避免 item 里有复杂计算。
    4. 图片用`Image`的`autoResize`和缓存。
    5. 用`List`的`onScrollIndex`做曝光统计。

**你的项目结合**：灵锡账单列表用 LazyForEach 实现，配合 cachedCount=5 预加载，滚动流畅；地铁查询宝的线路列表也是 LazyForEach。

### 第 10 题：自定义组件怎么设计？怎么传参、怎么回调事件？

**核心知识点**

- 定义：`@Component struct MyComponent { ... }`
- 传参：构造函数参数 + `@Prop`/`@Link`装饰。
- 事件回调：用函数类型参数，如`onClick?: () => void`，父组件传入回调。
- 插槽：用`@BuilderParam`实现自定义插槽，类似 Android 的自定义 View。
- 组件通信方式总结：
    1. 父子：@Prop/@Link/@ObjectLink。
    2. 跨层：@Provide/@Consume。
    3. 全局：AppStorage/LocalStorage。
    4. 事件总线：EventHub（UIAbility 级）或自己实现。
    5. 页面间：router 传参 / Navigation 传参。

## 模块三：HarmonyOS NEXT 系统机制

### 第 11 题：HarmonyOS NEXT（纯血鸿蒙）和兼容版鸿蒙（HarmonyOS 4 及以前）最大区别？

**核心知识点**

1. **内核**：NEXT 完全去掉 AOSP 安卓兼容层，只保留鸿蒙内核（微内核架构）。
2. **应用包**：NEXT 只支持`.hap`，不再支持`.apk`；兼容版同时支持 hap 和 apk。
3. **开发模型**：NEXT 只支持 Stage 模型，FA 模型彻底移除；只支持 ArkTS 声明式开发，JS 范式移除。
4. **API**：NEXT 用 API 12+，大量旧 API 废弃，系统能力更统一。
5. **安全**：沙箱机制更强，权限模型重构，应用间隔离更严格。
6. **分布式**：NEXT 分布式能力更完善，跨设备流转更顺畅。

**你的项目结合**：你做的淘宝 JSBridge 和灵锡都是 NEXT 纯血鸿蒙项目，用的 Stage 模型 + ArkTS，面试时强调 "我做的是纯血 NEXT，不是兼容版"。

### 第 12 题：Stage 模型详解：UIAbility、ExtensionAbility、Want 分别是什么？

**核心知识点**

- **UIAbility**：应用入口组件，有 UI，对应一个页面栈，负责用户交互。一个 App 可以有多个 UIAbility。
- **ExtensionAbility**：无 UI 的扩展组件，用于特定场景，如：
    - ServiceExtensionAbility：后台服务（NEXT 中逐渐被 BackgroundTask 替代）。
    - FormExtensionAbility：桌面卡片 / 元服务。
    - PushExtensionAbility：推送接收。
    - ShareExtensionAbility：系统分享。
- **Want**：组件间通信的载体，类似 Android 的 Intent，包含目标组件信息（bundleName、abilityName）和参数。
    - 显式 Want：指定具体 Ability。
    - 隐式 Want：只指定 action 和 uri，由系统匹配。

### 第 13 题：UIAbility 的三种启动模式（singleton/multiton/specified）什么区别？

**核心知识点**

- **singleton（单例）**：整个系统只有一个实例，每次启动都复用，如主界面。默认模式。
- **multiton（多实例）**：每次启动都创建新实例，如文档编辑器打开多个文档。
- **specified（指定实例）**：根据`key`标识实例，相同 key 复用，不同 key 新建，如淘宝小程序每个小程序一个实例。
- 配置位置：`module.json5`里的`abilities` → `launchType`字段。

**你的项目结合**：淘宝小程序鸿蒙适配用的 MegaAbility，本质就是多实例 / 指定实例模式，每个小程序运行在独立实例中，互不干扰。

### 第 14 题：鸿蒙的权限模型是什么？和 Android 权限有什么区别？

**核心知识点**

- 鸿蒙权限分三类：
    1. **normal（普通权限）**：默认授予，如网络访问。
    2. **system_basic（系统基础权限）**：需申请，用户授权，如相机、定位。
    3. **system_core（系统核心权限）**：仅系统应用可用，第三方申请不了。
- 申请流程：`module.json5`声明 → 运行时`requestPermissionsFromUser`弹窗 → 用户授权 → 回调结果。
- 和 Android 区别：
    1. 鸿蒙权限分级更清晰，normal 权限不用弹窗。
    2. 鸿蒙沙箱更严格，文件访问默认只能访问自己沙箱目录。
    3. 鸿蒙权限和 Ability 绑定，不是整个应用共享。

**你的项目结合**：淘宝 JSBridge 项目实现了小程序 scope 分级授权闭环，把鸿蒙系统权限映射成小程序权限，用户授权后缓存状态，避免重复弹窗。

### 第 15 题：沙箱机制是什么？应用能访问哪些目录？怎么共享文件？

**核心知识点**

- 每个应用有独立沙箱目录，其他应用无法访问。
- 可访问目录：
    - `context.filesDir`：应用文件目录，持久化。
    - `context.cacheDir`：缓存目录，系统可清理。
    - `context.tempDir`：临时目录。
- 不能直接访问：其他应用沙箱、系统根目录、用户相册（需权限 + FilePicker）。
- 共享文件方式：
    1. **FilePicker**：系统文件选择器，用户授权后获取 URI。
    2. **PhotoViewPicker**：选择图片 / 视频。
    3. **公共目录**：通过`@ohos.file.picker`访问。
    4. **应用间分享**：用 Want+URI 临时授权。

**你的项目结合**：淘宝 JSBridge 项目的文件系统模块（你独立完成 20 + 方法），就是在沙箱限制下实现文件读写、目录操作、路径转换，把小程序的文件 API 映射到鸿蒙沙箱。

## 模块四：性能调优（岗位重点：内存、功耗、兼容性）

### 第 16 题：鸿蒙应用内存泄漏常见场景有哪些？怎么排查和修复？

**核心知识点**

- **常见泄漏场景**：
    1. 定时器（setInterval/setTimeout）未清理。
    2. 事件监听（emitter/EventHub）未反注册。
    3. WebView 实例未销毁。
    4. 闭包持有组件实例，组件销毁后闭包还在。
    5. 长生命周期对象（如全局单例）持有短生命周期 UI 组件引用。
    6. 动画未停止。
- **排查工具**：DevEco Studio → Profiler → Memory，抓内存快照，对比操作前后快照，找未释放对象。
- **修复手段**：
    1. `aboutToDisappear`里清理所有定时器、监听、动画。
    2. WebView 用`controller.destroy()`销毁。
    3. 避免全局对象持有组件引用。
    4. 用 WeakReference 持有可能泄漏的对象。

**你的项目结合**：灵锡项目 WebView 页面多，你在`aboutToDisappear`里统一销毁 WebView 和注销 EventHub 事件，Profiler 验证内存平稳下降；淘宝项目排查过小程序页面关闭后 Bridge 对象未释放的问题。

### 第 17 题：功耗优化从哪些维度入手？

**核心知识点**

1. **CPU**：避免主线程耗时操作，用 TaskPool/Worker；减少频繁唤醒。
2. **网络**：合并请求，避免轮询，用推送代替轮询；减少后台网络。
3. **定位 / 传感器**：不用时及时注销，降低更新频率。
4. **屏幕**：减少不必要的亮屏，用`keepScreenOn`谨慎。
5. **UI 渲染**：减少过度渲染，避免频繁状态刷新，列表用 LazyForEach。
6. **后台**：切后台时暂停动画、定时器、定位、播放。
7. **任务调度**：用 WorkScheduler 在合适时机执行延迟任务。

**你的项目结合**：灵锡乘车码页面在`onBackground`时暂停定位和二维码刷新，`onForeground`恢复，实测后台功耗降低明显。

### 第 18 题：启动速度怎么优化？

**核心知识点**

- 冷启动流程：Application 初始化 → Ability onCreate → WindowStageCreate → 首帧渲染。
- 优化手段：
    1. `onCreate`里不做耗时操作，延迟初始化非必要模块。
    2. 首屏 UI 尽量简单，用骨架屏。
    3. 图片资源压缩，用合适分辨率。
    4. 减少首屏依赖的模块数量。
    5. 用`AppStorage`做全局状态，避免重复读取。
    6. 按需加载模块（动态 import）。
- 工具：Profiler → Startup，看各阶段耗时。

### 第 19 题：渲染性能 / 帧率优化怎么做？

**核心知识点**

1. 减少`build()`里的计算，用`@Memo`缓存。
2. 减少状态变量数量，缩小刷新范围（用`@Observed`+`@ObjectLink`精确刷新）。
3. 大列表 LazyForEach + cachedCount。
4. 避免频繁调用`forceUpdate`。
5. 动画用系统动画 API，不要用 setTimeout 手动改状态做动画。
6. 图片用`autoResize`，避免大图直接渲染。
7. 用`RenderGroup`对复杂组件做离屏渲染缓存。
8. Profiler → GPU/Frame 看帧率和掉帧。

### 第 20 题：多机型兼容性问题怎么处理？讲一个你的真实案例。

**核心知识点**

## 模块五：架构与设计模式

### 第 22 题：MVC、MVVM、VIPER 在鸿蒙里怎么落地？你选哪个？

**核心知识点**

- **MVC**：Model（数据）、View（UI）、Controller（逻辑）。鸿蒙里 Controller 可以是一个单独的类，但 View 和 Controller 容易耦合。
- **MVVM**：Model、View、ViewModel。鸿蒙声明式 UI 天然适合 MVVM：
    - View = `@Component`组件，只负责展示。
    - ViewModel = 用`@Observed`装饰的类，持有业务逻辑和状态。
    - Model = 数据模型 / 网络请求。
    - 数据双向绑定通过`@State`/`@ObjectLink`实现。
- **VIPER**：View、Interactor、Presenter、Entity、Router。分层最细，适合大型团队复杂项目，但代码量大。
- **我的选择**：中小型项目用 MVVM，开发效率高，鸿蒙原生支持好；大型复杂项目可以在 MVVM 基础上加 Router 层，接近 VIPER 思路。

**你的项目结合**：灵锡大型市民服务应用用 MVVM 分层，业务逻辑抽离到 ViewModel，UI 组件只做展示，便于单元测试和多人协作。

### 第 23 题：鸿蒙状态管理方案怎么选？（组件级 / 页面级 / 应用级）

**核心知识点**

表格

|层级|方案|场景|
|---|---|---|
|组件内|@State|组件私有状态|
|父子|@Prop/@Link/@ObjectLink|父子组件传值|
|跨层|@Provide/@Consume|祖孙组件透传|
|页面级|LocalStorage|单个 UIAbility 内共享|
|应用级|AppStorage|整个应用全局共享|
|持久化|PersistentStorage|持久化到磁盘，重启不丢|
|跨设备|DistributedStorage|多设备同步|

**你的项目结合**：淘宝小程序用 PersistentStorage 缓存用户授权状态和小程序配置；灵锡用 AppStorage 存全局用户登录态。

### 第 24 题：组件化 / 模块化怎么做？

**核心知识点**

1. **HSP（Harmony Shared Package）**：共享包，可被多个 HAP 依赖，放公共组件、工具类、网络层。
2. **HAR（Harmony Archive）**：静态共享包，编译时打包进 HAP。
3. **HAP**：应用包，可独立运行。
4. 模块划分：基础层（工具、网络、存储）、业务层（各业务模块）、应用层（主入口）。
5. 模块间通信：通过对外暴露的接口，避免直接依赖实现。

### 第 31 题：WebView 在鸿蒙 NEXT 里有哪些坑？你怎么处理的？

**核心知识点**

- **常见坑**：
    1. **内存泄漏**：WebView 实例不销毁会泄漏，必须`controller.destroy()`。
    2. **双向通信**：JS 调 Native 用`javaScriptProxy`注册对象；Native 调 JS 用`runJavaScript`。
    3. **沙箱限制**：WebView 不能直接访问本地文件，需用`webview.WebUtils`或自定义拦截。
    4. **生命周期同步**：页面切后台 WebView 要暂停，切前台恢复。
    5. **Cookie 管理**：鸿蒙 WebView 的 Cookie 和浏览器不共享，需单独管理。
    6. **性能**：WebView 初始化慢，可预加载。
- **你的处理**：灵锡项目大量 WebView 页面，封装了通用 WebView 组件，统一处理生命周期（aboutToAppear 加载、aboutToDisappear 销毁）、双向通信（EventHub+javaScriptProxy）、错误兜底。

### 第 32 题：Android 项目迁移到鸿蒙，你有哪些经验？踩过什么坑？

**核心知识点（你的双端迁移经验，加分项）**

- **迁移步骤**：
    1. 梳理 Android 项目功能模块和依赖。
    2. 架构设计：MVVM 分层，网络层、存储层、UI 层分别迁移。

- **踩过的坑**：

    2. 列表 RecyclerView→LazyForEach，需要实现 IDataSource。
    3. 路由管理差异，Android startActivity→router/Navigation。
    4. 第三方 SDK 缺失，需要找鸿蒙替代或自己封装。

## 模块九：跨端加分项（岗位优先条件）

### 第 33 题：Flutter 和鸿蒙原生混合集成会遇到什么问题？怎么优化性能？

**核心知识点**

- **混合集成难点**：
    1. 平台通道（MethodChannel）通信，Flutter 调鸿蒙原生能力。
    2. 生命周期同步，Flutter 页面和鸿蒙页面生命周期对齐。
    3. 内存管理，Flutter 引擎和鸿蒙各管各的内存。
    4. 页面跳转和返回栈管理。
    5. 渲染性能，Flutter 用 Skia/Impeller 渲染，和原生渲染混合可能有帧率问题。
- **性能优化**：
    1. 减少频繁跨平台通信，批量传递数据。
    2. 大列表用 Flutter 自己的 ListView 懒加载。
    3. 及时释放 Flutter 引擎资源。
    4. 图片缓存和预加载。

**核心知识点**
