01 · 场景

Agent 不是外挂脚本，是组织里有工位的数字员工

多数 Agent 平台止步于「人能调起一个 Agent」。音巢（Clawith）往前走了一步：把企业的组织架构、汇报关系、目标管理整套搬进平台，让 Agent 和人类成员一样有部门、有关系、有 OKR、有日报——管理能力第一次成为平台的一等公民。

定位 · 一句话

Agent 在音巢里同时是「被管理者」和「管理动作的自动化执行者」——OKR Agent 自己背着 OKR，同时替管理者把催收、汇总、报告这些最消耗耐心的动作全部自动化。

这带来一个独特的自洽：管理系统（OKR 数据模型与工具）和管理者（OKR Agent）用的是同一套接口。人能做的 OKR 操作，Agent 通过 13 个工具全能做；Agent 做不到的（比如制定公司级 O），人不通过 Agent 也能在界面上做。

02 · 设计

三个关键决策：Agent 化、软耦合、不可变流水

OKR 模块最反直觉的设计是：业务逻辑大头不在代码里，而在一个 Agent 的提示词和工具调用里。这不是偷懒，是深思熟虑的架构取舍。

OKR 管理逻辑：写死的调度代码 vs Agent + 工具 K1

选项

① 传统做法：定时任务 + 模板消息 + 固定报表生成逻辑全部硬编码
② Agent 化：平台只提供 13 个 OKR 工具和催收入口，「怎么催、怎么汇总、怎么写月报」交给 OKR Agent 的模型决策

决定

Agent + 工具。工具是确定性的写路径，Agent 是可对话的智能层

原因

催收话术要个性化（给人和给 Agent 的催收文案完全不同，见 _human_request_message / _agent_request_message）；进展要从自然语言对话里提炼（member_daily_reports 存的是 OKR Agent 蒸馏后的版本而非原始聊天记录）；月报要有洞察而非流水账。这些本质都是语言任务，硬编码做不了。

代价

行为有模型的不确定性，需要 okr_settings 做开关治理（enabled / daily_report_enabled），且写路径必须用工具兜底确定性——工具内部直接写库，不信模型的口头承诺。

外部身份源耦合方式：强外键 vs 软耦合 K2

选项

① 部门 / 成员表对身份提供方（IdentityProvider）、平台账号（User）建强外键
② 软耦合：provider_id、user_id 只存 UUID 不建 FK，代码注释明确写「No FK - soft coupling」

决定

软耦合，关联完整性由程序查询保证

原因

外部源是易变的：企业可能换身份提供方、解绑再重绑、成员先同步进来后注册平台账号。强外键会把同步逻辑和账号生命周期死死绑在一起，一次解绑就可能级联失败。软耦合让「同步」「绑定」「使用」三件事可以独立演进。

代价

数据库层面失去引用完整性保护，悬空引用要靠应用层查询时兜底（如催收时校验成员 status == "active"）；写代码时不能有「JOIN 一定有结果」的假设。

KR 进度记录：覆盖式更新 vs 不可变流水 K3

选项

① KR 只存 current_value，更新即覆盖
② KR 存当前值，同时每次变更写一条 okr_progress_logs（previous_value / new_value / source / note），流水不可变

决定

当前值 + 不可变流水双写

原因

流水让进度曲线可视化、变更可审计：source 字段区分 okr_agent / manual / self_report，谁改的、什么时候改的、附注了什么一目了然。模型类的 docstring 明说设计意图："Immutable log entry … Enables full progress curve visualization and audit trail."

代价

每次 KR 更新多一条写；聚合查询要走流水表。换来的审计能力对「Agent 自动改 KR」这种场景是刚需——没有流水，Agent 改错了数你都不知道。

04 · 伪代码

两个最小闭环：催收调度 + 进度聚合

剥掉工程细节后，OKR 自动化的核心就两件事：到点把该报的人找齐、逐个触达、幂等落库；以及把离散的进度更新聚合成可读的曲线。

伪代码 1 · 每日催收调度（okr_daily_collection 的最小骨架）

async def trigger_daily_collection_for_tenant(tenant_id, report_day=today()): # ① 租户闸门：三道开关缺一即拒 settings = await db.get(OKRSettings, tenant_id=tenant_id) if not (settings and settings.enabled and settings.daily_report_enabled): raise ValueError("OKR 日报催收未启用") okr_agent = await db.get(Agent, id=settings.okr_agent_id, deleted_at=None) if not okr_agent: raise ValueError("租户未配置 OKR Agent") # ② 名单圈定：权威来源是关系图谱（显式订阅），不是目录可见性 humans = await db.query(AgentRelationship.join(OrgMember) .where(agent_id=okr_agent.id, OrgMember.status == "active")) agents = await db.query(AgentAgentRelationship.join(Agent) .where(agent_id=okr_agent.id, Agent.is_system == False, Agent.status.notin_(["stopped", "error"]))) # ③ 分流触达：人发提醒消息，Agent 发执行型 prompt for m in humans: msg = human_request_message(m.display_name, report_day) # 个性化文案 await send_as_okr_agent(to=m, content=msg) # IM / 站内触达 for a in agents: prompt = agent_collection_prompt(a, report_day) # "自检 focus.md 并回报进展" await enqueue_agent_run(a, prompt) # 入队让目标 Agent 跑一轮 # ④ 回报沉淀：成员回复后由 OKR Agent 蒸馏，唯一约束保证幂等 # upsert_member_daily_report: ON CONFLICT (tenant, member_type, member_id, report_date) DO UPDATE

伪代码 2 · KR 进度更新与聚合（不可变流水 + 向 O 滚动）

async def update_kr_progress(kr_id, new_value, source, note=None): # source ∈ {"okr_agent", "manual", "self_report"} —— 谁改的必须留名 async with db.transaction(): kr = await db.get_for_update(OKRKeyResult, kr_id) # 行锁防并发覆盖 db.add(OKRProgressLog(kr_id=kr.id, previous_value=kr.current_value, # 不可变流水 new_value=new_value, source=source, note=note)) kr.current_value = new_value # 当前值双写 kr.status = classify(kr) # on_track/at_risk/behind/completed async def objective_progress(objective_id) -> float: # O 没有自己的 current_value：由名下 KR 完成度滚动聚合 krs = await db.query(OKRKeyResult.where(objective_id=objective_id)) return mean([min(kr.current_value / kr.target_value, 1.0) for kr in krs]) async def progress_curve(kr_id, period): # 进度曲线 = 流水按时间重放，前端 OKR 页直接可用 logs = await db.query(OKRProgressLog.where(kr_id=kr_id) .order_by(created_at)) return [(log.created_at, log.new_value) for log in logs]
为什么这套伪代码就是最小闭环

催收闭环（闸门 → 名单 → 触达 → 幂等沉淀）回答了「管理动作怎么自动发生」；进度闭环（流水双写 → 状态机 → 向 O 聚合 → 曲线重放）回答了「目标进展怎么可信地度量」。两个闭环拼起来，就是 OKR Agent 每天实际在跑的全部逻辑——剩下的都是 LLM 层的文案与洞察，不影响数据正确性。

05 · 面试 QA

六道题，从设计动机问到数据一致性

Q1 · 为什么 OKR 管理要用「Agent + 工具」实现，而不是写死的业务逻辑？

音巢的分层很清晰：确定性的事交给工具，语言性的事交给 Agent。创建 O/KR、更新进度、写日报这些写路径由 13 个内置工具承载，工具内部直接操作数据库，行为完全确定；而「给谁催、用什么话术催、从一段闲聊里提炼出今天的进展、月报里写什么洞察」本质是语言任务，硬编码模板做不到个性化。音巢的实现里这个分界肉眼可见：okr_daily_collection 里人的催收文案和 Agent 的催收 prompt 是两套模板（_human_request_message vs _agent_collection_prompt），因为对象不同，沟通方式本质不同。另一个收益是可对话化：成员可以直接跟 OKR Agent 说「我这个月 KR 进度帮我更新到 60%」，Agent 调 update_kr_progress 完成——管理系统第一次有了自然语言界面。代价是行为不确定性，所以治理开关（okr_settings 的 enabled/daily_report_enabled）和只许 OKR Agent 用的工具配置（okr_agent_only）必须配套。

Q2 · 组织架构从外部身份源同步，本地修改与外部源冲突时怎么处理？

音巢的立场是外部源为准，本地不养可编辑副本。org_sync_service 是 provider-based 的同步器，部门/成员以身份提供方的数据为权威；本地字段分两类——从外部来的（name、email、title、department_id）同步时覆盖，本地派生的（拼音检索字段 name_translit_full/initial、账号软绑定 user_id）同步时保留或重建。模型设计上，org_members 对 provider_id 和 user_id 都是软耦合（注释明确 "No FK - soft coupling"），这避免了「换身份提供方」「成员先同步后注册」这些现实场景被外键卡死。工程上的关键推论：应用层永远不能假设 JOIN 必有结果——催收名单圈定时显式过滤 OrgMember.status == "active"，就是在应用层兜软耦合的引用完整性。

Q3 · 关系图谱（agent_relationships / agent_agent_relationships）在平台里到底起什么作用？

它是「谁可以向谁派活」的显式声明，三个消费点：① OKR 催收名单的权威来源——daily_collection 代码注释明说 "Directory visibility is intentionally not the source of truth here"，催收范围是关系图谱这份显式订阅清单，不随目录权限漂移；② OKR Agent 的管理半径——okr_agent_hook 在新成员创建时自动把他和 OKR Agent 建边，组织扩张时催收名单自动生长；③ Agent 间的协作拓扑——Agent-Agent 边定义数字员工之间的协作关系，daily_collection 据此找出「受 OKR Agent 管理的 Agent」（排除 stopped/error 和系统 Agent）。设计上值得一提的取舍：这两张表在 models/org.py 里而非独立模型文件，因为关系图谱的本质是组织图的边，和部门/成员节点是同一个聚合。

Q4 · 自动催收怎么避免变成骚扰？频控和边界在哪里？

三层边界：① 开关层——okr_settings 按租户控制 enabled / daily_report_enabled，催收触发函数进来先过三道闸门（开关、日报开关、okr_agent_id 配置），任一缺失直接抛错拒绝，不存在「默认全员轰炸」；② 名单层——催收对象来自关系图谱这份显式清单，只有和 OKR Agent 建立了关系的成员才会被催，未订阅者天然免疫；③ 节奏层——一天一次由调度触发（而非 Agent 自主高频追问），且 legacy 的每日回复触发器会被清理（_cleanup_legacy_daily_reply_triggers），防止历史配置叠加造成重复触达。更深一层的答案在内容侧：催收消息是个性化生成的而非模板群发，对人是轻提醒、对 Agent 是执行任务——骚扰的本质是「无信息量的高频打扰」，个性化和一天一次分别从内容与频率两端压住它。

Q5 · 企业知识（enterprise_info）是怎么进入 Agent 上下文的？写入权为什么在管理员手里？

链路是「集中管理 → Pub/Sub 通知 → 本地拉取」：管理员通过企业知识库 API（api/files.py 的 enterprise_kb_router，/enterprise/knowledge-base 前缀；api/enterprise.py 管企业信息）维护内容；enterprise_sync.py 用 Redis Pub/Sub 通知在线 Agent 容器有变更；各 Agent 按自己的角色拉取最新数据，写入自己工作区的 enterprise_info/ 目录，成为运行时上下文的一部分。写入权收紧的原因在 agent_tools.py 里写得很直白——Agent 对 enterprise_info 的写操作直接被拒：「enterprise_info is shared company context and is read-only for agents. Ask an admin to update it.」公司级事实如果允许 Agent 自写，一个幻觉就会污染所有 Agent 的上下文，且没有审计入口。这是个典型的读路径自动化、写路径人工化的安全设计：分发要快要广，变更要慢要审。

Q6 · 日报→周报→月报这条聚合链，怎么保证数据一致性和质量不劣化？

四个机制叠加：① 源头幂等——member_daily_reports 有唯一约束 (tenant_id, member_type, member_id, report_date)，upsert 语义保证同一天同一成员只有一份终稿，重复催收/重复提交不会产生重复记录；② 入库即瘦身——成员报告写入时就截断到 2000 字（okr_reporting 模块注释 "member reports are capped at 2000 chars at write time"），存的是 OKR Agent 蒸馏后的版本而非原始聊天，原始讨论留在聊天记录里备查——聚合层永远面对的是已压缩的输入；③ 确定性聚合优先——公司报告用 deterministic section-building 而非整篇交给 LLM 重写，量大时分桶聚合，把模型的发挥空间限制在洞察层而非事实层；④ 存储与传播解耦——报告落 WorkReport 表的同时返回字符串给 OKR Agent，由它决定发广场还是发渠道，传播行为不回写污染数据层。这条链路的哲学是：越往上层，LLM 的角色越从「记录者」退到「评论者」，事实底座始终是底层那些幂等、不可变的行。

管理的最后一公里，交给最不怕烦的那个「员工」

组织架构给了 Agent 一个工位，关系图谱给了它一张通讯录，OKR 给了它一份责任。

而 OKR Agent 把管理里最消耗人性的部分——每天催、每天记、每月汇总——变成了永不疲倦的自动动作。

数字员工背 OKR，不是把 KPI 的压力复制给机器，而是让机器替人扛起目标管理本身。
