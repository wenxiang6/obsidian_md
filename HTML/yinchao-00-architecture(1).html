音巢整体架构
把 AI Agent 当数字员工运营的平台底座

音巢（Clawith）是一个开源多智能体协作平台（Apache 2.0）：每个 Agent 有持久人格、长期记忆、独立工作空间和主动意识，还能在 Plaza 广场上彼此社交。LLM 推理全部走外部 API，本地是一套标准 Web 应用 + Docker 编排——这篇总纲把它的分层、进程角色、租户隔离与 Durable Runtime 一次讲透。

01 · 场景

不是聊天机器人，是一家「数字员工公司」的操作系统

定位 · 一句话

Agent 是数字员工：有身份（soul.md 人格）、有记忆（memory.md）、有工位（独立工作空间）、有主动性（Aware + 6 种触发器）、有社交（Plaza 广场），并被组织管理。

这个定位直接决定了架构形态：它不是一个推理框架，而是一个「平台底座」——LLM 推理外包给外部 API，本地把身份、记忆、协作、治理这些框架给不了的东西做扎实。

02 · 设计

三个贯穿全局的取舍

音巢的架构可以被三个决策概括：单体还是微服务、租户怎么隔离、任务队列放哪里。它们决定了后面所有的代码形状。

模块化单体 + 进程角色 vs 微服务拆分 D1

选项

① 拆成 API 服务 / 运行时服务 / 连接器服务等多个微服务，独立仓库独立部署
② 单一代码库、单一 FastAPI 应用，用 PROCESS_ROLE 环境变量让一个二进制扮演不同角色

决定

选 ②：模块化单体，进程级角色分离（bootstrap / api / worker / connector）

原因

核心复杂度在 Agent 运行时语义（状态机、检查点、租户隔离），不在服务边界。角色拆分拿到部署弹性（api 可水平扩、connector 可单独重启），又避开微服务的分布式事务与接口治理成本。docker-compose.cd.yml 已经把 api 与 worker 拆成两个容器在跑。

代价

共享数据库连接池，worker 突发负载可能挤占 api 的 PG 连接；角色边界靠纪律维持，不是强制的网络边界。代价可接受：中间状态可经由 Redis / 数据库解耦。

行级租户隔离 vs 分库 / 分 Schema D2

选项

① 每租户独立数据库或 Schema，物理隔离
② 共享表 + tenant_id 列，由中间件注入 ContextVar、DAO 层自动追加租户条件

决定

选 ②：行级隔离，隔离逻辑收口在 TenantContextMiddleware + TenantScopedBaseDAO 两处

原因

64 张表 × N 个租户的分库方案会让 Alembic 迁移与备份成本爆炸；行级隔离用约 60 行的中间件和一个 DAO 基类换全局约束——scoped 方法在没有租户上下文时直接抛 RuntimeError，把「忘了带 tenant_id」变成启动期即可发现的故障，而不是线上数据串租。跨租户查询只允许平台管理员走父类方法，并要求注释 arch-guard 标记。

代价

隔离强度低于物理分库，依赖 DAO 纪律与代码评审兜底；大租户的数据倾斜需要后续再做表分区。

数据库表当工作队列 vs Celery / Kafka D3

选项

① 引入 Celery + Redis / Kafka 做 Agent 任务队列
② 用 agent_run_commands 表：pending → claimed（TTL 心跳）→ done / failed，失败按 attempt_count 重试

决定

选 ②：工作队列就是一张 PostgreSQL 表，worker 轮询认领

原因

Agent 运行状态本来就必须落库（LangGraph Postgres Checkpointer），命令放同一张库意味着「排队中的意图」和「执行中的状态」共享同一事务边界与备份策略，恢复语义天然一致；TTL 认领（默认 60s，每 20s 续约）+ 最大 5 次尝试覆盖了 worker 崩溃场景。少一个中间件，少一类运维事故。

代价

吞吐上限低于专用消息队列，高频心跳带来写放大；但 Agent 运行的瓶颈在 LLM API 延迟（秒级），不在队列吞吐，瓶颈错位使这个代价几乎不可见。

三个决策的共同审美

把复杂度压进「语义正确性」（租户不串、运行可恢复），把基础设施维持在「一个 PG + 一个 Redis 就能跑」的水平。这是一套为中小团队自部署优化的架构——也和 Apache 2.0 开源分发的目标一致：部署门槛每高一分，社区用户就少一批。

两段骨架看懂整个底座

伪代码 1

按 PROCESS_ROLE 分支启动（backend/app/main.py 的骨架）

def _role_enabled(*required): roles = {r.strip() for r in settings.PROCESS_ROLE.split(",")} # 缺省 "all" return "all" in roles or any(r in roles for r in required) async def lifespan(app): if _role_enabled("all", "bootstrap"): await create_all_tables() # 幂等；生产由 Alembic 接管 await seed_builtin_tools() # 内置工具 await seed_agent_templates() # 22 个 Agent 模板 await seed_skills() # 技能 await seed_default_agents() # 默认 Agent await seed_okr_agent() # 默认 OKR Agent if _role_enabled("all", "api"): await realtime_router.start(ws_manager.deliver_pubsub_message) # ↑ 订阅 Redis pub/sub，把别的实例上的 WS 消息投递到本地连接 if _role_enabled("all", "worker"): asyncio.create_task(start_trigger_daemon()) # 触发器守护 asyncio.create_task(start_scheduler()) # 定时任务调度 await stack.enter_async_context(running_runtime_worker_context()) # ↑ Durable Runtime worker：轮询认领 agent_run_commands if _role_enabled("all", "connector"): asyncio.create_task(feishu_ws_manager.start_all()) # 飞书 asyncio.create_task(dingtalk_stream_manager.start_all()) # 钉钉 asyncio.create_task(wecom_stream_manager.start_all()) # 企微 asyncio.create_task(wechat_poll_manager.start_all()) # 微信 asyncio.create_task(discord_gateway_manager.start_all()) # Discord yield # 关停时逆序回收：先停 worker 释放检查点锁，再关 Redis

要点：播种全部幂等（可反复执行不出错）；角色之间不通信，协调完全通过共享的 PostgreSQL 与 Redis 完成——这是「可拆进程部署」成立的前提。

伪代码 2

租户隔离最小闭环：中间件注入 + DAO 自动过滤

# backend/app/core/middleware.py + backend/app/dao/base.py 的最小化改写 _tenant_ctx: ContextVar[UUID | None] = ContextVar("tenant", default=None) class TenantContextMiddleware(BaseHTTPMiddleware): async def dispatch(self, request, call_next): payload = try_decode_jwt(request.headers.get("Authorization")) token = _tenant_ctx.set(payload.get("tenant_id") if payload else None) try: return await call_next(request) # 整个请求链共享这个 ContextVar finally: _tenant_ctx.reset(token) # 请求结束必须复位，防串租 class TenantScopedBaseDAO(BaseDAO): async def get_scoped(self, id): tid = _tenant_ctx.get() if tid is None: raise RuntimeError("no tenant context") # 故障尽早暴露 return await select(self.model).where( self.model.id == id, self.model.tenant_id == tid, # 租户条件自动追加，业务代码零感知 ) # list_scoped / add_scoped / delete_scoped 同理；写入时校验 tenant_id 一致

后台任务没有 HTTP 请求，用 tenant_context(tenant_id) 上下文管理器手动绑定；平台管理员的跨租户查询走父类 BaseDAO 方法，且调用点必须写 # arch-guard: allow 注释——隔离靠机制 + 纪律双重兜底。

05 · 面试 QA

六问六答：每个问题都落到音巢的真实代码上

Q1 · 为什么选模块化单体 + 进程角色，而不是微服务？

看复杂度的位置。音巢最难的部分是 Agent 运行时的语义——状态机怎么设计、检查点何时写、租户如何不串——这些是代码内部的复杂度，拆成微服务一分也减不掉，反而新增接口治理、分布式追踪、跨服务事务的成本。PROCESS_ROLE 方案用「一个二进制、四种人格」拿到了微服务最值钱的两样东西：api 角色可水平扩容、connector 角色可独立重启（IM 长连接抖动不影响 API）。docker-compose.cd.yml 已经在生产形态里跑了 backend-api 与 backend-worker 两个服务，证明拆分是真的、不是纸面设计。什么时候该重新考虑微服务？当 worker 的资源画像（CPU 密集沙箱）和 api（IO 密集）差异大到需要不同的实例规格与调度策略时。

Q2 · 行级租户隔离和分库分 Schema 怎么取舍？

音巢 64 张表、Alembic 管迁移。分库方案意味着每来一个租户迁移要跑一遍、备份策略要翻 N 倍，运维成本随租户数线性增长；而行级隔离把全部复杂度收进两个文件：TenantContextMiddleware（约 40 行，从 JWT 解 tenant_id 进 ContextVar）和 TenantScopedBaseDAO（scoped 方法自动追加 WHERE tenant_id = :tid）。关键设计是失败模式的选择：scoped 方法在没有租户上下文时抛 RuntimeError，把「忘带租户」变成开发期立刻炸的错误，而不是线上串数据的事故。代价是隔离强度低于物理隔离——靠 DAO 纪律兜底，所以跨租户查询被限制为平台管理员专用且强制 arch-guard 注释。对 SaaS 中早期（租户数十到数百），这个交换是赚的。

Q3 · 为什么用数据库表 agent_run_commands 当工作队列，而不是 Celery 或 Kafka？

三个理由。① 状态一致性：Agent 运行状态本来就落 PG（LangGraph checkpointer），命令也放 PG，「排队的意图」和「执行的状态」在同一事务边界里，崩溃恢复时不会出现「队列说做完了、库里没结果」的分裂。② 够用：Agent 任务的瓶颈是 LLM API 秒级延迟，不是队列吞吐；PG 轮询 + SKIP LOCKED 风格的认领在这个量级绰绰有余。③ 少一个组件：自部署用户只需要 PG + Redis，不用学 Kafka。可靠性语义自己实现了一小套：claimed 状态带 TTL（默认 60s）、每 20s 心跳续约、worker 死了 TTL 到期被别人重领、attempt_count 到 5 次标记失败。这套东西 Kafka 免费给你，但音巢要的不是消息队列的全部语义，只是「至少一次 + 崩溃重领」，用表实现反而更贴合。

Q4 · LangGraph 的 Postgres Checkpointer 到底解决了什么问题？

解决「Agent 运行是有状态的长事务，但进程是无状态的」这个根本矛盾。一次 Agent 运行可能持续几分钟、几十轮模型-工具循环，期间 worker 可能重启、用户可能点停止、渠道可能超时。Checkpointer 在图执行的每个超步（super-step）边界把完整状态写进 PG，于是：worker 崩溃后新认领者从最近检查点续跑而不是从头再来；「中断-人工干预-恢复」（审批、修改计划）成为一等能力；时间旅行调试（回放某一步的状态）免费获得。音巢在 config.py 里配了 AGENT_RUNTIME_CHECKPOINT_RETENTION_DAYS=30 做保留清理——检查点表会膨胀，这是用它必须付的存储税。

Q5 · WebSocket 在多实例部署下怎么路由？

问题本质是：用户的 WS 连接在 api 实例 A 上，但 Agent 运行结果产生在 worker 上，消息怎么找到 A？音巢的 RealtimeRouter（services/realtime_runtime/router.py）用 Redis 做注册表 + pub/sub 总线：连接建立时在 Redis 登记 connection_id → 实例的映射；worker 要推消息时先查路由表，再 publish 到目标实例的专属频道；每个 api 实例启动时跑一个 subscriber loop，收到本实例的消息后投递给本地 WS 连接。这个模式的要点是连接状态不共享、只共享路由——实例宕机时它名下的连接本来就断了，路由表随 TTL 过期自动清理，没有脑裂问题。

Q6 · 进程角色拆分的好处都说了，代价是什么？

四个真实代价。① 共享连接池争抢：worker 跑沙箱任务时 PG 连接消耗大，api 延迟会抖——缓解办法是拆容器后各自配池（compose.cd 已拆）。② 播种竞态：多实例同时以 bootstrap 启动会并发播种，所以播种必须全部幂等，且生产上应只让一个实例带 bootstrap 角色。③ 角色边界靠纪律：代码层面没有任何东西阻止 api 角色的代码调用 worker 的函数，边界是 review 出来的。④ 本地开发心智负担：排查问题要先想「这段代码在哪个角色里跑」。这些代价的共同点是——它们都是「管理问题」而非「正确性问题」，对一个小团队开源项目，这个交换方向是对的。

底座的审美：语义做重，设施做轻

音巢把复杂度押注在「数字员工」的语义上——身份、记忆、主动性、协作、治理；同时把基础设施压到最低：一个 PG、一个 Redis、一个二进制、四种角色。

LLM 推理外包给外部 API，换来的是任何团队 docker compose up 就能拥有一家「数字员工公司」。
