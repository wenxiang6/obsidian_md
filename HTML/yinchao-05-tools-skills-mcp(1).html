01 · 场景

没有工具的 Agent 只是聊天框，工具是它的双手与感官

LLM 本身只会「说」，不会「做」。音巢 Agent 平台把「做」的能力抽象成三层供给：内置工具随平台发版、MCP 工具运行时发现接入、技能由使用经验沉淀而来——分别对应「平台给的」「外部借的」「自己长的」。

93

33

五类真实业务场景

①

开箱即用的办公自动化

新创建的 Agent 绑定基础工具组即可干活：read/write/edit_file 操作工作区文件，convert_csv_to_xlsx、convert_html_to_pdf/pptx、convert_markdown_to_docx 做文档转换，web_search（jina/exa/duckduckgo/tavily/google/bing 多引擎）与 read_webpage 联网调研，execute_code（本地沙箱或 E2B）跑数据处理脚本，generate_image_*（SiliconFlow/OpenAI/Google/自定义）配图，send_email 发结果。零配置，创建即用。

②

企业协同：飞书全家桶 + OKR

飞书工具族覆盖消息收发、用户搜索、多维表格 bitable CRUD（bitable_create_app 到 bitable_delete_record 七个）、云文档/知识库读写、日历与审批流；OKR 工具族支撑目标查询、进度收集（collect_okr_progress）、日报/月报生成（generate_okr_report、generate_monthly_okr_report）。Agent 由此从「个人助手」升级为「组织成员」。

③

云端浏览器与电脑操作

AgentBay 云沙箱族 33 个工具让 Agent 在云端真实操作：浏览器导航/截图/点击/输入/登录，代码执行，乃至电脑 GUI 操控（窗口列举、激活、关闭、光标定位、可见应用枚举）。适合需要登录态、需要真实浏览器环境的采集与自动化场景，与本机沙箱形成互补。

④

运行时发现新能力：MCP 即搜即装

任务做到一半发现缺能力——比如要操作某个 SaaS 的 API。Agent 调 discover_resources 在 Smithery / ModelScope 注册中心搜索 MCP Server，再调 import_mcp_server 一键导入：连接、列出工具、落库、绑定，全程不打断当前任务。Agent 模板还可以在 meta.yaml 里声明 default_mcp_servers，创建时自动导入预置能力。

⑤

自我进化：把最佳实践打包成技能

一个 Agent 反复把「内容调研写作」做得很好，就可以用 skill-creator 元技能把这套方法论沉淀成新技能：分析器拆解成功样本、评分器按 schema 打分、脚本打包并跑评估，最后 install_skill 装回平台（或从 ClawHub 技能市场装别人的）。技能本质是文件包（SKILL.md + 脚本 + 参考文档），落 skills / skill_files 表，注入工作区供 Agent 按需阅读。

⑥

Agent 间协作的消息总线

send_message_to_agent 与消息发送族工具让 Agent 之间、Agent 与平台渠道之间互发消息——工具系统不仅是「调用外部世界」，也是多 Agent 协同（见 04 篇）的传输底座之一。

定位 · 一句话

工具、技能、MCP 是三件事：工具是「可调用的能力」，技能是「可复用的方法论」，MCP 是「能力的标准化插头」——音巢把它们拧进同一条治理管线。

所以本篇的主线不是「有哪些工具」（那是文档活），而是：三种供给形态如何被统一抽象、统一绑定、统一治理，以及运行时进化（发现→导入→沉淀→再装回）这条闭环怎么转起来。

02 · 设计

三个关键决策：统一契约、技能即文件、发现走注册中心

能力供给侧最大的设计风险是「每接一种新能力就开一条新管线」。音巢的设计哲学相反：供给侧可以百花齐放，消费侧必须收敛成一条线。

三种供给形态的本质区别

形态供给方载体模型感知方式治理
内置工具 平台发版 代码 + JSON Schema 定义（builtin_tool_definitions.py），启动播种进 tools 表 name + description + JSON Schema 注入模型上下文 自主分级 L1/L2/L3 + 执行落账 全量
MCP 工具 外部 MCP Server（运行时接入） 远程 Server 的 tools/list 结果，导入后落 tools 表（kind 标记 MCP 来源） 同上——导入时被清洗成与内置一致的 canonical schema 同上，治理口径与内置完全一致 全量
技能（Skill） 平台预置 / ClawHub 市场 / Agent 自创 文件包：SKILL.md + 脚本 + 参考文档，落 skills / skill_files 表 不作为工具注入；以文件形式进工作区，Agent 用既有文件工具阅读后按方法论行动 评分器 + 评估脚本把关质量；安装与启用走技能管理面 轻量

决策一：三种供给形态，共用同一条绑定与执行管线 K1

选项

① 内置工具、MCP 工具各走各的调用链（内置直接函数分发，MCP 走独立代理层），技能做成一种新的工具类型
② 全部收敛：统一落 tools 表、统一 agent_tools N-M 绑定、统一 canonical schema、统一经 control_guard → 自主分级 → 执行 → 审计的管线

决定

② 统一管线；技能不做成工具，保持文件包形态

原因

治理只写一遍：L1/L2/L3 自主分级、L3 审批中断、agent_tool_executions 审计落账对内置与 MCP 一视同仁，新增供给形态零治理成本。模型侧也只看到一种工具契约（get_agent_tools_for_llm() 统一组装），不感知工具来自本地还是远程。

代价

MCP 导入时要做一次「标准化清洗」：传输协议自动探测（SSE / Streamable HTTP）、schema 归一、命名与权限边界的落库表达——复杂度前置到了导入期，但换来运行期的完全统一。

决策二：技能是「文件包」而不是「新工具」 K2

选项

① 技能注册为新的工具类型，模型用 tool_call 显式调用
② 技能是文件包（SKILL.md + 脚本 + 参考资料），挂载进 Agent 工作区，Agent 通过读文件获得方法论，用既有通用工具执行

决定

② 文件包形态，skills + skill_files 两张表承载

原因

技能与工具解决的是不同问题：工具回答「能做什么」（能力接口），技能回答「怎么做好」（流程与经验）。文件包形态让技能天然可读、可版本化、可被 Agent 自创（skill-creator 产出的就是文件包），且不膨胀工具列表、不占用宝贵的工具选择注意力。这与业界 Agent Skills 的共识形态一致。

代价

技能生效依赖模型「愿意读、读得懂」——SKILL.md 的 frontmatter（name/description）质量直接决定触发率，因此 skill-creator 配套了评分器（grader）与评估脚本（run_eval）把质量做成可度量、可回归的环节，而不是靠自觉。

决策三：能力发现走注册中心，而不是让用户手填 URL K3

选项

① 用户手动填写 MCP Server 地址与配置导入
② 内置 discover_resources 工具直连 Smithery / ModelScope 注册中心搜索，import_mcp_server 一键导入；模板用 meta.yaml 的 default_mcp_servers 声明预置依赖

决定

② 为主，① 作为直接导入（import direct）通道保留

原因

「发现」是进化的起点。把搜索注册中心本身做成 Agent 可调用的工具，意味着发现能力这件事也被 Agent 化了——不是人去逛市场，而是 Agent 在任务上下文中自己找到缺的能力并装上，这才构成闭环。

代价

依赖外部注册中心的可用性与 API Key 管理（Smithery key 按 Agent 维度读取并解密）；远端 Server 的质量参差，导入即绑定需要克制——这也是把导入动作本身纳入自主分级治理的原因。

设计红线：供给侧可以无限扩张，上下文预算不能

136 个内置定义全量塞给模型既不经济也伤准确率。音巢的纪律是：工具默认不进入模型上下文，只有被 agent_tools 绑定到具体 Agent 的工具才会被 get_agent_tools_for_llm() 组装注入；AgentBay 电脑操控族还会按云端 OS 类型动态改写描述（_patch_computer_tool_descriptions）。能力是货架，不是全倒进购物车的。

04 · 伪代码

两个最小闭环：统一分发执行、MCP 一键导入

伪代码刻意省略重试、并发与观测细节，只保留机制骨架：工具怎么被管住地执行，外部能力怎么被标准化地接进来。

骨架一：工具的统一分发与执行

# 一次 tool_call 的最小闭环：校验 → 分级 → 分发 → 清洗 → 落账 async def execute_tool_call(agent_id, call): tool = await load_bound_tool(agent_id, call.name) # agent_tools 绑定校验：没绑定 = 不存在 if tool is None: return err("tool_not_available") # 错误结构化，不抛栈给模型 validate(call.args, tool.input_schema) # JSON Schema 校验，契约即护栏 level = await autonomy.check(agent_id, action=tool.name) # 默认 L2 if level == "L3": approval = await create_approval(agent_id, call) # Web + 飞书卡片通知创建者 raise Interrupt(approval.id) # 运行挂起；批准后从断点恢复 elif level in ("L1", "L2"): await notify_creator(agent_id, call) # 告知但不等待 try: if tool.kind == "mcp": # 统一契约，按 kind 分发 raw = await MCPClient(tool.server_url).call_tool(tool.remote_name, call.args) else: # builtin：本地沙箱 / E2B / AgentBay raw = await BUILTIN_HANDLERS[tool.name](agent_id, call.args) outcome = normalize_tool_outcome(raw) # 归一化为统一结果结构 except Exception as e: outcome = err("tool_failed", str(e)[:200]) # 失败也是合法结果，让模型自己补救 await db.insert("agent_tool_executions", # 全量落账：成败都留痕 agent_id=agent_id, tool=tool.name, args=sanitize_tool_arguments(call.args), # 敏感字段脱敏后落账 result=truncate(outcome, max_bytes=4096)) return sanitize_tool_feedback_text(outcome.text) # 清洗后回注模型上下文

骨架二：import_mcp_server 的最小导入流程

# 从「一个 MCP Server 引用」到「一组绑定就绪的工具」 async def import_mcp_server(agent_id, ref): # ref: Smithery ID 或直连 URL if ref.is_smithery_id: cfg = await smithery.resolve_connection(ref.id) # 注册中心换连接配置（含鉴权 URL） else: cfg = {"url": ref.url, "api_key": ref.api_key} # import direct 通道 client = MCPClient(cfg["url"], cfg["api_key"]) await client.initialize() # 自动探测传输：先 Streamable，失败回退 SSE remote_tools = await client.list_tools() # 拿到远端真实 schema —— 信任源头是协议 await autonomy.require_allowed(agent_id, "import_mcp_server") # 扩张动作同样过治理 for rt in remote_tools: row = await db.upsert("tools", # 幂等落库：重复导入不产生重复工具 name=namespaced(cfg["url"], rt["name"]), kind="mcp", server_url=cfg["url"], description=rt["description"], input_schema=rt["inputSchema"]) await db.upsert("agent_tools", agent_id=agent_id, tool_id=row.id) # N-M 绑定即生效 return {"imported": len(remote_tools), "server": cfg["url"]} # 之后 get_agent_tools_for_llm(agent_id) 自动包含这批工具 —— 当前任务内闭环
为什么这两个闭环是「最小」但「完备」的

骨架一证明了「统一管线」不是口号：builtin 与 MCP 的差异被压缩到 一次 if 分支，之前（校验、分级）之后（清洗、落账）全部共用。骨架二证明了「进化」不需要特殊机制：导入就是「连接 → list_tools → 落库 → 绑定」四步，绑定生效的瞬间，统一的组装函数自然把新工具送进模型上下文——没有任何「刷新」「重启」「重新发布」环节。

05 · 面试 QA

六道题，从协议原理问到工程取舍

每题都按「先讲清原理，再落到音巢的具体实现」来答——这也是面试中最有说服力的答法。

Q1 · MCP 协议到底是什么？它解决了什么本质问题？

MCP（Model Context Protocol）是 Anthropic 主导的开放协议，标准化「模型应用 ↔ 外部能力」之间的接口：Server 暴露 tools（可调用能力）、resources（可读数据）、prompts（提示模板），Client 通过 JSON-RPC 风格的 initialize / list_tools / call_tool 与之交互，传输层支持 stdio、SSE、Streamable HTTP。

它解决的本质问题是工具描述的 N×M 集成爆炸：没有标准时，N 个 Agent 框架接 M 个外部服务要写 N×M 个适配器；有了 MCP，服务方实现一次 Server，所有兼容 Client 即用。音巢的实现（services/mcp_client.py）里有一个很工程化的细节：Client 会自动探测传输协议——先尝试 Streamable HTTP，失败后回退 SSE——因为生态里两种实现的 Server 都大量存在，让用户（或 Agent）感知传输细节是集成体验的失败。这正是「协议标准化」落到代码里的样子：连协议版本的参差都要由 Client 侧吸收掉。

Q2 · 内置工具和 MCP 工具来源完全不同，schema 与治理上怎么做到统一？

关键是把差异消化在导入期，运行期只剩一种形态。MCP 工具在 import 时被「物化」：list_tools 拿到的 description 与 inputSchema 直接落进 tools 表，与内置工具同表存储、同结构表达（kind 字段区分来源）。之后所有环节无差别：agent_tools 绑定、get_agent_tools_for_llm() 组装、自主分级、执行落账，全都不感知工具来自哪里——分发执行时才按 kind 决定走本地 handler 还是 MCPClient.call_tool。

内置侧还有一个容易被忽视的设计：builtin_tool_definitions.py 文件头明确声明「数据库行不是模型契约，本模块才是」——内置工具的描述与 Schema 以代码为准，DB 行只管绑定、启停与配置。这带来两个好处：改工具文案不用写数据迁移；模型看到的契约永远与代码实现同源，不会出现「DB 里描述与代码行为漂移」的事故。治理统一的本质就是一句话：让审计和分级逻辑只写一遍，且对所有供给形态强制生效。

Q3 · 工具描述（description/schema）对 LLM 选工具的准确率有多大影响？有什么写法经验？

影响是决定性的——模型选工具时只能看到 name + description + 参数 schema，看不到实现。描述写得差，工具等于不存在，或者更糟：被误选。经验有四条：

  • 描述的第一句写「什么时候用」，不是「这是什么」。「读取 Agent 工作区内文件的文本内容；二进制文件请改用 execute_code」比「文件读取工具」有效得多——模型匹配的是场景，不是名词。
  • 把边界条件与互斥关系写进描述。比如音巢的 execute_code 与 execute_code_e2b 并存，描述必须说清本地沙箱与 E2B 云沙箱各自适用什么，否则模型随机二选一。
  • 参数级描述约束取值空间：路径类参数用「Agent 根目录相对路径」这类明确约定（音巢用 AGENT_RELATIVE_PATH_ARGUMENTS 统一约束了一整族文件工具的路径语义），比事后报错纠偏便宜得多。
  • 描述是运行时可调的。音巢会按 AgentBay 云端 OS 类型动态改写电脑操控工具的描述（_patch_computer_tool_descriptions）——同一份定义，面向 Windows 与 Linux 给不同的操作提示。这说明描述不该被当成静态文案，而是可以根据上下文投影的「活契约」。
Q4 · Agent 自创技能听起来很美好，质量怎么保证？会不会沉淀出一堆垃圾技能？

音巢的回答是：把技能生产本身做成一条带质量闸门的流水线，而不是一次灵光乍现。skill-creator 元技能（services/skill_creator_files/）是一整套角色与脚本的组合：analyzer 负责拆解成功任务样本、提炼可复用流程；comparator 对比候选写法；grader 按 schema 给技能草稿打分；run_eval / quick_validate 脚本用预设用例对技能做回归评估；package_skill 负责打包。技能不是「写完就上架」，而是「评分过线 + 评估通过」才进入可安装状态。

这背后的判断是：Agent 生成内容的最大风险不是错，而是不可度量地平庸——看起来都对，用起来没用。所以要引入两个外部锚点：一是 frontmatter 规范（name/description 决定触发率，评分器专门盯这个）；二是可执行的评估用例（技能宣称能做好什么任务，就用什么任务回归它）。ClawHub 市场侧同理，安装入口在 api/skills.py，安装的是文件包，出问题了卸载与降级的成本都很低——文件包形态（K2 决策）在这里又一次兑现了收益。

Q5 · 工具数量爆炸时，怎么决定哪些工具注入模型上下文？

先承认一个事实：工具选择是注意力分配问题，注入越多，单工具被选准的概率越低，token 成本还线性上涨。音巢的策略是三道闸：

  • 绑定即白名单。136 条定义默认与模型无关，只有通过 agent_tools 显式绑定到具体 Agent 的工具才会被 get_agent_tools_for_llm() 组装注入。创建 Agent 时选工具组，就是在做能力预算。
  • 条件投影。组装阶段按 Agent 实际配置动态裁剪与改写：没有配飞书的 Agent 不注入飞书工具族（_agent_has_feishu 判断），AgentBay 电脑工具按 OS 类型改写描述——同一货架，不同 Agent 看到不同的陈列。
  • 把「找能力」做成工具，而不是全量预装。这是最根本的一招：与其把 136 个工具塞进去防万一，不如只装当前够用的，再给一个 discover_resources——能力缺口在运行时被发现、被搜索、被导入（图 2 通道 A）。工具上下文从「全集快照」变成「按需流式加载」，这是进化系统相对静态工具列表的结构性优势。

补充一个反面教训：不要用「description 写短点」来省 token——描述是选择准确率的全部依据，省描述的钱会在误调用上十倍奉还。要省的是工具数量，不是单个工具的表达。

Q6 · L3 审批要求「人批准才能执行」，这跟工具执行的自动流转不矛盾吗？interrupt 怎么配合？

不矛盾，因为 LangGraph 的中断恢复机制让「等待人」成为一个一等公民的图状态，而不是工程上的尴尬例外。具体配合分四步：① 模型产出 tool_call 后，autonomy_service 按动作类型查策略，命中 L3 就创建审批单并抛出中断——运行图在此挂起，当前全部上下文（对话历史、已完成步骤）随 checkpoint 持久化；② 创建者收到 Web 通知与飞书审批卡片（feishu_approval_authorization.py 负责卡片交互）；③ 批准后，运行从中断点恢复，工具带着原始参数继续执行，模型侧无感知；④ 拒绝则生成结构化的「未获授权」结果回注上下文，让模型体面地向用户解释并换路径。

这套设计的要点在于：审批不改变工具执行链路，只是在链路上加了一扇可暂停的门。L1/L2/L3 共用同一条执行与落账路径（见伪代码骨架一），区别只在「过门之前等不等」。因此审批记录与执行记录在同一张流水里天然关联（approval_id），审计时能完整回答「这个高危操作谁批的、几点批的、执行结果如何」。相比「L3 操作直接拒绝」的偷懒方案，中断恢复保住了 Agent 处理高危但合理任务的能力；相比「先执行后补批」的放纵方案，它守住了副作用不外溢的底线。

能力不是清单，是生态

静态的 Agent 平台把工具做成一张发版时定死的清单；音巢把它做成一个生态——内置工具是底座，MCP 是伸向外部世界的标准化插头，技能是经验沉淀的容器。

而真正让这个生态转起来的，是两件不显眼的事：所有形态共用同一条治理管线（所以扩张不失控），以及发现与沉淀本身也是工具（所以进化可以自治）。

一个 Agent 平台的能力上限，不该由它的发版日决定，而该由它的使用史决定——这就是「能力的供给侧」最终要回答的问题。
