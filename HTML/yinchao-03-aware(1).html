Aware 自主意识系统

只会应答的 Agent 是客服，会自己醒过来的 Agent 才是员工。音巢（Clawith）的 Aware 系统由三块组成：Focus Items 让 Agent 记住「我在盯什么」，六种触发器让它知道「什么时候该醒」，心跳让它没事也会「起来转转」——时间、消息、网页、外部系统，都是它的闹钟。

01 · 场景

Aware 解决什么问题：从「随叫随到」到「不请自来」

传统对话式 Agent 的全部行为都由用户消息驱动——人不说话，它就永远睡着。Aware 系统把「唤醒源」从用户手里解放出来：时间到点、外部事件、消息到达、网页变化，都能成为一次 Agent Run 的起点。Agent 因此第一次拥有了「自己的工作日程」。

定位 · 一句话

Aware 不是「给 Agent 配一个 crontab」，而是把「什么时候醒、醒了做什么」变成 Agent 自己能读写的一等公民。

触发器和 Focus 都通过内置工具（set_trigger / upsert_focus_item 等）暴露给 Agent 自己管理——它可以在对话中自己决定「明天早上再提醒我跟进这件事」，这就是「自主意识」的工程含义。

02 · 设计

三个构件：Focus 记住目标，触发器负责唤醒，心跳负责巡检

设计上最关键的取舍是「状态放哪」和「谁来触发」。音巢的答案：状态入库（Postgres），触发统一收口到一个 15 秒节拍的守护循环，唤醒后一律转成 Agent Run 命令进入统一运行时。

构件一：Focus Items —— Agent 的「正在关注」清单

Focus 是结构化落库的关注点（表 agent_focus_items），每条有 key（Agent 内唯一）、标题、描述、状态（in_progress / completed）、类型（normal / system）与来源（user / trigger / a2a / okr）。它替代了早期的 focus.md 工作文件——模型注释里写得很直白：文件没有校验、没有稳定 ID，触发器与工具无法共享同一份事实源。

  • Agent 通过内置工具 list_focus_items / upsert_focus_item / complete_focus_item 自己增删改查（builtin_tool_definitions.py）；
  • Focus 会被渲染进每次 Run 的上下文（render_focus_context：进行中 / 系统关注 / 最近完成三段），Agent 每次醒来都知道自己「正在盯什么」；
  • 状态语义即清单语义：[ ] 待办、[/] 进行中、[x] 完成，对应 status 字段的取值流转。

决策：触发器由谁创建 —— 平台预置 vs Agent 自主注册 D1

选项

① 只允许管理员 / 用户在 UI 配置触发器，Agent 被动执行
② 把 set_trigger / update_trigger / cancel_trigger / list_triggers 做成内置工具，Agent 可自主注册与管理

决定

②，触发器是 Agent 的一等公民，Agent 自己管理；平台只负责限额与兜底

原因

「明天提醒我跟进」这类意图在对话中产生，只有 Agent 自己能把它变成结构化唤醒条件。reason 字段要求自包含——它会成为未来那次 Run 的指令；每个触发器必须挂到 Focus（focus_ref 缺省时系统自动建一条），保证醒来时有上下文。

代价

Agent 可能给自己埋一堆闹钟。用限额对冲：每 Agent 上限 20 个触发器、poll 最小 5 分钟、webhook 每分钟 5 次、on_message 每小时 30 次超限自动停用。

决策：唤醒后如何执行 —— 直接调用 vs 命令队列 D2

选项

① daemon 命中触发器后直接在当前进程内跑 Agent Run
② 先落 trigger_executions 执行记录（带幂等键），由 worker 按租约认领，再转为 trigger_completion 命令进 agent_run_commands 统一运行时

决定

②，三段式：评估 → 执行记录（可认领）→ 运行时命令

原因

多副本部署下必须防重复触发：幂等键唯一约束（trigger_id + idempotency_key）挡住重复入队，SELECT ... FOR UPDATE SKIP LOCKED + 5 分钟租约（lease_owner = 实例 ID）挡住重复执行。心跳、webhook、定时触发共享同一套运行时与审计。

代价

链路变长，从「到点」到「开跑」多了一个 tick + 一次认领的延迟（秒级）；换来的是水平扩展与崩溃恢复能力（租约过期自动回收重跑）。

Focus-Trigger 绑定：闭环的关键设计

触发器表上的 focus_ref 字段把「唤醒条件」绑回「关注点」：唤醒上下文里会注入「关联 Focus：{key}」，Agent 醒来就知道这次闹钟是为了哪件事。事情做完后 Agent 调 complete_focus_item 收尾，并用 cancel_trigger 停掉对应闹钟（工具描述里明确写着「任务完成时使用」）；once 触发器则在触发后由系统自动停用。目标与闹钟成对出现、成对消失，不留僵尸触发器。

心跳（heartbeat）不在这张图的主链路上：它由 daemon 每 4 个 tick（约 60 秒）顺带检查一次，对开启 heartbeat_enabled 且处于活跃时段的 Agent 做原子认领后直接入运行时——它是「无事件也醒来巡检」，与「有事件才唤醒」的触发器互补。

幂等键是确定性的：cron/interval 用应触发时刻，poll 用内容指纹的 sha256，on_message 用消息指纹的 sha256——同一事件无论被几个副本评估多少次，数据库唯一约束只放行第一条。认领后的租约过期（5 分钟未完成）会被其他 worker 回收重跑，崩溃不会丢任务。

两种触发模式：fire_on = "change"（默认）——值与上次不同才触发；fire_on = "match"——值等于 match_value 就触发（盯「状态变成 done」这类目标态）。无论是否触发，_last_value 都会回写到触发器 config，这就是「状态保存」：去重的依据不在内存里，在数据库里，重启不丢。首次轮询只建档不触发（last_value 为空时不报），避免 Agent 一注册就被历史状态轰炸。

心跳：没有事件也定期醒来

心跳服务的循环很简单：找出 heartbeat_enabled 且状态为 running/idle 的 Agent，按 Agent 时区检查活跃时段（默认 09:00–18:00），距上次心跳超过 heartbeat_interval_minutes（默认 240 分钟）就到点。认领是原子的——一条 UPDATE ... WHERE last_heartbeat_at <= now - interval，rowcount 为 1 才算抢到，多副本安全。醒来后 Agent 拿到一份有界上下文（任务、收件箱等），按 HEARTBEAT.md 自定义指令（或默认指令）巡检：无事可做就以 HEARTBEAT_OK 收尾，有事就完成并只报告已验证的结果。私有 Agent 有额外护栏：不得向广场（Plaza）等组织级公开面发布内容。

04 · 伪代码

两个循环：daemon 的 15 秒，poll 的一次判定

省略 ORM 与异常处理细节，保留最小闭环：扫描 → 判定 → 幂等入队 → 租约认领 → 执行 → 回写。

伪代码 1 · trigger_daemon 调度循环

# 对应 services/trigger_daemon.py 的 _tick 主循环 async def trigger_daemon_loop(): while True: now = utcnow() triggers = await db.query(AgentTrigger).where(is_enabled=True) for t in triggers: if t.expires_at and now >= t.expires_at: t.is_enabled = False; continue # 过期自动停用 scheduled_at = await evaluate_trigger(t, now) # 见伪代码 2 if scheduled_at is None: continue # 没到点 / 被闸门拦下 key = build_idempotency_key(t, scheduled_at) # 确定性幂等键 try: await db.insert(TriggerExecution( trigger_id=t.id, idempotency_key=key, status="pending", scheduled_at=scheduled_at, payload=runtime_payload(t), # 匹配到的消息等上下文 )) except IntegrityError: continue # 别副本已入队，去重成功 t.last_fired_at = now; t.fire_count += 1 if t.type == "once": t.is_enabled = False # 一次性触发即停 # worker 侧：认领 pending 执行，转统一运行时命令 pairs = await claim_pending_trigger_executions() # FOR UPDATE SKIP LOCKED for execution, trigger in pairs: execution.lease_owner = INSTANCE_ID # 5 分钟租约 await enqueue(agent_run_commands, type="trigger_completion", context=build_trigger_context(trigger)) # 唤醒原因 + 关联 Focus await asyncio.sleep(15) # TICK_INTERVAL

伪代码 2 · poll 触发器评估（变化检测 + 状态保存）

# 对应 services/trigger_runtime/evaluator.py 的 poll 分支 async def evaluate_poll(trigger, now): cfg = trigger.config if now - (trigger.last_fired_at or trigger.created_at) \ < minutes(max(cfg.interval_min, 5)): # 最小轮询间隔防滥用 return None if is_private_url(cfg.url): # SSRF 闸门：拒私网/回环 raise Blocked("private/internal URL") resp = await httpx.request(cfg.method or "GET", cfg.url, headers=cfg.headers, timeout=10) current = extract_json_path(resp.json(), cfg.json_path or "$") if cfg.fire_on == "match": # 模式一：命中目标值 should_fire = current == cfg.match_value else: # 模式二：变化检测（默认） should_fire = cfg.get("_last_value") is not None \ and str(current) != cfg["_last_value"] cfg["_last_value"] = str(current) # 状态入库，重启不丢 await db.update(AgentTrigger, id=trigger.id, config=cfg) return now if should_fire else None # 变化才触发，平安不打扰
读法提示

两段伪代码合起来就是 Aware 的最小闭环：判定只负责「该不该醒」，入队负责「只醒一次」，运行时负责「醒来干什么」。幂等键唯一约束与 SKIP LOCKED 租约是分布式安全的两颗螺丝，少了任何一颗，多副本部署都会在同一个闹钟上把 Agent 叫醒两次。

05 · 面试 QA

六道题，从分布式安全问到设计哲学

Q1 · 多副本部署下，如何避免同一个触发器被多个实例重复触发？

音巢用了三层防重，而不是指望单点部署：① 入队去重——每次触发先算确定性幂等键（cron 用应触发时刻、poll 用内容指纹 sha256、on_message 用消息指纹 sha256），写入 trigger_executions 时靠 uq(trigger_id, idempotency_key) 唯一约束挡重，撞键即放弃；② 认领互斥——worker 用 SELECT ... FOR UPDATE SKIP LOCKED 抢 pending 记录，抢到后写上 lease_owner（实例 ID）和 5 分钟租约；③ 崩溃回收——租约过期未完成的记录重新变为可认领，任务不丢。这套「数据库即协调器」的方案不依赖外部锁服务，Postgres 就是分布式锁。

Q2 · cron 触发器错过执行时间（misfire）怎么办？

看 miss 了多久。音巢的策略是 30 秒宽容窗（MISFIRE_GRACE）：evaluator 用 croniter 按 Agent 所在时区算出「上一个应触发时刻」，如果它落在 now 往前 30 秒内，照常触发——daemon 的 tick 是 15 秒，所以正常抖动和一次 tick 延迟都能被宽容掉。超过 30 秒就放弃这一次，等下一个周期，不补跑。为什么不是一律补跑？因为对「每天 9 点汇总竞品」这类任务，9 点半补跑出来的报告语境已经不对了，过期执行比漏执行更糟；且 scheduled_at <= created_at 的判定还顺手挡住了「刚注册就把历史时刻全补一遍」的风暴。这是个有观点的取舍：定时 Agent 任务的语义更像日历提醒，不像消息队列。

Q3 · webhook 是公开端点（无鉴权），安全怎么做？

/api/webhooks/t/{token} 确实是公开 POST 端点（main.py 挂载时注明无 API 前缀），安全靠四道闸而非登录态：① 不可猜的 URL token 本身就是凭证，且 token 查不到时也返回 200，不泄露 token 是否存在；② 限流——Redis 滑动窗口每 token 每分钟 5 次（Agent 级可配 webhook_rate_limit），硬顶 60 次/分钟防内存滥用，被限流的丢弃会写审计日志（webhook_rate_limited）让主人看得见；③ 负载上限 64KB；④ 可选 HMAC 验签——config 里配了 secret 就校验 x-hub-signature-256（GitHub 风格），用 hmac.compare_digest 防时序攻击。防重放则交给下游幂等键：同一事件重复 POST 也只入队一次。

Q4 · Agent 能自己注册触发器，怎么防止它给自己埋一堆闹钟把系统打爆？

限额是分层设计的，而不是一刀切的开关：数量闸——每 Agent 默认 20 个触发器上限（agents.max_triggers，租户级有默认值 default_max_triggers）；频率闸——poll 最小间隔 5 分钟（Agent 级 min_poll_interval_min，租户有下限 floor 防调低），每个触发器还有 cooldown_seconds（默认 60 秒）冷却；行为闸——on_message 每 Agent 每小时最多触发 30 次，超限自动停用该触发器并告警（防 A2A 消息环路：A 醒来说话触发 B，B 说话又触发 A）；寿命闸——max_fires 到数自动停、expires_at 到期自动停、once 触发即停。设计上值得注意的一点：这些限额写在 Agent 和租户两张表上，是配置而非硬编码，运营上可以按租户调节奏。

Q5 · 这套触发器和 crontab / Airflow 的本质区别是什么？

三个字：一等公民。crontab 的调度对象是无状态的脚本，Airflow 的 DAG 由工程师在代码里定义；音巢的触发器是 Agent 自己可读写的资源——它通过 set_trigger 工具在对话中自主注册（「明早提醒我」这句话直接变成一条 cron 记录），reason 字段就是未来那次唤醒的指令，focus_ref 把闹钟绑到具体关注点，醒来后进入的是和真人对话完全相同的 Agent Runtime（同一命令队列、同一工具面、同一审计）。还有一个容易被忽略的差异：crontab 触发的是「任务」，这里触发的是「带上下文的判断」——唤醒上下文里带着原因和关联 Focus，Agent 醒来后可以决定「看了眼情况，其实不用行动」，这是调度系统给不了的。

Q6 · poll 触发器的去重与状态是怎么保存的？重启会丢吗？

状态不在内存，在数据库——每次轮询后把当前值写回触发器 config 的 _last_value 字段（JSONB），下次比对的就是上一轮的落库值，进程重启、副本切换都不影响。去重有两个层面：判定层——值没变（或首次建档）就不触发，「变化才唤醒，平安不打扰」；入队层——poll 的幂等键是 poll:{trigger_id}:{sha256(_last_value)}，同一内容即使被多个副本同时判为「变了」，唯一约束也只放行一条执行记录。另外有两个防御细节值得说：抓取前做 is_private_url 检查（解析 DNS 后拒绝私网/回环地址，防 Agent 被诱导当 SSRF 跳板打内网）；HTTP 超时固定 10 秒，慢目标不会拖垮 15 秒的调度节拍。

自主意识，始于「自己会醒」

Focus 让 Agent 记得自己在盯什么，触发器让外部世界能叫醒它，心跳让它没事也会起来转转。

这三块拼起来，Agent 才第一次有了自己的时间表——而不是永远等着人类开口。

所谓数字员工，不是「随叫随到」，而是「不请自来，来了还真有事」。Aware 系统就是把这件事做成了工程。
