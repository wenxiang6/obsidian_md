01 · 背景与目标

业务助理有「手」了，还需要一个「脑」

目标 · 一句话

让业务助理从「只能查数据」升级为「数据 + 规则都能答」，且每一条规则答案都带来源引用、留审计流水。

实现路径的关键决策已经做出：知识库不自研，直接采用三方成熟能力——火山方舟。本方案解决的是「怎么接、接成什么样、分几步接、坑在哪里」。

02 · 选型

为什么是三方知识库，而不是自己造

知识库的难点从来不在「存向量」，而在切片质量、向量模型、召回调优这一整条需要持续投入的工程链。业务团队的资源应该花在知识内容本身。

维度自研 · ES BM25自研 · 本地向量库火山方舟知识库
切片质量无切片概念，按文档/字段索引需自研切片策略（按语义/标题/长度），质量靠调平台自动切片，针对中文文档优化，控制台可视
向量模型无语义召回（BM25 纯关键词）需自购/自部署 embedding 模型，效果自担内置向量化模型，与豆包生成模型同栈协同
运维成本ES 集群已在跑（7.17），增量小向量库部署、索引重建、容量规划全套自理托管服务，零运维；底层 VikingDB 向量库
召回调优只能调分词与权重切片/向量/重排三层都要自己调控制台试召回 + topK / 阈值参数化，调优有界面
上线周期短，但天花板低长（模型选型 + 工程链搭建以周计）短：建库、传文档、调 API 三步
成本近似为零（既有集群）GPU/存储 + 人力，隐性成本高按 token/调用计费，新用户有免费额度，量级可控
关于本机已有的 ES 7.17

本机部署的 ES 7.17 已在跑，但 IK 中文分词插件缺失（external-coordination 登记的外部阻塞，解除时间未定）；即便补上 IK，BM25 也只是关键词匹配，没有语义召回能力——「券用不了」匹配不到「优惠券核销门槛」。ES 继续服务商品搜索场景，知识问答不在它身上叠加。

结论：知识库是成熟的三方能力，业务团队不该养一支向量检索队。火山方舟同时提供知识库（自动切片 + 向量化 + VikingDB 索引）与豆包系列生成模型，召回与生成同栈，是本项目约束下（小团队、快上线、可审计）的最优解。火山方舟能力的官方描述以火山引擎官方文档为准。

关键决策：在线集成模式 A vs B

显式召回 + 自行组装 vs 对话即召回 K1

选项

① 模式 A：chat.completions 挂内置 knowledge_base_search 工具，模型自主决定何时检索
② 模式 B：先调知识检索接口拿 topN + 分数，业务侧做阈值判断与 prompt 组装，再调 LLM 生成

决定

模式 B 为主，模式 A 列为二期简化选项

原因

与 WriteGuard 同一套服务端护栏传统：每步可审计（检索词、命中切片、分数、prompt、答案全落流水）；低分可兜底（不硬答）；答案可带引用溯源（切片标题 + 分数）。模式 A 简单但检索时机与结果不可控、审计粒度粗。

代价

链路上多一次检索调用，延迟增加；阈值与 prompt 模板需要自己调优维护。换取的是每一步的可见性与可干预性。

05 · 工具设计

两个只读工具，挂在既有治理链上

工具数量刻意克制：检索与生成分开，是为了让业务助理可以只召回不生成（便宜、可自检），也让验收可以分层进行。

工具入参返回说明
kb_search query（≤200 字）, topK（默认 5，封顶 10） 切片列表：标题 / 来源文档 / 摘要 / score 显式召回，不含生成；供业务助理自检「知识库里到底有没有这条规则」 读
kb_ask question（≤500 字）, topK（默认 5，封顶 10） 答案正文 + 引用列表 + 命中分数；低分时为兜底话术 + 候选标题 检索 → 阈值判断 → 豆包生成全链路（图 2） 读
  • 只读不写：知识库的内容管理（上传 / 更新 / 删除）走方舟控制台或独立同步流程，不进入 MCP 工具面——与「高危操作通道化」的长期边界一致，Agent 没有改知识的通道。
  • 超时与降级：检索与生成各设 8s 超时；失败返回明确错误结构（code / message / suggestion），不抛栈给模型。
  • 审计：kb 调用同样写 mcp_audit_log，tool_name 区分；记录检索词、命中切片与分数、token 用量——成本与质量双回溯。
  • 参数规范：question / query 长度上限（500 / 200 字），topK 封顶 10（Math.min(topK, 10)）——延续「所有无界入参必须有服务端封顶」的既有规范。
  • 幂等不适用：只读工具无写副作用，不走 WriteGuard 幂等链；但鉴权与审计照走，治理口径与 18 个既有工具完全一致。
06 · 数据与同步

首批 50–80 篇入库，hash 对账、每周校验

知识库的价值上限由内容质量决定——首批清单求精不求全，同步机制求稳不求快。

首批入库清单

知识源内容量级入库方式
工作台 docs/business-domain-overview、各端仓库说明、external-coordination（外部阻塞与口径登记）约 10 篇md 直传
iterations/ 档案精选各迭代 technical-design 与排障实录（组织记忆；activity 流水不入库，噪声大）15–25 篇md 精选后传

元数据规范（每篇必带）

  • title：人读标题，引用标注时直接展示；source：来源路径（如 docs/business-domain-overview.md），便于回查原文；domain：业务域标签（order / coupon / aftersale / ops / dev），一期仅做标注，二期用于按域过滤与分级。
  • 元数据随上传写入方舟文档属性（具体字段实现期核对官方文档），本地 kb_sync 表留存同一份，两侧可对账。

同步策略

  • 变更触发：文档变更 → 重传对应篇（方舟侧按文档 ID 覆盖更新）；kb_sync 记录文件 hash，hash 不变不上传，避免无效重写索引。
  • 全量校验：每周一次全量比对（本地清单 vs 方舟文档列表 vs hash），漂移项进巡检告警。
  • 删除策略：源文档下线 → 方舟侧同步删除 + kb_sync 标记 tombstone，保留 30 天记录供审计追溯；知识库不留「孤儿文档」。
07 · 安全与合规

密钥不出本机，流水全部留痕，成本有闸门

  • 内容可见范围：一期入库内容按「内部全员可见」处理——所有入库文档默认可被任何持凭证的调用方检索到。制度分级（如薪酬、财务相关）明确不进一期范围，分级机制（按域过滤 + 按调用方角色裁剪）留到二期。
  • 密钥管理：方舟 API Key（ARK_API_KEY，VikingDB 若直调则用独立密钥或 AK/SK 签名）走环境变量 / 本机密钥存储注入，不进代码库、不进迭代文档、不出现在本方案之外的任何明文位置——与工作台铁律一致。迭代文档中只出现变量名，不出现值。
  • 上传前脱敏：清洗规范的第一条是敏感信息剥离——文档里的密钥、内部凭证、个人数据在上传方舟前必须移除；kb_sync 登记清洗人/清洗时间，责任可追溯。
  • 审计留痕口径：kb_search / kb_ask 调用全量写 mcp_audit_log（调用方、问题、命中切片与分数、token 用量、耗时），与 18 个既有工具同一口径，审计模块无需改动。
  • 成本与限流：方舟按 token 计费，新用户有免费额度；在 mall-mcp 侧做两道闸——① 日级 token 用量统计入审计表，超阈值（初值由 M1 调优后定）触发熔断提醒而非静默烧钱；② kb 工具纳入既有调用频控讨论范围（中期限流路线图的一项）。

09 · 风险与外部协调

显式登记，不静默跳过

按工作台铁律，外部阻塞进 external-coordination 登记。以下六项是本方案最可能翻车的点。

外部依赖 · 火山引擎账号

账号注册、实名认证、知识库服务开通审批均在火山引擎侧，周期不可控。M0 启动即登记 external-coordination，账号未开通前 M1 之后全部阻塞——不静默等待，每周同步状态。

费用与免费额度边界

检索与生成按 token 计费。新用户免费额度够支撑开发与验收，但演示期高频调用可能触达边界——M1 调优时必须产出「单次答疑平均 token 成本」基线，日用量闸门（安全节）依赖这个数。

代理网络可达性

本机有代理残留的前科（JDK net.properties 的 socksProxyHost=127.0.0.1:7890 曾导致 Maven SOCKS 拒连）。Java 进程出访方舟 API 前，需确认 JVM 未继承错误代理配置，或为方舟域名配置直连——M0 的连通性验证就是为此而设。

内容质量决定召回上限

垃圾进垃圾出：制度文档不成文、迭代档案不精选，召回再准也答不出可信答案。首批入库清单（数据节）是质量闸门，宁可少入不可滥入；召回差评的案例要回溯到具体文档并修文档，不是调参数。

服务降级的体验口径

方舟不可用时业务助理不能说「我不知道」就结束——按降级路径返回结构化错误与替代建议（转数据查询 / 稍后再试）。降级话术在 M3 用例中验收，不允许临时发挥。

口径红线：知识库答案 ≠ 业务事实

涉及账户、金额、订单状态的问题，知识库只提供规则解释，事实必须回查工具（双轮协同图 3 的纪律）。kb_ask 的 prompt 模板中写入这条约束：生成答案不得虚构具体订单 / 金额数据，遇到事实性追问引导调用查询工具。

从「工具调用」到「知识供给」

mall-mcp 给了 Agent 一双手——18 个工具，能查、能办、能审批，每一次写操作都有幂等与审计兜底。

知识库给 Agent 一个脑——规则、制度、口径、历史经验，每一条答案都有来源引用，每一次检索都留流水。

手脑配合，才是完整的业务助理。手让我们相信它「能办成事」，脑让我们相信它「说的是对的」。
