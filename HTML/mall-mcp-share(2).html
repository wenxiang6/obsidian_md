Part 1

项目全貌：为什么做、做成了什么

business-agent 工作台的「业务助理」模块需要真实的能力出口。这次迭代把它接上：一个独立运行的 MCP Server，背后是真的 mall 业务库、真的幂等与审计护栏、真的 3000 单数据基线。

01 · 背景与问题

「业务助理」需要一个真实的能力出口

此前业务能力的演示形态停留在前端交互脚本。要让 Agent 真正办成事，业务系统必须提供一组「为 Agent 设计」的调用面，而不是把给人用的东西直接递过去。

业务系统的 REST API，为什么不适合直接喂给 Agent

为页面设计，粒度太粗

mall-admin 的接口按后台页面组织：一个订单列表接口返回的是页面所需的全部字段与嵌套结构。Agent 调用时上下文按 token 计费，一页 50 条「页面级」数据足以把上下文窗口烧掉大半，其中九成字段模型根本用不到。

会话态权限模型，不是凭证态

后台登录走 POST /admin/login 换 JWT，再带 Authorization 头。这套「人登录 → 会话 → 页面操作」的模型，与 Agent「常驻服务、按需调用、调用需留痕到具体操作者」的模型不匹配——Agent 不该去模拟一个管理员登录态。

无幂等、无审计语义

页面操作背后站着人：人不会在一秒内连点三次发货，人记得自己干过什么。Agent 会重试、会循环、会并行。REST 接口没有幂等键、没有回执、没有操作流水，直接暴露给 Agent 等于把护栏拆掉。

为什么不走另外两条捷径

捷径为什么被否决
Agent 直连数据库 等于把全部业务约束（状态机、金额口径、操作历史写入）交给模型即兴发挥。模型知道「发货是改 status=2」，但它不会每次都记得同时写 oms_order_operate_history；更无法解释「谁在什么时候改的」。数据库直连是演示期看起来最快、出事时最难收场的方式。
裸调现有 REST 粒度与鉴权问题如上；并且写接口（发货、关单、审批）在 mall-admin 里耦合着 Spring Security 的登录用户体系，Agent 调它们必须伪装成一个管理员账号，操作者身份在审计层面彻底丢失。

结论：需要一层独立的「协议出口」——为 Agent 的调用习惯重新设计粒度（摘要式返回、分页上限），自带凭证鉴权、幂等、审计、状态机守护。这层出口就是 mall-mcp。

02 · 为什么是 MCP

MCP 是什么，以及为什么是它

Model Context Protocol 是 Anthropic 主导开放的模型上下文协议。一句话定位：把「工具 / 资源 / 提示词」的暴露方式标准化，让任何兼容客户端都能发现并使用服务能力。

协议骨架

  • 传输层是 JSON-RPC 2.0：每个请求有 jsonrpc:"2.0"、method、params、id；通知（notification）不携带 id、不需要应答——这个区别在排障实录 D 里救过我们一命，也坑过我们一次。
  • 生命周期是显式的：initialize 握手协商协议版本与双方能力 → 客户端回 notifications/initialized → 之后才能 tools/list 发现工具、tools/call 调用工具。
  • 能力自描述：每个工具带名称、自然语言描述、入参 JSON Schema。客户端（模型）靠描述决定「什么时候用、怎么填参」，不需要人事先写提示词教它。
  • 两种传输：stdio（本地子进程，客户端拉起即用）与远程 HTTP（SSE / Streamable HTTP）。mall-mcp 选的是后者——原因见技术选型一节。

03 · 业务价值

四类能力，覆盖「业务助理」的全部演示场景

18 个工具按业务语义分四类。分类口径说明：迭代早期的技术方案按「17 个」登记，是把退货申请查询（return_apply_list）漏算进了查询类；实测 tools/list 注册 18 个，本文以实测为准。

查

查询 · 9 个

商品、订单、会员、优惠券、退货申请五大域的搜索与详情。对应业务助理的「查一下订单 M2026… 到哪了」「这个会员累计消费多少」。全部只读、分页上限 50、状态码翻译成中文。

办

办理 · 2 个

订单发货（order_ship）、关闭待付款订单（order_close）。对应「帮我把这单发了」「这单超时没付，关掉」。写操作，强制幂等键 + 审计回执 + 状态机守护。

批

审批 · 1 个

退货申请审批（return_apply_handle）：通过流转为退货中，驳回为已拒绝，写处理人与备注。对应「售后单给我批一下」。审批是「办理」中责任最重的一类，单独成类。

指

指标 · 6 个

销售概览、销售趋势、销售额 Top 商品、会员增长、订单状态分布、券核销率。对应「本周卖得怎么样」——这是本次迭代新增的能力面，直接建立在 3000 单数据基线上才有说服力。

与 business-agent 理念的一一对应

business-agent 理念在 mall-mcp 里的落法
人只在决策点出现MCP 层不做「确认卡」交互，但写工具全部幂等 + 审计回执——上层 Agent 界面确认后下发的调用，可以安全重试；每一笔写操作都有 RCPT 回执可对人交差。
发布权在人高危操作（改价、批量发券）根本不暴露为工具，只能走需求迭代任务通道。能力面的「不提供」本身就是一道闸门。
外部阻塞显式记录状态守护的拒绝语义是显式的：「当前状态为『已发货』，不允许发货（仅待发货可发货）」——失败原因说人话，绝不静默跳过、绝不假装成功。
操作留痕、版本可审计mcp_audit_log 记录工具名、参数摘要、操作者、回执号、成败；操作者来自请求头 X-MCP-Operator，穿透到审计流水。
一句话价值主张

业务人员在 IM 或工作台里用自然语言，完成原本要登录后台、找菜单、点按钮的事

「上周 GMV 多少」「把订单 20000017 发顺丰 SF1234」「这批退货申请帮我过一遍」——模型的表达力负责理解意图，mall-mcp 的纪律负责安全执行。前者可以换，后者不能缺。

Part 2

数据基线工程：让任何环境开箱即有可信数据

指标工具的可信度完全取决于数据底座。这部分记录一套数据基线（staging data baseline）初始化工具是如何设计与验收的：数据即代码、固定种子可复现、ID 段避开存量数据、幂等导入可重复执行。

05 · 为什么先做数据基线

38 个商品、65 张订单的存量数据，撑不起指标联调

预发/演示环境的预置数据（mall.sql 初始数据）量级是：38 个商品、65 张订单。对着它调用 metric_sales_trend，近 30 天序列大面积为零；调用 metric_order_status_distribution，占比分布没有统计意义；「本周销售额」的答案在个位数订单上没有任何说服力，联调与压测更无从谈起。

因此我们需要一套数据基线初始化工具：环境拉起后一键注入一批规模足够、分布合理、业务自洽的数据，让任何环境开箱即达到「可演示、可联调、可验收」的基线水位。两条硬约束：

  • 不能破坏存量数据——mall-admin 后台的原有功能（商品管理、订单列表分页）必须照常可用，基线数据只能增量叠加，不能改写或删除存量行；
  • 必须可复现、可重复导入——任何一台机器、任何一次环境重建，跑同一个脚本要得到同一份数据；导入失败重来不能留下半份脏数据。
关键决策

不写一次性手工 SQL，而是写一个数据基线生成器：document/sql/staging/gen-staging-data.js（Node，无第三方依赖）。数据即代码——分布规则、ID 规划、业务联动全部可读可评审，重建环境时一键重放。

06 · 生成器设计

可复现随机 + ID 段规划 + 业务联动

生成器约 330 行，输出一份 4.5MB 的多行 INSERT SQL（staging-data.sql）。设计上有四个值得展开的点。

固定种子的可复现随机

用 mulberry32 伪随机算法，种子固定为 20261019。重复运行产出逐字节一致的 SQL——这意味着「数据问题」可以被当作代码问题来复现和评审，而不是「我这边随机出来的不一样」。

let _seed = 20261019; function rnd() { // mulberry32 _seed |= 0; _seed = (_seed + 0x6D2B79F5) | 0; let t = Math.imul(_seed ^ (_seed >>> 15), 1 | _seed); t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t; return ((t ^ (t >>> 14)) >>> 0) / 4294967296; }

时间分布与状态演化：让数据「像真的发生过」

  • 订单创建时间：近 180 天内按 Math.pow(rnd(), 0.6) 分布——指数小于 1 使密度近密远疏，模拟「最近单量多」的真实电商曲线，也让近 7 天 / 近 30 天指标都有料。
  • 订单状态按单龄演化：1 天内的单约 55% 还在待付款（真实场景新单来不及付）；1–3 天的单大部分已发货在途；3 天以上约 78% 已完成，残留少量已发货、已关闭、待发货的「长尾异常单」。这个演化规则直接决定了「待发货队列里永远有单可发」——写工具演示因此随时可行。
  • 时间字段联动：支付时间 = 创建时间 + 1~40 分钟；发货时间 = 支付 + 8~48 小时；收货时间 = 发货 + 24~96 小时；四成已完成订单带评价时间。整条生命周期的时间戳不出现因果倒置。

真实感来源与业务联动

人的真实感

姓氏池（王李张刘…近百姓）× 名字池（伟/芳/梓涵/浩然…）拼中文名，英文昵称池（Momo/Leo/Kobe24…）兜底；手机号走真实号段（130-199 共 27 段）；地址用真实省市区 + 街道名 + 「楼栋/室」组合。65% 中文昵称、35% 英文昵称，接近真实会员构成。

货的真实感

59 个商品全部是有价格带认知的真实品名：华为 Mate 70 Pro 6499、小米手环10 279、美的酷省电空调 2399、优衣库 AIRism T恤 79……覆盖 12 个类目、9 个品牌，价格从 79 到 13999 拉开梯度，客单价分布才自然。

钱的联动

痕迹的联动

09 · 技术选型与背后原因

五个决定，每个都写清「选项 → 决定 → 原因 → 代价」

选型不是列答案，是记录权衡。代价一栏与结论同等重要——它决定了未来什么时候应该推翻这个决定。

独立模块 vs 嵌入 mall-admin D1

选项

① 新建 mall-mcp 模块
② 在 mall-admin 里加 MCP 端点

决定

独立模块，端口 8186

原因

隔离爆炸半径：MCP 层出问题不影响后台服务；独立演进：协议栈升级、工具增删不必动业务模块；独立端口便于网关层单独限流与审计。

代价

多一个进程要维护；与 mall-admin 的口径一致性要靠约定（指标口径一节）而非编译期保证。

JdbcTemplate vs 引入 mall-mbg 的 MyBatis D2

选项

① 复用 mall-mbg 生成的 Mapper/Model
② 裸 JdbcTemplate 手写 SQL

决定

JdbcTemplate

原因

MCP 工具以聚合与关联查询为主（GMV、趋势、Top 榜、状态分布），生成式 Mapper 的 Example 查询模型表达这类 SQL 反而绕；引入 mall-mbg 等于拖入整个 MyBatis 体系和 152 个用不到的 model 类。

代价

手写 SQL 要自己保证字段名正确（没有编译期检查）；防注入靠参数绑定纪律，本次 coupon_list 的 keyword 过滤即手工剥除单引号——已知粗糙点，记录在案。

SSE 远程服务 vs stdio D3

选项

① stdio：客户端拉起本地子进程
② 远程 HTTP（SSE）：常驻服务

决定

SSE 远程服务 :8186

原因

常驻服务才能多客户端共享同一份工具与治理；HTTP 可审计可限流；与 business-agent「状态在常驻 Host」的理念一致——浏览器/客户端只是遥控器。

代价

SSE 是 MCP 早期传输形态，官方已标记 legacy（Streamable HTTP 是后继）；且 Spring AI 1.0.2 的 SSE 实现有传输层缺陷（排障实录 C）。

静态 X-MCP-Token vs 接 mall-security JWT D4

选项

① 静态凭证头
② 对接 mall-security 的 JWT/RBAC

决定

静态 token，过滤器一处收口

原因

演示边界内不过度设计：JWT 体系依赖登录会话与用户表，与「常驻服务、机器调用」模型不匹配；鉴权逻辑集中在 McpAuthFilter 一个类里，生产化时在过滤器内换实现即可，调用链不动。

代价

静态 token 无法区分真实操作者（只能靠 X-MCP-Operator 自报家门，写入审计但不防伪）；token 泄露即全量能力泄露。演进路线里有 OAuth 与 RBAC 两节专门收口此事。

服务端幂等+审计 vs 只靠上层确认卡 D5

选项

① 信任上层 Agent 的确认卡交互
② MCP 服务端自建 WriteGuard

决定

服务端护栏不可替代

原因

确认卡防的是「未经人同意」，防不了「同意之后执行两次」：Agent 会重试（网络抖动）、会循环（自我修正）、会并行（多步任务）。幂等是执行层问题，必须在执行层解决。

代价

每个写工具都要经 WriteGuard 包一层；幂等表随时间膨胀，需要后续加归档策略（见演进路线）。

10 · 工具设计规范

写给模型看的接口，和写给人看的不是一回事

  • 读写分级与命名：只读工具用 search / get / list / history / metric_* 命名，写工具用动词（ship / close / handle）并在描述首句标注「（写操作）」。模型选工具时第一眼就能看到副作用等级。
  • 描述即提示词：每个 @Tool 的 description 写明「做什么 + 关键约束」，例如 order_ship 的描述直接写明「仅待发货（status=1）可发货，需幂等键」——模型的参数填充与前置判断高度依赖这段文字，写它是设计工作不是注释工作。
  • 分页上限 50，防上下文爆炸：所有 list/search 工具 pageSize 默认 10、封顶 50（Math.min(pageSize, 50)）；指标类 days 封顶 365、榜单 limit 封顶 50。模型很容易「给我全部」——上限就是给这句话的护栏。
  • 状态码中文化：数据库里是 0/1/2/3/4，模型和业务看到的必须是「待付款/待发货/已发货」。Dicts 类集中维护订单、退货、支付方式、来源四个字典，与 mall 前端口径一致；查询结果统一补 status_text 等字段，不让模型去猜数字含义。

11 · 治理设计：WriteGuard

幂等、审计、状态机守护，收在一条执行链里

所有写工具共用一个护栏：写操作的业务语义各有不同，但「重复安全、全程留痕、不产生脏流转」这三件事是统一的。

执行链

requestId 为空？
拒绝执行 查 mcp_idempotency 命中 → 返回首次结果
标 duplicate:true 未命中 → 执行业务动作
（状态守护 UPDATE） 审计落库
生成 RCPT 回执 结果写入幂等表
  • 幂等键即主键：mcp_idempotency 主键为 (request_id, tool_name)，同一 requestId 重复 INSERT 抛 DuplicateKeyException 直接吞掉——并发下同 requestId 只保留第一条，数据库约束兜底，不依赖应用层判断的时序。
  • 审计先于返回：业务动作执行后立即落 mcp_audit_log 并生成回执号，回执号格式 RCPT-yyyyMMddHHmmss + 4位随机（如 RCPT-2026101914302207xx）。回执随结果返回给调用方，可对人口头交差，可在审计模块反查。
  • 状态机守护在 SQL 层：发货的 UPDATE 写成 UPDATE oms_order SET … status=2 WHERE id=? AND status=1——前置状态条件嵌在 WHERE 里，并发下两个发货请求只会有一个影响行数为 1，另一个影响行数为 0 即判失败，不产生「已发货又被发一次」的脏流转。代码层的状态预检（SELECT status）只是为了给出「当前状态为『已发货』」的人话提示，真正的防线是 WHERE 条件。
  • 事务边界：写工具方法标 @Transactional，业务 UPDATE 与操作历史 INSERT 同生共死。

关键决策：为什么审计表和幂等表是两张表

职责不同、生命周期不同、查询模式不同。审计表是追加写的流水：成功失败都记、永远只增、按时间检索、未来要归档；幂等表是去重字典：只记成功执行的最终结果、以主键命中为唯一访问方式、记录可以随业务窗口期清理。合成一张表，两个职责会互相绑架索引设计与清理策略。分开之后，审计可以大胆记全量，幂等可以放心存完整结果 JSON。

12 · 指标口径定义

口径先于 SQL：六个指标工具的计算规则

指标最大的风险不是算错，是「和后台看到的对不上」。本节把所有口径写明，与 mall-admin 的统计语义保持一致。

工具口径定义SQL 要点
metric_sales_overviewGMV = 近 N 天已支付订单（status ∈ 1,2,3，即待发货/已发货/已完成）的 pay_amount 汇总；支付转化率 = 已支付单 / 创建单（保留 1 位小数）；客单价 = GMV / 已支付单数SUM(CASE WHEN status IN (1,2,3) THEN pay_amount END)；转化率用 Math.round(paid*1000/total)/10
metric_sales_trend近 N 天按创建日期的订单数与 GMV 双序列，GMV 口径同上GROUP BY DATE(create_time) ORDER BY stat_date
metric_top_products近 N 天已支付订单的明细按商品聚合，销售额降序oms_order_item JOIN oms_order，o.status IN (1,2,3)，ORDER BY sale_amount DESC
metric_member_growth近 N 天按注册日期的新增会员序列 + 期末总会员数ums_member GROUP BY DATE(create_time)；total 另查全表 COUNT
metric_order_status_distribution全量订单按状态分组计数与占比（占比和 ≈ 100%）GROUP BY status，ratio 保留 1 位小数，附 status_text
metric_coupon_usage核销率 = use_count / receive_count × 100（1 位小数），全券或指定券ROUND(c.use_count*100.0/NULLIF(c.receive_count,0),1)，NULLIF 防除零

「已支付」取 status ∈ (1,2,3) 而非仅看 pay_type：待付款（0）与已关闭（4）不产生 GMV；无效订单（5）同样排除。这个口径与 mall-admin 订单统计的语义一致，业务在后台看到的数字和 Agent 报出的数字可以对账。

13 · 排障实录

六个坑：从本机代理到协议栈缺陷

按遇到的时间顺序排列。前两个是环境坑，中间两个是 MCP 协议栈坑，后两个是依赖与工程习惯坑。

A

本机 JDK 内置代理未运行：Maven 报 SOCKS Connection refused

环境层 · 耗时约 40 分钟

现象

mvn package 下载依赖全部失败，错误是 SOCKS: Connection refused；同一时段 docker compose pull 拉取 quay.io 的 minio 镜像同样失败。两处错误表面无关。

定位过程

  • 先查 Maven 的 settings.xml：只配置了阿里云镜像，没有任何 proxy 配置——排除「配置文件里写了代理」；
  • 再查 shell 环境变量：http_proxy / https_proxy / all_proxy 全部为空——排除「环境变量注入」；
  • 最终定位到 JDK 的 net.properties：本机 JDK 的该文件里写死了 socksProxyHost=127.0.0.1 / socksProxyPort=7890（此前为别的事情配置后遗留在 JDK 安装目录里，属于 JDK 级默认值，任何 Java 进程都会继承）。本机 7890 端口的代理软件当时并未运行，于是所有 Java 网络出站都撞在 Connection refused 上。

根因

JDK 安装目录内的 conf/net.properties 是 JVM 网络默认值来源，优先级低于命令行 -D 参数但高于「什么都没配」的直觉。它是一个不会被 settings.xml、不会被环境变量、也不会被 IDE 设置覆盖的暗层。

解法

构建时显式清空代理属性：MAVEN_OPTS="-Dhttp.proxyHost= -Dhttps.proxyHost= -DsocksProxyHost="（置空字符串即禁用），不改 JDK 安装目录本身（它还被别的用途占用）。Docker 拉取失败同属代理缺失，按已知限制跳过 minio 并在文档显式登记。

坑与教训
  • 「网络不通」和「配置错误」要在报错层面区分开：Connection refused 指向的是有一个配置在引用一个不存在的服务，而不是外网不可达——排查方向完全不同。
  • CI 化/工作台化时，环境检查应探活代理端口（能连通 7890 才算代理可用），而不是检查「有没有配代理」。
  • JDK 安装目录是有状态的。换 JDK、重装 JDK 之后配置消失，问题会「自愈」并在半年后无人能解释。
B

Docker Desktop 容器 start 假死

环境层 · 耗时约 30 分钟

现象

docker start mysql 命令挂起无输出、无报错、无超时；docker ps -a 里容器停在 Created 态纹丝不动；Docker Desktop 的 UI 同样转圈。

定位过程

先怀疑容器自身问题：docker logs 无输出（容器从未真正起来）；docker inspect 显示状态正常但 PID 为空。再怀疑镜像损坏，但 docker images 正常。最终确认是 Docker Desktop 的虚拟机层卡死：所有 daemon 级操作都无响应，与具体容器无关。

根因

Docker Desktop（macOS）的 Linux VM 偶发状态不一致，容器操作被卡在 VM 层。属于桌面版 Docker 的已知不稳定类问题，与项目配置无关。

解法

killall Docker && open -a Docker 重启 Docker Desktop。重启后所有容器正常启动，数据卷无损——基线数据随后重新导入（幂等导入的设计此时兑现了价值）。

坑与教训
  • 「命令挂起无输出」本身就是诊断信号：先区分是被操作对象的问题还是操作通道的问题。用另一个无关容器试一次 start，一分钟就能分清。
  • 数据层的幂等可重放能力（基线数据的 DELETE+INSERT 导入）让环境故障的恢复成本趋近于零——重放设计在平时是洁癖，在故障时是保险。
C

Spring AI 1.0.2 的 SSE 传输缺陷：tools/list 永久挂起

协议栈 · 耗时约 2 小时 · 本迭代最深的坑

现象

SSE 握手正常、initialize 正常应答，但 tools/list 与 tools/call 请求发出后永久无响应：SSE 流上没有结果事件、没有错误事件，客户端等到天荒地老。服务端 DEBUG 日志停在收到请求的一刻：

定位过程

  • 先怀疑客户端：自写测试脚本是自己拼的 JSON-RPC，逐字节核对请求格式——无误；
  • 对比排除法：同样的会话链路、同样的 POST 通道，initialize 能拿到应答而 tools/list 不能——证明传输通道本身是通的，问题出在「请求被收下之后」的处理环节；
  • 换客户端验证：用官方 MCP 客户端连同一个服务，复现同样的挂起——确认是服务端问题而非自写脚本问题；
  • 查 Spring AI 与 MCP Java SDK 的 issue/更新记录：1.0.x 的 SSE 传输层存在已知缺陷，在请求-响应关联（session 内 requestId 路由）上会丢请求。

根因

Spring AI MCP Server 1.0.2 所依赖的 MCP Java SDK 早期版本，SSE 传输实现在 session 内分发请求响应时存在缺陷：请求被 session 接收（日志可见）但响应未正确路由回 SSE 流。initialize 能应答是因为握手路径走了另一条初始化分支。

解法

升级 Spring AI 到 1.1.8（pom 中 <spring-ai.version>1.1.8</spring-ai.version>），同一份业务代码零改动，tools/list 与 tools/call 立即正常。这正是 pom 里把版本抽成属性的意义——升级是一行的事。

坑与教训
  • 协议栈早期版本的传输层缺陷，症状是「静默吞请求」——没有异常栈可查。先建立基线再怀疑自己：用官方客户端验证服务端、用已知好使的服务端验证客户端，两端各有一个参照物，二分才有支点。
  • 「initialize 正常」不代表「传输正常」。协议实现里握手路径和业务路径常常是两套代码，验证要覆盖到真正的业务调用。
  • 依赖版本升级应作为首选解法之一纳入排查清单，而不是最后手段——早期协议栈的 bug 密度足以让「升级试试」成为高期望值动作。

MCP 会话状态机：notifications/initialized 的两个细节

协议层 · 与 C 叠加出现

现象

两个问题先后出现：① 客户端把 notifications/initialized 当成普通请求带上了 id，服务端返回 Method not found；② 修正后漏发该通知直接调 tools/list，请求既无响应也无错误，像被黑洞吞掉。

定位过程

对照 MCP 规范逐字核对握手流程：initialized 是 notification（通知），协议规定通知不携带 id、不期望应答；带了 id 它就被当作一个名为 initialized 的「方法调用」，而服务端没有这个方法，于是 Method not found。第二个现象对照服务端会话状态机：收到 initialized 之前，session 处于「初始化中」态，规范允许实现直接丢弃其他请求——Spring AI 的实现就是静默丢弃。

根因

JSON-RPC 2.0 里 notification 与 request 的差别不只是「要不要等回包」，而是协议状态机的不同输入。自写客户端把两者混为一谈，就会在状态机边界上踩空。

解法

自写测试客户端严格区分：initialize 带 id 等应答 → 收到应答后立刻发 {jsonrpc:"2.0", method:"notifications/initialized"}（无 id 字段）→ 之后才进入 tools/list、tools/call 阶段。测试脚本里用注释把这半步标为「协议关键路径」。

坑与教训
  • 「没有响应」在协议层是合法的。排障时不要把无响应当成网络问题重试——它可能正是状态机给你的答案。
  • 自写协议客户端时，把规范的「生命周期」章节当作代码来读，每个状态迁移都对应一行必须存在（或必须不存在）的字段。

mysql-connector 9.x 时间类型变化：coupon_list 抛 ClassCastException

依赖层 · 耗时约 20 分钟

现象

coupon_list 调用报错：java.time.LocalDateTime cannot be cast to java.util.Date。代码里对 start_time / end_time 做了 (java.util.Date) 强转以计算券的当前有效性。

定位过程

异常栈直指强转行。核对驱动版本：父 pom 的 mysql-connector-j 为 9.3.0。8.x 时代 MySQL 的 DATETIME 列经 queryForList 取出默认映射为 java.sql.Timestamp（java.util.Date 的子类，强转成立）；9.x 起默认映射改为 java.time.LocalDateTime，强转链条断裂。

根因

JDBC 4.2 之后驱动对时间类型的 Java 8 时间 API 映射是推荐路径，9.x 把它变成了默认行为。任何依赖「取出来强转 java.util.Date」老习惯的代码都会在驱动大版本升级后爆炸。

解法

不改全局映射（避免影响面扩大），在 CouponTools 内加类型兜底的 toEpoch 工具方法：

private static long toEpoch(Object time) { if (time instanceof java.time.LocalDateTime ldt) { return ldt.atZone(ZoneId.systemDefault()).toInstant().toEpochMilli(); } if (time instanceof java.util.Date date) { return date.getTime(); } return 0; }
坑与教训
  • 驱动主版本升级（8→9）必须重测类型映射，尤其是时间、布尔、无符号整数这三类「静默换型」高发区。
  • 对 JDBC 取出的 Object 做类型假设是技术债；instanceof 兜底虽丑，但在「读别人库的表」这种没有实体类保护的场景里是诚实的写法。

依赖解析错误与编译错误叠加时的排查顺序

工程习惯 · 贯穿全程

现象

升级 Spring AI 版本后首次构建，控制台同时滚动两类错误：上半屏是依赖解析失败（artifact not found），下半屏是编译错误（符号找不到）。先修编译错误的人会在错误的战场上浪费时间——符号找不到只是因为 jar 根本没下下来。

定位过程

另一个干扰项是 -q 静默模式：它把「下载失败」的 WARN 也压掉了，只剩下最后的 BUILD FAILURE 和一堆编译报错，看起来像极了「代码写错了」。去掉 -q 重跑，依赖解析错误立刻显形。

根因

Maven 构建的阶段顺序决定了错误有明确的因果链：依赖解析 → 编译 → 测试 → 打包。上游阶段的错误会以变形的方式在下游阶段重复出现（缺 jar 表现为缺符号）。

解法

固定排查顺序：先 mvn dependency:resolve 确认 POM 与仓库层面干净，再谈编译；构建失败时永远先去掉 -q 拿全量日志。

坑与教训
  • 下游错误是上游错误的影子，修影子于事无补。构建排障的第一原则是「沿阶段顺序从上游往下修」。
  • 静默模式是为「已知健康的工程」准备的，排障时它制造的信息缺口比节省的滚动条贵得多。

18 · 长期与边界

纪律先于能力：哪些事永远不该让工具做

  • 高危操作通道化，而非工具化：改价、批量发券这类影响面大的操作，设计上就不进入 MCP 工具面。它们应该走 business-agent 的需求迭代任务通道——有确认卡、有版本指纹、有验收与回滚方案。「工具能做」和「应该能随手做」是两回事，能力面的克制本身就是安全设计。
  • 写操作双人复核：涉及资金与库存的写工具，中期 RBAC 之上还应引入四人眼原则——同一操作需两个不同 operator 的回执才生效。这在 MCP 层可以实现为「待复核状态 + 第二人确认工具」，评审后再定。
  • 幂等表外部化：当前幂等记录存在业务库 MySQL 里，单实例够用。多实例部署时幂等键的判定要搬到共享存储（Redis 或独立库），且要定义记录保留窗口——幂等承诺不应该是永久的。
  • schema 变更的契约测试与版本指纹：呼应 business-agent 的版本失效理念——工具的入参 Schema 与返回结构应计算版本指纹，指纹变化时下游（工作台展示映射、测试断言）的授权自动失效，强制重新确认。工具契约的静默漂移，是这个架构里最需要防的慢性病。
  • 工具语义版本管理：工具改名、改语义、改口径都必须升版本（如 metric_sales_overview v2），旧版本保留一个周期。模型按描述行事，描述变了而名字没变，是最危险的变更形态。

写在最后：从「给模型一个接口」到「给业务一条纪律」

把 REST 接口直接扔给 Agent，技术上半天就能跑通；这次迭代真正花时间的，是幂等键、审计回执、状态机守护、指标口径、ID 段隔离、幂等导入——全是「纪律」。

MCP 层做的事，是把业务系统多年沉淀的规矩（谁能调、调了算谁的、重复调怎么办、状态不对怎么拒）固化在协议出口上。

模型可以换，客户端可以换，协议可以再演进——但纪律不变。纪律才是那层真正属于业务的资产。

协议与选型 · Q1 – Q5

Q1协议★☆☆
MCP 解决什么问题？与 function calling 直接写 JSON Schema 相比，优劣各是什么？

MCP（Model Context Protocol）把「工具 / 资源 / 提示词」的暴露方式标准化：服务端按协议自描述能力，任何兼容客户端都能发现并使用。它解决的不是「模型能不能调工具」——function calling 也能——而是「每接一个客户端就要重新对接一遍」的 N×M 问题。

对比手写 JSON Schema 的 function calling：后者工具定义硬编码在客户端，服务端加一个工具，所有客户端都要改；MCP 靠 tools/list 运行时自描述，服务端加工具客户端即见。对比 REST 包装一层：REST 没有为模型设计的发现与协商机制，鉴权、分页、错误格式各家自定。

代价也真实存在：引入了一整套协议栈（握手、会话状态机、传输层），调试成本显著上升——本文排障实录 C/D 两个坑都出在协议层而非业务层。结论：能力面会持续增长、调用方不止一个时，MCP 的标准化收益大于协议成本；一次性集成则不必。

Q2协议★★☆
MCP 的传输方式有哪几种？stdio、SSE、Streamable HTTP 的区别与适用场景？

stdio：客户端拉起本地子进程，走标准输入输出。零网络配置、拉起即用，适合本地工具与单用户场景；但进程随客户端生灭，无法多客户端共享，也没有 HTTP 层的鉴权、审计、限流可挂。

SSE（远程 HTTP）：常驻服务，客户端 GET /sse 建立事件流，服务端通过 endpoint 事件下发一个带 sessionId 的 POST 地址，请求与响应走「POST 发、SSE 收」双通道。有状态会话、可多客户端共享、HTTP 语义对防火墙与代理友好。mall-mcp 选它正是因为演示环境需要多客户端共享一个常驻服务，且 HTTP 层可挂过滤器做鉴权审计。

Streamable HTTP：官方钦定的 SSE 后继，把双通道收敛为单端点并支持可恢复流。本项目演进路线已列入升级——Spring AI 1.1.x 已支持且与 SSE 双端点并存，SSE 端点保留一个版本周期供旧客户端过渡。

Q3协议★★★
SSE 的原理？与 WebSocket 的本质区别？为什么 MCP 早期选 SSE、后来演进为 Streamable HTTP？

SSE 本质是一条永不结束的 HTTP 响应：Content-Type 为 text/event-stream，服务端按 `event:` / `data:` 帧格式持续推送。它是单向的（server→client）、纯 HTTP 语义、浏览器 EventSource 自带自动重连（Last-Event-ID），对代理与防火墙天然友好。

WebSocket 则是通过 Upgrade 握手把 HTTP 连接切换为独立的双向帧协议：双向、低延迟，但脱离了 HTTP 语义——代理需要单独支持、鉴权/限流/审计这些 HTTP 层设施都要重做。MCP 的请求-响应模型本就是「客户端发请求、服务端回事件」，双向帧并非刚需。

MCP 早期选 SSE，是因为在「单向推送 + 独立 POST 请求通道」的组合下，整个会话都留在 HTTP 语义内，网关、过滤器、日志全部复用。但双通道（一个 SSE 流 + 一个 POST 端点）带来了会话管理复杂度，Streamable HTTP 把两者收敛进单端点、并支持断线恢复，因此成为后继。本文的取舍表里 SSE 已被官方标记 legacy。

Q4协议★★★
完整描述 MCP 一次会话的握手流程：initialize 协商了什么？notifications/initialized 的作用？为什么它必须不带 id？

三步：① 客户端发 initialize 请求，双方协商 protocolVersion（协议版本）、capabilities（双方能力集）、serverInfo/clientInfo（实现标识）；② 客户端回 notifications/initialized 通知，宣告「握手完成」；③ 之后才进入 tools/list 发现工具、tools/call 调用工具的正常阶段。

initialized 的作用是显式推进服务端会话状态机：收到它之前，session 处于「初始化中」态，规范允许实现直接丢弃其他请求——Spring AI 的实现就是静默丢弃。本文踩坑实录：漏发该通知直接调 tools/list，请求既无响应也无错误，像被黑洞吞掉。

必须不带 id，因为 JSON-RPC 2.0 里通知（notification）与请求（request）是状态机的两种不同输入：通知不携带 id、不期望应答。带了 id，它就被当作一个名为 initialized 的方法调用，而服务端没有这个方法，于是返回 Method not found——这是本文排障实录 D 的第一个现象。

Q5协议★★☆
tools/list 动态发现工具 vs 客户端硬编码工具定义，工程上优劣？工具描述为什么直接影响 LLM 调用质量？

动态发现的优势是能力面演进零客户端成本：服务端注册新工具，客户端下次 tools/list 即见，不用发版；工具的入参 Schema 也随之下发，参数校验规则单点维护。硬编码则胜在确定性——客户端可以做静态检查与定制 UI，但每次能力变更都要同步发布。

代价是描述与 Schema 成为常驻上下文：本项目 18 个工具的描述 + JSON Schema 全部注入会占用模型上下文，工具数量持续增长时这是关键成本——演进路线里 Kimi Code 的 deferred 工具按需加载就是针对性的解法。

描述直接影响调用质量，因为模型是靠自然语言描述决定「什么时候用、怎么填参」的。本文的原则是「描述即提示词」：order_ship 的描述直接写明「仅待发货（status=1）可发货，需幂等键」——写描述是设计工作，不是注释工作。

工程实现 · Q6 / Q10 / Q11 / Q15 / Q19

Q6工程★★☆
面向 LLM 的工具设计有哪些原则？

本项目沉淀了五条。① 参数可枚举可校验：入参用 JSON Schema 圈定取值域，模型填参不超出合法空间。② 返回有界：list/search 分页默认 10、封顶 50，指标 days 封顶 365、榜单 limit 封顶 50——模型很容易说「给我全部」，上限就是给这句话的护栏。

③ 错误信息对模型可读：状态码翻译成中文人话（如「当前状态为『已发货』，无法重复发货」），模型拿到错误能自我修正，而不是只看到一串栈。④ 读写分离命名：query/order 类与 ship/close/handle 类从命名上就可分辨，18 个工具按查询、办理、审批、指标四类组织。

⑤ 摘要不倾倒：工具返回面向决策的摘要结构，不把整表 dump 给模型。底层逻辑是一致的：工具的每一面（描述、参数、返回、错误）都是给模型读的接口文档，设计标准应该按「模型能否一次调对」来验收。

Q10工程★★☆
为什么用 JdbcTemplate 而不是 MyBatis / mall-mbg？什么情况下你会改回 MyBatis？

mall-mcp 的 SQL 以聚合与关联查询为主——GMV 汇总、按天趋势、Top 榜、状态分布，这类 SQL 用 MyBatis 生成式 Mapper 的 Example 查询模型来表达反而绕，最后还是要手写，体系却整个背上了。

会改回 MyBatis 的情况：写操作显著增多、对象关系映射与复杂事务成为主体；或团队统一数据访问规范、要求与 mall-admin 同构。选型标准不是哪个框架好，而是查询形态与团队约定——本项目两个条件都不满足。

Q11工程★★☆
为什么做成独立模块 mall-mcp，而不是嵌进 mall-admin？

核心理由是爆炸半径隔离：MCP 出口是新增的调用面，鉴权、限流、审计策略都会独立快速迭代；嵌进 mall-admin 意味着每次协议层调整都要动后台服务的发布节奏，故障也互相牵连。独立模块 + 独立端口 8186，治理策略（过滤器、限流、超时）可以单独收口。

第二是零侵入：不改 mall-admin / mall-portal 一行代码，直读直写业务库。对一个迭代型项目，这决定了老系统的回归成本为零。

反而应该合并的情形：工具面稳定为产品的长期能力、与后台共享大量业务服务代码、且团队希望统一发布与运维单元。拆分的收益在变化期最大，在稳定期递减——届时合并是合理的再决策，不是推翻。

Q15工程★★☆
工具返回为什么要分页且上限 50？从 LLM 上下文成本视角怎么算这笔账？大结果集的正确做法？

LLM 的上下文是按 token 计费且有硬上限的稀缺资源。一页 50 条订单摘要约数千 token，「给我全部」在 3000 单基线下就是几十万 token——直接撑爆上下文，还会稀释模型对关键信息的注意力。上限 50（Math.min(pageSize, 50)）就是把这句口头要求变成代码护栏。

同理，指标类 days 封顶 365、榜单 limit 封顶 50：所有可能无界增长的入参都必须有服务端封顶，不能信任调用方自觉。

大结果集的正确做法不是放开上限，而是换通道：① 先返回聚合摘要让模型判断是否需要明细；② 明细走游标分页逐页取；③ 真正的大批量导出应该走文件/报表通道，根本不经过模型上下文。上下文里只放「决策需要的信息」。

Q19工程★★☆
mysql-connector 9.x 时间类型变化（LocalDateTime 强转崩溃）体现了什么工程原则？

现象：coupon_list 报 java.time.LocalDateTime cannot be cast to java.util.Date。根因是驱动行为变更：8.x 时代 DATETIME 列经 queryForList 取出默认映射为 java.sql.Timestamp（java.util.Date 的子类，强转成立）；9.x 起默认映射改为 java.time.LocalDateTime，隐式的类型假设随依赖主版本升级而断裂。

修复不是换一种强转，而是用 instanceof 做类型分派兜底：LocalDateTime 走 toEpoch，Timestamp/Date 走原路径——代码对驱动行为差异保持防御姿态，而不是假设。

体现的原则有三：① 依赖主版本升级必须带重测清单，行为兼容性不在编译期体现；② 类型假设要显式化，隐式继承链（Timestamp extends Date）是最脆的依赖；③ 升级前读驱动的 release notes / 迁移指南，成本远低于线上踩坑。

治理设计 · Q7 / Q8 / Q9 / Q12 / Q17

Q7治理★★★
写操作幂等怎么设计？本文 requestId 方案与 MQ at-least-once + 幂等消费是什么关系？为什么不允许没有幂等键的写调用？

本文 WriteGuard 的链路：requestId 为空直接拒绝 → 查 mcp_idempotency 表，命中则返回 duplicate:true + 首次执行结果 → 未命中则执行业务动作 → 审计落库生成回执 → 结果写入幂等表。幂等表主键为 (request_id, tool_name)，重复 INSERT 抛 DuplicateKeyException 直接吞掉——并发下同 requestId 只保留第一条，数据库唯一约束兜底，不依赖应用层「先查后写」的时序运气。

这与消息队列 at-least-once + 幂等消费是同构问题：投递侧（MQ / Agent）都可能重复，去重责任必须落在执行侧。差别只在触发源——MQ 重投是基础设施行为，Agent 重复调用是模型行为（网络重试、自我修正循环、多步任务并行）。

不允许无幂等键的写调用，是因为「同意之后执行两次」在 Agent 场景是常态而非异常：确认卡防的是「未经人同意」，防不了重复执行。没有键就没有判重锚点，幂等无从谈起——所以它不是可选项，是写工具的调用契约。

Q8治理★★★
并发下如何保证状态机不脏流转？对比悲观锁 / 乐观锁 / 条件更新 / 分布式锁，本文为什么选条件更新？

四种方案：悲观锁（SELECT … FOR UPDATE）正确但持有行锁、拉长事务；乐观锁（version 列）需要改表结构且要处理重试；分布式锁引入额外组件与超时语义；条件更新把前置状态嵌进 SQL 的 WHERE 子句：UPDATE oms_order SET … status=2 WHERE id=? AND status=1。

并发下两个发货请求只有一个影响行数为 1，另一个影响行数为 0 即判失败——状态检查与状态变更在同一条 SQL 里原子完成，不存在检查与变更之间的竞态窗口，也不产生「已发货又被发一次」的脏流转。

选它的原因：单行状态流转的场景下，条件更新是零额外组件、零表结构侵入、零锁持有的最简正确解。代码层的 SELECT 状态预检只保留一个用途——给出「当前状态为『已发货』」的人话提示给模型；真正的防线永远在那条 WHERE 上。

Q9治理★★☆
审计日志怎么设计才有用？为什么每次写操作都返回回执号 RCPT-xxx？审计表与幂等表为什么分表？

有用的审计要满足三点：先于返回落库（业务动作执行后立即写 mcp_audit_log，再生成回执返回，不存在「干了没记」的窗口）；内容可溯源（工具名、操作者、参数摘要、结果、耗时齐全）；回执可引用——回执号格式 RCPT-yyyyMMddHHmmss + 4 位随机，随结果返回调用方，客服可对人口头交差，审计模块可反查。

回执号的价值在于把「执行过」变成一个可传递、可核验的凭据：Agent 对人说「已发货，回执 RCPT-2026101914302207xx」，人拿号就能反查——这与 business-agent 工作台的回执理念同源。

审计表与幂等表分表，因为两者生命周期与语义不同：幂等表是去重状态，记录可归档可过期（幂等承诺不应永久）；审计表是事实流水，只增不删、长期保留。混在一起，归档策略必然打架。

Q12治理★★☆
生产上如何做鉴权？本文演示期为什么用静态 X-MCP-Token？生产化路径是什么？

本文方案：McpAuthFilter 单点收口，保护 /sse 与 /mcp/* 全部入口，校验 X-MCP-Token，失败返回 401（JSON-RPC 错误码 -32001），未带凭证的健康检查探测也一律 401——该拦截已纳入固定测试用例。

选静态 token 的理由是演示边界内不过度设计：mall-security 的 JWT 体系依赖登录会话与用户表，与「常驻服务、机器调用」的模型不匹配。已知代价记录在案：token 无法区分真实操作者（X-MCP-Operator 只是自报家门，写入审计但不防伪）、泄露即全量能力泄露。

生产化路径清晰分层：① token → OAuth2 client credentials，机器身份可独立吊销；② 按工具声明角色，对接 RBAC，读工具与写工具分权；③ 高危写操作再叠加四人眼复核。关键是鉴权集中在过滤器一个类里，换实现不动调用链——这是当初单点收口设计真正在还的技术债利息。

Q17治理★★★
怎么防止 LLM / Agent 滥用写工具？护栏分哪几层？为什么服务端护栏不可替代？

护栏分三层。协议层：McpAuthFilter 鉴权，无凭证 401。客户端层：Agent 平台的确认卡，防「未经人同意」。服务端层：WriteGuard 的幂等键判重 + SQL 层状态机守护 + 审计回执，防「同意之后执行两次」与「状态不对硬执行」。

服务端护栏不可替代的原因：客户端不可信。Agent 会重试（网络抖动）、会循环（自我修正）、会并行（多步任务），确认卡只约束「人点没点同意」，约束不了执行次数与状态合法性。幂等是执行层问题，必须在执行层解决。

护栏之外还有一道「不建护栏」的边界设计：高危操作通道化而非工具化——改价、批量发券这类影响面大的操作，设计上就不进入 MCP 工具面，走有确认卡、版本指纹、验收与回滚方案的需求迭代通道。「工具能做」和「应该能随手做」是两回事，能力面的克制本身就是安全设计。

稳定性与排障 · Q13 / Q18 / Q20

Q13稳定性★★★
遇到开源库 bug（Spring AI 1.0.2 SSE 挂起），你的定位方法论是什么？这个故事面试时怎么讲？

现象：SSE 握手正常、initialize 正常应答，但 tools/list 与 tools/call 发出后永久无响应——流上既没有结果事件也没有错误事件。定位走了四步：① 先怀疑自己——自写测试脚本是手拼的 JSON-RPC，逐字节核对请求格式，无误；② 对比排除——同一条会话链路、同一个 POST 通道，initialize 能拿到应答而 tools/list 不能，证明传输通道是通的，问题出在「请求被收下之后」的处理环节；③ DEBUG 日志——服务端日志停在 Received request: tools/call 一刻，请求进了 session 再无下文；④ 定性为库缺陷，升级 Spring AI 1.0.2 → 1.1.8，业务代码零改动立即恢复。

收尾动作同样重要：把版本抽成 pom 属性（升级是一行的事）、把契约级回归固化进测试脚本（排障 C/D 证明协议层回归必须自动化，人跑会漏）。

面试讲法按「现象 → 假设树 → 每步用什么证据剪枝 → 修复与沉淀」组织，重点不在「我升了个版本」，而在「我怎么把嫌疑从自己的代码收敛到库的传输层」。同一次迭代里还有两个环境层对照案例可讲：JDK net.properties 残留 socksProxyHost=127.0.0.1:7890 导致 Maven SOCKS 拒连（MAVEN_OPTS 清空解决）；Docker Desktop VM 层假死导致容器 start 挂起（重启 Desktop，数据卷无损，靠幂等导入重放基线数据）。

Q18稳定性★★☆
MCP Server 怎么做测试？本文的验证矩阵怎么设计的？为什么健康检查用「未授权 401」反而合理？

Q20协议★★★
protocolVersion 协商与协议向后兼容怎么理解？服务端该如何对待未知方法？

initialize 握手时客户端上报自己支持的 protocolVersion，服务端在响应中选定版本——版本协商让协议能力可以演进而不掐断旧客户端，这是所有长生命周期协议的共同设计（HTTP、TLS 同理）。能力集 capabilities 同理：双方都只承诺自己声明过的能力。

对未知方法，JSON-RPC 2.0 的纪律是返回 Method not found（-32601）错误，而不是静默吞掉或崩掉连接——本文排障 D 的第一个现象正是这条纪律的实证：把通知误带 id，它就成了一个不存在的方法调用，服务端按规范报错。

而通知（无 id）天然不应答，叠加会话状态机「initialized 之前可丢弃请求」的规范许可，就产生了「请求被黑洞吞掉」的体感。设计含义：协议使用者必须区分 request 与 notification 两种输入；协议实现者对非法时序的输入，报错永远优于静默——静默把协议问题伪装成网络问题，是排障成本最高的形态。

数据与指标 · Q14

Q14数据★★★
指标口径怎么定？GMV 的三种常见口径分歧在哪？本文选了哪种，为什么？口径不一致会导致什么后果？

GMV 常见三种口径：下单口径（创建即计，含未付款）、支付口径（已支付才计）、结算口径（完成无售后才计）。三者数值依次收紧，分别服务运营热度、收入现实、财务确认三种视角——没有绝对正确，只有与用途匹配。

本文选支付口径：GMV = SUM(pay_amount)，status ∈ (1,2,3)（待发货/已发货/已完成），排除待付款（0）、已关闭（4）、无效单（5）。选择理由不是「它最准」，而是与 mall-admin 后台订单统计的语义一致——Agent 报出的数字必须能和业务在后台看到的数字对账。支付转化率 = 已支付单 / 创建单，Math.round(paid*1000/total)/10 保留 1 位小数。

口径不一致的后果是信任崩塌：Agent 说 GMV 两千万、后台显示另一套数，业务无法判断谁错——对不上账的指标，报得越快信任破产得越快。实测值：全库 GMV ¥2012 万、近 30 天转化率 90.9%、券核销率 37.5%，三个数均与直查 SQL 手工核算一致。

Q16演进★★★
调用量涨 10 倍怎么扩展？

分层作答。读路径：指标目前实时算在 oms_order 上，3000 单无压力；量级上来后走「预聚合表（按天滚动的 sales_daily）+ 只读缓存」——评审点是口径从实时 SQL 迁到预聚合表之后的一致性校验方案。查询类工具加结果缓存，列表页数据读从库，读写分离。

治理面同步扩容：幂等表随时间膨胀需要归档策略；多实例部署时幂等键判定要搬到共享存储（Redis 或独立库），并定义记录保留窗口——幂等承诺不应该是永久的。扩展的答案从来不只是「加机器」，而是每一层治理设施都要回答一遍「10 倍之后你还成立吗」。

Q21演进★★★ · 加分题
如果你来设计 v2，工具粒度怎么收敛？18 个工具是不是太多？按什么维度合并 / 拆分？

先回答「多不多」：18 个工具按查询、办理、审批、指标四类分域平铺，数量本身不是问题的核心，描述与 Schema 常驻上下文的成本才是——Kimi Code 的 deferred 工具按需加载（平时只挂元信息、命中意图再载入完整 Schema）说明生态已经在解这个成本，v2 设计应该假设这个能力存在。

收敛维度看调用意图与参数面的重合度，而不是表归属。查询类可以合并：多域 search 收敛为统一入口（domain + query + filters 参数化），模型学习一次参数模式即可查五域。指标类 6 个可收敛为带 metric 与维度参数的少量入口。拆分维度则看治理等级：写工具必须保持单一职责、细粒度——order_ship 与 order_close 各自携带独立的幂等、状态机与审计约束，合并只会让 Schema 里的条件分支爆炸、描述里的约束互相稀释。

另一条纪律来自长期路线：工具语义版本化——改名、改语义、改口径都必须升版本（metric_sales_overview v2），旧版本保留一个周期。模型按描述行事，描述变了而名字没变，是最危险的变更形态。v2 的粒度答案因此是：读收敛、写守恒、变更必升版。
