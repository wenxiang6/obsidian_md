01 · 场景

Agent 是黑盒，可观测性就是开盒器

一个 7×24 自主运行的 Agent 平台，最怕的不是它犯错，而是它犯了错却没有人知道、没有人知道为什么、也没有人知道花了多少钱。音巢的可观测性体系围绕四个真实追问展开。

3 层
运行数据模型：run → command → event
13
agent_run_events 事件类型（CheckConstraint 约束）
2 路
事件消费：WS 实时推送 + 离线统计聚合
4 类
配额闸门：会话 / LLM 调用 / 建 Agent / 有效期

四个每天都要回答的追问

①

「这个 Agent 今天干了啥、花了多少钱？」

管理者的成本追问。daily_token_usage 按 租户 × Agent × 日期 聚合 token 用量（含缓存读写分列），Agent 详情页直接展示日/月/累计用量——成本归因到具体 Agent，有据可查。

②

「它为什么给出这么离谱的答案？」

坏答案回溯。从用户反馈定位到 chat_session → agent_run → 该 run 的全部事件与工具执行记录，逐帧回放模型步与工具步，定位到具体哪一次模型输出或哪一次工具调用翻车。

③

「危险操作谁批准的？能审计吗？」

合规追问。audit_logs 全量记录敏感动作，approval_requests 留存审批链（前端 AgentDetail 有独立的 ApprovalsTab），危险操作审批留痕、可全量审计。

④

「它现在是不是在正常运行？」

运维追问。/api/health 与 /api/version 端点供探活与版本核对；前端 Aware 视图实时展示 Agent 自主触发的「内心独白」（Reflections），让人直观看到它在想什么。

定位 · 一句话

把 Agent 的每一次「思考—行动—交付」变成结构化、可查询、可推送的数据资产，而不是一堆没人翻的日志文件。

这是音巢与传统后端可观测性的根本分歧点：日志是给人排障用的副产品，而 agent_run_events 是产品功能本身的数据底座——前端实时视图、成本统计、审计合规全部长在同一张事件表上。

02 · 设计

四个设计决策，一条主线：观测数据是一等公民

可观测性不是事后补的监控面板，而是和数据模型一起长出来的。音巢的每个决策都在回答同一个问题：这份数据以后要被谁、以什么方式消费？

推理过程：打日志 vs 建成结构化事件表 D1

选项

① 传统做法：运行时往日志文件打 INFO 行，排障时 grep
② 音巢做法：run 生命周期的每个关键节点落成 agent_run_events 行（event_type + summary + JSONB payload + artifact_refs）

决定

建成 append-only 的结构化事件表，日志（loguru）只留工程级调试信息

原因

事件要被三种消费者用：前端实时渲染（WS 推送）、离线统计（按 tenant_id + event_type + created_at 索引检索）、审计回溯。日志做不到 SQL 可查、做不到幂等重放（事件表有 run_id + idempotency_key 唯一约束）、做不到级联删除（tenant 删除时 CASCADE 清理）。

代价

每次状态跃迁都多一次数据库写入；事件类型被 CheckConstraint 锁死在 13 种，新增类型要走迁移。换来的是「可查询、可重建、可推送」三个能力。

token 计量：实时流式估算 vs 最终以 usage 为准 D2

选项

① 只在 LLM 响应结束时记录 usage（简单，但流式中断就丢账）
② 流式期间按字符估算，结束时以真实 usage 校准

决定

两者结合：token_tracker 提供 estimate_tokens_from_chars（约 3 字符 ≈ 1 token）做兜底估算，extract_token_usage 兼容 OpenAI / Anthropic / Gemini 三种 usage 格式做精确结算

原因

流式响应中断、供应商不回传 usage 都是常态；完全没有估算会让成本统计出现系统性低估。而估算必须有标记——TokenUsage 里 estimated_tokens 单列，不与真实量混淆。

代价

计量口径双轨制，对账时要区分 estimated 与真实值；但避免了「中断即丢账」的成本黑洞。

观测数据的四层模型

层表 / 模型回答的问题消费者

设计主线

所有观测数据都带 tenant_id 且外键级联——多租户隔离从数据模型层就锁死；所有事件写入都幂等——(run_id, idempotency_key) 唯一约束保证重试不产生重复事件；所有计量都可区分真伪——estimated 与真实 usage 分列。观测系统的可信度，是靠约束而不是靠纪律保证的。

三级钻取的精度分工：agent_run_events 给出「哪个阶段出了问题」的时间线（等待、恢复、交付失败都有独立事件类型）；agent_tool_executions 给出「哪次工具调用返回了脏数据」；LangGraph checkpoint 保存逐步消息现场，给出「模型当时看到的上下文是什么」。三层各管一段，任何一层都不需要翻日志。

注意一个诚实的口径：quota_guard 的闸门是调用次数维度而非 token 金额维度——token 计量（daily_token_usage）负责「算清账」，调用次数闸门负责「踩住刹车」。两者组合覆盖成本治理的两端：事后可归因，事前可兜底。计量用独立 DB session 落账（避免污染调用方事务），失败只记 warning 不打断主流程——观测绝不能拖垮业务。

一处与直觉不符的核实结论

前端 MindTab.tsx 并不是「内心独白」视图——它是 Agent 灵魂文件的浏览器（soul.md / memory/ / HEARTBEAT.md）。真正的 Reflections 展示在 AgentDetailPage 的 Aware 侧栏：数据来自触发器自主运行产生的会话（trigger_completion 在 run 收尾时写入终态反思消息）。写文档、做分享时以源码为准，不要望文生义。

04 · 伪代码

两个最小闭环：事件怎么流出去，token 怎么变成闸门

伪代码提炼自上游实现，省略错误处理与多租户样板，只保留机制主干。

闭环一：事件埋点 → 落库 → 实时推送

# ── 节点执行时埋点：事件是唯一事实源，推送只是投影 ── async def emit_run_event(run, event_type, summary, payload={}): event = AgentRunEvent( run_id=run.id, tenant_id=run.tenant_id, agent_id=run.agent_id, event_type=event_type, # 13 类之一，CheckConstraint 兜底 summary=summary, payload=payload, idempotency_key=f"{run.id}:{event_type}:{checkpoint_id}", source_checkpoint_id=checkpoint_id, ) await db.execute( insert(AgentRunEvent).values(...) .on_conflict_do_nothing() # 重试幂等：同一 checkpoint 不重复成事件 ) await db.commit() # 落库成功后才推送——推送失败不影响事实源 await realtime.publish_to_agent(run.agent_id, { "type": "run_event", "event": to_dict(event), }) # ── 多实例扇出：事件路由到持有 WS 连接的那个实例 ── async def publish_to_agent(agent_id, message): redis = await get_redis() conn_ids = await redis.smembers(agent_index_key(agent_id)) for cid in conn_ids: conn = await redis.hgetall(connection_key(cid)) if conn["instance"] == MY_INSTANCE_ID: ws_manager.deliver_local(cid, message) # 本实例直投 else: await redis.publish( # 跨实例走 pub/sub f"realtime:instance:{conn['instance']}", envelope) # ── 前端订阅：事件驱动 UI 刷新（Aware 视图 / 运行状态）── ws = new WebSocket(`/ws/chat/${agentId}`) ws.onmessage = (frame) => { if (frame.type === "run_event") renderTimeline(frame.event) }

闭环二：LLM usage → 日聚合 → 配额闸门

# ── 计量：usage 归一化 → 双写（计数器 + 日聚合）── async def after_llm_response(agent_id, response): usage = extract_token_usage(response.usage) # OpenAI / Anthropic / Gemini 通吃 if usage is None: # 流式中断 / 供应商不回传 usage = estimate_token_usage_from_chars(total_chars) # ~3 字符 ≈ 1 token if usage.total_tokens <= 0: return async with independent_session() as db: # 独立事务：记账失败不拖垮主流程 agent = await db.get(Agent, agent_id) agent.tokens_used_today += usage.total_tokens # 日 / 月 / 累计三档 agent.tokens_used_month += usage.total_tokens agent.tokens_used_total += usage.total_tokens # 缓存读写 token 同理分列 await db.execute( insert(DailyTokenUsage).values( tenant_id=agent.tenant_id, agent_id=agent.id, date=utc_today(), tokens_used=usage.total_tokens, ...) .on_conflict_do_update( # (agent_id, date) 冲突即累加 index_elements=["agent_id", "date"], set_={"tokens_used": DailyTokenUsage.tokens_used + usage.total_tokens, ...}) ) await db.commit() # ── 闸门：每次调模型前先过检 ── async def before_llm_call(agent_id): agent = await load_agent(agent_id) if agent.is_expired or utcnow() >= agent.expires_at: raise AgentExpired(agent.name) # 有效期闸 if utcnow().date() > agent.llm_calls_reset_at.date(): agent.llm_calls_today = 0 # 跨天清零 if agent.llm_calls_today >= agent.max_llm_calls_per_day: raise QuotaExceeded(quota_type="agent_llm") # 调用数闸 agent.llm_calls_today += 1

两个闭环共同的设计纪律：事实源优先（事件先落库再推送，token 先记真账再估算兜底）、失败隔离（推送失败、记账失败都只降级不打断）、幂等兜底（事件靠 idempotency_key，日聚合靠 upsert，重试安全）。

05 · 面试 QA

六道题，考察的是「Agent 系统观」而不是八股

Q1 · 传统可观测性三支柱（logs / metrics / traces）在 Agent 系统里如何映射？

音巢给出了一个具体答案：logs → agent_run_events（但不是「日志搬家」，而是把非确定性的推理过程结构化成 13 类可查询事件）；metrics → daily_token_usage + agents 表三档计数器（成本是这个系统最重要的指标，没有之一）；traces → agent_runs → agent_run_commands → agent_run_events → agent_tool_executions 的四层钻取（一次 run 就是一条 trace，checkpoint 提供 span 级现场）。差异在于：传统 trace 的 span 是确定的函数调用，Agent trace 的「span」是一次模型推理——内容本身就是要观测的对象，所以 payload 必须是 JSONB 结构化存储，而不是一行文本。

Q2 · 为什么把推理过程做成一等公民数据（agent_run_events 表），而不是打日志？

因为它有三种日志满足不了的消费者：① 产品功能——前端要实时渲染运行状态与内心独白，日志没法被前端订阅；② 统计分析——按 tenant_id + event_type + created_at 的复合索引做 SQL 聚合，日志做不了；③ 审计合规——事件随租户 CASCADE 删除、靠 (run_id, idempotency_key) 幂等，日志两者都做不到。本质判断标准是：这份数据是「副产品」还是「产品」。在 Agent 平台里，可观测性数据就是产品功能本身（Mind/Aware 视图、成本报表都长在它上面），所以它必须进数据库、必须有约束、必须有索引。loguru 日志在音巢里只剩一个角色：工程级调试。

Q3 · 流式 token 计量与最终 usage 不一致怎么处理？

音巢的策略是「双轨 + 标记」：流式期间或供应商不回传 usage 时，用 estimate_tokens_from_chars（约 3 字符 ≈ 1 token）估算，估算值记入 TokenUsage 的 estimated_tokens 独立字段，与真实 input/output 分列落 daily_token_usage——对账时永远分得清哪部分是估的。拿到真实 usage 后（extract_token_usage 兼容 OpenAI 的 prompt_tokens、Anthropic 的 input_tokens、Gemini 的 promptTokenCount 三种格式，连 prompt cache 的读写都单列），以真实值为准结算。工程上还有两个细节：计量走独立 DB session，记账失败只 warning 不打断对话；total_tokens ≤ 0 直接丢弃，避免脏数据污染聚合。

Q4 · 审计日志的写入性能与合规保留怎么平衡？

音巢 audit_logger 的选择是裸 SQL INSERT（write_audit_log 直接拼 INSERT INTO audit_logs）——绕过 ORM 的对象构造与变更追踪开销，审计写入是高频旁路操作，越轻越好。合规侧的设计是「分层留痕」：危险操作不只写 audit_logs，还生成 approval_requests 审批单（前端有独立 ApprovalsTab），审批链是显式数据而不是日志里的暗文。性能与合规真正的矛盾点在「全量 vs 抽样」——音巢的做法是审计动作分类（AuditAction 枚举），写操作全量、读操作按需，避免审计表被查询流量打爆。

Q5 · 如何向非技术管理者解释 Agent 的行为？观测数据的产品价值在哪？

这是音巢把「内心独白」（Reflections）做成前端功能的动机。触发器自主运行的 Agent 在收尾时会写一条终态反思消息（trigger_completion 追加 reflection），前端 Aware 视图把这些反思按会话展示成时间线——管理者看到的不是「CPU 利用率」，而是「它今天主动巡检了什么、得出了什么结论、为什么决定不打扰你」。观测数据从运维工具升维成信任工具：用户敢不敢让 Agent 自主干活，取决于他能不能随时看到 Agent 在想什么。技术上这条链路零额外成本——反思就是 chat 会话里的消息，复用全部既有管道，产品价值却极高。

Q6 · 观测数据本身的存储膨胀怎么治理？

先澄清一个容易混淆的点：上游的 run_compactor.py 压缩的不是观测数据，而是 LangGraph 线程上下文（在 token 预算高水位时压缩消息历史，保持原子工具调用边界）——它是「控制未来产生多少观测数据」的上游手段。对已落库的观测数据，音巢的治理靠三层：① 事件类型收敛——CheckConstraint 把事件锁死在 13 种生命周期节点，不允许把每条模型输出都塞成事件（细粒度现场留在 checkpoint 里，事件表只存「产品级」跃迁），从源头控制行数；② 级联清理——tenant / run 删除时事件 CASCADE 跟着走，不留孤儿数据；③ 聚合替代明细——成本维度只保留 daily_token_usage 日聚合，明细用完即弃。经验法则是：观测系统的存储设计，从第一天就要回答「什么数据活得比它的消费者久」。

观测 Agent，就是观测「不确定性」本身

传统后端的行为是代码决定的，看日志就够了；Agent 的行为是模型在运行时决定的，每一次推理都是一次新的决策。

所以音巢把推理过程建成事件表、把成本建成日聚合、把审批建成数据单——不是为了监控，而是为了信任。

看得见，才敢放手。可观测性不是 Agent 平台的附属功能，它是自主性的前提。
