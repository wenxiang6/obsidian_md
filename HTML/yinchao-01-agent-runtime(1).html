01 · 场景

Agent 不能死在半路：运行时为什么必须是「持久化」的

普通聊天机器人丢了上下文大不了重问一遍；但音巢的 Agent 会调工具、改数据、跨小时执行任务、等人审批——任何一步因为进程重启而丢失，都是数据正确性事故。Durable Agent Runtime V2（代码位于 backend/app/services/agent_runtime/）就是为这类场景造的内核。

五个真实业务场景

①

长任务断点续跑

一个 OKR 周报汇总 Agent 跑了 40 分钟、已调用十几次工具，此时后端发版重启。checkpoint 落库后，worker 拉起时从最后一个已提交的图状态继续，已执行的工具不会重跑，进度零丢失。

②

危险操作人工审批

Agent 想执行 L3 风险级工具（如群删除、发起飞书审批）时，运行时在工具步前 interrupt() 挂起，写 approval_requests，等人工批准后由一条新命令唤醒——人在环路上，而不是事后审计。

③

单 Agent 串行执行

同一个 Agent 同一时刻只允许跑一条冲突的 Run：thread_lock.py 用 Postgres 咨询锁（pg_try_advisory_lock）按 thread 串行化，避免两条并发 Run 同时改一份会话上下文造成的错乱。

④

工具循环失控防护

LLM 偶发会陷入「委派 A → 委派 B → 又委派 A」的死循环。cycle_guard.py 基于数据库中的委派边计算环计数，超过 MAX_AGENT_CYCLE_COUNT = 5 直接拒绝，把失控拦在图执行之前。

⑤

多入口统一内核

群聊消息、定时触发器、心跳自省、A2A 跨 Agent 调用——入口形态完全不同，但统一由 chat_intake / trigger_completion / heartbeat_completion / a2a_completion 转成命令写入同一张队列表，一种运行时服务所有触发源。

定位 · 一句话

把 Agent 执行建模为「可持久化的状态机」：命令是队列里的行，进度是 checkpoint 里的快照，人的审批只是另一条入队命令。

这三个抽象让「恢复」「重试」「介入」都不再是特殊逻辑——它们全部复用同一条命令通道与同一份状态存储，这是整个运行时设计的主轴。

02 · 设计

三个关键取舍：用表做队列、把状态交给 LangGraph、危险动作必须过人

运行时的设计难点不在「跑起来」，而在「出事之后语义仍然正确」。音巢在队列选型、状态归属、人工介入三个点上做了明确取舍，每一个都有对应代价。

工作队列载体：数据库表 vs 专职 MQ D1

选项

① Redis Stream：轻量、有消费组语义
② Kafka：吞吐与回放能力强
③ Postgres agent_run_commands 表 + FOR UPDATE SKIP LOCKED 竞争认领

决定

③ Postgres 表做命令队列，persistence 层用行锁实现租约认领

原因

少一个组件：部署面只有 Postgres，不新增中间件；事务一致性：命令状态与 agent_runs / agent_run_events 同事务提交，不存在「队列说成功、业务表没写」的两半状态；可观测：队列积压、卡死命令直接 SQL 可查；租约续约在表上就是一个 UPDATE，语义直白。

代价

吞吐天花板低于专职 MQ，依赖行锁与索引设计；高频轮询给数据库带来固定负载。换取的是部署、事务、排障三件事的极致简化——对一个企业内多智能体平台，这个交换是赚的。

运行时状态的单一事实源：checkpoint 优先，不做双写 D2

选项

① 业务表与 LangGraph checkpoint 双写，两边各自维护状态
② checkpoint 作为图执行状态的唯一事实源，业务表（agent_runs / 事件流）只做投影与查询视图

决定

② checkpoint 为事实源——checkpointer.py 的模块注释写得很直白：「without product-state dual writes」

原因

双写意味着两份状态要永远一致，崩溃恰好落在两次写之间就出现无法归责的漂移。checkpoint 每节点提交一次、天然带版本（checkpoint_id），恢复语义由 LangGraph 保证；业务侧只把「用户要看的部分」投影成表，投影坏了可重建，事实源不脏。

代价

团队必须理解 LangGraph 的 thread / checkpoint 模型，排查问题要在两套视角（图状态 vs 业务投影）之间切换；checkpoint 数据需定期清理（保留 30 天，AGENT_RUNTIME_CHECKPOINT_RETENTION_DAYS）。

危险工具的处理：失败重试 vs 挂起等人 D3

选项

① 高风险工具直接拒绝执行，由 Agent 改用话术回复
② 命中 L3 风险策略时 interrupt() 挂起整条 Run，人批准后从 checkpoint 恢复继续

决定

② interrupt → approval_requests → resume，审批本身也是一条命令

原因

直接拒绝会把「能不能做」永久焊死在策略里，业务上大量高危操作其实是「该做、但要人点头」。挂起语义让审批不阻塞 worker（图状态已落库，资源释放），批准动作以新命令入队——复用同一条队列通道，不需要单独的回调系统。

代价

一次 Run 可能跨小时甚至跨天，上下文管理、checkpoint 留存、用户侧「等待审批」的体验设计都要跟上；审批超时要有兜底策略。

关键概念对齐

概念载体语义
Run（一次运行） agent_runs 表 + LangGraph 一次图执行 Agent 的一次完整任务执行，有终态（completed / failed / cancelled）。
Command（命令） agent_run_commands 表（工作队列） 驱动 Run 前进的最小单位：发起、审批唤醒、恢复续跑都是命令；带 attempt_count 与租约字段。
Thread（线程） LangGraph checkpoint 的 thread_id 图状态的命名空间。注意：Thread ≠ Run——直接聊天可以把多个逻辑 Run 放在同一 Thread 上，群聊与后台 Run 则各自持有独立的 run_id Thread（见 checkpointer.py 的 runtime_thread_config 注释）。
Thread / Lane 锁 pg_try_advisory_lock（thread_lock.py） 按 thread_id 哈希取 Postgres 咨询锁，保证同一会话上下文不被两条 Run 并发改写；拿不到锁即放弃，不排队阻塞。
事件流 agent_run_events 表 运行过程的可观测投影：模型输出、工具调用、状态迁移按序落库，供 WS 推送与事后审计。

终态分支触发条件后续动作

dead（超限死亡） attempt_count 达到 AGENT_RUNTIME_COMMAND_MAX_ATTEMPTS = 5 命令置 dead，Run 置 failed，错误摘要落库（「reconcile the command after repeated attempts」）
崩溃回收 worker 宕机，租约 60s 到期未续约 其他 worker 的认领查询命中「running 但租约过期」的记录，接管续跑——不需要外部看门狗

租约参数有硬约束：续约间隔必须小于 TTL（command_worker.py 初始化时直接校验，违规抛 ValueError）。这把「续约比过期快」从运维纪律变成了代码不变量。

04 · 伪代码

两个最小闭环：认领循环与图定义

剥掉监控、优雅退出、配置装配之后，整个运行时的核心机制就浓缩在下面两段伪代码里：一段管「命令谁来跑、死了谁接」，一段管「图怎么转、在哪挂起」。

闭环一：command_worker 认领循环（租约 + 重试）

# command_worker.py 核心循环的最小骨架（真实代码含并发上限 10、退避与优雅退出） while running: async with db.begin(): row = await db.execute(""" SELECT * FROM agent_run_commands WHERE status = 'pending' OR (status = 'running' AND claim_expires_at < now()) -- 崩溃回收 ORDER BY created_at LIMIT 1 FOR UPDATE SKIP LOCKED -- 多 worker 互不踩踏 """) if row is None: break # 队列空了，睡一轮再来 await begin_command_attempt(row) # status→running, attempt_count+1, 写 60s 租约 try: async with heartbeat(every=20): # 后台任务：每 20s renew_command_claim 续约 async with thread_lock(row.thread_id): # pg_try_advisory_lock，拿不到即放弃 await driver.run(row) # langgraph_driver 驱动图执行 await mark_done(row) except RetryableToolNodeError: if row.attempt_count < 5: # AGENT_RUNTIME_COMMAND_MAX_ATTEMPTS await mark_retry(row) # 回 pending；checkpoint 还在，续跑不重来 else: await mark_dead(row) # dead + Run 置 failed

不变量由代码强制：renew_seconds < claim_ttl_seconds，初始化即校验。worker 宕机时无需任何外部看门狗——租约过期本身就让命令重新变得「可认领」。

闭环二：LangGraph 图定义骨架（控制流 + 挂起点）

# graph.py 的结构性骨架（节点名与真实代码一致） g = StateGraph(RuntimeGraphState) g.add_node("control_guard", control_guard) # 路由闸门：取消 / 等待 / 压缩 / 终态 g.add_node("model", model_step) # 模型步：一次 LLM 决策 g.add_node("tool", tool_step) # 工具步：执行 + L3 审批判定 g.add_node("wait", wait_node) # resume_value = interrupt(waiting_request) g.add_node("terminal", terminal_node) # 终态收敛：completed / failed / cancelled g.add_edge(START, "control_guard") g.add_conditional_edges("control_guard", route, { "run_model": "model", # 还有事要做 → 让模型决策 "wait": "wait", # 等人 / 等外部 / 等 Agent → 挂起 "done": "terminal", # 命中终态 → 收敛 }) g.add_conditional_edges("model", after_model, { "has_tool_calls": "tool", "final_answer": "terminal", }) g.add_edge("tool", "control_guard") # 工具结果回灌，进入下一轮循环 app = g.compile( checkpointer=AsyncPostgresSaver(conn, serde=EncryptedSerializer(...)), ) # 每个节点提交即落 checkpoint：崩溃后从最近快照精确恢复

「循环」在图里是显式的边（tool → control_guard），不是 while 循环——这让每一轮模型-工具交替都是一个可 checkpoint、可观测、可拦截的节点提交，cycle_guard 与 run_compactor 都挂在 control_guard 这个唯一闸门上。

05 · 面试 QA

六道题，从队列选型考到恢复语义

以下回答全部结合音巢的实际实现，不是泛泛八股——每个答案都能在源码里指到具体位置。

Q1 · 为什么用数据库表做工作队列，而不是 Redis Stream 或 Kafka？

三个理由，按重要性排序：① 事务一致性——命令状态迁移与 agent_runs / agent_run_events 在同一事务里提交，不存在「队列 ack 了但业务表没写」的两半状态；用外部 MQ 就得引入 outbox 模式或最终一致补偿，复杂度反而更高。② 少组件——音巢的部署面本来就强依赖 Postgres（业务数据 + checkpoint 都在里面），队列复用它意味着运维面零扩张，一个小团队不用养第三套中间件。③ 可观测性——队列积压、卡死命令、重试历史全部 SQL 可查，排障不需要学一套 MQ 专属工具。Postgres 的 FOR UPDATE SKIP LOCKED（见 persistence.py）让多 worker 竞争认领成为标准动作，这个语法本来就是为「表即队列」设计的。代价是吞吐天花板与轮询负载，但 Agent 执行的瓶颈在 LLM 调用时延，远不在队列。

Q2 · LangGraph checkpoint 的原理是什么？恢复语义到底保证什么？

LangGraph 把图执行建模为状态机：每个节点执行完提交一次，把当时的完整 state 以 checkpoint 形式写入存储，每个 checkpoint 有递增的 checkpoint_id，挂在 thread_id 命名空间下。音巢用 AsyncPostgresSaver 落到独立的 langgraph_checkpoint schema，并用 EncryptedSerializer（密钥 LANGGRAPH_AES_KEY）加密序列化内容。恢复语义是：从最近一个已提交 checkpoint 精确续跑，该节点之前的效果不重放。这意味着工具节点的幂等性压力集中在「当前正在执行的那个节点」上——如果崩溃恰好在工具执行中间，恢复后该工具可能重跑，所以音巢在工具层还有 RetryableToolNodeError 与安全读工具的重试次数（SAFE_READ_MAX_ATTEMPTS）等配套设计。另外音巢刻意不做业务表与 checkpoint 双写，checkpoint 是图状态的唯一事实源，业务表只是投影。

Q3 · interrupt / resume 在 LangGraph 里怎么实现？音巢怎么用它做审批？

LangGraph 的 interrupt() 在节点内被调用时，会把「等待什么」的负载序列化进 checkpoint，然后让整次图调用正常退出——它不是阻塞等待，而是一次带书签的返回。恢复时用 Command(resume=...) 重新调用图，执行从 interrupt 点继续，且 interrupt() 这次返回传入的 resume 值。音巢在 graph.py 的 wait 节点里做这件事（resume_value = interrupt(waiting_request)）：工具步命中 L3 风险策略时路由到 wait 节点挂起，同时写 approval_requests 表并推送审批通知；人批准后，审批回调把「审批结论」作为一条新命令写入 agent_run_commands，worker 认领后从 checkpoint 恢复图执行，审批值经 resume 传回图内，工具才真正执行。精妙之处在于：审批唤醒没有走任何特殊通道，它就是队列里一条普通命令——挂起期间 worker 零资源占用，审批可以跨天、跨进程重启。

Q4 · 如何防止 Agent 陷入工具调用死循环？

音巢有三层防线，由外到内：① 委派环防护（cycle_guard.py）——针对多 Agent 委派场景（A 委派 B、B 又委派 A），基于数据库里已发生的委派边计算环计数，候选委派会使环计数超过 MAX_AGENT_CYCLE_COUNT = 5 时直接抛 AgentCycleGuardError，把失控拦在图执行之前。② 图结构本身——模型-工具循环不是裸 while 循环，而是 tool → control_guard → model 的显式边，control_guard 是每轮必经的闸门，取消、终态、压缩都在这一处裁决，想加「最大轮数」这类策略只需改一个节点。③ 上下文压缩（run_compactor.py）——循环往往伴随上下文膨胀，当用量达到窗口的 85%（AGENT_RUNTIME_SUMMARY_THRESHOLD_RATIO）时压缩历史，避免长 Run 因 context 爆炸而行为退化。面试时要点出：防死循环不是单一阈值能解决的，而是「委派拓扑 + 控制流闸门 + 资源配额」的组合。

Q5 · worker 崩溃后，它手里的命令怎么被重新认领？

租约（lease）机制，不需要任何外部看门狗。命令被认领时写入 claim_expires_at = now() + 60s（AGENT_RUNTIME_COMMAND_CLAIM_TTL_SECONDS）；执行期间后台心跳任务每 20s 调 renew_command_claim 续期（CLAIM_RENEW_SECONDS）。认领查询的条件是 status='pending' OR (status='running' AND claim_expires_at < now())——worker 崩溃后心跳停止，60s 后租约自然过期，命令对其他 worker 重新可见，被 FOR UPDATE SKIP LOCKED 认领续跑。恢复不重跑已完成的节点，因为 checkpoint 里已有进度。代码层面有个硬约束值得说：command_worker.py 初始化时校验 renew < TTL，不满足直接抛 ValueError——把「续约必须比过期快」从运维约定变成启动期不变量。TTL 取 60s 是权衡：太短会因正常抖动误回收（同一命令被两个 worker 执行，虽 thread_lock 兜底但浪费）；太长则故障恢复慢。

Q6 · 「一个 Agent 同一时刻只跑一条 Run」的并发控制具体怎么做？

精确地说，音巢的粒度是 thread 级串行 + 全局并发配额，两层机制：① thread_lock（thread_lock.py）——把 thread_id 哈希成整数键，执行前 SELECT pg_try_advisory_lock(lock_key)，拿不到立刻抛 ThreadLockNotAcquired（不排队阻塞），结束 pg_advisory_unlock。Postgres 咨询锁的好处是跨进程、跨 worker 实例有效，且随数据库连接断开自动释放——worker 崩溃不会留死锁。由于直接聊天允许多个 Run 共享一个 Thread，锁在 thread 上恰好等于「同一会话上下文不被并发改写」。② 全局配额——AGENT_RUNTIME_COMMAND_CONCURRENCY = 10 限制单 worker 进程同时执行的命令数，thread/lane 锁负责冲突串行，配额负责总容量。这里有个值得展开的设计细节：advisory lock 用 try 而非阻塞获取，是因为队列模型下「拿不到锁」不等于失败——命令可以释放后让位给其他可执行的命令，worker 容量不被一条等锁的命令占住。

把「不可靠的执行」关进「可靠的框架」

LLM 本质上不可靠：会超时、会循环、会给出危险指令。音巢运行时的回答是承认这一点，然后用工程手段兜底——命令入表、状态落 checkpoint、危险动作过人、租约兜住崩溃。

每一个「兜底」都不是特殊通道：恢复是命令、审批是命令、重试还是命令。一条队列、一份 checkpoint、一个确定性控制流，撑起所有非常规路径。

Durable 的真义不是「不出错」，而是「出错之后，系统知道自己在哪，并且能接着走」。
