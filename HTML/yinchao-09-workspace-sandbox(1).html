01 · 场景

没有文件系统和沙箱的 Agent，只是一个聊天框

LLM 的上下文窗口是易失的：会话结束，中间产物全没了。音巢把工作区与沙箱做成平台级基础设施——每个 Agent 独占一套文件系统，产出物落盘、版本化、可分享；代码在隔离环境里执行，宿主机永远不被污染。

定位 · 一句话

工作区是 Agent 的手脚——让产出物落得住；沙箱是保险柜——让代码跑得开、又伤不到人。

这两个子系统共同回答了多智能体平台最现实的问题：Agent 干完活，东西放哪、怎么回溯、怎么分享；Agent 要跑代码，在哪跑、跑挂了谁兜底。音巢的答案是：独占文件系统 + 版本化 + 可插拔存储，多后端沙箱 + 注册表选择 + fail-closed 默认。

02 · 设计

三个关键取舍：分区约定、可插拔后端、宁可不可用不可不安全

工作区与沙箱的设计没有炫技成分，全是工程上反复权衡后的保守选择——因为这两层一旦出事，丢的是用户数据、宿主机安全。

决策一：存储后端做成可插拔，而不是绑死本地盘

本地磁盘 vs 对象存储 D1

选项

① 所有文件只落本地磁盘，简单直接
② 抽象存储接口，本地 / S3 双后端，配置切换

决定

② 可插拔：STORAGE_BACKEND=local|s3，S3 走 boto3/aioboto3 + 预签名 URL

原因

平台是多租户 SaaS 形态：本地盘无法水平扩展、容器重建即丢数据、大文件（用户上传的文档、Agent 产出的视频/安装包）会撑爆磁盘。S3 后端把字节流挪到对象存储，预签名 URL 让下载直连对象存储、不过应用带宽。

代价

多一层抽象与一致性取舍：S3 是最终一致语义，写入确认、失败重试、本地缓存都要自己处理；预签名 URL 过期（S3_PRESIGN_TTL_SECONDS=3600）要前端配合刷新。

决策二：隔离缺失时 fail-closed，而不是降级裸跑

bwrap 缺失时怎么办 D2

选项

① 检测不到 bubblewrap 就退化为普通 subprocess，保证功能可用
② 拒绝执行，返回明确错误，除非显式设置开关

决定

② fail-closed：默认拒绝；只有 SANDBOX_ALLOW_UNSAFE_FALLBACK_WHEN_BWRAP_MISSING=true 才允许降级

原因

execute_code 跑的是 LLM 生成的代码——本质上是不可信输入。在容器化部署里失去 bwrap 就等于在 backend 容器里裸跑任意代码，一次提示词注入就能读写整个工作区根目录。可用性可以靠报错恢复，安全洞补不回来。

代价

部署门槛变高：backend 容器需要装 bwrap，进而需要 privileged + SYS_ADMIN 能力；启动时只做告警不阻断（_log_bwrap_startup_status），问题延迟到首次 execute_code 才暴露，依赖运维看日志。

设计哲学：把「不可信」当默认值

沙箱模块的所有默认值都在收紧而不是放宽：cpu_limit=0.5 核、memory_limit=256m、default_timeout=180s、max_timeout=300s 服务端封顶；workspace_mode 支持 merge / isolated_output 两种产物回收策略。LLM 生成的代码按「可能恶意」对待，是这个模块与「能跑就行」的玩具实现之间最本质的分界线。

04 · 伪代码

两个最小闭环：沙箱执行与带版本化的文件写入

剥掉日志、指标、异常分类后的骨架，核心机制就这两段：注册表选后端跑代码，取锁写文件留版本。

骨架一：沙箱执行最小闭环

# services/sandbox/ —— execute_code 的核心路径（简化） async def execute_code(code: str, lang: str, timeout: int) -> ExecResult: cfg = SandboxConfig.from_settings() # type / 限额 / 超时 backend = get_sandbox_backend(cfg) # registry: type -> Backend 类 if cfg.type == "subprocess" and not shutil.which("bwrap"): if not cfg.allow_unsafe_fallback_when_bwrap_missing: raise SandboxUnavailable("bwrap missing, fail closed") # 显式开关才允许降级为裸 subprocess timeout = min(timeout, cfg.max_timeout) # 服务端封顶 300s await backend.prepare() # 镜像 / 会话 / 工作目录 try: result = await backend.run( code, lang, timeout=timeout, # 默认 180s limits={"cpu": cfg.cpu_limit, # "0.5" "mem": cfg.memory_limit, # "256m" "net": cfg.allow_network}, ) artifacts = await backend.collect_outputs() # 按 workspace_mode 回收产物 return ExecResult(result.stdout, result.stderr, artifacts) finally: await backend.cleanup() # 杀进程 / 销容器 / 关会话

05 · 面试 QA

六道题，从隔离原理问到设计哲学

Q1 · bubblewrap 和 Docker 的隔离强度差在哪？音巢为什么容器内还要套一层 bwrap？

Docker 是完整的容器隔离：独立 namespaces + cgroups + 镜像文件系统，隔离边界厚重但代价是每次执行要起容器、拉镜像，冷启动以秒计。bwrap 是轻量沙箱：用 user/mount/pid namespace 把单个进程包起来，百毫秒级启动，但不带镜像分发能力。音巢 backend 本身跑在容器里，execute_code 用 bwrap 是纵深防御：外层容器防的是平台被入侵后扩散，内层 bwrap 防的是「LLM 生成的代码」这个一等不可信输入在容器内乱窜——读写其他 Agent 的工作区、摸环境变量里的密钥。一层防外敌，一层防家贼。追求更强隔离可以切 docker 后端（sibling 容器）或 E2B（Firecracker 微虚拟机）。

Q2 · 什么是 fail-closed？音巢在沙箱上是怎么贯彻的？

fail-closed 指「安全依赖的能力缺失时，默认拒绝服务」；反义是 fail-open——为了可用性静默降级。音巢的做法：main.py 启动时 _log_bwrap_startup_status 检测 bwrap，缺失只告警不阻断进程（平台其他功能不该陪葬）；但真正执行 execute_code 时，bwrap 缺失直接返回明确错误，除非运维显式设置 SANDBOX_ALLOW_UNSAFE_FALLBACK_WHEN_BWRAP_MISSING=true。这个设计的关键在于降级必须是一个显式动作：开关名里带 UNSAFE，谁开的谁负责，事后审计也有据可查。安全工程里最常见的灾难不是攻击多高明，而是某次「先让它能跑」的静默降级被遗忘了。

Q3 · 为什么 backend 容器需要 privileged 和 docker.sock？风险怎么收？

两个需求来源：① bwrap 在容器内创建 user namespace 需要 SYS_ADMIN capability，默认容器 seccomp/权限策略会拦；② docker 后端要通过 /var/run/docker.sock 起 sibling 容器做执行隔离。风险是实打实的：privileged 容器被突破约等于宿主机失守。收敛手段：① docker-compose 里 privileged 只给 backend，其他服务不挂；② 不可信代码永远先进 bwrap / sibling 容器，特权只被「沙箱管理器」这一小段代码使用；③ 对安全更敏感的部署可以整体切 self_hosted / E2B 后端，把执行面挪出 backend 容器，这时可以摘掉 privileged——沙箱后端可插拔的价值在这里兑现：部署形态决定隔离策略，而不是反过来。

Q4 · 文件编辑锁的粒度怎么选？怎么避免死锁？

音巢的锁粒度是 (agent_id, path) 行级锁，落在 workspace_edit_locks 表。选数据库锁而不是进程内锁，是因为平台多进程 / 多副本部署，内存锁根本不可见；选文件级而不是目录级，是因为 Agent 的典型写模式是「读几个文件、改一个文件」，目录锁会把无关文件串行化。死锁避免靠三条：① 锁在 finally 里必释放，写路径持锁时间只覆盖「读旧版 + 写新版」，不含 LLM 调用等长耗时操作；② 单写者模型——一个 Agent 的执行循环是串行的，锁主要防的是多会话 / 协同 Agent 并发改同一文件，锁顺序冲突的场景极少；③ 数据库行锁天然带超时与事务回滚，持锁方崩溃由数据库清理，不会留孤儿锁。

Q5 · S3 预签名 URL 的安全边界在哪里？

预签名 URL 把「下载授权」从应用服务器转移给对象存储：URL 里带签名，持链即可下载，TTL 到期自动失效（音巢 S3_PRESIGN_TTL_SECONDS=3600）。边界要想清楚三件事：① URL 即凭证——它一旦泄露（日志、转发、截图），TTL 内任何人可用，所以只用于短期下载、不进持久化存储；② 签名按 key 精确生成，不能目录级通配，越权读其他租户文件的窗口不存在；③ 写路径不用预签名 POST 放权给客户端乱传，字节流仍走后端校验。它的价值是卸载带宽——大文件下载不挤应用服务器；代价是把「访问控制的有效期」从会话级缩短到 TTL 级，这是个可接受的置换。

Q6 · 版本化存储的成本怎么控制？AgentBay 这类云沙箱又打开了什么新场景？

版本化（workspace_file_revisions）的成本是写放大：每次覆盖写都留一份旧版本，一个被反复重写的大文件会产生线性增长的历史。控制手段的常规菜单：按文件大小设版本化阈值（小文件全留、大文件只留元数据或最近 N 版）、按时间窗口合并、冷版本转廉价存储——配合 workspace_reconciliation 对账任务定期清理孤儿版本。AgentBay 的意义在于把沙箱从「代码解释器」扩展成「一台云端的电脑」：浏览器会话让 Agent 能操作需要登录态的网页、截图取证、做端到端 UI 验证；电脑操控会话打开了 GUI 自动化这一类本地 bwrap 根本覆盖不了的场景。多后端架构的回报就在这儿——新执行形态出现时，加一个后端而不是重写一个子系统。

给 Agent 一台电脑，也给它上好锁

工作区让 Agent 的产出落得住、查得回、发得出；沙箱让 Agent 的代码跑得开、限得住、伤不到人。

这两层都不性感，但它们决定了多智能体平台是「演示玩具」还是「生产系统」。

信任不是给的，是设计出来的：默认隔离、默认版本化、默认 fail-closed。
