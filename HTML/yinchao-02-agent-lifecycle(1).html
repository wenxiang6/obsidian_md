01 · 场景

把 Agent 当员工管，而不是当脚本跑

大多数 Agent 框架只回答「怎么让 LLM 调工具」，音巢 Agent 平台回答的是另一个问题：当平台上有几十上百个 Agent 长期运行时，怎么管它们——谁能创建、能做什么、花多少钱、出了事谁审批。这就是数字员工管理的定位。

五类真实业务场景

①

人才市场一键「招聘」

运营同学打开人才市场（TalentMarketModal），从 22 个内置职业模板里挑一个「Backend Architect」或「SEO Specialist」，填个名字就完成创建——人格、技能、默认 MCP 工具、自主策略全部由模板预置，零提示词工程门槛。

②

危险操作要人批

Agent 自主工作时想「发外部消息」「修改自己的人格文件」「做财务操作」，这些动作默认落在 L3：执行被挂起，审批单进入 ApprovalsTab，创建者点「批准」后才真正执行。自主不等于放任。

③

给 Agent 限额，防止 token 烧钱

一个跑飞了的自主 Agent 一晚上能烧掉惊人的 token。音巢给每个 Agent 配了 token 日/月限额、LLM 日调用上限（默认 1000 次）、存活 TTL（expires_at）与触发器限额——超限时同步拦截，而不是事后看账单。

④

远程 OpenClaw 机器人纳管

跑在用户自己机器上的 OpenClaw 机器人，通过 API Key + 网关轮询（/gateway/poll）接入平台，和平台托管的 native Agent 一样被分配任务、收发消息、接受配额与状态管理——混合舰队，一套治理。

⑤

新员工入职仪式

用户第一次打开某个 Agent 的对话时，触发 onboarding：Agent 主动问候、自我介绍、通过一轮真实对话校准对用户偏好的理解并写下工作笔记——按 (agent, user) 记录入职状态，不重复打扰。

定位 · 一句话

Agent 生命周期管理 = HR 系统 + 权限系统 + 财务管控，只不过管理对象是数字员工。

模板市场是「招聘渠道」，agents 表是「员工档案」，自主策略是「授权手册」，配额是「预算科目」，审批流是「签批制度」。理解了这层类比，本篇的每个设计决策都不难推导。

02 · 设计

三个关键决策：双轨定义、分级授权、文件即人格

数字员工管理的核心矛盾是「开箱即用的便利」与「长期运行的可控」之间的张力。音巢用三个决策回应它。

关键概念速览

概念取值 / 载体含义
双轨定义 backend/agent_template/ + agent_templates/*/meta.yaml + agents 表 文件侧是「原型」（人格、心跳、记忆骨架），模板侧是「职业说明书」（能力、默认技能/MCP/策略），库侧是「员工档案」（模型绑定、配额、状态）。三者各司其职，创建时合流。
agent_type native / openclaw native 由平台托管运行（容器 + 平台 LLM 配置）；openclaw 是远程机器人，凭 API Key 轮询网关收派消息。两种类型同表同状态机，治理口径一致。
access_mode company / private / custom company：全员可用且进 Plaza 广场；private：仅创建者可用可管；custom：全员可用、显式授权行授予 manage 权限，不进 Plaza。
生命周期状态 creating / running / idle / stopped / error agents.status 枚举，创建默认 creating，由运行时与容器状态推进。

人格与记忆：文件系统 vs 数据库字段 D1

选项

① 人格 prompt、记忆、技能全部存数据库字段 / 向量库
② 以目录树承载：soul.md、HEARTBEAT.md、memory/、skills/、workspace/、state.json，实例化时拷贝到 agent_data/<uuid>/

决定

文件即人格：每个 Agent 一个目录，数据库只存档案与治理字段

原因

人格与记忆本质是「给 LLM 读的上下文」，文件天然可被 LLM 直接读写、可被人审阅 diff、可被 Git 化备份；且 openclaw 远程机器人需要把整套目录同步到本地运行——文件是唯一两端同构的载体。

代价

失去数据库的事务与查询能力：跨 Agent 检索记忆要靠额外索引（经验库补齐），并发写要靠工作区锁。换来的是可读性、可移植性与 LLM 原生可操作性。

自主权限：全局开关 vs 按操作分级 D2

选项

① 一个「全自动 / 全人工」总开关
② 按操作类型分级：10 类操作各自标 L1（自动执行）/ L2（执行并通知）/ L3（人工审批后才执行）

决定

按操作分级 L1/L2/L3，模板可为每类操作预置默认值，Agent 创建后可逐类调整

原因

真实授权从来不是二元的：读文件该放手（L1），写工作区文件执行后告知即可（L2），发外部消息、改人格、财务操作必须人批（L3）。分级让「自主权」成为可逐项授予的资产，与 Human-in-the-loop 天然兼容。

代价

每次工具调用都要过一次 autonomy_service 判定；L3 挂起需要审批单、通知与恢复执行的完整链路。换来的是自主 Agent 敢真正放权运行。

模板与实例：运行时引用 vs 创建时拷贝 D3

选项

① 实例运行时直接引用模板文件，省存储
② 创建时把模板目录渲染 + 拷贝成实例私有目录，从此各自演化

决定

创建时一次性拷贝（含 {{agent_name}} 等占位符渲染），实例独立演化

原因

数字员工入职后要「成长」：记忆、工作区产物、甚至人格都会被运行过程改写。若共享模板文件，一个 Agent 的学习会污染所有同模板实例；拷贝让模板只影响「出厂配置」。

代价

模板升级无法自动传导到存量实例（需要显式重建或迁移）；存储随实例数线性增长。换来实例间的彻底隔离。

04 · 伪代码

两个最小闭环：创建即独立，调用必过闸

伪代码刻意省略事务、异常与日志细节，只保留机制骨架——对照上游实现（agent_manager.initialize_agent_files、autonomy_service.check_and_enforce）可读。

闭环一：创建 Agent（渲染 → 拷贝 → 建档 → 绑定默认能力）

# 最小创建流程：模板双轨合流为一个独立实例 async def create_agent(db, user, req): tpl = await get_template(db, req.template_id) # agent_templates 表（seeder 从 meta.yaml 灌入） agent = Agent( name=req.name, creator_id=user.id, tenant_id=user.tenant_id, status="creating", # 状态机起点 template_id=tpl.id, autonomy_policy=tpl.default_autonomy_policy, # 10 类操作的 L1/L2/L3 默认值 ) db.add(agent); await db.flush() # 先拿 uuid # 1) 渲染人格：{{agent_name}} / {{creator_name}} / {{created_at}} soul = render_soul_template(read("agent_template/soul.md"), agent_name=agent.name, creator_name=user.name) # 2) 拷贝目录：模板 → agent_data/<uuid>/（此后实例独立演化） copy_tree("agent_template/", f"agent_data/{agent.id}/", overrides={"soul.md": soul}) # 3) 绑定默认能力：技能直接挂，MCP 走 Smithery 自动导入（幂等） for skill in tpl.default_skills: bind_skill(db, agent, skill) for smithery_id in tpl.default_mcp_servers: tool = await import_mcp_from_smithery(smithery_id) # 同 URL 已存在则复用 bind_tool(db, agent, tool) agent.status = "idle" # 建档完成，待命 await db.commit() return agent

闭环二：自主策略判定（每次工具调用的同步闸门）

# autonomy_service.check_and_enforce 的骨架 async def check_and_enforce(db, agent, action_type, details): level = agent.autonomy_policy.get(action_type, "L2") # 未知操作默认 L2，安全收敛 if level == "L1": return {"level": "L1"} # 直接放行（如 read_files） if level == "L2": await notify_creator(agent, action_type, details) # 执行并告知 return {"level": "L2"} # L3：确定性审批单 —— 同一 tool_call 重试不重复开单 approval_id = uuid5(NS, f"runtime-approval:{action_type}:{details.tool_call_id}") existing = await get_approval(db, approval_id) if existing: assert_matches(existing, action_type, details) # 防审批重放到别的操作 if existing.status == "approved": return {"level": "L3", "approval_status": "approved"} raise ApprovalPending(approval_id) # 挂起本次运行 await create_approval_request(db, id=approval_id, agent=agent, action=action_type, details=details) raise ApprovalPending(approval_id) # 等待 ApprovalsTab 人工签批
为什么「挂起」用异常而不是阻塞等待

L3 命中的工具调用通过抛出 ApprovalPending 中断当前 Agent Run，而不是在原地 await 审批结果——审批可能几小时后才发生，长时间持有协程与数据库连接既浪费资源又无法跨进程恢复。审批单落库后运行即可安全结束，批准后由审批回调按 tool_call_id 恢复现场，这正是持久化运行时（见本系列第 01 篇）的价值所在。

05 · 面试 QA

六道题，检验你是否真的懂「管理 Agent」

每道题都对应音巢的一个真实实现选择，回答请对着代码讲，不要背八股。

Q1 · 人格和记忆为什么用文件（soul.md / memory/）而不是数据库字段或向量库？

三个理由，层层递进：①消费者是 LLM——人格与记忆的最终读者是模型，文件是 LLM 工具链（读/写/列目录）原生可操作的形式，放进数据库反而要再包一层读写工具；②可审阅可演化——Agent 运行中会持续改写自己的记忆与人格，文件 diff 对人类可读，这是「自主 Agent 可治理」的前提；③跨部署形态同构——openclaw 远程机器人要把整套目录同步到用户本地运行，文件是唯一在平台侧与远程侧都成立的载体。代价是失去事务与结构化查询，音巢用经验库（experience）补检索、用工作区锁补并发——不是文件万能，而是把缺口显式补上。

Q2 · L1/L2/L3 自主分级是怎么落地 Human-in-the-loop 的？为什么未知操作默认 L2？

落地链路：每次工具调用过 autonomy_service.check_and_enforce，按 action_type 查 agents 表里的 autonomy_policy JSON。L1 直接放行；L2 执行并通知创建者；L3 生成审批单（approval_requests 表）并抛出挂起异常，终止当前 Run，等创建者在 ApprovalsTab 批准后按 tool_call_id 恢复执行。两个工程细节值得展开：审批单 ID 用 uuid5("runtime-approval:{action_type}:{tool_call_id}") 确定性生成，天然幂等；恢复执行前校验动作一致性，防止「批了 A 操作被执行成 B 操作」。未知操作默认 L2 而非 L1，是安全默认值：新接的 MCP 工具哪怕平台还没分级，也至少保证「执行了一定告知主人」。

Q3 · 配额防烧钱应该同步拦截还是异步统计？音巢怎么选的？

两者都要，但职责必须分开。音巢的分工是：同步拦截在 quota_guard——check_agent_llm_quota 在每次 LLM 调用前检查日调用上限（默认 1000 次），check_agent_expired 检查 expires_at 存活 TTL，超限直接抛 QuotaExceeded / AgentExpired 终止请求，这是防线，必须同步，否则烧钱已成事实；异步统计在 token_tracker——token 日/月用量、cache read/creation 分桶计数在调用后归集到 agents 表的计数字段，配合日/月 reset 时间戳滚动清零。为什么不同步拦 token？因为一次调用的 token 数在调用前不可知，只能用「调用次数」做前置闸门、用「token 累计」做后置熔断——这是用可预测的量做同步闸、用不可预测的量做异步账的典型取舍。

Q4 · 主备 LLM failover 是怎么设计的？什么场景会触发切换？

agents 表上有一对字段：primary_model_id 与 fallback_model_id，都指向 llm_models 表。运行时优先用主模型发起调用，当主模型不可用（超时、限流、服务商故障）时降级到备模型，保证数字员工不因为单一供应商抖动而「失能」。设计上要注意三点：①主备最好跨服务商，否则同城同云故障会双杀；②切换只影响当次/当轮调用，不改档案——故障恢复后自动回到主模型，避免人工干预；③主备模型的上下文窗口与工具调用能力要对齐，否则 failover 后行为漂移（比如备模型不支持 function calling 时整轮 Run 的失败模式完全不同），这是选型备模型时的硬约束。

Q5 · 远程 OpenClaw 机器人用「轮询网关」而不是 WebSocket 长连接，优缺点各是什么？

模型：机器人持有 API Key（平台存 api_key_hash 校验），周期性 GET /gateway/poll 拉取待处理消息，执行后 POST /report 回执，另有 /heartbeat 与 /send-message。优点：穿透性——轮询是出站 HTTPS，机器人可以在任意 NAT/企业防火墙后运行，不需要平台反向触达；健壮性——无连接状态，机器人重启、网络闪断都不丢消息（消息在网关侧排队）；简单性——无长连接管理、无重连风暴。缺点：延迟——消息时延下限是轮询间隔；空转成本——空闲时也在打 poll（可用 openclaw_last_seen 做在线状态与退避）；实时性要求高的场景（流式输出）不适合。对「任务型远程员工」这个定位，穿透性与健壮性的收益远大于秒级延迟的损失，是正确取舍。

Q6 · 模板市场的「默认 MCP 自动绑定」是怎么实现的？重复创建会怎样？

链路分三段：①模板的 meta.yaml 里声明 default_mcp_servers，内容是 Smithery 服务器 ID（如 "shibui/finance"），seeder 灌入 agent_templates 表；②创建 Agent 时（api/agents.py 的 create_agent），逐个调用 import_mcp_from_smithery——用系统级 Smithery Key 拉取该 MCP Server 的接入信息，在平台侧注册为 Tool；③通过 AgentTool 关联把 Tool 绑定到新 Agent。幂等设计：如果平台已存在相同 mcp_server_url 的 Tool，直接复用而不是重复注册——所以从同一个模板创建 10 个 Agent，MCP Server 只导入一次，绑定关系各自独立。这把「装工具」从用户的手工配置变成了模板的一部分，是人才市场「一键招聘、到岗即能干活」体验的关键一环。

自治的前提，是可治理

文件即人格，让数字员工可以被阅读、被审计、被带走；分级授权与审批流，让自主运行有刹车；配额防线，让长期运行不失控。

模板市场解决「招来就能用」，生命周期治理解决「用着不出事」——两者相加，Agent 才从 Demo 变成员工。

敢放权，是因为每一级权力都标好了价格与审批人。
