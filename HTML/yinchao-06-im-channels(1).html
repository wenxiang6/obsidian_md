01 · 场景

Agent 的价值，取决于它离员工的工作入口有多近

一个只能在自己网页里对话的 Agent，使用率会输给「在群里 @ 一下就能干活」的 Agent。IM 渠道集成的定位，就是把音巢 Agent 平台里的每一个数字员工，变成各大 IM 里一个有独立身份的机器人同事。

四类业务场景

①

工作群里的数字员工

每个 Agent 绑定独立的飞书/钉钉机器人身份。群里 @ 它就派活：「@数据分析 跑一下昨天的留存漏斗」，执行结果回帖到群里。员工不需要开新网页，Agent 就在已有的工作入口里。

②

企微 / 微信客服前台

企业微信与客户微信是最重的外部触达面。Agent 以客服身份承接咨询，会话上下文由 channel_session 按渠道 + 外部会话 ID 维持，多轮问答不断片。

③

海外团队协作

Slack / Discord / Microsoft Teams 覆盖海外团队与开源社区场景。Discord 在国内网络环境下需要代理出口——音巢的做法是进程内启动 ss-local SOCKS5，而不是要求整机翻墙。

④

远程机器人 OpenClaw

不想把凭证托管在平台上的场景：用户自部署的 OpenClaw 机器人持 API Key 走 api/gateway.py 轮询拉消息、上报结果、发心跳——消息照样进入同一个 Agent Runtime。

定位 · 一句话

IM 集成不是「做七个机器人 Demo」，而是把七种协议差异关进 connector 进程，给 Agent Runtime 只暴露一种消息模型。

入站：渠道事件验签、去重、归一化为站内消息后命令入队；出站：Agent 回复落库后由 outbox（channel_deliveries）按渠道适配格式投递回去。Runtime 自始至终不知道消息来自飞书还是 Discord。

02 · 设计

核心决策：长连接优先，Webhook 兜底

IM 接入只有两条路：平台方回调你的公网 Webhook，或者你主动连平台的长连接收事件。音巢为每个渠道选哪条路，取决于平台能力、部署方的网络条件，以及运维复杂度三件事。

入站事件通道：长连接（WebSocket / Stream）vs 公网 Webhook D1

选项

① 全 Webhook：每个渠道一个公网回调端点，平台推事件
② 全长连接：SDK 主动连平台收事件，无需公网入口
③ 混合：有官方长连接 SDK 的优先长连接，只有 Webhook 的保留回调端点

决定

混合策略：飞书/钉钉/企微/Discord 走长连接，微信走轮询，Slack/Teams/WhatsApp 保留 Webhook 回调

原因

长连接不要求部署方有公网域名和 HTTPS 证书——私有化部署、NAT 内网、开发本机都能直接收事件，这是企业软件落地最现实的门槛。且长连接天然有顺序与心跳，验签压力小。

代价

长连接是有状态资源：断线重连、多实例去重、进程退出清理都要自己管。音巢为此单设 connector 进程角色，把这份复杂度隔离在一个可独立伸缩的进程里。

两个细节值得记住：① 飞书侧的去重标记是在处理成功之后才写入 _processed_events（api/feishu.py 注释明确：先标记后崩溃会导致重试事件被吞）；② 归一化阶段会把飞书消息里的 @_user_1 占位符还原成真实用户名（_restore_feishu_text_mentions），让 Runtime 看到的文本与人看到的一致。

为什么 ack 在入队之后就返回，而不是等 Agent 跑完

IM 平台的回调超时通常只有 3~5 秒，而一个 Agent 任务可能跑几分钟。链路在「命令入队」处异步化：渠道侧立即拿到 ack，执行与回复走图 3 的出站投递闭环。这也是 channel_deliveries 存在的根本原因——用一张表把「渠道时序」和「Runtime 时序」解耦。

认领用「状态 + 租约」两字段实现，无需分布式锁：多个 Worker 并发抢单时，数据库行锁保证只有一个能把 pending 改成 claimed；Worker 崩溃不释放，租约到期后自然被接管。配合 (run_id, idempotency_key) 唯一约束，同一条回复最多一张投递单。

04 · 伪代码

两个闭环：事件进来，回复出去

伪代码保留真实实现的关键机制——去重标记后置、幂等键贯穿、租约认领与退避——省略渠道 SDK 的样板代码。

闭环一：飞书长连接事件处理骨架（对应 feishu_ws.py + api/feishu.py）

# connector 进程内：每个绑定了飞书渠道的 Agent 一个 WS 客户端 class FeishuWSManager: async def start_client(agent_id, app_id, app_secret): handler = build_event_handler(on_message=lambda data: dispatch_to_main_loop(agent_id, data)) client = lark.ws.Client(app_id, app_secret, event_handler=handler) await client.start() # 长连接由 SDK 维持与重连 async def process_feishu_event(agent_id, body): event_id = body["header"]["event_id"] if event_id in _processed_events: # 去重：渠道重推直接吞掉 return {"code": 0, "msg": "already processed"} message = parse_message(body["event"]["message"]) text = restore_mentions(message.text, message.mentions) # @_user_1 → 真实姓名 session = await find_or_create_channel_session( # 渠道会话 → 站内会话 channel="feishu", external_chat_id=message.chat_id) await accept_runtime_message( # 命令入队，幂等键 = 渠道消息 ID agent_id, session, text, external_event_id=message.message_id or event_id, source_message_id=message.message_id if is_group else None) _processed_events.add(event_id) # ★ 成功之后才标记—— if len(_processed_events) > 1000: # 保证崩溃重试不被吞 _processed_events.clear() return {"code": 0} # 立即 ack，不等 Agent 执行

闭环二：出站投递循环（对应 agent_runtime/channel_delivery.py + channel_provider_delivery.py）

# Runtime 侧：回复落库后写投递单（run_id + idempotency_key 唯一，重复写会被约束挡下） stage_channel_delivery(run, session, content) # → INSERT channel_deliveries(status='pending') # Worker 侧：认领 → 发送 → 回执，租约兜底崩溃恢复 class ChannelDeliveryWorker: async def loop(): while True: envelope = await self._claim() # pending → claimed，写 claimed_by + claim_expires_at if envelope is None: # 同时回收租约过期的孤儿单 await sleep(poll_interval); continue try: result = await sender.send(envelope) # 按 channel 分发适配器 await self._complete(envelope, result) # → delivered + delivery_succeeded 事件 except ChannelDeliveryError as e: await self._retry_or_fail(envelope, e) # pending(退避) 或 failed 终态 class DatabaseChannelDeliverySender: SENDERS = {"feishu": _feishu, "dingtalk": _dingtalk, "wecom": _wecom, "wechat": _wechat, "slack": _slack, "discord": _discord, "microsoft_teams": _teams, "whatsapp": _whatsapp} async def send(envelope): config = await load_channel_config(envelope) # channel_configs 取凭证与目标 for chunk in _chunks(envelope.text, CHANNEL_LIMIT): # 超长消息按渠道上限切片 await SENDERS[envelope.channel](envelope, config, chunk) await recall_thinking_reaction(envelope, config) # 钉钉：撤回「思考中」表情

两个闭环之间没有任何直接调用——接缝就是数据库。这意味着 connector 进程和 Runtime worker 可以分别崩溃、分别重启、分别伸缩，消息不丢（未 ack 的事件渠道会重推）、回复不重（幂等键 + 唯一约束）。

05 · 面试 QA

六道题，从选型聊到崩溃恢复

每道题的回答都落到音巢的真实实现上，不停留在概念层。

Q1 · 长连接（WebSocket/Stream）和公网 Webhook 回调，怎么取舍？

看三个变量：平台能力、部署方网络、运维成本。Webhook 模式实现最简单——起一个 HTTP 端点等平台推——但它要求部署方有公网可达的 HTTPS 入口，这对私有化部署和内网客户是硬门槛。长连接模式反过来：实现重（重连、心跳、状态管理），但对部署方零网络要求，本机开发都能收事件。音巢的答案是混合：有成熟长连接 SDK 的（飞书 lark-oapi、钉钉 dingtalk-stream、企微 wecom-aibot-sdk、Discord discord.py）一律长连接；只有回调形态的（Slack/Teams/WhatsApp）保留 Webhook；微信连 SDK 都没有，直接轮询。复杂度集中在 connector 进程角色里，用 PROCESS_ROLE 把它从 API 进程中拆出去独立伸缩。

Q2 · IM 平台保证的是「至少一次」投递，重复消息怎么去重？

音巢是三层去重，各管一段：① 事件层——飞书事件带 event_id，处理前查内存集合 _processed_events，重复事件直接返回成功；关键是标记在处理成功之后才写入，否则进程在入队前崩溃、渠道重推时会被误判为已处理而吞掉消息。② 命令层——归一化后入 Runtime 的命令带 idempotency_key（由渠道消息 ID 派生），数据库唯一约束兜底，即使进程重启、内存集合丢了，同一事件也不会产生第二次执行。③ 出站层——channel_deliveries 上 (run_id, idempotency_key) 唯一，同一条 Agent 回复最多生成一张投递单。内存集合是第一道低成本防线，数据库约束才是正确性来源。

Q3 · 七个渠道的消息模型差异巨大，怎么抽象出统一模型而不丢能力？

抽象的原则是「归一化到 Runtime 需要的最小集合，渠道特性留在两侧适配层」。入站侧，各渠道的事件各自解析（飞书要还原 @ 提及占位符，企微要按帧类型分 text/image/file，钉钉要下载媒体附件），但最终都收敛成同一件事：find_or_create_channel_session(channel, external_chat_id) 找到站内会话，然后带 external_event_id 入队一条命令。Runtime 看到的只有「某会话收到一条文本消息」，不知道也不关心来自哪个渠道。出站侧对称：DatabaseChannelDeliverySender 里按 channel 分发到八个发送分支，长消息切片、表情回应撤回这类渠道怪癖都收在各自分支里。抽象层只管「会话 + 文本 + 幂等键」，渠道能力靠适配层而不是靠污染统一模型。

Q4 · 长连接断了、进程重启了，这段时间的消息会不会丢？

分入站和出站看。入站：主流 IM 平台对未成功 ack 的事件会重推（飞书会按梯度重试），所以断线窗口内的消息靠平台重试补偿，进程恢复后能补收；配合 Q2 的去重，重推不会造成重复执行。真正会丢的是「平台重试窗口之外的漏收」，这要靠运营层的对账兜底，设计上接受这个残余风险。出站：投递单持久化在 channel_deliveries，Worker 崩溃靠租约机制恢复——认领时写 claimed_by + claim_expires_at，崩溃的单子租约到期后被下一个 Worker 重新认领；可重试失败走 attempt_count 递增的退避重试，不可重试进 failed 终态留痕。整个设计的基调是：进程随时可死，状态全在表里。

Q5 · Agent 在平台内是流式输出的，IM 侧怎么模拟「正在输入」的体验？

IM 渠道大多没有原生的流式消息 API，音巢用了两个替代手段。一是表情反应当进度信号：钉钉群场景下，收到消息后先给消息打一个「思考中」的 reaction，回复发送成功后在投递层调用 recall_thinking_reaction 撤回（飞书侧对称地有 add_message_reaction）——用户在 Agent 思考期间有明确反馈，而不是对着沉默的群干等。二是终态消息一次送达：回复按渠道长度上限切片（_chunks）后顺序发送，而不是边生成边推。这是有意的取舍：IM 是异步场景，用户预期是「@ 之后过一会儿收到完整回复」，流式逐字刷新既做不到（多数渠道编辑消息有限流）也没必要。把流式体验留在 Web 端，IM 端保证的是「有反馈、答复完整、不刷屏」。

Q6 · Discord 需要代理出口，这种环境适配怎么和正常配置隔离？

看 main.py 的 _start_ss_local，它是一个教科书式的「环境适配层」写法：① 配置外置——代理节点从 SS_CONFIG_FILE（默认 /data/ss-nodes.json，gitignore，Docker 卷挂载）读取，凭证不进代码库；文件缺失时降级到 SS_SERVER/SS_PASSWORD 环境变量。② 进程内拉起——用 asyncio 子进程启动 ss-local，监听 127.0.0.1:1080，按节点优先级逐个试，成功才把 DISCORD_PROXY=socks5h://... 写进环境变量给 discord.py 用。③ 失败不炸——ss-local 不存在、配置为空、JSON 损坏、所有节点连不上，全部只记日志继续启动，Discord 直连降级运行。配置隔离的精髓是：环境差异被压缩成一个「可选的环境变量」，主流程代码里不出现任何 if-china 式的分支。

渠道会过时，闭环不会

今天接的是飞书和钉钉，明天可能是下一个还没出生的协作平台。音巢 IM 集成真正沉淀下来的，不是七个渠道的适配代码，而是那个不变的结构：协议差异关进 connector，消息进出走两张表，Runtime 永远只面对一种消息模型。

当 Agent 活在员工已有的工作入口里，它才从「一个要特意打开的工具」变成「一个随时在场的同事」。
