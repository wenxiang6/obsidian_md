01 · 问题背景

AI 时代的研发瓶颈，不在"写代码"

当 AI 已经能写出大部分业务代码，真正拖慢迭代的，是代码之外的一切：环境、权限、流程、协作与失控的 AI 本身。

环境是隐形的生产力黑洞

JDK 版本、Maven 镜像、容器、端口、前端依赖……一个新成员（或一次新会话）开工前，动辄半天到数天消耗在"让项目跑起来"上。

权限与平台是业务无法跨越的墙

Git、发布平台、日志平台、菜单配置、数据库账号……业务方想推进一个小改动，却被一串需要登录、申请、配置的门槛挡在门外，事事依赖产研。

流程靠口头约定，迭代靠个人习惯

需求—设计—开发—测试—发布，每个环节的产物和确认点因人而异、因项目而异。迭代一多，谁也不知道当前进行到哪一步、上次改了什么。

AI 会"漂移"，产出不可预期

没有约束的 AI：改错仓库、静默跳过阻塞、编造完成状态、越权提交发布。能力越强，偏离轨道的代价越大。

产研的时间被大量"非研发"事务消耗

配环境、拉服务、发预览链接、写进度同步、查日志……真正创造价值的架构与编码时间被严重挤占。

经验在人脑里，人走经验走

业务域知识、排坑记录、发布注意事项散落在聊天记录与个人记忆中，无法沉淀为组织资产。

02 · 解决什么问题

工作台：把迭代所需的一切，封装成一个"代理"

工作台是一个独立于业务仓的目录：制度（AGENTS.md）、声明配置（automation.config.json）、自动化引擎、领域知识文档、迭代记录，全部就位。AI 在此开工，业务在此对话。

流程标准化，迭代可控

内置 10 个固定阶段（检查 → 产品设计 → 交互设计 → 技术方案 → 用例 → 开发 → 预览 → 测试 → 提交 → 发布），每个阶段有明确产物与放行条件。任何一次迭代都走同一条路，进度与状态一目了然。

环境与权限对业务彻底隐身

环境搭建、容器编排、JDK/Maven 工具链，以及 Git、发布平台、日志平台、菜单配置、数据库账号等所有需要登录的权限，全部封在工作台内部。业务与产品无需感知。

IDE 的 MCP / Skills 预装预配

前端的蓝湖 MCP、各类物料库 Skill，后端的二方 SDK 物料……这些 AI 干活所需的"扳手与零件"，由工作台统一配置，业务不需要知道它们的存在，AI 却每次都能直接用。

业务直面迭代，释放产研生产力

不懂产研流程的业务方，可以用自然语言直接发起、跟进、验收一次迭代。产研从"环境工、传话筒、进度同步员"回归为"审核者与决策者"。

显著降低 AI 漂移风险

强制开工顺序、声明式单一事实源、三处人工确认卡点、铁律约束——AI 的行为被制度与配置双重锚定，产出从"看运气"变成"可预期"。（详见第 05 节）

迭代全程留痕，永不混乱

每个迭代有独立目录与活动日志（activity.md），每个阶段前后强制记录。任何时刻都能回答："这个迭代做了什么、为什么这么做、卡在哪。"

知识资产化，经验不随人流失

业务域总览、仓库档案、外部阻塞清单以文档形式持续累积。任何新成员、新会话读完即满血开工——组织不再依赖"某个熟悉项目的人"。

可复制到任意业务线

工作台与业务代码完全解耦：换一套业务仓，改一份配置与文档，同一套迭代范式即刻生效。一次建设，多处复用。

最核心的一点

生产资料的所有权，就是 AI 时代的不可替代性

在 AI 时代，"写代码"本身正在快速商品化。而业务的生产资料——流程标准、环境配置、权限通道、领域知识、AI 约束——也就是这套工作台本身，目前由"我"掌控并持续迭代。谁掌握并进化生产资料，谁就掌握生产力分配的入口。这才是真正的护城河。

04 · 迭代流水线

十个阶段，每个节点都为"防呆"而定制

流水线的价值不在"有流程"，而在每个节点的定制化处理都精确命中一个真实痛点。三处琥珀色节点为人工确认卡点——AI 无权自动越过。

① 开工检查 ② 产品设计人审 ③ 交互设计人审 ④ 技术方案 ⑤ 测试用例 ⑥ 开发 ⑦ 预览 ⑧ 测试 ⑨ 提交 ⑩ 发布人审 AI 自动执行人工确认卡点
1

check · 开工检查

全自动

定制化处理

  • 一条命令扫描全部前置条件：Docker 容器、JDK/Maven 版本、端口占用、服务健康、文档完整性
  • critical 失败直接阻断；可修复项由 init 自动修复（起容器、装依赖）
  • 后端挂起不阻塞纯前端迭代（frontend-only 降级策略）

价值

把"环境不一致"这个最大的时间黑洞消灭在开工前。任何人、任何一次 AI 会话，拿到的都是同一个可工作的起点——没有"在我机器上是好的"。

2

product-design · 产品设计

人工确认产物 product-design.md

定制化处理

  • AI 起草结构化 PRD：需求背景、用户故事、验收标准、边界 case
  • 铁律：必须人工确认后才放行下一阶段，AI 不得自动跳过

价值

需求共识前置，返工成本最小化；验收标准同时成为后续测试阶段的判定基准。AI 做执行，人做产品决策——权责各归其位。

3

ux-design · 交互设计

人工确认产物 ux-design.md

定制化处理

  • 通过蓝湖 MCP 直接读取设计稿，物料库 Skill 匹配可用组件
  • 页面结构与交互说明落成文档，人工确认后放行

价值

设计还原零口头传递：AI 拿到的是设计稿本身而非转述，前端有现成物料可直接拼装，还原度与速度兼得。

4

technical-design · 技术方案

AI 主导产物 technical-design.md

定制化处理

  • 动笔前必读 docs/business-repositories/ 仓库档案：表结构、关键流程、端口约定、已知坑
  • 方案必须锚定到具体仓库与文件，改动范围明确
  • 涉及新知识时同步更新档案文档

价值

方案不悬空——直接建立在真实代码与领域知识之上；知识文档随每次迭代增值，形成复利，越做越准。

5

test-cases · 测试用例

AI 主导产物 api-test-cases.md

定制化处理

  • 先于开发产出 API / 场景用例，覆盖正常流与边界流
  • 用例直接引用第 2 阶段的验收标准

价值

TDD 式约束：先立靶子再放箭。防止 AI"自说自话式完成"——完成与否由事先写下的用例裁决，而非 AI 自己宣布。

6

dev · 开发

AI 主导

定制化处理

  • 一键拉起 infra 容器 + 前后端服务，端口、工具链全部固定（勿改）
  • 代码只落在业务仓；工作台仓不提交业务代码（铁律）
  • 阶段前后强制写入活动日志（requireActivity 开启）

价值

本地复现与联调零配置；改动边界清晰——工作台管流程，业务仓管代码，互不污染，历史干净可追溯。

7

preview · 预览

全自动

定制化处理

  • 自动生成预览地址：localhost + 局域网 IP 双地址
  • 远程协作（cc-connect）场景下主动推送局域网地址 + 同网段提醒
  • 前端 --host 监听 0.0.0.0，API 自动指向页面所在主机，CORS 已放开

价值

业务方"点链接就能看"，评审不等部署、不等发版。远程场景下 AI 不会犯"把 localhost 发给远程用户"的低级错误——规则已写进制度。

8

test · 测试

全自动产物 test-report.md

定制化处理

  • 按声明的测试清单执行健康检查（HTTP 状态 + 用例）
  • 报告落盘留档，纳入迭代记录

价值

质量门禁自动化：每次迭代都有一份可信的、可回溯的测试报告，而不是"我本地试过没问题"。

9

commit · 提交

规则约束

定制化处理

  • 提交动作在各业务仓内完成，工作台仓不混入业务代码
  • 不输出、不提交任何密钥与敏感配置（铁律）

价值

每个业务仓的 git 历史独立、干净、可审计；安全边界以制度形式固化，不依赖 AI 的"自觉"。

10

publish · 发布

人工确认

定制化处理

  • 发布策略显式声明（当前为 local-only：仅本地提交，不推远端）
  • 发布前必须人工确认；外部阻塞（插件缺失、SMTP 未配等）必须显式登记，不得静默跳过

价值

发布权永远在人手里，对外可见的动作零意外；阻塞透明化——问题被看见才可能被解决，不会被 AI 悄悄绕开。

05 · 驯服 AI 漂移

六重约束：把 AI 从"不可预测"变成"可托付"

漂移不是靠更强的模型解决的，而是靠工程化的约束解决的。工作台用六层机制把 AI 锚在轨道上。

1

强制开工顺序

AGENTS.md 规定：先跑环境检查、再读制度与知识、确认当前迭代，然后才允许动手。顺序即纪律。

2

声明式单一事实源

端口、命令、阶段、测试清单全部集中在一份配置。AI 查配置而非靠记忆，杜绝"凭印象写端口"这类漂移。

3

人工确认卡点 ×3

产品设计、交互设计、发布三处必须人审。AI 的自由度被精确限定在执行层，决策层永远有人。

4

阶段前后强制留痕

每个阶段开始与结束都必须写活动日志。AI 无法"悄悄做完"，所有动作在时间上连续可查。

5

外部阻塞显式登记

缺插件、缺权限、缺账号——一律写入阻塞清单并告知，严禁静默跳过。AI 最常见的"报喜不报忧"被制度禁止。

6

先立靶子再放箭

验收标准与测试用例先于代码产生，完成与否由事先的契约裁决，而非 AI 自评。

06 · 真实迭代案例

一句话需求，如何走完全程

来自工作台的一次真实迭代记录：20261018-0439-工作台支持局域网预览地址（cc-connect 场景）

"远程连接的用户看到的设备不是本机，localhost 地址对他无效。让工作台在 dev 阶段自动给出局域网预览地址。"

新建迭代，生成骨架

一条命令创建迭代目录与阶段产物文档，设为当前活跃迭代

开发：工作台与业务仓联动修改

自动化引擎新增局域网 IP 解析；启动配置中前端加 --host；两个业务仓的 http 层新增 API 地址自动解析；制度文档新增远程预览规则

验证：真实链路打通

确认端口监听 0.0.0.0；局域网地址访问前后端全部 200；浏览器实测 H5 首页真实业务数据渲染正常

留痕与交接

活动日志记录实现细节与验证结论；遗留事项显式登记（骨架文档待人工确认、业务仓改动待提交）；开工检查通过

结果：远程用户此后每次进入 dev 阶段，都会自动收到可直达的局域网预览地址与同网段提醒——一次迭代，永久生效。这正是"工作台本身持续进化"的缩影。
07 · 模式对比

08 · 演进路线

从"迭代工作台"到"业务项目 Agent"

工作台不是终点。当流程与知识沉淀到位，它可以生长为直接参与业务运转的智能体。

当前
PHASE 1

迭代工作台

流程标准化 + 环境与权限封装，业务可直面迭代：

  • 十阶段流水线与人工卡点
  • 一键环境与健康检查
  • 领域知识与迭代记录沉淀
进行中
PHASE 2

能力扩展

在迭代之外，增添运维与排查能力：

  • 日志链路查询 MCP
  • 告警排查与纠错 Skill
  • 业务数据查询与巡检
规划
PHASE 3

业务项目 Agent

业务接口封装为 MCP / Skill 后，Agent 直接执行业务工作：

  • 上架商品、配置营销活动等操作直达
  • 人只做确认与监督
  • 工作台 owner 持续掌控生产资料

写在最后

AI 让"执行"趋近免费，但执行什么、按什么标准、在什么约束下执行——这些定义权，比以往任何时候都值钱。

工作台即生产资料。掌控并持续迭代它的人，就是 AI 时代最难被替代的人。
