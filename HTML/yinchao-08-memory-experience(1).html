01 · 场景

没有记忆的 Agent，每天都是新员工

单次对话里的 Agent 可以很聪明，但会话一关，一切归零：偏好要重讲、坑要重踩、长任务做到一半被上下文窗口「截断」。音巢的记忆与经验体系，解决的就是「跨时间的连续性」——让 Agent 的工作经验随时间增值，而不是随会话蒸发。

定位 · 一句话

记忆不是外挂的向量库，而是 Agent 工作区里「可读、可改、可版本化」的一等公民。

音巢的选择是：人格与长期记忆用文件（soul.md / memory.md），组织经验用受审核的数据库条目（experience_entries），会话热数据用可压缩的上下文状态（session_context_states）——三种介质对应三种变化频率，各归其位。

02 · 设计

按「变化频率」分层，按「信任级别」管控

设计记忆体系首先要回答两个问题：什么东西多久变一次（决定存哪、怎么注入）；谁能写、写什么（决定质量与安全边界）。音巢的答案浓缩在下面两个决策块里。

四层记忆：从「永不变」到「随时被压缩」

层次内容变化频率写入者
soul.md 人格、职责边界、行为准则——「我是谁」 几乎不变 人格层 模板播种 + 管理员维护
memory/memory.md 用户偏好、历史决策、项目背景——「我记得什么」 慢变（天/周级） 长期记忆 Agent 自己在工作区里读写
experience_entries 踩坑记录、可复用做法——「组织学会了什么」 中变，需人工审核后才生效 组织级 Agent 提案草稿 → 人审核发布
session 上下文 当前会话的消息与中间结论——「我们正在干什么」 快变，超阈值即被压缩 易失 运行时自动管理

记忆介质：文件式记忆 vs 向量库记忆 D1

选项

① 向量库路线：记忆切片向量化，语义召回注入 prompt
② 文件式路线：记忆就是 Agent 工作区里的 Markdown 文件，Agent 用文件工具自己读写，注入时按层拼接

决定

长期记忆走文件式（soul.md / memory.md / MEMORY_INDEX.md / curiosity_journal.md），组织经验走数据库条目 + 关键词检索（experience_retrieval）

原因

文件可读、可编辑、可 diff、可随工作区版本化与备份——记忆对人和 Agent 都是透明的；Agent 平台本来就有成熟的文件工具链，写入零额外基础设施。经验库则因「多 Agent 共享 + 审核 + 引用统计」的诉求，天然该进数据库。

代价

文件式没有语义召回能力，记忆规模大了以后靠 Agent 自觉维护索引（MEMORY_INDEX.md）与目录结构，检索精度让位于可解释性；数据库经验条目的召回是关键词 + 可见性过滤，不依赖向量模型。

经验入库：直接写 vs 提案审核管线 D2

选项

① Agent 任务完成后直接写经验条目，立即可被检索
② Agent 只能提交「草稿提案」，人工审核发布后才进入可检索目录

决定

提案审核管线：propose_experience_draft 产生 draft，reviewed_by 人工把关后转为 published；已发布条目的修订走 draft_of_id 影子草稿，发布后合并回源条目

原因

经验会被注入所有有可见权限的 Agent 的上下文——一条错误的经验是组织级的「投毒」。draft 状态明确标注「AI 生成或人撰写、尚不可检索」，published 才进 Agent 上下文目录，把质量闸门卡在进入信任域之前。

代价

沉淀有时延：从踩坑到全员可用隔着一次人工审核；审核队列需要运营。影子草稿机制（draft_of_id）也让引用计数与采纳统计始终挂在稳定的源条目上，模型与流程都更绕一层。

上下文注入的分层组装

每次会话构造 prompt 时，音巢按层注入：soul.md（人格） + memory（长期记忆） + enterprise_info（企业知识） + 经验提示（build_experience_hint） + 群聊共享上下文（GroupContextBuilder 抓取的近期消息与参与者）。各层来源不同、信任级别不同，但在模型眼里是同一份「我是谁、我记得什么、我在哪」的开场白。

四个层次对应四种介质与四种治理强度：文件（人格/记忆）随工作区版本化；数据库条目（经验）受审核与可见性管控；会话状态表（session_context_states）只做运行态持久化。注入顺序即信任顺序——越靠上的层越稳定，越不该被运行时污染。

04 · 伪代码

两个最小闭环：压缩与召回

伪代码略去鉴权、日志与重试，只保留机制骨架：压缩闭环回答「上下文怎么不失忆地瘦身」，召回闭环回答「经验怎么在对的时刻出现在 prompt 里」。

闭环一：会话上下文压缩（对应 session_context_compactor）

# 每轮会话构造上下文前执行；阈值比率来自 AGENT_RUNTIME_SUMMARY_THRESHOLD_RATIO async def maybe_compact_session(db, session, settings): budget = context_budget(session.model) # 模型上下文窗口 limit = budget * settings.AGENT_RUNTIME_SUMMARY_THRESHOLD_RATIO # 触发线 payload = build_context_payload(session) # 历史消息 + 已有摘要 if estimate_tokens(payload) <= limit: return payload # 未超阈值，原样使用 # 超阈值：让模型自我浓缩——它最清楚哪些结论不能丢 candidate = await llm_call_with_tool( messages = COMPACT_INSTRUCTION + payload, # 指令：生成可续跑的紧凑摘要 tools = [commit_session_context], # 唯一可用工具 require = "call commit_session_context exactly once", ) summary = candidate.arguments["summary"] if not summary.strip(): raise SessionContextError("empty_summary") # 拒绝空摘要 try: state = await load_state(db, session.id) # session_context_states 行 await state.apply_candidate(summary, keep_recent=N) # Snapshot → Candidate → Delta await db.commit() except SessionContextConflict: # 并发压缩：显式冲突，让一方重试，绝不静默覆盖 raise return build_context_payload(session) # = 摘要 + 最近 N 条消息，续跑

闭环二：经验检索与注入（对应 experience_retrieval）

# Agent 发起 search_experience 时的最小链路 async def search_experience(db, agent_id, query, top_n=5): agent = await resolve_agent(db, agent_id) depts = await agent_department_ids(agent) # 可见性边界 needles = expand_query(query) # 可选的查询扩展 rows = await db.query(ExperienceEntry) \ .filter(status == "published") # 草稿永不被检索 \ .filter(visibility_condition(depts)) # 按部门/范围过滤 \ .filter(title.ilike_any(needles) | applicability.ilike_any(needles)) # 关键词相关性 \ .limit(top_n) # 只回预览两行：title + applicability，Agent 判断相关后再 read_experience 读全文 return [{"entry_id": r.id, "title": r.title, "applicability": r.applicability, # 适用条件与失效信号 "freshness": freshness_marker(r)} for r in rows] # 注入侧：会话开始时把高频可用经验拼进上下文目录 async def build_experience_hint(db, agent_id): entries = await published_entries_for(db, agent_id) # 同套可见性过滤 return "\n".join(f"- [{e.id}] {e.title} — {e.applicability}" for e in entries) # 引用留痕：Agent 采纳某条经验后写 experience_references（谁 / 哪个任务 / 哪条）
05 · 面试 QA

六问六答：从取舍到落地细节

Q1 · 长期记忆为什么用文件而不是向量库？这个取舍的代价是什么？

音巢选文件式的核心理由是透明性与零新增基础设施：memory.md 是 Agent 工作区里的普通 Markdown，人可直接审阅修改、随工作区版本化备份，Agent 读写它复用既有文件工具链，不需要引入 embedding 模型与向量库运维。代价是没有语义召回——「用券失败」匹配不到「核销门槛」这类问题在文件式里靠 Agent 自觉维护索引（模板自带的 MEMORY_INDEX.md）与目录约定来缓解。本质是把「检索精度」换成了「可解释、可干预」：记忆出错时你能打开文件指到那一行，而不是对着一堆向量猜。

Q2 · 上下文压缩必然丢信息，音巢怎么控制损失？

三层控制：① 摘要者是模型自己——压缩不是机械截断，而是驱动 LLM 调用 commit_session_context 工具提交一份「可供后续模型续跑」的紧凑摘要，由最理解对话的一方决定保留什么，且该工具要求恰好调用一次、空摘要直接拒绝；② 保留近期原文——压缩后上下文 = 摘要 + 最近 N 条消息原文，正在进行的子任务细节不经过摘要这一道有损环节；③ 阈值留余量——触发线是「预算 × AGENT_RUNTIME_SUMMARY_THRESHOLD_RATIO」而非顶格，比率之外的余量正是留给生成摘要的。状态侧用 Snapshot / Candidate / Delta 三态演进，并发压缩抛 SessionContextConflict 而非静默覆盖。

Q3 · 经验库怎么冷启动？怎么防止 Agent 把错误经验「投毒」给全组织？

防投毒靠权限不对称：Agent 只有提案权（propose_experience_draft），没有发布权；草稿 status=draft 时检索层（experience_retrieval 只查 published）根本看不到它，必须 reviewed_by 人工审核转 published 后才进 Agent 上下文目录。修订已发布条目也走 draft_of_id 影子草稿，发布后合并回源条目，引用与采纳统计不断链。冷启动的实务做法：先由人把历史排障文档、运维手册整理成首批种子条目直接发布，让检索「有米下锅」；Agent 提案早期可以设定「高价值任务完成后必须复盘提案」的节奏约束，用流程密度换积累速度。

Q4 · 记忆应该在什么时候写入——每轮对话结束，还是定期复盘？

音巢是两者结合，且刻意偏后者。每轮结束就写的问题在于：对话中间态噪声大，Agent 容易把试探性结论当成事实固化；而且写文件本身是工具调用，每轮都写增加时延与 token 成本。音巢的模板里带 HEARTBEAT.md 与 daily_reports/ 目录，节奏是「按心跳复盘」——Agent 周期性地回顾一段时间的工作，把验证过的结论、遗留问题写成每日报告，再把真正长期有效的部分沉淀进 memory.md。即时写入只留给「用户明确纠正偏好」这类高置信信号。这个设计的判断标准是：写入的记忆会被未来的自己无条件信任，所以写入门槛要高于读取门槛。

Q5 · 多 Agent 共享记忆时，一致性问题怎么处理？

音巢把「共享」拆成两类，分别治理：① 文件层不做运行时共享——memory.md 是每个 Agent 的私有财产（agent_data/<agent_id>/memory/），群聊里通过 group_file_service 提供受控的读写视图（如 agents/<agent_id>/memory/memory.md 路径映射），写冲突靠文件层的版本与工作区治理兜底，而不是运行时锁；② 组织级共享走数据库——经验库是共享的那一层，一致性由 DB 事务与状态机保证：draft/published 状态迁移、draft_of_id 影子草稿、reviewed_by 审核人都是行级事实；可见性用 _visibility_condition 按 Agent 所属部门过滤，避免「全公司可见」成为唯一选项。会话层的一致性则由 session_context_states 的冲突显式化（SessionContextConflict）兜底。

Q6 · 「RAG 外挂知识库」与「Agent 自己管文件」两条路线，音巢各取了什么？

音巢是按内容性质分治的混合派：企业结构化知识（enterprise_info）与经验库走「检索注入」这一侧——经验库的 search_experience 就是一次受控的 RAG：按可见性过滤 + 关键词召回 top N，只返回 title/applicability 两行预览，Agent 确认相关后才 read_experience 读全文，注入位置、条数、预览粒度全部服务端可控；而人格与长期记忆走「Agent 自己管文件」这一侧——因为这部分内容要求的是高信任、高可解释、随工作区演进，而不是海量语料的语义召回。两条路线的分野标准可以总结为：读多写少、需要跨主体共享的，进检索管线；写读都频繁、属于个体连续性的，进文件。

记忆，是 Agent 的时间维度

工具给了 Agent 手的灵巧，编排给了它脑的条理，而记忆与经验给了它时间的厚度——昨天的教训成为今天的直觉，一个人的踩坑成为全组织的资产。

音巢的做法朴素但有效：人格与记忆写成文件，经验过审核入库，上下文超窗就自我浓缩。没有魔法，全是工程。

衡量一个 Agent 平台是否成熟，不看它一次能跑多快，而看它一年后还记得什么。
