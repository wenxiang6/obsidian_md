Business Agent
任务型业务智能体

一套与具体业务、公司基建无关的任务型编码 Agent 架构：业务用自然语言提需求，Agent 在常驻 Host 上跑完全部流程，人只在决策点拍板。浏览器只是遥控器，关掉页面任务照跑。

01 · 问题背景

一条业务改动，需要三样东西同时在场

看懂需求的人、能改已登记仓库的执行者、在方案和发布点拍板的人。把执行者只放在某个研发的本地 IDE 里，链条会在多处断开：

能力IDE 开着IDE 关掉 / 机器休眠
读代码、改代码有无
预览与验证占着本机无
过夜跑验证不稳定无
业务追问进度没有任务对象无
同时来两条需求靠人记住没有调度
换一台机器状态在本地磁盘上下文丢失

聊天窗口装不下任务

一次改动要看方案全文、点同意、打开预览——消息卡片装不下。关掉窗口，任务就停了。

即时通讯里会长出第二套状态机

若在 IM 适配器里再做一套阶段推进，它会和真正改仓库的内核分叉，两处状态永远对不上。

AI 的执行权没有边界

未确认就改代码、模型自称"用户已同意"、随手推保护分支——没有内核级校验，这些都防不住。

02 · 产品原则

七条原则，定义"任务型 Web Agent"

环境事先备在常驻 Host 上，提出人描述目标即可；研发仍负责审代码、处理权限与外部阻塞、执行受控发布。

1

任务是一等公民

一次需求对应一条可恢复的任务，而不是聊天记录的副作用。问候、咨询、讨论思路不创建任务。

2

人只在决策点出现

需要拍板时给出确认卡。没有回执，功能开发不开始。其余时间 Agent 自主推进。

3

一个进行中

已有未收口任务时，新需求进入队列并说清原因，绝不覆盖当前任务。

4

关页面不等于停工

状态在 Host 的文件里。关掉浏览器，只是放下遥控器。

5

影响面由需求决定

提出人不预选仓库。Agent 读领域文档后判断并写进方案，人可以纠正。

6

发布权留在人

默认只生成发布交接。保护分支推送需要 operator 的显式确认。

7

维护必须有界

长期优化与周期巡检写在文档里，只有已授权的具体实施才占用进行中通道。

一句话架构

Web 是遥控器，Host 是备好的环境，Kernel 是唯一能改世界的手

浏览器、IDE 插件、IM 适配器都只是"通道"；真正建任务、拉分支、验证、发布的，只有经过内核校验的命令。界面给提出人讲业务语言——"方案等你确认"、"可以预览了"；仓库名、分支名、命令名留在研发旁路和审计文件里。

03 · 能力全景

一个工作台，装下业务的整个研发生命周期

以"需求迭代"为核心通道，向外生长出运维、数据与日常业务能力。所有能力共享同一个内核与同一套闸门。

核心

需求迭代

对话 → 需求卡 → 五张确认卡 → 分支开发 → 验证 → 验收 → 发布交接，全流程可恢复。人只在决策点点"同意"或"要改"。

业务直达

业务助理

不用进业务系统，对话即办理：查询、提单、审批。业务接口封装为受控工具后，操作直达并全程留痕。

排障

日志链路排查

按 traceId 串起跨服务调用链，trace 级根因定位，给出证据与修复建议。只读，不改服务。

数据

链路化数据 Mock

一句话造出一条完整业务链路的测试数据（商品 → 订单 → 营销），外键自动对齐，一键写入沙箱。

运维

巡检与维护

有界维护：巡检不占进行中通道，只有已授权的具体实施才进入迭代流水线，已收口任务不被重开。

交付

发布管理

Agent 默认只生成交接计划：目标环境、提交、未执行的动作。保护分支推送必须 operator 显式确认。

治理

审计与权限

确认回执、版本指纹、操作留痕；四级角色分工，任何人口头说明都不能豁免闸门。

沉淀

知识库与文档

领域文档驱动影响面判断；外部阻塞显式登记、写明要谁处理，绝不静默跳过。

04 · 迭代流水线

一条需求，从对话到收口的完整旅程

每个确认卡都绑定产物版本：上游一变，下游授权全部作废，从对应阶段重走。开发只使用最新确认的快照。

对话澄清 需求卡确认 排队 / 开工检查 拉功能分支 产品方案确认 界面方案确认 技术方案确认 测试用例确认 实施方案确认 开发 配置化验证 业务验收确认 交付提交 发布交接确认 收口释放通道 Agent 自动推进人工确认卡点
A

对话与需求卡

确认后入队

机制设计

  • AI 整理目标、范围、验收标准、影响仓库、是否涉及界面；有关键缺口才追问
  • 提出人确认的是当前版本需求卡，确认即写入持久化队列
  • 问候与咨询停在对话里，不建任务、不占通道

价值

提出人不用选仓库、选模型、选模式，用自己的语言说清楚"谁在用、想改变什么、怎样算做完"就够了。

B

排队与开工检查

单一通道

机制设计

  • 同一时刻至多一条进行中任务；忙碌时入队并说明占用原因与下一步，不编造等待时长
  • check 区分工作台层与业务层；可自动修复项交给 init，权限/凭证类外部条件升级给人
  • 取消进行中任务是破坏性动作：两次主动确认，默认按钮是"返回继续"

价值

排队原因人话可读，环境状态分钟级可知；提出人永远知道"卡在哪、要谁处理"。

C

五张确认卡

人审 × 5产品 · 界面 · 技术 · 用例 · 实施

机制设计

  • 每个阶段读取需求快照与全部前序产物，不只读上一阶段摘要
  • 技术方案必须引用实际读过的源码位置与版本；没读到的行为写"未知"，不补造
  • 实施方案列出允许改的路径、明确不改的路径、将用的验证命令（来自配置而非模型现编）
  • 密钥、依赖清单、发布清单默认不在自动写入范围内，除非逐项列出并获确认

价值

AI 的自由度被精确限定在执行层：方案一层比一层具体，人在每一层都有否决权，而不用盯全程。

D

开发与验证

受控执行

机制设计

  • 业务改动从该仓刚 fetch 的主干创建新功能分支，不复用旧分支
  • 编码运行时只按已确认清单改允许的文件；验证命令来自业务绑定配置
  • 验证失败自动修复有上限（默认 2 轮），相同源码相同失败即停止，不空转
  • 执行器未就绪时停在"等待研发接管"，不伪装成正在改代码

价值

改动可复现、可回滚、可审计； Host 重启后从文件恢复继续，模型上下文丢了也不怕。

E

验收与发布交接

确认 × 2

机制设计

  • 提出人逐项验收，通过才保存本地交付提交
  • 发布默认只生成交接计划：目标环境、仓库、提交、尚未执行的动作
  • 保护分支推送必须 operator/admin 的通道身份确认，模型不能自签
  • 验收时若要调需求：旧授权全部失效，从产品方案重走

价值

对外可见的动作零意外——发布权永远在人手里，且有据可查。

05 · 系统架构

五层架构：通道可以很多，手只有一只

研发 IDE 与 Web 调用同一套 Kernel——页面上的任务和 iterations/<id>/ 目录是同一件事。

通道层 Channel

只读状态 · 不碰 Git
Web 工作台任务列表 · 时间线 · 确认卡 · 预览入口
研发 IDE审代码 · 接管写锁
可选适配器IM 通知等，不实现第二套阶段机

会话层 Session

身份与任务绑定
鉴权访问凭证 · 四级角色
确认回执投递决定落盘为可核对回执

编排层 Orchestrator

状态不只在内存
队列 · 单任务锁新消息归类：当前任务 / 排队 / 拒绝
阶段机 · 心跳与恢复重启后从文件继续

内核 Kernel —— 唯一能改世界的手

不变量 · 确认 · 验证 · 发布
check / init环境检查与有限修复
new-iteration / checkout任务与分支纪律
confirm回执落盘，口头不算数
dev / test / complete受控开发与验证
publish默认只交接，确认才推送

执行层 Runtime

受控工具面
编码模型只通过受控工具改已登记仓库
Agent 仓库命令 · 规则 · 领域文档 · 迭代档案（提交 Git，不含业务源码）
target-repos/<key>业务仓独立 clone，提交只发生在各仓自己的历史
runtime/锁 · 队列 · 心跳 · 事件 · 密钥（不进 Git）
1

通道只通过 Kernel 改变世界

浏览器、IDE 插件、IM 适配器都不直接 git 写业务仓。

2

编码模型不绕过 Kernel

建任务、拉分支、完成、发布、写业务文件，都要经过命令校验。

3

文件是状态源

可恢复的事实在 iterations/ 与 runtime/。模型上下文和聊天历史不是状态源。

4

一份可写副本

每个已登记仓库全环境只有一份可写工作区；研发要改代码时显式接管写锁。

06 · 内核不变量

K1 – K10：写进命令里的纪律，不靠提示词自觉

任何通道、任何模型、任何运行时都必须满足。违反时命令失败并留下证据——不允许"警告后继续"。

ID不变量违反时
K1全局至多一条进行中 / 阻塞的迭代拒绝新建，并打印当前任务与收口方式
K2业务改动从刚 fetch 的主干创建新功能分支仓库缺失、fetch 失败、同名分支，均失败
K3脏工作区不得切分支列出 git status，等人处理
K4业务提交只发生在业务仓自己的 Git 历史Agent 仓库拒绝暂存 target-repos/
K5已登记仓库必须是独立 clone发现符号链接即 check 失败
K6密钥不写入档案、日志、页面与模型上下文命中密钥材料拒绝落盘，只记事件类型
K7必须确认的阶段，没有回执不得进入下游聊天里的"好的"不算数，超时不自动批准
K8dev 必须指定一个已登记仓库且分支正确缺仓库、多仓库、分支不符都拒绝
K9保护分支只有带人工确认的 publish 才能推送其他 push 拒绝；默认发布只写交接计划
K10编码运行时与人不得同时可写同一仓库锁持有者唯一；心跳过期只告警，不抢锁
确认回执 · K7 的灵魂

超时不自动批准；模型自签无效；下游执行前重新核对回执与产物版本

每张确认卡落盘为一条结构化回执：confirmation_id、阶段、产物版本、决定（approve / reject / comment）、操作者角色、时间。需求卡或任何前序产物一变，下游授权即刻失效——旧全文与旧回执保留供审计，但不再放行任何动作。

07 · 角色与权限

四级角色：谁能做什么，写死在边界上

同一个人可以兼多个角色，但任何人口头说明都不能豁免闸门。默认界面按提出人设计。

角色能做不能做
viewer 看自己可见的任务状态 提需求、确认、改代码
requester · 提出人 提需求、追问、确认或退回方案、验收、取消当前任务、移出未开始的排队项 推送保护分支、清除写锁、读取密钥、改写他人任务
operator · 操作员 提出人全部能力，加上审代码、接管写锁、发布确认、完成任务 代替模型跳过确认去改未授权文件
admin 放弃任务、在显式操作下切换活动迭代 用口头说明豁免闸门
08 · 实例化

蓝图 → 任意业务的专属 Agent

蓝图本身不含任何公司的仓库地址、身份系统与业务规则。把蓝图交给实施 AI，按实例化协议读完并填空，即可搭出该业务自己的 Agent。每个实例只服务一个业务、一组已登记仓库。

阶段 A

绑定 Binding

只读勘察候选仓库（主干、构建、测试、保护分支），起草绑定配置与领域文档；列未知项向人提问，人确认前停止。

产物：实例目录
阶段 B

内核 Kernel

先写闸门测试再实现命令：并发拒绝、脏工作区、无回执不放行、未确认 publish 只出计划……全部在临时 Git 仓通过，不碰真实远端。

闸门测试先行
阶段 C

对话、队列与 Host

访问口令、需求卡版本、确认入队、K1 忙碌时的人话原因；关掉客户端再查询，任务仍在。

可恢复
阶段 D

编码与验收

接入编码模型，工具面只有合同允许的内核操作；临时样板跑通后，再对一个低风险真实任务由人确认执行。自动编码开关由人显式打开。

渐进放权
阶段 E

可选项

证据源、统一登录反代、IM 适配器、风险归档——主路径可用后单独加，每一项都不得新增状态机或放宽 K1–K10。

不放宽不变量

与本工作台实践的关系

当前的 ai-dev-proxy 工作台，正是这套蓝图在 mall 电商业务上的一次单机实战雏形：十阶段流水线、三处人审卡点、铁律与迭代档案，都能在蓝图中找到对应的抽象。蓝图把这些经验提炼为业务无关的架构与协议，使同一模式可复制到任何业务线。

写在最后

聊天窗口是短会话的容器，任务是长工作的容器。当 AI 开始真正改仓库、跑验证、碰发布，"任务"就必须从聊天记录里毕业，成为有状态、有闸门、有回执的一等公民。

关掉页面，任务照跑；该人拍板的地方，一张确认卡都不会少。
