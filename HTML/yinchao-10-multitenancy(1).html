01 · 场景

多租户不是「加个 company_id」，是一整套管控底座

音巢 Agent 平台要让多家公司共用一套部署：A 公司的销售助理 Agent 绝不能被 B 公司的员工看见，平台运营方又要能横向管理所有租户。这一章解决的核心问题是：身份怎么来、数据怎么隔、权限怎么判。

1→N
一个 Identity 可加入 N 个租户（tenant_users）
4
角色等级 member → platform_admin
3×2
Agent 三档可见性 × 两档操作权
7+
SSO 身份源（飞书/钉钉/企微/Google/Teams…）

四类典型业务场景

①

SaaS 多公司托管

一套音巢部署服务多家公司：注册时按邮箱域名（tenants.sso_domain）或邀请码自动归入对应租户；所有业务表带 tenant_id，查询在 DAO 与 SQLAlchemy 事件层双重兜底隔离，数据互相不可见。

②

企业 SSO 与扫码登录

员工用飞书 / 钉钉 / 企业微信扫码或 OAuth 登录：sso_scan_sessions 承载扫码会话状态机，登录后按 provider_user_id / union_id 绑定到全局 Identity，再落到对应租户的 User 上——无需记第二套密码。

③

部门-成员-Agent 细粒度授权

财务 Agent 只对财务部可见可聊（custom 可见性 + agent_permissions 授权行）；谁能「用」（use）、谁能「改配置 / 删 Agent」（manage）分两档判定，创建者与管理员另有特权通道。

④

平台方横向运营

平台管理员（Identity.is_platform_admin）不属于任何租户，却能通过 api/admin.py 的横截面接口看所有公司、发邀请码、调配额——前端 PlatformDashboard / AdminCompanies / InvitationCodes 三个页面即为此服务。

定位 · 一句话

把「你是谁、你属于哪家公司」在请求入口一次性解析，之后的每一层代码都不再需要、也不被允许自己判断租户。

入口解析靠 JWT + ContextVar 中间件；隔离兜底靠 SQLAlchemy 的 do_orm_execute 全局事件；业务判定集中在 core/permissions.py。三个机制各司其职，任何一层失守都有下一层接住。

02 · 设计

四个关键决策：隔离粒度、身份分层、角色模型、资源授权

多租户系统的每一个设计点都是取舍：隔离越强运维越贵，模型越细判定越慢。音巢的选择明显偏向「工程可落地 + 防呆兜底」。

隔离粒度：行级隔离（shared schema）vs 库级隔离 D1

选项

① 每租户独立数据库 / schema，物理隔离
② 所有租户共享一套表，每行带 tenant_id，查询强制过滤

决定

共享库行级隔离，但用三层机制防漏写 where

原因

租户量级是「几十上百家公司」而非「几个巨型客户」，库级隔离的迁移、备份、跨租户统计成本不成比例。行级隔离的最大风险是开发漏写 tenant 条件——音巢用 TenantScopedBaseDAO 的 scoped 方法 + do_orm_execute 全局事件 + 业务层 tenant_id 比对三重兜底，把「人不可靠」当成设计前提。

代价

单点漏洞理论影响面是所有租户；热点表（agents、users）需为 tenant_id 建复合索引（如 ix_agents_active_tenant_created_at）；平台管理员的跨租户查询必须显式绕过（arch-guard 注释标记）。

身份模型：Identity（自然人）与 User（租户成员）分层 D2

选项

① 每个租户一套独立账号体系
② 全局 Identity 表存登录凭证（邮箱/手机/密码哈希），User 表存「某人在某租户的角色与配额」，一对多

决定

identities + users 双层，Identity 全局唯一

原因

现实里一个人常服务多家公司（外包、集团多主体）。双层模型让 SSO 绑定、换公司、跨租户的平台管理员都自然成立：邮箱/手机是全局权威身份声明（registration_service 的安全注释明确「只有 email 和 phone 是权威身份声明」），角色、配额、display_name 则是租户内的属性。

代价

登录要两步解析（Identity → 当前租户的 User）；User 查询需要「查某身份的全部租户成员」这一受控例外（__identity_membership_tenant_bypass__），是全库唯一允许绕过租户过滤的口子。

四级角色与 Agent 权限模型

维度取值语义
用户角色 user.role member / agent_admin / org_admin / platform_admin ROLE_HIERARCHY 升序定义在 core/security.py；接口用 require_role("org_admin", "platform_admin") 这类依赖工厂做角色门禁，platform_admin 还可由 Identity.is_platform_admin 全局标记旁路
Agent 可见性 access_mode company / private / custom company：全公司可用、进广场（Plaza）；private：仅创建者；custom：按 agent_permissions 授权行逐人判定，不进广场
授权范围 scope_type company / department / user agent_permissions.scope_type 枚举；当前判定代码实际消费的是 user 维度行（scope_id = user_id），company/department 为模型预留
操作档位 access_level use / manage use = 聊天/任务/工具/工作区；manage = 改配置、删 Agent、管授权。check_agent_access 返回 (agent, level) 二元组供上层区分

租户上下文传递：显式参数 vs ContextVar 隐式注入 D3

选项

① 每个 DAO 方法显式传 tenant_id 参数
② 中间件从 JWT 解出 tenant_id 写入 ContextVar，DAO 与事件层自动读取

决定

ContextVar 隐式注入 + 显式 tenant_context() 兜底

原因

显式传参的最大问题是「传错」和「漏传」都不会报错，只会静默查出别家数据。ContextVar 方案下，HTTP 请求由 TenantContextMiddleware 自动绑定；后台 worker / trigger daemon 没有请求上下文，必须显式 with tenant_context(tenant_id)——这条纪律直接写在 dao/base.py 的 docstring 里。

代价

隐式上下文在 async 任务泄漏场景下有风险（见面试 QA 第 2 题）；中间件只做轻量解码不做完整校验，若被误当成鉴权依据会出事故——所以 get_current_user 仍做完整校验，双层各司其职。

设计红线：租户隔离不靠「程序员记得」

音巢的多租户防线全部建立在「人会犯错」的假设上：业务代码可以漏写 where（事件层兜底）、可以传错 tenant_id（add_scoped 三处一致性校验直接 raise）、可以忘记鉴权（DAO scoped 方法在无上下文时拒绝服务或降级到安全默认）。可观测的安全，而不是约定俗成的安全。

sso_scan_sessions 是一个五态状态机（pending / scanned / authorized / expired / completed），带 expires_at 与一次性 access_token 字段。绑定策略的顺序很关键：先按 provider 侧稳定 ID（union_id 优先）精确命中，再退到邮箱匹配做账号合并——避免同一个人在飞书和邮箱注册出两个身份。租户的 sso_enabled / sso_domain 决定这个邮箱域名归哪家公司。

04 · 伪代码

两个最小闭环：租户上下文的注入与消费、Agent 访问判定

以下伪代码提炼自 core/middleware.py、dao/base.py 与 core/permissions.py 的真实结构，去掉工程细节后每个机制不超过四十行，但关键的防御分支一个不少。

闭环一：JWT → ContextVar → 自动租户谓词

# ── 入口：中间件（core/middleware.py）──────────────── class TenantContextMiddleware: def dispatch(request, call_next): tenant_id = extract(request) # 非校验性解码：验签名但 verify_exp=False if tenant_id is not None: token = _tenant_ctx.set(tenant_id) # 绑定到当前协程上下文 try: return await call_next(request) finally: _tenant_ctx.reset(token) # 必须复位，防协程复用串租户 return await call_next(request) # 无 token：公共接口照常放行 # ── 兜底：SQLAlchemy 全局事件（dao/base.py）────────── # @event.listens_for(Session, "do_orm_execute") def _inject_tenant_scope(execute_state): if not execute_state.is_select: return tenant_id = _tenant_ctx.get() if tenant_id is None: return # 无上下文（迁移/平台管理）不过滤 for mapper in execute_state.all_mappers: model = mapper.class_ if is_identity_membership_bypass(execute_state, model): continue # 唯一受控例外：按 identity_id 查全部成员 if _is_tenant_scoped_model(model): # __tenant_scoped__ 或 tenant_id 非空列 statement += with_loader_criteria(model, cls.tenant_id == tenant_id, include_aliases=True) execute_state.statement = statement # ── 消费：scoped DAO 方法（写入路径三重校验）───────── class TenantScopedBaseDAO: def add_scoped(db, obj, tenant_id=None): ctx = _tenant_ctx.get() if tenant_id and ctx and tenant_id != ctx: raise RuntimeError("explicit tenant != active context") resolved = tenant_id or ctx if resolved is None: raise RuntimeError("tenant-scoped write needs tenant_id") if obj.tenant_id and obj.tenant_id != resolved: raise RuntimeError("object tenant mismatch") obj.tenant_id = resolved; db.add(obj) # ── 后台任务没有 HTTP 上下文：显式绑定 ────────────── with tenant_context(agent.tenant_id): # worker / trigger daemon 纪律 agents = await agent_dao.list_scoped()

三个细节值得记住：① 中间件的 finally-reset 是 async 服务防串租户的命门；② 事件层在「无上下文」时选择不过滤而不是报错——因为迁移脚本与平台管理员横查需要全量视角，但此时业务判定层（permissions.py 的 tenant_id 比对）仍然在岗；③ scoped 写入对「显式值、上下文值、对象值」三者做两两一致性校验，任何矛盾直接抛错，宁可中断请求也不写错租户。

闭环二：Agent 访问判定（use / manage）

# core/permissions.py —— 判定顺序即防线顺序 async def check_agent_access(user, agent_id) -> (Agent, str): agent = await agent_dao.get_active(agent_id) if not agent: raise 404("Agent not found") if agent.tenant_id != user.tenant_id: raise 403("No access") # 第一道：跨租户一律拒 if agent.creator_id == user.id: return agent, "manage" # 第二道：创建者恒 manage if await can_manage_agent(user, agent): return agent, "manage" if await can_use_agent(user, agent): return agent, "use" raise 403("No access") async def can_use_agent(user, agent) -> bool: # 前置硬条件：未删除 ∧ 用户在职 ∧ 同租户 ∧ 创建者直接放行 mode = agent.access_mode or "company" if mode == "company": return True # 全公司可用 if mode == "private": return False # 仅创建者（上面已放行） # custom：管理员天然可用，否则查授权行 if user.role in ("platform_admin", "org_admin"): return True perm = await agent_dao.get_user_permission(agent.id, user.id) return perm and perm.access_level in ("use", "manage") async def can_manage_agent(user, agent) -> bool: # 同前置；admin 对 private 也不放行（private 是创建者的自留地） if is_admin(user) and mode != "private": return True if mode == "custom": perm = await agent_dao.get_user_permission(agent.id, user.id) return perm and perm.access_level == "manage" return False

注意一个反直觉的设计：管理员管不了别人的 private Agent——can_manage_agent 里 admin 分支显式排除 private 模式。这是「私人空间不受公司管理员穿透」的产品承诺在代码层的落地。另外 can_use_agent_static 是无 DB 命中的纯内存快判，用于列表页批量预过滤，查授权行的慢路径只在 custom 模式才走。

05 · 面试 QA

六道题，都对应代码里真实的坑

Q1 · 行级隔离（shared schema）和库级隔离怎么选？音巢为什么选前者？

看租户画像：库级隔离适合「少量巨型客户 + 强合规」（银行外包、政企专有云），换来的是迁移脚本 × N、连接池 × N、跨租户统计要联邦查询。音巢的租户是「几十上百家中小公司」，单库行级隔离的运维成本低一个量级，且天然支持平台管理员的横截面运营（AdminCompanies 一页看所有租户）。代价是隔离正确性从「数据库保证」退化为「代码保证」——所以音巢把防线做成了三层：业务代码显式写、TenantScopedBaseDAO 强制带、do_orm_execute 事件兜底自动加，外加 add_scoped 写入时的三值一致性校验。选型结论不是「行级更好」，而是「行级 + 系统性防漏写机制」在这个租户量级下性价比最高。

Q2 · 用 ContextVar 传租户上下文，在 async 下有什么坑？音巢怎么处理？

三个经典坑：① 忘记 reset——协程被连接池/任务队列复用时，上一个请求的 tenant_id 泄漏到下一个请求；音巢在中间件 dispatch 里用 try/finally 保证 reset。② 上下文不跨任务传播方向错误——asyncio.create_task 会拷贝当前上下文（对的方向），但若在 ContextVar.set 之前就 spawn 了后台任务，任务里读到的是 None；所以后台 worker、trigger daemon 这类不走 HTTP 的代码被要求显式 with tenant_context(tenant_id)，这条纪律写在 dao/base.py 的 docstring 里。③ 把中间件的轻量解码当鉴权——TenantContextMiddleware 用 verify_exp=False 解 JWT，只信任签名不信过期；若下游直接拿 ContextVar 当「已认证身份」就会放过过期 token。音巢的分工是：ContextVar 只用于数据隔离谓词，认证与过期校验永远由 get_current_user 完整执行。

Q3 · DAO 层强制租户条件如何真正防住「漏写 where」？

关键在 dao/base.py 注册在 SQLAlchemy Session 的 do_orm_execute 事件上（AsyncSession 的执行底座也是它，所以一条钩子覆盖全部 ORM 查询）：每次 SELECT 执行前，若 ContextVar 里有 tenant_id，就对所有「租户拥有的模型」追加 with_loader_criteria(model, cls.tenant_id == tenant_id, include_aliases=True)。include_aliases=True 保证 join 里的别名表也被约束。判定「租户拥有」的规则是 schema 级的：__tenant_scoped__ = True 或 tenant_id 列非空——不靠人肉登记清单。两个受控出口：平台管理员横查走 BaseDAO 原始方法并在代码里留 arch-guard 注释；「按 identity_id 查某人的全部租户成员」走 __identity_membership_tenant_bypass__ + execution_options 的显式声明，全库只有 User 表开这个口子。漏写 where 的查询会被事件层自动补上谓词，写错租户的新行会被 add_scoped 直接 raise。

Q4 · JWT 是无状态的，怎么实现「踢人下线」？

无状态令牌确实无法单独撤销，音巢的实际解法是把状态检查放回 get_current_user：它不只验签，还查库确认 User 存在且 is_active——管理员停用账号（is_active=False）后，该用户下一个请求就被 401，等效于踢下线，无需令牌黑名单。真正无法立即回收的是「令牌过期前的剩余窗口」，窗口长度由 JWT_ACCESS_TOKEN_EXPIRE_MINUTES 控制，是安全与体验的权衡参数。identity 层面同理：Identity.is_active=False 可全局封禁一个自然人（影响其在所有租户的 User）。如果业务需要秒级踢人，就要引入 Redis 令牌版本号或黑名单——那是另一个复杂度量级，音巢选择用「查库确认活跃」这个近似零成本的方案覆盖绝大多数场景。

Q5 · SSO 账号和本地账号怎么绑定？会不会一个人注册出两个身份？

registration_service.register_with_sso 的绑定顺序是设计好的防重复管线：① 先按 provider 侧稳定 ID（union_id 优先于 open_id，因为同一企业下 union_id 跨应用不变）调 resolve_user_identity 精确命中已有绑定；② 未命中再按邮箱在同租户内 match_user_by_email，命中则 link_identity 把 SSO 身份挂到既有账号上；③ 都没有才走 handle_sso_registration 新建 Identity + User。Identity 表上 email / phone / username 都是全局唯一索引，从 schema 层封死重复。安全上有一个明确的声明：find_or_create_identity 的注释写明「只有 email 和 phone 是权威身份声明」——用户名可改、显示名可撞，都不作为账号合并依据。租户归属由 tenants.sso_domain 按邮箱域名决定，员工换公司时同一 Identity 下新增一个 User，而不是迁移旧账号。

Q6 · 「首个注册用户自动成为平台管理员」是引导式体验还是安全隐患？

两者都是，音巢的处理值得拆解。引导价值：私有化部署零配置可用——api/auth.py 注册流程里 is_first_user = await identity_dao.is_empty()，首用户自动 role=platform_admin、is_active=True、并自动创建 default 租户，省去「初始化管理员」的部署脚本。风险也很实在：① 竞争条件——两个并发注册都读到空表就成双管理员，生产上应由数据库约束或部署期锁兜底；② 环境暴露——公网可注册的首部署窗口期谁先注册谁拿平台。缓解手段：平台管理员的横查接口全部挂在 require_role("platform_admin") 下且后续注册不受影响；正式环境通常配邀请码（invitation_codes，used_count < max_uses 校验）收紧注册入口。面试时可以主动指出：这个设计把「部署易用性」和「首启动安全窗口」的矛盾显性化了，比藏在部署文档里一句「请先创建管理员」诚实得多。

Q7 · custom 可见性的授权表怎么设计？查询性能如何保证？

agent_permissions 的表结构是三元组：(agent_id, scope_type, scope_id, access_level)，scope_type 枚举 company/department/user，scope_id 对 user 维度存 user_id。判定慢路径只在 custom 模式触发：can_use_agent 先走纯内存的 can_use_agent_static（同租户、创建者、company 直接判完），custom 才查 agent_dao.get_user_permission(agent_id, user_id)——单行主键级查询。列表页更不能逐 Agent 查授权：build_visible_agents_query 用 EXISTS (agent_permissions WHERE agent_id = Agent.id AND scope_id = :user AND access_level IN ('use','manage')) 子查询把可见性折叠进一条 SQL，配合 agents 表上的 ix_agents_active_tenant_created_at 复合索引（tenant_id + created_at + 软删除条件），分页查询走索引不扫全表。scope_type 里的 company/department 是模型预留——当前判定代码只消费 user 维度，这是「表结构先行、判定逻辑渐进」的典型演进策略。

隔离的尽头是「默认安全」

多租户做得好不好，不看文档里写了多少条纪律，而看一个疲惫的工程师在周五晚上漏写一个 where 时会发生什么。

音巢的答案是：什么都不会发生——事件层补上谓词，写入校验抛出异常，跨租户访问撞在 tenant_id 比对上。

把安全做进默认路径，让正确成为阻力最小的方向——这就是组织级管控底座存在的意义。
