01 · 场景

OpenDesign 是什么：一间「不带 Agent」的 AI 设计工作室

OpenDesign（GitHub: nexu-io/open-design，Apache 2.0）自称是「1st collaborative AI design agent workspace」——协作式 AI 设计工作台。它的核心理念很反常：自己不带 Agent，而是把你本机已有的编码 Agent CLI（Claude Code / Codex / Cursor / Kimi CLI 等 26 种）当作设计引擎；没有 CLI 时，走 BYOK API 代理。

架构上它是一个本地优先的双进程产品：Next.js 16 前端（人看的预览）+ 本地 daemon（Express + better-sqlite3）。daemon 负责 spawn 编码 CLI 或转发 BYOK SSE 代理；项目 = 文件工作区，文件一变，预览实时更新——这正是「设计工作台」该有的样子。

Agent 时代的设计痛点

Agent 会写代码，但产不出「遵循品牌语言」的设计稿；设计工具，又都不面向 Agent。

让 Claude Code 写一个活动页，你得到的是裸 HTML：每次从零配色、排版、选字体，品牌一致性无从谈起；Figma 这类工具是人手驱动的 GUI，没有给 Agent 的工具面，官方 API 昂贵且封闭；而 Agent 生成的文件要经浏览器或截图工具人工查看，迭代慢。OpenDesign 就是为填这个缝生的：本地优先、项目即文件、四张可移植平面提供品牌语言，MCP 工具面让 Agent 直接读写，预览实时跟随文件。

02 · 设计

三个组成部分：一个大脑，两双眼睛和手

看懂 OpenDesign 只需要分清三个进程：daemon 是大脑与仓库，web 是人的眼睛和手，MCP server 是 Agent 的眼睛和手——后两者是同一套 daemon API 的两个消费面，彼此不直接通信。

三个组成部分及其关系

组成部分技术栈面向谁职责
daemon（服务本身）Express + better-sqlite3人与 Agent 共用唯一事实源：项目 / 文件 / 技能 / 插件 / 设计系统；spawn 引擎；REST API + SSE 流
web（Studio）Next.js 16 App Router人项目文件树、沙箱 iframe 预览、对话界面、导出（HTML / PDF / PPTX / MP4）
MCP serverod mcp（stdio）Agent22 个工具的瘦客户端，全部转发 daemon REST API——mcp.ts 头注释写明「every tool resolves to a fetch() against OD_DAEMON_URL」

这个划分带来的工程红利：web 与 MCP 永远不需要互相同步。Agent 通过 MCP 写入的文件，人打开 web 立刻可见；人在 Studio 里的操作，Agent 通过 MCP 读到的就是最新状态。状态的唯一性由 daemon 保证，消费面可以无限增加（CLI、桌面端、第三方集成都在这层之上）。

接入决策

决策 1 · 集成层级，选多深 D1

选项

① 只搬资产：把 skills / design-systems 拷进自己的 Agent 配置
② 平台级接入：daemon sidecar + MCP 打通，Agent 全权读写 OD 项目
③ 产品级集成：把 Studio 嵌入自己的产品与工作流

决定

第 ② 层：平台级接入

原因

② 拿到的是「活的设计工作台」而非静态文件：预览实时、可导 PPTX/PDF，22 个工具覆盖项目 / 文件 / artifact 全生命周期。① 丢掉了预览与渲染能力；③ 依赖 ② 先成立，一步到位风险大。

代价

多一个 Node 常驻进程（daemon + web）和一座可能的传输桥，需要维护端口规划与重启脚本——第 04 章一并交付。

决策 2 · MCP vs 自定义 HTTP 工具 D2

选项

① 在 Agent 侧把 daemon REST API 包装成一组自定义工具
② 直接接入 OD 官方 MCP server（od mcp）

决定

② 官方 MCP，读写全权交给 Agent

原因

OD 官方 MCP 是瘦客户端——mcp.ts 头注释写明「every tool resolves to a fetch() against OD_DAEMON_URL」。22 个工具与 daemon API 同步演进，接入方零适配；自写 HTTP 层反而要把 22 个工具逐一翻译并长期跟进上游变更。让 Agent 当设计师，它的本职就是读写自己的设计稿。

代价

接受官方工具面的全部能力（含写文件）。治理不在协议层裁剪，而在客户端 / 平台的工具授权层——给谁用、何时用，是接入方的问题。

决策 3 · stdio 直连 vs SSE 桥：按客户端能力选 D3

选项

① 客户端原生支持 stdio：直接 spawn od mcp 子进程
② 客户端只支持 HTTP/SSE：supergateway 做 stdio→SSE 桥接

决定

本机客户端走 ①，平台型客户端走 ②，两者可共存

原因

stdio 零配置、无端口、天然本机，Claude Desktop / Cursor 这类客户端直接支持；SSE 可跨主机——客户端跑在 Docker 容器、局域网另一台机器或云端时，桥接只需一条 npx 命令，客户端侧零改动。

代价

桥方案多一个常驻进程与一跳转发；supergateway 默认监听所有网卡且无鉴权，暴露面需要用 --host 参数或隧道主动收敛（见 04 章安全提示）。

踩坑实录（2026-10 真实记录）

坑 ① · 直连 GitHub 克隆极慢

git clone 直连 github.com，13 分钟只拉了 5MB。换 gh-proxy 镜像前缀后 7 分钟完成全量克隆——网络好时可以直连，网络一般时直接上镜像，别硬等。

坑 ② · pnpm install 死于 electron postinstall

仓库 postinstall 会下载 Electron 二进制，卡死或超时整个 install。ELECTRON_SKIP_BINARY_DOWNLOAD=1 pnpm install 跳过即可——只要 daemon + web，根本不打包桌面端。

坑 ③ · macOS 上 daemon 频繁 EMFILE，预览停止刷新

daemon 用 chokidar 给每个项目挂文件监听，而 macOS 默认 fd 上限只有 256（ulimit -n），项目一多描述符就被打满，watcher 接连报 EMFILE、预览不再更新。调大上限：ulimit -n 10240（当前 shell）或 launchctl limit maxfiles 10240 10240（持久）。源码 apps/daemon/src/project-watchers.ts 对 EMFILE/ENOSPC 做了轮询降级容错——但那是保命绳，不是常态。

坑 ④ · 对话面板模型报错，别在错误链路上排障

OD 对话面板的模型测试返回 400，第一反应是去查 MCP 桥接——与 MCP 链路无关，是 BYOK 引擎侧的问题。排障时先分清「文件工具链」（MCP / daemon / 文件）和「生成引擎链」（/api/chat 或 /api/proxy），别在错误的那条链上浪费时间。

04 · 实现

配置实录：从零到 tools/list 返回 22 个工具

本章是重头：按真实执行顺序给出每一步命令，全部可复制直接跑。环境为 macOS + nvm；客户端在容器、局域网或云端的网络场景见步骤 7 的四种配置。

步骤 1 · Node 24 环境（nvm）

# Node 24（nvm 环境） nvm install 24 nvm use 24 node -v # v24.x # corepack 接管 pnpm（仓库 packageManager 锁定 pnpm@10.33.2） corepack enable pnpm -v # 10.33.2

步骤 2 · 克隆仓库（gh-proxy 镜像）

# 网络好可直接用 github.com；gh-proxy 镜像实测 13min/5MB → 7min 全量 git clone --depth 1 https://gh-proxy.com/https://github.com/nexu-io/open-design.git cd open-design

步骤 3 · 安装与构建

# 跳过 Electron 二进制下载（只要 daemon + web，不打包桌面端） ELECTRON_SKIP_BINARY_DOWNLOAD=1 pnpm install # 只构建 daemon（MCP server 与 cli.js 都在这个包里） pnpm --filter @open-design/daemon build

步骤 4 · 启动 daemon 与 web 预览

# 终端 1：daemon（HTTP API + SQLite + 项目文件，端口 7457） pnpm tools-dev start daemon --daemon-port 7457 # 终端 2：web 预览（Next.js 16，端口 5175；首次编译约 60s 属正常） pnpm tools-dev start web --daemon-port 7457 --web-port 5175

步骤 5 · 启动 SSE 桥（客户端只支持 SSE 时）

# 终端 3：OD MCP(stdio) → SSE，绑 0.0.0.0 供容器 / 局域网访问 # 客户端原生支持 stdio（Claude Desktop / Cursor）可跳过本步，直接 od mcp npx -y supergateway \ --stdio "node apps/daemon/dist/cli.js mcp --daemon-url http://127.0.0.1:7457" \ --port 7459 --host 0.0.0.0

apps/daemon/dist/cli.js 是步骤 3 构建产物；od mcp 子命令内部走 runMcpStdio。0.0.0.0 是 supergateway 的默认监听行为，这里显式写出——提醒自己在做「对局域网开放」的决定。

步骤 6 · 验证

# 1) daemon 健康检查（返回 ok 即 daemon 就位） curl -s http://127.0.0.1:7457/api/health # 2) SSE 端点连通（返回 text/event-stream 事件流即桥已就位） curl -sN http://127.0.0.1:7459/sse | head -5 # 3) tools/list 端到端：实测返回 22 个工具 # （create_project / write_file / get_file / start_run …） # 客户端侧：mcpServers 配置处「测试连接」确认

步骤 7 · MCP 配置 JSON · 客户端的四种网络场景

标准 mcpServers 格式，在任意 MCP 客户端（Claude Desktop / Cursor / Kimi Code / 自研 Agent 平台）的配置处整段粘贴。按「客户端与 daemon 宿主的网络关系」四选一：

场景一 · 客户端在 Docker 容器 桥接场景最常用 ✅——容器回环不是宿主回环，走 host.docker.internal：

{ "mcpServers": { "open-design": { "type": "sse", "url": "http://host.docker.internal:7459/sse" } } }

场景二 · 客户端在本机宿主机 同机回环——supergateway 就在本机，直接走回环：

{ "mcpServers": { "open-design": { "type": "sse", "url": "http://127.0.0.1:7459/sse" } } }

场景三 · 客户端在局域网其他机器 按实际 IP 改——supergateway 已绑 0.0.0.0，填宿主的局域网地址：

{ "mcpServers": { "open-design": { "type": "sse", "url": "http://192.168.1.4:7459/sse" } } }

192.168.1.4 为本记录中 Mac 宿主的真实局域网 IP，使用时替换成你自己 ifconfig 查到的地址。

场景四 · 客户端在云端服务器 SSH 反向隧道——云机到 Mac 没有直达路由，先在云机建反向隧道：

# 云端客户端所在机器上执行：把它的 7459 反向转发到 Mac 宿主的 7459 ssh -N -R 7459:127.0.0.1:7459 user@192.168.1.4
{ "mcpServers": { "open-design": { "type": "sse", "url": "http://127.0.0.1:7459/sse" } } }

隧道在云机本地还原出 127.0.0.1:7459，所以 JSON 与场景二相同——区别只在连通方式。此时 supergateway 甚至可以绑回 127.0.0.1（--host 127.0.0.1），由 SSH 自己做安全边界。

步骤 8 · 一键重启脚本

daemon + web + supergateway 合一条命令序列，存成 restart-od.sh 随时拉回全链路：

# restart-od.sh：杀掉旧进程 → 拉起 daemon / web / supergateway → 健康检查 pkill -f "supergateway"; pkill -f "tools-dev start"; sleep 1 cd ~/codeWorks/open-design || exit 1 nohup pnpm tools-dev start daemon --daemon-port 7457 > /tmp/od-daemon.log 2>&1 & nohup pnpm tools-dev start web --daemon-port 7457 --web-port 5175 > /tmp/od-web.log 2>&1 & nohup npx -y supergateway \ --stdio "node apps/daemon/dist/cli.js mcp --daemon-url http://127.0.0.1:7457" \ --port 7459 --host 0.0.0.0 > /tmp/od-mcp.log 2>&1 & sleep 3 && curl -s http://127.0.0.1:7457/api/health
安全提示 · 0.0.0.0 = 局域网内任何人可读写

supergateway 无鉴权，且默认监听所有网卡——绑 0.0.0.0 意味着局域网内任何机器都能通过 MCP 读写全部 OD 项目文件（write_file / delete_project 就在工具面里）。可信内网自用可以接受；不信网络时显式加 --host 127.0.0.1 锁回环，远程需求一律走 SSH 隧道（场景四），别让桥直接暴露在不可信网段。

接入实例

音巢（Clawith）：一个平台型客户端的接入

用三十秒看这个平台级接入长什么样——对 OD 而言，它只是又一个标准 MCP 客户端。

05 · 面试 QA

六个问题，验证你是真接通过还是看过文档

全部来自本篇的真实接入与源码阅读，回答都落在具体代码与真实坑位上。

Q1 · OD 的 MCP server 是瘦客户端还是胖服务端？

瘦客户端。mcp.ts 头注释写得很直白：「every tool resolves to a fetch() against OD_DAEMON_URL」。server 本身无状态、不碰文件系统——daemon 没起时 tools/list 照常返回 22 个工具 schema，只有真正调用才报 "daemon not reachable"。真正的读写在 daemon 与项目文件系统里，MCP 层只是协议翻译。

Q2 · daemon、web、MCP server 三者的职责边界在哪？

daemon 是唯一事实源：项目 / 文件 / SQLite 元数据、引擎调度、REST API + SSE 全归它；web 是人的消费面（文件树、iframe 预览、对话、导出），dev 模式靠 next.config.ts 把 /api 等路径 rewrite 到 daemon，生产模式干脆由 daemon 伺服它的静态导出；MCP 是 Agent 的消费面，22 个瘦工具转发同一套 API。边界纪律是：web 与 MCP 永不直接对话，一切状态进出都走 daemon——所以消费面想加多少个都可以。

Q3 · 一个只支持 SSE 的 Agent 平台怎么接 stdio MCP？

先讲清传输层差异：stdio 是进程管道——客户端 spawn 子进程，数据走 stdin/stdout，天然本地、无端口无网络；SSE 是 HTTP 长连接——客户端 GET 一个事件流端点，可跨主机，但服务端要监听端口并处理暴露面。OD MCP 原生 stdio，而平台只实现 HTTP/SSE 时，supergateway 做双向翻译：把 od mcp 起成子进程，把 stdin/stdout 上的 JSON-RPC 帧封装成 SSE 事件对外提供——平台侧零改动，还顺带获得跨主机能力（容器 / 局域网 / 云端）。

Q4 · 项目一多 daemon 就报 EMFILE、预览停止刷新，怎么回事？

文件描述符被打满了。daemon 用 chokidar 给每个项目挂文件监听 watcher，而 macOS 默认 ulimit -n 只有 256，项目与 watcher 一多 fd 就耗尽，于是 EMFILE、监听失效、预览不刷新。处理：当前 shell ulimit -n 10240，持久化用 launchctl limit maxfiles；同时控制单 daemon 挂的项目数量。源码 project-watchers.ts:133 的注释直言这是「saturated inotify watches」，并做了轮询降级容错——但降级是保命绳，不是常态。

Q5 · 两条引擎链路（Local CLI vs BYOK API）怎么选？

默认 Local CLI：daemon 检测到本机装了编码 CLI 时，走 /api/chat 直接 spawn，结构化工具 / 文件事件经 SSE 回流、直接落项目文件——质量最高，且 CLI 订阅很多团队已经付了；纯文本流的 CLI 走 text-artifact 兜底路径。无 CLI 或要统一用自家模型时走 BYOK：/api/proxy/{provider}/stream 把厂商 SSE 归一化成 delta/end/error，再由 <artifact> 解析器提取产物。两条链路汇入同一文件工作区，预览、导出、MCP 工具面对引擎选择完全无感——选链路是部署决策，不是架构决策。

Q6 · 这套平台里唯一可能产生费用的是哪一环？

设计引擎。OD 本体 Apache 2.0 开源、全本地、无账号无鉴权；MCP server、daemon、web 预览、文件读写链路全部免费。只有 commission 类生成任务会 spawn 你的编码 CLI 或走 BYOK 模型 API——钱花在 CLI 订阅或模型 token 上。纯文件读写链路（create_project / write_file / 预览）一分钱不花。
